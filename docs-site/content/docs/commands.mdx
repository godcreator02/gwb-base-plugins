**本页回答**：命令插件 `@godcreator/gwb-commands` 管什么、刻意不知道什么；它的表里存什么形状；它提供哪些接口、依赖哪些接口；不启动工作台怎么测它；代码从哪读起。登记方、调用方各保证什么写在接缝页[命令总线](/docs/seams/bus)。

## 管什么

**一张命令表，外面包一层 cordis 服务。** 表本身是 `registry.ts` 里的 `createRegistry`：一个按命令名索引的 `Map`，只收检查过的定义，不碰 cordis 上下文，只接一个写日志的函数：

外面那层是继承 cordis `Service` 的 `GwbCommandBus`，服务名 `gwbCommands`。它只做表做不了的两件事：从调用方取包名，把注销登记在调用方的 `effect` 上：

{/* ref file="../plugins/commands/src/index.ts" lines="67-74" */}

`Service` 的方法里 `this.ctx` 是调用方的上下文，所以 `this.ctx.fiber` 上是 loader 放的调用方条目，`this.ctx.effect` 在调用方卸载时执行。这就是为什么命令总线是 `Service` 而不是 `ctx.provide` 出去的普通对象（取舍见轨迹卡[命令总线改成继承 cordis Service](/trajectory/2026-09-24-commands-bus-as-service)）。

**四条规则**，契约与钉住的实现都在[命令总线](/docs/seams/bus)那一页，这里只列出来：

- 登记时检查定义：`name`、`description`、`usage` 缺一项或为空串就抛错；`plugin` 由命令总线从调用方取，登记方写了不同的包名也抛错（轨迹卡[命令定义改在登记时检查](/trajectory/2026-09-24-command-def-checked-at-register)）
- 同名命令后登记的生效并写 warn；注销函数只删表里仍是自己那条的记录
- `run` 从不抛错：处理函数返回带 `ok` 的对象原样交回，其余包成 `{ ok: true, data }`，抛错与找不到命令都回 `{ ok: false, error }`
- 请求来源 `{ via }` 原样交给处理函数，不给就是 `plugin`；命令总线不按来源限制调用（轨迹卡[命令总线把请求来源转交给处理函数](/trajectory/2026-09-24-commands-carry-request-source)）

**每次登记、执行都写一行日志**：成功写 info，返回失败、抛错、找不到命令写 warn。异常都变成了回执，不写日志就查不到谁在什么时候调了哪条命令。

**带一份说明书 `gwb-commands`**，放在包根 `skills/gwb-commands/`。说明书插件在时交给它登记，不在时命令总线照常加载：

## 不知道什么

**不认识任何命令名。** 表里每一条都是别的插件登记的；命令总线自己一条命令都不登记，命令做什么、参数怎么校验由登记它的插件决定。页面发来的命令由内核应用收下再交给 `run`，命令总线不接收 IPC 消息。

**不认识说明书插件的包。** 说明书插件依赖命令总线，命令总线反过来 import 它的类型会让两个包互相依赖，pnpm 12 的 `pnpm -r` 遇到工作区里的依赖环直接报错退出。所以只按形状声明用到的那一个方法，`package.json` 的 dev 里也没有 `@godcreator/gwb-skills`（轨迹卡[拆掉 commands ↔ skills 的包依赖环](/trajectory/2026-09-17-break-commands-skills-cycle)）：

{/* ref file="../plugins/commands/src/index.ts" lines="22-25" */}

{/* ref file="../plugins/commands/package.json" lines="29-35" */}

**不核实请求来源。** `via` 是调用方自己写的：内核转页面的命令时写 `ui`，MCP 入口写 `mcp`。命令总线只转交，谁冒充谁它也看不出来。

**不知道命令怎么展示给 agent。** `list()` 只交出定义；`index`、`search` 返回什么格式由 [MCP 入口](/docs/mcp)决定。

**不管时限、不保存。** `run` 一直等到处理函数返回；表只在内存里，重启就空，靠各插件加载时重新登记。

## 提供的接口

| 接口 | 做什么 | 契约在 |
| --- | --- | --- |
| 服务 `ctx.gwbCommands` 的 `register(def, handler)`、`run(name, args?, context?)` | 登记一条命令、拿回注销函数；按名字执行，返回 `Promise<GwbResult>` | [1 命令总线](/docs/seams/bus) |
| 服务 `ctx.gwbCommands` 的 `list()` | 全部命令的 `{ name, description, usage, plugin }`；MCP 入口的 `index`、`search` 从这里取 | [3 命令表开给 agent](/docs/seams/agent-surface) |
| 导出的类型 `GwbCommands`、`GwbCommandDef`、`RegisteredCommandDef`、`GwbCommandContext`、`GwbCommandHandler`、`GwbRequestSource` | 用命令总线的插件 `import type` 它们；`import type {} from '@godcreator/gwb-commands'` 就让 `ctx.gwbCommands` 有类型 | [1 命令总线](/docs/seams/bus) |
| 说明书 `gwb-commands` | 包根 `skills/gwb-commands/`，讲回执怎么读、失败有哪几种、插件里怎么登记命令 | [4 说明书](/docs/seams/skills) |

## 依赖的接口

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| cordis 的 `Service`、`effect`、`inject`、`logger` | 提供服务；把注销登记在调用方的 `effect` 上；局部注入说明书插件；写日志 | 内核带的 cordis，写在 peer（`^4.0.0-rc.10`），构建产物按值 import 它，必须和内核同一份 | dev 里的 `cordis` 4.0.0-rc.10 |
| loader 放在调用方 fiber 上的 `entry.options.name`（[8 条目身份](/docs/seams/entry-identity)） | 取登记方的包名，记成命令的 `plugin` | 内核带的 cordis loader | dev 里的 `@cordisjs/plugin-loader` 1.0.0-rc.7，真 loader |
| 说明书插件服务 `gwbSkills` 的 `register(dir)`（局部注入） | 登记自带的说明书 | [gwb-skills](/docs/skills) | 测试里不提供，这一段不走 |
| 词汇表包的 `GwbContext`、`GwbResult` | 类型 | `@godcreator/gwb-plugin-api`（dev，`^0.4.1`），只在编译时用 | 同一份 |
| 内核包 `@godcreator/gwb-kernel-desktop` | peer 范围 `^0.4.1` 声明兼容哪些内核，代码里不用它 | home 根上装的内核包 | 不装 |

{/* ref file="../plugins/commands/package.json" lines="52-56" */}

`GwbResult` 出现在本包导出的类型里，而发布出去的包不带词汇表包：用命令总线类型的插件要自己在 dev 里列词汇表包，原因见[遇到过的问题](/docs/pitfalls)。

## 怎么单独测

三个测试文件，都在 `plugins/commands/tests/`，不启动工作台：

**`registry.test.ts` 测表本身**：直接调 `checkedCommandDef` 与 `createRegistry`，日志传一个什么都不做的对象，要看告警的用例传 `vi.fn()`。证明的是：缺字段与 `plugin` 不符时的报错文本、来源原样转交、回执的两种形状、抛错收成失败回执、同名后登记的生效并告警、注销只删自己那条。

{/* ref file="../plugins/commands/tests/registry.test.ts" lines="4-11" */}

**`service.test.ts` 测服务这一层**：真 cordis 加真 loader，loader 的模块加载换成按包名查表，插件按包名建成条目加载，fiber 上就有 loader 放的 `entry`：

{/* ref file="../plugins/commands/tests/service.test.ts" lines="22-50" */}

证明的是：`plugin` 取自调用方条目，在 `ctx.inject` 回调里、`ctx.plugin` 装的子插件里、`Service.init` 里登记都取得到；不经 loader 加载的插件登记时抛错；调用方卸载后命令自动注销，调用方自己包了 `ctx.effect` 也只注销一次；同名命令被接手后，先登记的插件卸载不删接手的那条。

**`artifact.test.ts` 查构建产物**：相对 import 带 `.js`，包名 import 只有 node 内置模块与 `cordis`。没构建时整组跳过，改了代码先 `pnpm build` 再 `pnpm check`。

页面经内核调到命令、MCP 入口带 `{ via: 'mcp' }` 调到命令，这两段不在本包的测试里：前者只能在隔离 home 里验证，后者由 [gwb-mcp](/docs/mcp) 的 `apply.test.ts` 测。
