**本页回答**：命令插件有哪些功能；插件、页面和 agent 经哪些接口用它，登记、注销、执行各有什么规则，各属于哪条接缝；它依赖什么、缺了会怎样；哪些事常被以为归它、其实归别的插件。包名 `@godcreator/gwb-commands`，源码目录 `plugins/commands/src`，入口文件 `index.ts`。

命令插件提供命令总线：一张「命令名 → 处理函数」的表，插件把自己的能力登记成命令，页面、agent 和别的插件都经这张表调用。它是 `cordis.yml` 里的一条普通条目，和别的插件一样装在 home 里、可以停用和升级。

## 功能

- **登记命令**：插件把一个处理函数登记成一条命令，拿回注销函数；登记方插件卸载时命令自动注销，登记方不用包 `ctx.effect`
- **登记时检查定义**：`name`、`description`、`usage` 缺一项或为空串就抛错；命令记在哪个包名下由命令总线从调用方取，登记方写的 `plugin` 与之不同也抛错
- **同名命令后登记的生效**：同时写一条告警，写明原来是哪个插件、现在是哪个；先登记的插件卸载时只删自己那条，不删接手的那条
- **按名字执行命令**：页面经 `window.gwb.command`（内核应用收下后交给命令总线）、agent 经 MCP 入口的 `run`、别的插件直接调，执行的是同一张表
- **转交请求来源**：内核带 `{ via: 'ui' }`、MCP 入口带 `{ via: 'mcp' }`，别的插件不带，处理函数的第二个参数收到的就是 `plugin`；命令总线只转交，不按来源限制能调什么
- **执行不抛错**：回执只有成功、失败两种形状；处理函数抛错、命令不存在，都回成失败回执并写明原因
- **列出全部命令**：每条带名字、一句话介绍、用法和所属插件的包名
- **写日志**：每次登记、执行都写一行日志
- **带一份说明书 `gwb-commands`**：给 agent 讲回执怎么拆、失败有哪几种

## 接口

每条接缝上交换什么、各方保证什么，写在接缝页；本节只列命令插件提供了哪些接口、定义在哪里。

| 接口 | 做什么 | 接缝 |
| --- | --- | --- |
| 服务 `ctx.gwbCommands` 的 `register`、`run` | 插件登记命令、按名字执行命令；类型 `GwbCommands`、`GwbCommandDef` 由本包导出 | [1 命令总线](/docs/seams/bus) |
| 服务 `ctx.gwbCommands` 的 `list` | 全部命令的名字、一句话介绍、用法、包名；MCP 入口的 `index`、`search` 从这里取 | [3 命令表开给 agent](/docs/seams/agent-surface) |
| 回执 `GwbResult` | `{ ok: true, data }` 或 `{ ok: false, error }`，类型在词汇表包 `@godcreator/gwb-plugin-api` | [1 命令总线](/docs/seams/bus) |
| 说明书 `gwb-commands` | 包根 `skills/gwb-commands/`，交给说明书插件登记 | [4 说明书](/docs/seams/skills) |

### 服务 `ctx.gwbCommands`

类型 `GwbCommands`，由本包导出（`import type { GwbCommands } from '@godcreator/gwb-commands'`），三个方法：

| 方法 | 做什么 |
| --- | --- |
| `register(def, handler)` | 登记一条命令，返回注销函数。`def` 的类型是 `GwbCommandDef`：`name`、`description`（一句话介绍）、`usage`（参数形状与注意事项）三项必写，`plugin`（登记方的包名）可以不写 |
| `run(name, args, context?)` | 按名字执行一条命令，返回 `Promise<GwbResult>`，不抛错。`context` 是 `{ via }`，原样成为处理函数的第二个参数，不给就是 `{ via: 'plugin' }` |
| `list()` | 返回全部命令的说明，每条的 `plugin` 是登记方的完整包名 |

服务由继承 cordis `Service` 的类 `GwbCommandBus` 提供，本插件卸载时服务自动撤销：

{/* has file="../plugins/commands/src/index.ts" text="export default class GwbCommandBus extends Service implements GwbCommands {" */}

用它的插件把 `gwbCommands` 写进 `export const inject`；命令对这个插件可有可无时（没有命令，服务照样完整），改用 `ctx.inject(['gwbCommands'], …)` 局部注入。登记一条命令的写法：

```ts
export const inject = ['gwbCommands']

export function apply(ctx: GwbContext) {
  ctx.gwbCommands.register(
    { name: 'mine.hello', description: '回一句话', usage: '参数 { n }' },
    (args) => ({ got: args }),
  )
}
```

### 登记与注销的规则

<Diagram name="command-unregister" title="两个插件先后登记同名命令、再先后卸载（分步）">
- 左边是插件 A（`@scope/a`）与插件 B（`@scope/b`），各自的 effect 上登记着注销函数；右边是命令表里 `mine.hello` 此刻指向谁，以及这一步写的日志
- 第 1 步：A 调 `ctx.gwbCommands.register`，表里 `mine.hello` 指向 A 的处理函数，写 info
- 第 2 步：B 登记同名命令，后登记的生效，写 warn「后登记的生效：@scope/a → @scope/b」
- 第 3 步：A 卸载，A 的 effect 执行注销函数；表里已经是 B 的记录，什么也不删
- 第 4 步：B 卸载，B 的注销函数删掉这条命令
</Diagram>

- **注销跟着登记方走**：服务方法里的 `this.ctx` 是调用方的上下文，`register` 把注销登记在登记方的 `effect` 上，登记方卸载时命令自动注销，不用自己包 `ctx.effect`。返回的注销函数给要提前注销的场景用，调第二次什么也不做；登记方自己又包了一层 `ctx.effect` 也没关系，卸载时只注销一次
- **`name`、`description`、`usage` 必写，缺了抛错**：三项都要是非空字符串，错误文本写明哪个包、哪条命令、缺哪一项、该怎么写。`usage` 为空时 agent 分不清这条命令是没有参数还是登记方忘了写，所以无参数的命令也要写「无参数」
- **`description` 与 `usage` 分开写**：`description` 是一句话介绍，出现在 MCP 入口 `index` 返回的清单里；`usage` 写参数形状与注意事项，只在 `search` 命中时返回。都写进 `description` 的话，`index` 返回的清单会变得很长
- **`plugin` 由命令总线取**：`register` 从调用方 fiber 上 loader 放的条目读包名（`entry.options.name`），记成这条命令的 `plugin`；调用方在 `ctx.inject`、`ctx.plugin` 里建的子上下文也带着同一个条目。登记方可以不写 `plugin`，写了就必须与取到的包名相同，不同就抛错并写明两者。取不到条目（不是经 `cordis.yml` 加载的插件在调用）也抛错。agent 按包名装卸、升级插件，MCP 入口的 `search {plugin}` 按它筛选命令
- **同名命令，后登记的生效，并告警**：插件之间平等，换掉一条命令是允许的，但不告警的话调用方从此调到另一个插件上，两边都不报错
- **注销只删自己那条**：注销函数先确认表里还是自己登记的那条记录才删除，同名命令被替换后，先登记的插件卸载不影响接手的那条

### 执行的规则与回执 `GwbResult`

<Diagram name="command-run" title="一条命令从调用方到处理函数、回执原路返回（分步）">
- 三类调用方：页面调 `window.gwb.command`，内核收下后交给 `run` 并带上 `{ via: 'ui' }`；agent 调 MCP 入口的 `run` 工具，MCP 入口交给 `run` 并带上 `{ via: 'mcp' }`；别的插件直接调 `ctx.gwbCommands.run`，不带来源
- 命令总线按命令名查内存里的命令表，找不到回 `{ ok: false, error: '没有这条命令：<命令名>' }`
- 找到就把参数和来源交给登记方的处理函数（没带来源就是 `{ via: 'plugin' }`）：返回带 `ok` 的对象原样返回，返回别的值包成 `{ ok: true, data }`，抛错收成 `{ ok: false, error }`
- 回执沿原路回到调用方；成功写 info，失败写 warn
</Diagram>

- 回执只有两种形状：`{ ok: true, data }` 与 `{ ok: false, error }`
- 处理函数自己返回了带 `ok` 的对象，原样返回，别的字段和 `ok` 在同一层（命令行运行插件的回执带 `stdout`、`exitCode` 等字段）；返回别的值，一律包成 `{ ok: true, data: 值 }`
- 处理函数抛错，回成 `{ ok: false, error: '<异常文本>' }`，不把异常抛给调用方：调用方可能是页面上的一次点击
- 没有这条命令，回 `{ ok: false, error: '没有这条命令：<命令名>' }`
- 参数由处理函数自己校验，校验不过就抛错，命令插件把它转成失败回执
- 成功写 info 日志，失败与找不到命令写 warn：异常都转成了回执，不写日志的话查不到谁在什么时候调了哪条命令、结果如何

## 依赖

| 依赖 | 用来做什么 | 缺了会怎样 |
| --- | --- | --- |
| 内核里的 cordis：`Service` 基类、`effect`、`inject`、`logger`（peer，`^4.0.0-rc.10`） | 提供服务、把注销登记在登记方的 `effect` 上、局部注入说明书插件、写日志 | 由内核提供，不会缺；构建产物里按值 import 了 `cordis`，必须和内核用同一份，所以写 peer |
| loader 放在调用方 fiber 上的条目 `entry`（[8 条目身份](/docs/seams/entry-identity)） | 取登记方的包名，记成命令的 `plugin` | 不是经 `cordis.yml` 加载的插件登记命令时，`register` 抛错 |
| 说明书插件的服务 `gwbSkills` 的 `register(dir)`（局部注入，[gwb-skills](/docs/skills)） | 登记自带的说明书 | 不登记说明书，命令总线照常加载 |
| 词汇表包 `@godcreator/gwb-plugin-api`（dev，`^0.4.1`） | `GwbContext`、`GwbResult` 的类型 | 只在编译时用；`GwbResult` 出现在导出的类型里，发布出去的命令插件不带词汇表包，用命令插件类型的插件要自己在 dev 里列它，否则关掉 `skipLibCheck` 的类型检查失败；运行时没有影响 |
| 内核包 `@godcreator/gwb-kernel-desktop`（peer，`^0.4.1`） | 声明兼容哪些内核：`plugin-manager.list` 报出范围不包含 home 里内核的插件 | 不 import，运行时没有影响；没写或范围不包含 devkit 所在 home 的内核时，`devkit.release` 不发 |

说明书插件不写进服务类的 `static inject`，用 `ctx.inject(['gwbSkills'], …)` 局部注入：写进 `static inject` 的话，没装说明书插件的 home 里命令总线会一直等待。命令插件也不 import 说明书插件的类型，只按形状声明用到的 `register`：说明书插件反过来依赖命令总线，这样包之间的依赖是单向的，pnpm 12 的 `pnpm -r` 遇到工作区里的依赖环会直接报错退出。

## 不做的事

- **不登记任何命令**：表里每一条都是别的插件登记的，命令做什么由登记它的插件决定
- **不校验参数、不给命令分权限**：参数由处理函数自己校验；登记时只检查命令的定义
- **不按来源限制调用**：页面、agent、插件调的是同一个 `run`、同一张表；来源只转交给处理函数，由处理函数自己决定用不用它（比如记进历史）。来源是内核与 MCP 入口自己写的，命令插件不核实
- **不决定命令怎么展示给 agent**：`index` / `search` 返回什么格式由 [MCP 入口](/docs/mcp)决定；MCP 入口的工具只有 `index`、`search`、`run` 三个，命令不能登记成单独的工具
- **不运行命令行程序**：处理函数是普通的 JS 函数，在主进程里执行；启动子进程运行命令行程序的是 [gwb-node-cli](/docs/node-cli) 与 [gwb-py-cli](/docs/py-cli)，它们把自己的命令也登记到这张表上
- **不给命令设时限**：`run` 一直等到处理函数返回；命令行程序的时限由两个命令行运行插件管
- **不保存命令表**：表只在内存里、不写进文件，登记命令的插件卸载时它登记的命令自动注销
- **不接收页面的 IPC 消息**：页面发来的命令由内核应用收下、带上 `{ via: 'ui' }` 交给 `run`；内核不认识任何命令名
- **不管说明书怎么登记、怎么读**：说明书由说明书插件登记、agent 经 MCP 入口读；命令插件只把自己的 `skills/` 目录交给说明书插件
