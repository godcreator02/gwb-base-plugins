# gwb-commands

**没有这个插件，界面调不到任何 node 侧的能力**——内核一条命令名都不认识，`gwb:command`
收到什么就原样派给 `ctx.gwbCommands`；没装这个插件就是一句「认不出」。

包名 `@godcreator/gwb-commands`，服务 `ctx.gwbCommands`。产物 4 个文件、零运行时依赖。

## 怎么用

**登记一条命令**（在你的插件里）：

```ts
export const inject = ['gwbCommands']

export function apply(ctx: GwbContext) {
  ctx.effect(() =>
    ctx.gwbCommands.register(
      { name: 'mine.hello', description: '回一句话', usage: '参数 { n }', plugin: '@scope/mine' },
      (args) => ({ got: args }),
    ),
  )
}
```

`register` 回的是注销函数，**用 `ctx.effect` 包着**——本插件卸载时注册自动回收。

`plugin` 这个字段由注册方自带，不从 `ctx.name` 读：那是 cordis 的追踪属性，没 `inject`
就读会抛。

## description 与 usage 分家

`description` 是**一句话介绍**——与 skill 的 description 同义，是地图层的导航触发文本；
`usage` 装**参数形状与行为注意**。经 [gwb-mcp](/docs/mcp) 出去时：`index` 的地图行只带
description（两表同形、约两千 token），`search` 的命中行带 usage——agent 调命令之前看
的那一行就是它。

所以写法定死：`description` 一句话说清这条命令是什么；`usage` 里带参数的把形状写出来
（`{ entryId }`、`{ pkg, spec? }` 这种），无参数的写「无参数」。两格挤在一句话里的旧写法
随 commands 0.4 退役——地图被长描述撑爆的病就是这么来的。

## plugin 写包名

`plugin` 一律写**包名**（`@godcreator/gwb-xxx`）：它是 agent 侧的操作键——装卸升走
plugin-manager、反馈投递按包定位仓，短名到时候都得拼回去；门的 `search {plugin}` 也靠它
跨两张表精确筛。注册表有一道软守卫：见到不带 `@` 的值 warn 一句、照挂不拦——逮漏网，
不升格失败。

{/* ref file="../plugins/commands/src/registry.ts" lines="36-46" */}

短名没有被废除，只是各回各家：cordis 条目 id、日志、AGENTS 散文照旧用短名——那些是
运行时与人的词汇，不是跨进程的操作键。

**从界面调**（在你的 client 束里）：

```js
args.host.call('mine.hello', { n: 7 }).then((res) => {
  // { ok: true, data: { got: { n: 7 } } }
})
```

整条链路是：界面 → IPC（`gwb:command`）→ 主进程里的 `ctx.gwbCommands` → 你的 handler
→ 原路回。插件与桥同一个进程，中间没有第三跳。

## 它不是 CLI 运行器

handler 就是个普通 JS 函数，跑在宿主这个 node 进程里——**这条总线不执行命令行**。
真的起子进程跑 CLI 的是 [gwb-node-cli](/docs/node-cli) 与 [gwb-py-cli](/docs/py-cli)，
而它们把自己登记的命令**也挂进这条总线**：所以那两个插件跟这个是叠着的、不是并列的。
看见命令名里带 `cli` 就来这儿找 spawn，找不着——spawn 在那两个插件里。

## 回执的形状

handler **自己判过成败就原样透传**，没判的一律算成了：

- 回 `{ ok: false, error: '...' }` → 原样交给调用方
- 回 `42` → 包成 `{ ok: true, data: 42 }`
- 抛异常 → `{ ok: false, error: '<异常文本>' }`，不炸到调用方
- 命令没注册 → `{ ok: false, error: '没有这条命令：xxx' }`

## 没有顶层申报位

命令没有「让 agent 在工具清单顶层直接看见」这个动作——MCP 门 0.5 起工具面封顶
`index` / `search` / `run` 三枚，一切命令经 `run` 按名调，发现面是 `index` 与 `search`
的回执。曾经的 `top: true` 申报链（0.2 生、0.3 死）连字段一起拆掉了：顶层是协议形状，
不是插件能登记的东西。要动那个封顶是 major 级的协议变更，先问人——判据在
[mcp](/docs/mcp) 的封顶粒度那节。

## 说明书走局部注入

这个插件自己也带一份说明书（`skills/` 目录），挂它走 `ctx.inject(['gwbSkills'], …)`
而**不写进 `export const inject`**：没装 skills 插件的 home 里，命令总线照样得能挂上——
**说明书不是它能不能干活的前提**。写进 `inject` 的话，少那一个插件整个总线就 PENDING 了。

@@docfirst ref plugins/commands/src/index.ts:41-47 @@

局部注入这个模式别的插件也用（[skills](/docs/skills) 那页讲了为什么），钉在这儿的是
这个插件自己的那一处。

跟别的插件不同的一点：**本插件不引 `@godcreator/gwb-skills` 的类型**。skills 插件反过来
依赖本插件（静态 inject 总线、类型面引本包），本插件这边只按形状取它用得到的那一个
`register(dir)`，所以包依赖图单向、无环——pnpm 12 的 `pnpm -r` 对 workspace 依赖环直接报错退出。

## 三条判据

写进测试的那三条，各自的理由见[撞过的墙](/docs/walls)：

1. **撞名后来者赢，但要告警** —— 静默改派的话两边谁都不报错
2. **注销只收自己那份** —— 撞名后先卸的不该带走接手的
3. **handler 抛出来不炸调用方** —— 它可能是界面上的一次点击
