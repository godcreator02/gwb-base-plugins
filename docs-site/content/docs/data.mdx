# gwb-data

包名 `@godcreator02/gwb-data`，服务 `ctx.gwbData`。无界面，零第三方依赖。

插件要往盘上存自己的东西（JSON 文档、图片、日志），不用自己拼路径、不用自己写原子
落盘——写 `inject: ['gwbData']`，拿一个绑着自己身份的专属目录。

## 数据落在哪：归属是条目，不是包

`<home>/data/<条目 id 的末段>/`。**按条目 id 切、不按包名切**——`id` 才是 cordis
条目模型里的身份，`name` 只说「装哪个包」；同一个包挂两条条目是两份独立配置的实例，
按包名切的话它们共用一个目录、互相覆盖。姊妹插件 `gwb-settings` 的分区键是同一个答案：

## 读与写的语义

**readDoc：没有 / 坏了都回 undefined**——第一次跑没文件，调用方直接用默认值；但坏了
要 warn 一声，数据烂掉悄悄变成「用默认值」是最难查的那种。

**writeDoc：整份替换、原子落盘**——先写同目录的临时文件再 rename 覆盖。直接往目标写
的话，写到一半崩了会留下半个文件，那份数据就毁了；rename 只在同一分区上原子，所以

## 条目没写 id，只 warn 一声

home 级数据按条目 id 落目录，而条目不写 `id` 时 loader 发的是 8 位随机十六进制串、
每次启动都变，那条条目的数据每次启动都新建一份。`dir` 每读写一次认一遍，认出随机
id 就 warn——**不抛错**（那条条目本来能跑），**也不静默**（对不上是最难查的那种），

## 怎么单独测

`paths.ts` 与 `store.ts` 是纯逻辑加真 fs（临时目录），单测直接喂：路径规则三样
（文档名 kebab、entryId 段数与字符集、随机 id 认形）、读写的容错（没有、坏了、写失败
清临时文件）。`index.ts` 的接线（身份绑定、构造时取 home）靠实机——探针插件挂上、
落盘的目录是不是探针自己那条条目的。
