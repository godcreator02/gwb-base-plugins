**本页回答**：数据插件 `@godcreator/gwb-data` 管什么、刻意不知道什么；磁盘上是什么形状；它提供哪些接口、依赖哪些接口；不启动工作台怎么测它；代码从哪读起。用它的插件要遵守什么写在接缝页[数据](/docs/seams/data)，目录归属写在[数据归属](/docs/seams/owners)。

## 管什么

插件要在磁盘上存自己的东西（JSON 文档、图片、日志），把 `gwbData` 写进 `inject`，拿到一个只属于自己那条条目的目录，不用自己拼路径、不用自己写原子写入。

**分为四个文件。** `paths.ts` 只算路径与名字；`store.ts` 读写一份文档；`owner.ts` 读写目录里的归属文件；`index.ts` 是继承 cordis `Service` 的服务，认出调用方、核对归属、写日志。

**服务按调用方条目给目录。** 方法里的 `this.ctx` 是调用方的上下文，服务从它 fiber 上 loader 放的条目取条目 id 与包名；目录是 `<home>/data/<条目 id 的末段>/`，同一个包在 `cordis.yml` 里配两条条目就是两个目录：

**每次取目录都先核对归属。** 目录里没有 `.owner.json` 就建目录、写下调用方的包名；归自己放行；归别的包抛错，报错写明两种处理办法（给条目换 id，或确认是同一个插件改了包名、调 `plugin-manager.transfer-owner`）。`dir` 是同步的 getter，插件拿到路径就可能自己往里写，所以核对也同步做；核对过的目录记在内存里，不重复读磁盘：

**读文档**：没有这份文档回 `undefined`；解析不了也回 `undefined`，另写一条 warn——数据坏了悄悄变成默认值是最难查的那种问题：

{/* ref file="../plugins/data/src/store.ts" lines="6-21" */}

**写文档**：整份替换。先序列化（循环引用之类在建目录之前就抛出），再写同目录的临时文件（名字带随机后缀）、改名覆盖；改名失败删掉临时文件。同一份文档的写入按发起顺序排队，后发起的那次最后写进文件（轨迹卡[写入排队](/trajectory/2026-09-24-serialize-file-writes)）。服务这一层写失败先写一条 error 再把异常抛给调用方——调用方常把异常吞掉：

{/* ref file="../plugins/data/src/store.ts" lines="56-62" */}

{/* ref file="../plugins/data/src/index.ts" lines="66-76" */}

**名字写错当场报错**：文档名与条目 id 的每一段都必须是 kebab-case，字符集里没有点号，`.` 与 `..` 进不来；条目 id 超过两段抛错。

**条目没写 id 时提醒**：条目 id 是 loader 生成的 8 位十六进制随机串时写一条 warn——这种 id 每次启动都变，数据每次启动都会新建一份；每条条目只写一次。

## 不知道什么

**不管目录里的其他文件。** `dir` 交出去后插件在里面存什么都行，数据插件只认 `<文档名>.json` 与 `.owner.json`。

**不是安全边界。** 插件和数据插件在同一个进程里，有完整的 Node 权限，能写任何路径；名字校验只防误写出意外的嵌套目录。

**不做局部更新、不做读改写的并发控制。** `writeDoc` 整份替换；两方各自读出、改好、写回，后发起写入的一方覆盖前一方的改动。

**不删数据。** 条目删掉后目录留在磁盘上，谁来清理不归数据插件。

**不知道命令总线与说明书。** 没有命令、没有说明书，页面与 agent 看不到数据目录；要给外面看，由插件自己登记命令。`package.json` 的依赖里没有别的插件：

{/* ref file="../plugins/data/package.json" lines="28-38" */}

**不管设置。** 设置在 [gwb-settings](/docs/settings)，写在 `<home>/settings.json`，不在数据目录里。

**算目录名的那段逻辑与设置插件各有一份**（`entryDirName` 与 `entrySection`），两份靠约定保持一致，见[条目身份](/docs/seams/entry-identity)。

## 数据结构

磁盘上：

- `<home>/data/<条目 id 末段>/`：一条条目的数据目录
- `<目录>/<文档名>.json`：一份文档，两格缩进的 JSON，末尾一个换行
- `<目录>/.owner.json`：`{ "pkg": "<包名>" }`。文件名带点，文档名是 kebab-case，两者撞不上

## 提供的接口

| 接口 | 做什么 | 契约在 |
| --- | --- | --- |
| 服务 `ctx.gwbData` 的 `dir`、`readDoc(doc)`、`writeDoc(doc, value)` | 调用方条目的数据目录；按文档名读、整份替换写 | [6 数据](/docs/seams/data) |
| 服务 `ctx.gwbData` 的 `owners()`、`transferOwner(id, pkg)` | 各数据目录归哪个包；把一个目录改归另一个包 | [7 数据归属](/docs/seams/owners) |
| 目录 `<home>/data/<条目 id 末段>/` | 目录名由调用方的条目 id 算出 | [8 条目身份](/docs/seams/entry-identity) |
| 文件 `.owner.json` | 目录归哪个包 | [7 数据归属](/docs/seams/owners) |
| 导出的类型 `GwbDataApi` | `import type {} from '@godcreator/gwb-data'` 让 `ctx.gwbData` 有类型 | [6 数据](/docs/seams/data) |

## 依赖的接口

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| 内核服务 `gwbKernel` 的 `dataDir`（经 `src/vocab.ts` 的 `requireKernel` 取，不写进 `inject`） | 算出 `<home>/data`；缺了构造时抛错、插件加载失败 | 内核应用 | `{ dataDir: <临时目录> }` |
| cordis 的 `Service`、`logger` | 提供服务；方法里的 `this.ctx` 是调用方的上下文 | 内核带的 cordis（peer `^4.0.0-rc.10`），必须和内核同一份 | dev 里的 `cordis` 4.0.0-rc.10 |
| loader 放在调用方 fiber 上的 `entry.id`、`entry.options.name`（[8 条目身份](/docs/seams/entry-identity)） | 认出调用方的条目 id 与包名；取不到时抛错 | 内核带的 cordis loader | 调用方插件在 `apply` 里自己往 fiber 上放一个 `entry` |
| 文件系统 | 建目录，读写文档与 `.owner.json` | `node:fs` | 临时目录里的真文件 |
| 词汇表包的 `GwbContext`、`GwbKernelApi` | 类型 | `@godcreator/gwb-plugin-api`（dev，`^0.4.1`） | 同一份 |
| 内核包 `@godcreator/gwb-kernel-desktop` | peer 范围 `^0.4.1` 声明兼容哪些内核 | home 根上装的内核包 | 不装 |

## 怎么单独测

五个测试文件，都在 `plugins/data/tests/`：

- `paths.test.ts`：文档名与条目 id 的字符集、只取末段、超过两段抛错、随机 id 的判断、同一个包的两条条目各是各的目录
- `store.test.ts`：在临时目录里测读的三种结果（没有、有、坏了要 warn），写的整份替换、不留临时文件、序列化失败不留半个文件、覆盖失败不毁掉原来那份、同时写好几次时最后发起的那次留下
- `owner.test.ts`：没有归属文件的目录第一次被用就写上、目录里原有的数据不动、scope 不同短名相同的包拿不到别人的目录、归属文件坏了当场抛、列出归属时坏的那份写 warn
- `service.test.ts`：见下
- `artifact.test.ts`：相对 import 带 `.js`，包名 import 只有 node 内置模块与 `cordis`

**`service.test.ts` 测服务这一层**：真 cordis 根上下文提供内核替身，调用方插件在 `apply` 里往自己的 fiber 上放一个 `entry`，模拟 loader：

{/* ref file="../plugins/data/tests/service.test.ts" lines="19-48" */}

证明的是：第一次取 `dir` 就建出目录并记下包名；同一个包的两条条目各是各的目录；读写回原样、坏文档写 warn；写失败先写 error 再抛；目录归别的包时三个方法都抛错；取不到条目时抛错；随机 id 只告警一次；`owners()` 与 `transferOwner` 的行为。

loader 真的把调用方自己那条条目放在 fiber 上，只能在隔离 home 里验证。
