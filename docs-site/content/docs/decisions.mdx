# 定过的事

按 `gwb-decide` 的规矩：选型推完交人拍板，拍板之后记进这页。只记关系**件**的选型；
关系**规则**的（命名、依赖判据、内核该不该做某事）归内核仓的站。

## 2026-09-12：多桌面第二波——保活重试，浮层户口迁回本桌

**定**（shell 0.3.0，配套 hello 0.2.2 / logger 0.2.2 / plugins 0.4.2）：

1. **保活语义重做**：一口桌面一口井、井常驻。非活动那口 `visibility:hidden` +
   `pointer-events:none` + `inert`——只是不显示、不可交互，DOM、定时器、订阅全活着。
   开机只挂活动井，其余**第一次切到才挂（冷挂）、挂上常驻**
2. **浮层户口迁回本桌**：每口桌面一个 portal 节点，`mountPane` 契约加 `shell.portal`，
   件里 radix Portal 的挂载点指它——浮层从此物理上是本桌的后代，桌面藏它自动跟着藏。
   切换后扫 body **探雷**（只点名不删）：挂 body 的浮层不属于任何桌面，藏不掉
3. 契约加 `shell.onVisibility`：桌面可见性通知，**协作式降级、通知不强制**；logger
   第一个示范（切走停渲染、切回重取历史段）
4. 档升 **v3**：`{ v, active, desktops: [{ id, name, layout }], saved }`。v2 的 current
   **当场迁成第一口「主桌面」**、saved 原样带走；v1 照旧「认不出当没有」
5. 命令 `shell.desktop.list / switch / new`：井在页面那半，switch 与 new 经内核事件口
   转发给页面执行（`gwbKernel.emit` → 页面 `window.gwb.on`，logger 推日志同一条路），
   **回执 ok 只代表转发了**；状态栏加「桌面」段（列桌面 / 切换 / 新建）
6. 契约边界：`pane.instance` **井内唯一、跨井不保证**；`planOpen` 与查重、预览格「至多
   一份」全按本井算；格间总线仍按条目分桶——跨桌面听得见，现状写明
7. **行为变化**：模态遮罩从此只盖本桌主区（状态栏 z 更高、永远可点）——可以从模态里
   切桌面逃出

**撤了又上、而且还是保活，凭什么**。0.0.14 撤回留下的门槛是「先把切换悬案钉死再动手」。
第二波**不验尸旧实现**——社区证据独立钉住了那晚的两个向量，不用看旧代码也对得上：

- radix Portal 挂 `body` 的浮层**不跟宿主子树隐藏**（radix 官方 Portal 文档与讨论、
  React 侧同款 issue facebook/react#35000）。「后面的桌面盖住前面的」就是它——切走
  的桌面上恰好有个开着的浮层挂在 body，原样盖着新桌面
- `display:none` 给 ResizeObserver 报 0×0、回显不重排在 dockview 有前科（#1063 /
  #1130 / #1495）。「无响应」就是它

这两个向量还正好解释「受控复测复现不出」：复现需要非活动桌面**恰好**挂着 body 浮层
这个条件。所以重做按**直防向量**设计，不是复刻旧版修一修——hide 用什么、浮层挂哪、
命中测试怎么拦，每一条都对着上面的向量来。

**非活动井为什么用 `visibility:hidden` 而不是 `display:none`**：dockview 自己在面板粒度
上就从 display:none 换成了 `visibility:hidden + pointer-events:none`（PR #1130）——保持
占位、尺寸不归零，ResizeObserver 不发 0×0。照抄它的配方到井粒度，再补一道 `inert`
（HTML 原生的「整棵子树不可交互」，把 pointer-events 拦不干净的后代全覆盖掉）。多口井
绝对定位叠在同一主区，任何时刻恰好一口可见；井不挪 DOM（挪动会重载 iframe 类内容），
桌面那一节上**绝不加 transform / filter / perspective / will-change**——fixed 浮层的定位
基准一旦从视口改成这层，户口迁进本桌的浮层坐标全漂。

**浮层户口为什么值得动件契约**。CSS 只能藏 DOM 后代；portal 到 body 的浮层不是任何桌面
的后代，藏桌面藏不掉它。迁回本桌是**机制根除**，不靠任何行为约定。**这跟 0.1 时代删掉的
`portal.tsx` + container 补丁形状像、理由不同**：那次删是为样式围栏（前缀围栏下挂哪都有
样式，补丁失去存在理由），这次接回是为桌面归属——logger 的 package.json 里「别再加回来」
针对的是旧理由，这条就是翻案依据。不接线的件**不会坏**：浮层照旧挂 body 照常能用，只是
切桌时被探雷点名——软义务，可以分批迁。

**onVisibility 为什么是通知不强制**。浏览器那套免费节流（rAF 暂停、后台定时器限流）只
作用于「整页不可见」，不作用于同页里被 CSS 藏掉的一片；同页里也没有「暂停某棵子树的
JS」的机制（React `<Activity>` 是杀 effects 那一档，dockview 井吃不起）。所以只剩协作式：
外壳通知、件自己停订阅 / 停渲染 / 停媒体。N 桌常驻的空闲 CPU 是保活的固有税，降多降少
看各件配合度——logger 示范了标准做法：切走丢实时（node 半照常缓冲两千条）、切回重取
历史段，seq 去重挡住交叠。

**模态为什么只盖本桌**。户口迁回本桌后遮罩参与根层叠；状态栏给 z-[60] 压过它。盖整窗的
模态会把状态栏也锁死，而状态栏是桌面切换器所在、兜着「窗格全关光」的底。代价：菜单下拉
（z-50）在极贴底的位置可能被状态栏压住一截（radix 的碰撞翻转通常会避开），收下——
「永远能切桌面」比「模态盖满」值钱。

**踩到的一处**：prefix 守卫把探雷话术里的英文单词 `container` 当成漏前缀的类抓了——
它真是 Tailwind 的工具类（container 布局那个），守卫没坏，是它工作得太好。探雷那句话
改成中文说法了事。

**验的方式**：单测钉纯函数——档 v3 形状与 v2 迁移（layout.test 重写）、desktops 的
id 优先解析与事件记号（desktops.test 新增）、可见性枢纽的分发 / 注册即回 / 退订 /
听众隔离（visibility.test 新增）；门禁 `pnpm check` 全绿（671 条）。**实机验收待做**
（隔离 home，向量清单：非活动井零命中零绘制、切走带模态的桌面 body 无残留、回显尺寸
正确、焦点交接、v2 档迁移、`shell.desktop` 三条命令、logger 切走停渲染切回补段、N 桌
常驻 idle CPU）——读数随后补进这一段。

## 2026-09-11：一格的身份是它装的内容，外加预览格

**定**（shell 那一侧）：**`duplicable`（注册位）与 `duplicate`（开格选项）整个删除**，换成
件开格时给一个不透明的内容身份 `key`；一格另有两态——**预览格**（至多一份、可被顶掉）与
正式格。契约面变动四处：

1. `openPane(paneId, { key?, params?, preview? })`，加一条 `keepPane()`
2. `mountPane` 的句柄多一支**可选的** `retarget(params)`：给了就软换（件自己换内容、保住
   该保的状态），没给外壳就拆了重挂（硬换）
3. `planOpen` 吃的从 `taken: (id) => boolean` 换成**这一格此刻开着的几份**
   （`{ id, key, preview }[]`），多一种 kind `retarget`；`taken` 从这张表里推
4. `key` 与 `preview` 进外壳保留键名单，跟着面板 params 落盘

**推翻的是「谁给过开第二份的权限」这个问法。** 现场是块笔记：它一直拿 `duplicate: true`
表达「打开某一块」，外壳听到的意思是「我要一份新的」，于是同一块点两次开两格、点十条评论
开十格。根因不在块笔记——**外壳的窗格压根没有「装的是什么」这个概念**，`params` 是开格
那一刻塞进去的一包东西、外壳完全不解释，所以它答得了「这个 paneId 的第几份开着吗」，
答不了「这一块已经开着了吗」。照 VS Code 的分法：视图永远一份，编辑器可以很多份，
**多份是因为装着不同的东西**。所以 `duplicable` 那个布尔问错了问题。

**预览格的语义照抄 VS Code，实现是我们自己的**：dockview 的 PinnedTabs 是付费模块，而且
它的 pin 管的是排序与溢出，跟「别换我的内容」不是一件事。记号只标预览格（标题前一枚
**小空心圆点**，**不用斜体**——中文没有真斜体，浏览器画的伪斜体很难看），正式格一个像素
都不变：标例外不标常态。**没有反方向**，正式格变不回预览格，VS Code 也没有。

记号**当天改过一版**（同一轮改动里，没发过版）：第一版是「标题淡一档」，而**未激活的
标签本来整体就是 muted 前景色**——在那半边再淡一档等于没标，偏偏预览格多数时候不是激活
的那一枚。换成形状（有没有那枚圆点）就跟深浅无关了，颜色交给 currentColor 跟着标签四态走。

**状态栏那个「已开」记号问 `planOpen` 自己**（`willFocus`：点下去会不会走成聚焦），不问
「这一格有没有开着」。那条入口不给 `key`，所以它开/聚焦的是空身份那一份；件拿几个 key
开了几份、而空身份那份没开着时，两个判据岔开，人看见「已开」点下去却多一格空白的。
**记号与效果必须同一个判据**——在接线侧另写一条就是第二份真相，而漂了没有任何现象，
只是那个记号开始说谎。（开格行为本身没动：「打开这一格」就是打开没装特定内容的那一份，
那是内容身份模型的正常结论。）

**软换硬换那条分岔按形状判**（`pickRetarget`，跟 `pickMountPane` / `pickDispose` 同一套）：
挑得到就调，挑不到就重挂。挑不到是**正常路径**不是契约不符——简单的件不必为此写一行代码，
代价是那一格的状态跟着重来一遍。

**踩到的一处**：dockview 的 `api.updateParameters` **是并不是换**（`DockviewPanel.update`
里 `{ …旧, …新 }`，只有值写成 `undefined` 的键才删）。不补 `replaceParams` 这一道，上一份
内容的参数会赖在这一格里跟着 `toJSON()` 落盘，而现象只是「件收到了一个它这一轮没传过的
参数」。转正正好是同一条机制的另一面：删掉 `preview` 就是给它写一个 `undefined`。

**盘上的档不用迁移**：`duplicable` 从来没进过面板 params（只取 `spec.params` 加 icon）。
老档里的格没有 `key`，读出来是空串——跟「件不给 key 开的那一份」是同一格，正好接得上。

**验的方式**：`planOpen` 的四条规则、预览格那几条、保留键、`replaceParams` 与
`paramsKeyOf` 全钉在 node 跑的单测里（shell 那几份测试 +23 条），连「状态栏那条入口在
件开了几份之后是 open 不是 focus」也钉着——那正是「已开」记号的判据。实机验收（预览格
顶替、双击转正、软换保状态、圆点看不看得出）随块笔记那半一起做，不在本仓。

## 2026-09-10：装件时把该进 home 的 peer 一并装成直接依赖

**定**（plugins 0.4.0/0.4.1）：`plugins.install` 在「pnpm add 进 home」与「加条目」之间多一步
——读刚装进来那个包的 `peerDependencies`，把**该进 home 的**逐条 `pnpm add` 成 home 的直接
依赖（装 latest）。判据四条按顺序：已经在 home 清单里的 `present`（**版本一个字不动**）→
`cordis` 跳过 → `@godcreator02/gwb-*` 里共享包装、件跳过（判据是清单里有没有 `gwb.shared`）
→ 其余一律装。**装不上不让整条 install 失败**，回执 `peers` 逐条报 installed / present /
skipped / failed。**卸载不动 peer。**

**为什么要有这一步**：件依赖一个会独立升级、只读文件不 import 代码的包时（`gwb-docfirst-workflow`
之于 `@godcreator02/docfirst-workflow` 就是），正确形状是把它写成 peer、件每次现查
`<home>/node_modules/<包名>`——那是一条会被 pnpm 改指的 junction，指向永远是当前版本，
升级不用重启也不用重挂。而**那条路径只有在包进了 home 的 `package.json` 时才存在**。
内核仓 `probes/2609101500_peer-dep-live-swap` 实测三条：pnpm 自动补的 peer 只塞进 `.pnpm/`
与件的解析面，home 顶层没有；`pnpm outdated` 只看 `package.json`，于是自动补的 peer 永远
不在过期清单里、[一键热升](#2026-09-09一键更新是热重挂不重启)也永远升不到它；
`auto-install-peers` 那个开关帮不上忙（默认本来就是开的，而且在 pnpm 11 上写 `.npmrc` 完全
不认）。三条路（件替它装 / 开开关 / 人手装）里只有第一条成立。

**为什么共享包也算「该进 home 的」**：`gwb-shared-react` / `gwb-tokens` 本来就该是 home 的
直接依赖——内核只扫 home 的 dependencies 拼页面 importmap，它们不在那张清单里等于没有。
跟这次要接的 peer 是同一个形状，先例已经在跑。区分「共享包」与「件」不猜，读那个包清单里
的 `gwb.shared`：内核扫它拼 importmap、`plugins.shared` 读同一批，是本生态既有的标记。
读不出来（多半是条 `optional` 的 peer，pnpm 不为这种自动补）**保守当件跳过**。

**为什么卸载不动 peer**：**代价不对称**——残留一个没人用的包只是占磁盘，误删一个还有件在
用的包是运行时故障。所以 `plugins.uninstall` 不去追引用计数。这条要写在说明书上，免得下一个
人以为是漏了。

**为什么装 latest 不装清单上那条 range**：这个生态的 peer range 一律写 `>=`（`//peerRange`），
latest 通常都满足；按 range 装会把 `^1.2.3` 这种范围原样写进 home 的清单。range 原样带进
回执，对不上时人看得见。**一条一趟 pnpm 不批量**：一趟 `add a b c` 里有一个包源上没有，
pnpm 整趟失败、好的一个都装不上，而且不告诉你是哪个挂的。

**踩到的一处**：peer 的清单**不在** `<home>/node_modules/<件>/node_modules/` 下（那儿只有
`.bin`）——pnpm 把 peer 跟件并排放在虚拟仓那一层。0.4.0 按前者找，于是每条 gwb peer 都落进
「认不出种类」的保守分支、共享包跟着被当件跳过；0.4.1 改成先 `realpath` 解开那条 junction
再按包名段数往上退，实机复验共享包正确入账。

**验的方式**：单测钉住纯函数（`toPeerDependencies` / `peerKindOf` / `planPeers` 四条判据与
排序）与真碰盘的 `readPeerManifest`（临时目录里搭一份 pnpm 布局，junction、顶层兜底、
两处都没有、平铺布局四种）。**实机验过**：隔离 home（`peerdep2-2609101601`，只装 commands
与 plugins 两件）里 `plugins.install @godcreator02/gwb-theme` → `gwb-shared-react` /
`gwb-tokens` 进了 home 清单、`gwb-plugin-api` / `gwb-settings` 报 skipped「本生态的件」；
装一个自造的假件 → 好的 peer `installed`、源上不存在的那条 `failed` 而**件本身照样装上、
条目照样落**；再发一版假库之后 `plugins.outdated` 看得见那条 peer，`plugins.update-all`
把它升掉、`<home>/node_modules/<包名>` 的 junction 改指新版本、读出来是新内容。假件已
unpublish、测试 home 已删。**没升 default home。**

## 2026-09-09：一键更新是热重挂，不重启

**定**（plugins 0.3.0，配套 shell 0.2.2 / mcp 0.3.1）：

1. **`plugins.update-all`**：`outdated` 拿清单 → **一趟** `pnpm add a@x b@y …`（精确版本）→
   升了的每个包的**每条条目**停用再启用 → `shell.reload` 整页重载。**不重启内核。**
   `{ only?: string[] }` 可限定包名
2. **升级与重挂在同一条命令里做完**，中间不留「下一条命令」的窗口
3. **本件自己排最后、回执之后才重挂**：回执先交出去，`setTimeout(…, 0)` 的闭包里再停用/
   启用自己，然后才 `shell.reload`。回执上 `selfDeferred: true`、`reload: 'deferred'`
4. **外壳加 `shell.reload`**（主进程 `import('electron')`，逐扇 `webContents.reload()`；没窗口
   回 `ok: false`）；命令表里没有它就在回执 `note` 里写「界面要手动刷新」
5. **mcp 的 instructions 加一行**：发完新版本调 `plugins.update-all`；升到 mcp 自己时回执会丢，
   重连后 `plugins.list` 核对

**为什么是热重挂而不是重启**：agent 在干活途中改件、发版是这台工作台鼓励的事（instructions
里写着），可 0.2 的 `plugins.update` 升完只能说一句「重启内核后才换成新的」——发一版验一版
就得重启一次，agent 的会话（MCP 连接）跟着断一次。而事实基础（读 `@cordisjs/plugin-loader`
核过的）是：条目 `disabled: true` → `fiber.dispose()`；再把 `disabled` 抹掉 → `update()` 见
fiber 没了走 `init()`，而 `_init()` **每次重新 `tree.import(name)`**。所以「停用再启用」本身
就是一次干净的重 import，不用 remove / create，条目在 yml 里的 id 与位置一字不动，设置与
数据的归属（都按 id 分区）也就不动。做法见[插件管理](/docs/plugins)。

**为什么升级与重挂要在同一条命令里**：pnpm 升级会**删掉旧版本目录**。分成两条命令
（先 `update` 再 `remount`）的话，两条之间旧件若读盘（惰性 import 一个子模块、读自己
包里的模板）会读空——而那段时间有多长取决于人或 agent 什么时候调下一条。合成一条，
窗口就只剩 pnpm 退出到第一条 `tree.update` 之间的几毫秒。

**为什么每条条目都自己重挂，不靠级联**：被大家 inject 的件（commands / settings…）重挂时，
cordis 会把依赖它的件停了再起——看着像连带升级了，其实那是**重跑内存里的旧模块**，盘上的
新版本它碰都没碰。所以计划里升了的每个包的每条条目都在清单上，一条不省。

**为什么自己最后、而且在回执之后**：处理器里停用自己，这条 await 链随 fiber 一起拆掉，
回执永远到不了调用方——界面上就是「点了没反应」。所以自己那条从计划里单独标出来
（`planUpdateAll` 的 `self`），处理器把别人的都做完、回执交出去，下一个宏任务再动自己。
那段闭包**只持 tree、id、总线的引用与那只 logger**——本件的 fiber 已经拆了，ctx 上取服务
会「inactive context」。

**依赖内核那次改动**：主进程没有 `--expose-internals`，件的裸名由内核塞给 `loader.internal`
的那五行解析——它原来走 `createRequire(home).resolve(name)`，而 Node 的 CJS 解析有
**进程级缓存**，装了新版本还会回旧版本的路径，重 import 拿到的还是旧文件。内核当天改成
先 `realpathSync.native` 把 home 里那个名字解成真实目录再解析（内核仓轨迹卡
`2026-09-09-wall-resolver-cache`，提交 `1e744bc`）。**没有那一步，这条线上「停用再启用」
重 import 到的仍是旧版本**——热重挂能成立，一半在件这边、一半在内核那五行。

**渲染层为什么整页重载**：开着的格持的是旧的 client 束，importmap 只在开机注一次；
node 半换了新版本、页面上那份还是旧的。外壳内部重建做不到——束已经 import 进来了，
ESM 没有卸载。所以收尾是 `shell.reload`（就是状态栏那颗「刷新」的命令版），归外壳。

**验的方式**：单测钉住纯函数——`planUpdateAll`（一趟 pnpm、精确版本、包按名排自己最后、
包内自己那条最后、停用的带标、`only` 限定与 `ignored`）、`fiberStateOf`、`settleFiber`
（到点就走）、`describeUpdateAll`（回执→几行话）、外壳的 `reloadWindows`（没窗口 `ok: false`）
与 `electronWindows`（不在 Electron 里 reject）；三包 `pnpm check` 全绿。**实机没验**——
default home 正被连着的会话占着，而这条改动恰恰要装进 home 才验得出来（内核那次解析器
改动也得先起新内核）；留给下一次起机时由人验：发一版 hello → 点「全部更新」→ 看
`plugins.list` 的版本与 active、页面是否重载、`gwb.log` 有没有 error。

## 2026-09-09：MCP 工具面收窄——固定两枚加登记时标了 `top` 的；配置走 settings

**定**（mcp 0.3.0，配套 commands 0.2.0 / skills 0.2.0 / node-cli 0.2.0 / py-cli 0.2.0）：

1. **桥只渲染固定两枚**（`gwb_command_list` / `gwb_command_run`）**加登记表里标了
   `top: true` 的命令**；其余一律经 `gwb_command_run` 按名调。`GwbCommandDef` 加可选
   `top`，总线原样带进 `list()`，缺省 `false`
2. **顶层是开发时定的**：件在登记命令时标 `top: true` 就是决定，桥看到就渲染——**没有
   运行时名单、没有批准这一步**。「同意」只剩一条纪律，写进 instructions：agent 标它
   之前先停下来问人。缺省只有说明书那两条（skills 件自己标的）
3. **件的配置一律走 `gwbSettings.define`**，不吃 `cordis.yml` 的 `config`。mcp 的端口
   改成 `port` 设置（缺省按 home 名：default 2870、其它 0），硬 `inject` settings
4. **instructions 改成固定文本**（二十行内），不再列说明书清单；说明书的发现面改为
   `skill_list` 的回执，正文 `skill_read` 与 resources 两条路
5. **命令描述必须写参数形状**（`{ entryId }`、`{ args?: string[], cwd?: string }` 这种；

6. **两个 CLI 运行器的 `run` 加按次的 `cwd`**：必须是存在的目录的绝对路径，不合规回
   `{ ok: false, error }` 不抛；总线镜像认 `{ args, cwd }`

**依据**：三样发现面、两样是快照、一样会截断。实测 Claude Code 连着时，顶层工具清单与
resources 列表都是**连接时的快照**（停用一个件，它那枚工具还挂着；新装的不长新的），
server instructions 则会被**截断**（十三份说明书列到第八份就断）。而逐条渲染出来的每枚
工具 schema 都只是 `args: unknown`，比 `gwb_command_run` 只多一个名字——为一个名字占一个
会被截断的稀缺位，不划算。mcp 页一直写的就是「工具面只有两件、没有逐条门牌」，逐条
渲染是当天一次提交信息为「a」的提交带进来的、没记理由，这一次是回到文档写的设计。

**顶层为什么不做成名单**：起初推的是「件申请（`top: true`）+ mcp 一项 `top` 设置做人批的
名单」，settings 为此加了 `list` 类型。当天改判：顶层是**开发时**的决定，不是装进软件
之后批的事——名单是给运行时留的机制，而这个系统里 agent 拿着整台机器，任何「同意」都只
能是纪律，做成机制只是多一处要维护的表。于是 `top: true` 写在代码里就是决定，settings
的 `list` 类型随之撤回（那版没发出去），「标之前问人」写进 instructions 的门里。

**配置为什么走 settings**：`cordis.yml` 的 `config` 只有改文件重挂一条路，界面看不见、
agent 也调不到；settings 有界面、有命令、有缺省值的展示。件的配置面只留一条。

**验的方式**：单测钉住纯函数（`selectTop` 只挑标了 top 的、`choosePort` 收 unknown 且
数字串也认、`defaultPort` 跟不给值时一致、`checkCwd` 三种拒法、`parseInvocation` 认两种
形状、instructions 二十行内且点名固定工具），门禁 `pnpm check` 全绿。**装机没做**——
default home 正被一条连着的会话占着，留给下一次起机时由人验。

## 2026-09-09：`default` home 的 MCP 口不许退让

**定**（mcp 0.2.0，三件一起）：

1. **端口按 home 名分档**。`default` 要 `config.port ?? 2870`，**被占就报错、不监听、
   不退让**；其它 home 默认系统随机口，显式给了口才试那个、被占照旧退让。判断抽成纯
   函数放 `endpoint.ts`，接线里不留判断
2. **`mcp.info` 多回一个 `mcpServers`**，形状照 Claude Code 的 `.mcp.json` 标准，
   客户端照抄即可
3. **`instructions.md` 写明 agent 自改这台工作台的门**：哪些不用问就能做、哪些先问人

**依据**：

第一条推翻的是「首选 + 退让」这个看着最稳妥的写法。退让在多 home 同开时确实体面，
但它体面的前提是**没人把某个口当契约用**——而 default 恰恰就是被当契约用的那个：连
工作台的 agent 会话手上那份 `.mcp.json` 写死 2870，不会再问一次。于是有这条时间线：
测试 home 先起占住 2870 → default 退让到随机口 → 会话连上的是**测试 home**，命令面、
数据、说明书全是另一套，**两头都不报错**。这类错的代价不在于它多严重，在于**它不
出声**：agent 会一路干下去，人要到结果落在别的 home 里才发现。

于是判据是「**静默连错 vs 当场看得见**」，不是「开着 vs 关着」。不开这道口是一行
`log.error` 加一句 `mcp.info` 的 `ok: false`，人一问就知道；开在别处则要等下游出怪事。
`fallback` 这个位子就是这条判断的落点，它只对「显式给了口的非 default home」为真。

第二条是同一条判据的小号：`url` / `token` 拿到手还得自己拼一遍配置，而拼错的三种
（scheme 写成 `sse`、漏 `Bearer ` 前缀、url 少 `/mcp`）症状都是「连不上」，从客户端
那头看不出为什么。把拼装收进工作台一侧，机会就没了。

第三条不是新机制，是**把已经在执行的规矩写下来**。这台工作台鼓励 agent 在干活途中改件、
发版、装回 home，可「哪些能自己动、哪些得问人」以前只活在人的脑子里。分界线是**改动的
爆炸半径**：修 bug、补 `SKILL.md`、加命令加件错了只波及它自己；改内核、改那七件被别人
`inject` 的契约面或依赖，错了是整台工作台起不来或别的件静默失灵——而 agent 在自己的
会话里看不见那个半径，所以这条得由说明书替它看见。写进 `instructions.md` 是因为**那段
每个 agent 连上来都会读**，是唯一不用它主动去找的位置；代价是每会话的固定上下文，
所以只写门本身，理由留在这一页。

**验的方式**：单测钉住纯函数（home 名末段两种分隔符、default 两支不退让、非 default
两支、配置写坏当没给、片段形状与 url 一致），门禁 `pnpm check` 全绿。**装机没做**——
default home 当时正被一条热更实验占着，端口这条改动恰恰要重启 home 才验得出来，留给
下一次起机时验。

## 2026-09-09：样式围栏从选择器 scope 换成 Tailwind 前缀

**定**：件的样式围栏改用 **Tailwind 4 的 `prefix(<短名>)`**——类名从源头就是 `hello:flex`
这种，规则全页有效，但只可能匹配到本件画出来的元素。原来那套**构建期把每条选择器改写成
`:where([data-gwb-plugin="…"]) …`** 的 scope 方案退场。

拍板时的打算是**逐件迁、不赶**：先出 `hello` 0.2.0 一份样板，两套围栏互不干扰、谁都不必
等谁，两代件在同一张页面上并存本来就跑得通。**实际当天就迁完了**——五个带界面的件全在
0.2.0，`tools/build-styles.ts` 与它服务的那条线一起删掉，两代并存的状态结束。经过与读数
见下面「同日：其余四件全迁，scope 线退场」。

**令牌那两条一个字没动**：值全局共享一份（页面加载声明面那张表），组件各拉各的
（每件一份 `components.json`，要什么从 shadcn 官方拉什么）。

### 契约与形状怎么变

| | scope 方案（已退场） | 前缀方案（0.2 起，五件全体） |
| --- | --- | --- |
| 输入怎么来 | `tools/build-styles.ts` 在内存里拼输入，再拿 postcss 逐条改写选择器 | 件根一份 `src/client/styles.css`（五行 import），`@tailwindcss/cli` 直出 |
| 围栏是什么 | **DOM 祖先关系**——元素得待在那个属性之下 | **类名的唯一性**——名字自带前缀 |
| 弹层（radix Portal 挂 `body`） | 出了围栏就一个类名都不生效，得给 `DropdownMenuContent` 打 `container` 补丁 | **无关**。portal 到哪都有样式，拉下来的组件一个补丁都不打 |
| 容器上的 `data-gwb-plugin` | **围栏本身**，容器上不挂它，那些件的类名一个都不生效 | **只是身份标记** |
| shadcn CLI 拉下来的组件 | 类名是裸的，本来就在围栏里 | `components.json` 的 `tailwind.prefix` 让 CLI 直接写带前缀的类 |
| 唯一的静默失效点 | 见下——弹层裸奔 / 规则漏进别人窗格 / 加载顺序 | **忘写前缀**（那个类当场不生效，写代码时就看得见） |

### 为什么 scope 本来是必需的

这一段得讲透，否则下一个人会以为围栏是可有可无的洁癖。

**Tailwind 是按需编译的**：它扫源码，你用到哪个类就编哪条规则，编不出来的一个字节都不出。
于是每个件的那张表都是**全集的一个子集，而且各是各的子集**。子集本身没问题，问题出在
**几张子集表叠在同一层里**——Tailwind 的工具类全在 `@layer utilities` 下，同层同权重，
**谁排在后面谁赢**。

具体到会疼的那一下：A 件的元素上写着 `p-4 px-2`（先四边 padding，再让左右覆盖成 2）；
B 件只用了 `p-4`，所以 **B 的表里只有 `p-4` 没有 `px-2`**；而 B 的表**后加载**。于是最终
层里的顺序是「A 的 `p-4` → A 的 `px-2` → B 的 `p-4`」——**B 那条 `p-4` 排在 A 的 `px-2`
后面，把 padding 整个重置回四边 4**。A 件的元素从此少了那条 `px-2`，而**没有任何一处报错**：
两张表都编得对、都加载成功了，只是撞在了一起。

所以「规则必须彼此隔离」这条从头到尾没被推翻，**换的只是隔离手段**：从「按 DOM 祖先关系
隔离」换成「按类名唯一性隔离」。

### 依据：位置是运行时才确定的，名字是写代码时就确定的

两套方案的失效点不对称，而且**不对称在最要命的那一维上——错什么时候被人看见**。

**scope 方案的失效发生在 DOM 变化那一刻**，一共撞出过三种形态：

- **弹层 portal 到 `body` 就裸奔**。radix 的 Portal 默认挂 `body`，一挂出去就不在
  `[data-gwb-plugin="…"]` 之下了，菜单一个类名都不生效
- **外壳的规则漏进所有窗格**。外壳的根是每一格窗格的祖先，所以外壳那张 scope 表的
  `:where([data-gwb-plugin="@godcreator02/gwb-shell"]) .foo` 对窗格里同名的元素照样成立
- **加载顺序成了隐含前提**。哪张表先注进页面决定谁盖谁，而那个顺序是运行时的事

三种都**不报错**：没有构建期告警，没有运行期异常，只有「这块怎么没样式」或者「这块怎么
被别人改了」。

**前缀方案的失效只剩一种：忘写前缀。** 而那个类**当场不生效**——写代码的人打开页面就看见，
不用等到某个弹层被打开、某两个件被同时装上。它还能用一条守卫堵死（见下面「验的方式」）。

**工具链原生支持，不用自写手术。** Tailwind 4 的 `prefix()`、shadcn `components.json` 的
`tailwind.prefix`、`cn` 包（tailwind-merge）对带前缀类名的冲突合并——三处都是上游本来就有的
能力。scope 那条路是我们自己写的 postcss 改写，外加给每个带 Portal 的组件打补丁：**两笔
自维护的成本，换来的围栏还更弱。**

### 验的方式

**先在内存与一个 scratch 工程里把机制逐条问清楚**，八条读数：

- `prefix()` 得写在**拆开的 `theme.css` 导入**上才生效，写别处不认
- 不带前缀的类在带前缀的编译下**一个字节都不出**——这既是围栏的强度，也是那条守卫的判据
- shadcn 4.21.0 给官方组件加前缀是**完整的**：237 处该带的全带上了
- `cn` 包默认就把 `hello:h-9` / `hello:h-8` 合并对，**不用为前缀配任何东西**
- **不引令牌那张映射面则颜色类整个是空的**——`bg-primary` 编不出 `var(--primary)`，静默无规则
- **不引 `tw-animate-css` 则 `animate-in` 一族全部不生成**；引了会带出不带前缀的全局
  `@keyframes enter/exit` 与十七个 `--tw-enter-*` `--tw-exit-*` 的 `@property`（每件一份、
  内容相同，无害）
- **Tailwind 4 的 prefix 会把内置主题变量名也改掉**：spacing 编成 `var(--hello-spacing, 0.25rem)`。
  走 `theme(reference)` 时那个变量永远不声明、落到默认值，所以没坏——但它意味着**令牌只能
  经映射面送值**，指望在全局声明 Tailwind 的默认主题变量去影响所有件是行不通的

**再实机取证**（home `prefix-2609090824`，经 CDP）：hello 那张表 **167 个类 token 除祖先身份的
`.dark` 外全带 `.hello\:`**、`data-gwb-plugin` 一处都没有；按钮底色 `oklch(0.92 0.004 286.32)`
等于 `--primary`；窗格 1069px 时变体按钮排 `row`、压到 300px 变 `column`（容器查询按**这一格**
的宽度判，不看视口）；菜单内容**挂在 `body` 下与 `#root` 平级**，底色等于 `--popover`、8px 圆角、
1px 边框——portal 出去照样有样式；切亮暗后按钮色变成新的 `--primary`。`gwb.log` 零 error。

**两条守卫钉住这个形态**：产物里的类选择器一律 `.hello\:` 开头（放行的只有祖先身份的 `.dark`），
且整张表不许出现 `data-gwb-plugin`——有它就说明构建又走回了 scope 那条路；另一条是
`plugins/hello/tests/prefix.test.ts`，把 `src/client` 下 tsx 里的字符串字面量抽出来切成 token，
在**去掉 `prefix(hello)` 的同一份输入**下逐个试编，**编得出规则的就是漏加前缀的类**。判据是
「这一步有没有把产物撑大」（`compile().build()` 是增量的，不能跟空基线比）。唯一的排除是
`outline`——它是 `variant="outline"` 的值，恰好也是个工具类。

### 代价与遗留

- **源码里每个类多一个前缀。** 这是明面上的税，一直要交
- **已有件迁移是全量改类名。** 原打算逐件分期、不设期限（两代并存本来就跑得通），
  实际当天就把剩下四件迁完了
- **残余耦合：Tailwind 内部的 `--tw-*` `@property` 不随前缀走。** 每张表各注册一遍同名的那批，
  同名后注册的赢——所以**全生态仍然得同一个 Tailwind 大版本**。这条不是前缀方案引入的，
  但前缀方案也没消掉它
- **两堵新墙**：`tw-animate-css` 不引则 shadcn new-york 的组件静默不动画（scope 方案的件
  一直如此，只是没人报）；CSS 头注里写 `--tw-enter-*` 那个 `*/` 会提前闭合注释，而报的错
  完全不指根因。两条都记在[撞过的墙](/docs/walls)
- **一桩取证时的未决现象**：CDP 切不动 dockview 的标签。跟本次改动无关（`GwbTab.tsx` 没动），
  同样记在墙那页

#### 迁移时撞出来的三条

**一、`group` 这类标记类也要带前缀。** `logger:group-hover:*` 编出来的选择器是
`:is(:where(.logger\:group):hover *)`——它认的是**带前缀的** `.logger\:group`。标记类本身
若还写成裸的 `group`，规则永远不命中，而且**不报错**：类名在、规则也在，只是对不上。
凡是「一个类当锚、另一个类的变体去找它」的搭配（`group` / `peer` 这一族），两头都得带前缀。
这条记进了[撞过的墙](/docs/walls)。

**二、plugins 件的对话框遮罩从此盖整窗。** 老线里 `mountPane` 给容器配过一句
`container.style.position = 'relative'`——那是 scope 时代为了把 portal 拽回围栏里留下的
配套手术。组件重拉成原样时它一并去掉了，于是 `fixed inset-0` 的遮罩改为相对视口定位，
**盖的是整窗而不是只盖这一格**。这是模态该有的样子，不是回归。

**三、lucide 图标的 `.lucide` 不算围栏泄漏。** 它是图标库烤进 SVG 的身份属性
（`class="lucide lucide-xxx"`）；全站没有任何一条规则匹配 `.lucide`，跟容器上的
`data-gwb-plugin` 同性质——**DOM 里有这个名字，不等于样式表里有这条规则**。守卫查的是
产物里的选择器、不是 DOM 里的类名，所以两者都不触发它。这条也记进了墙那页。

#### 守卫的排除项：只放值，不放类

`tests/prefix.test.ts` 把 `src/client` 下的字符串字面量切成 token 逐个试编，编得出规则的
就是漏加前缀的类。五件的排除表：

| 件 | 排除 | 为什么 |
| --- | --- | --- |
| hello / plugins | `outline` | `variant="outline"` 的值，恰好也是个工具类 |
| theme | `font-sans` / `font-mono` | 本件设置项的 key |
| shell / logger | **空表** | 没有这种撞名 |

**排除表短是这条守卫立得住的前提**：每加一条都是给「漏写前缀」开一个口子，所以只放
**明确不是类名的值**进去。

## 2026-09-09：全部件迁到单进程内核的 0.1 契约

**定**：这个仓从今天起对着**单进程内核** `gwb-kernel-min`（单元 `26090705ymz`）与
**词汇表 0.1**（`@godcreator02/gwb-plugin-api@0.1.0`）。十二件一起发 0.1.0。
**旧内核 `gwb-kernel` 退役**——它那套（宿主子进程、fd3、`gwb://`、`kernel.info`）不再是
这些件的运行环境。

契约变了这几处，件那边一一对应：

| 从前（旧内核） | 现在（0.1 契约） | 谁改了 |
| --- | --- | --- |
| 内核按 `exports` 表解析 `gwb://asset/plugins/<包>/client` | 件注册窗格时自报 `client` / `style` 的 `file://` 地址，从自己的 `import.meta.url` 算 | 窗格件全体（shell 的注册表加两个字段） |
| 内核挑「谁是外壳」并 boot 它 | 外壳 node 半自己 `kernel.setShell(本包的 client.js)`；开机要的 home 与三张样式表走新命令 `shell.env` | shell |
| 日志管道在内核（四路汇总、缓冲、`window.gwb.logs`） | 日志件自己挂 cordis exporter 收三路（件 / 内核 / 渲染层）、自己缓冲、经 `gwbKernel.emit` 推；页面订 `window.gwb.on` | logger |
| `kernel.info` 报 `shared` / `sharedPkgs` | importmap 还是内核拼（扫 home 里各包的 `gwb.shared`），但**没有自省命令**：件管理改自己读 home 的 `node_modules`，开了一条 `plugins.shared` | plugins |
| `gwbKernel.appVersion` | 没有了。MCP 桥报给客户端的版本改成**本件自己的** | mcp |
| `gwbKernel.install(specs)` / `kernel.install` | 没有了。装包一直就是 `plugins.install` 走 pnpm | 无（本仓从没用过内核那条） |

**共享包的声明面没动**：`gwb.shared` 还是提供方在自己清单里声明，内核只搬运。所以
`gwb-shared-react`（0.0.2）与 `gwb-tokens`（0.0.5）这一轮不发版。

**依据**：不是「顺手升级」——旧内核已经不再是这些件跑的地方，件仓不跟上就是一整仓对着
一个没人再起的宿主写代码。改动面也确实只有上表那几处：`commands` / `node-cli` / `py-cli` /
`data` / `settings` / `skills` 六件**一行源码都没动**，只换了依赖来源与版本号——契约面本来
就小，这是它小的好处。

**验的方式**：十二件从本机 registry 装进 `gwb-kernel-min` 的一个隔离 home，起内核经 CDP
取证：五格窗格全部自报了 `client` 与 `style`、十二条条目全 `active`、`hello.node` 与
`hello.python` 退出码 0、`plugins.shared` 认出两个共享包、`mcp.info` 回连接串、页面
`console.log` 一句 800 毫秒内出现在日志格里。

## 2026-09-08：状态格机制整个下架，件各画各的窗格

**定**：`gwb-status` 与整条状态格机制（`registerCell` / `mountCell` / `status.cells` /
`gwb-status:cells` 事件）删除——**要给人看的件，自己画自己的窗格**。

**经过**（三步都没离开当天的工作区，前两步的判词各留一句）：先走声明式（0.0.1——格子
内容由消费件报数据+档位、渲染器只有状态件一份，理由是数据起源于 node 半、渲染统一不靠

整个下架。

**下架的依据**：格子的价值本在「多个件的健康一屏看全」，可这条线至今只有两三个件、
且各有各的窗格——聚合的需求从没真到过（准入第二关）。而每颗格子要 node 半注册 +
client 半自绘 + 一套取数轮询，比一扇窗格多一层服务、一层事件、一条软契约
（`mountCell` 的形状）。件各画各的窗格之后这套全没了；哪天真要「一屏看全」，再做一个
聚合窗格的件也不迟——加回来永远比拿掉容易。

**收尾**：registry 上的 0.0.1–0.0.4 佚版留档不撤（照 `gwb-market` 先例）；hello 去格发
0.0.20（`hello.probe` / `hello.bump` 两条命令保留——探针数据口与格子无关）；devkit 的
「插件源」格改开一扇普通窗格；gwb-windows-backup 撤格留窗格。

## 2026-09-08（同日再改判）：「可装」的白名单退场，改 registry 检索

**改判**：上一条里「白名单判据原样保留」作废。可装段不再认手工清单，改为
`plugins.search` 查 **npm registry 标准检索协议**（`/-/v1/search`），列出
`@godcreator02` scope 下 `gwb-` 前缀的全部。拍板人的原话：「不要主动注册了，直接找
以 gwb- 开头的插件都列进来就行了」「market 就是去 npm 找 @godcreator02，应该做到
解耦，Verdaccio 是接管了这个而已」。

**解耦那条是钉死的**：代码里不出现任何具体源的名字与地址——基址从 pnpm 配置解析

## 2026-09-08（第三改）：插件卸载做上了

**改判**：gwb-plugins 第一版「没有 uninstall」的决定推翻——`plugins.uninstall` 上线：
先把这个包在 cordis.yml 里的**全部条目**摘掉（fiber 随条目当场卸下），再 `pnpm remove`
掉包本身；设置与数据留盘。界面入口在「已装」段的条目下拉（包级动作）与「已装、没挂
条目」区；共享包不给入口。

**旧判据与新解法**：当初不做的理由是「删包比留着危险得多」——一刀 pnpm remove 之后，
条目还在 yml 里、依赖它的件还挂着，现场一片 ghost。解法不是不做，是**把顺序做对**：
先摘条目后卸包（`reconcile` 早就预言过「包被 pnpm remove 掉、条目还在」的 ghost 形态，
顺序对了它就不出现）；pnpm 失败**不回滚**——条目已摘是正当落点，包落进「已装、没挂
条目」区看得见、重试就行。装卸检升都齐了、独缺「拿掉」，这是准入第二关意义上的真实
需求到了。

**与 remove-entry 的分工**：删一条条目、包留着（服务第二条实例的场合），走
`plugins.remove-entry`；整包走人，走 `plugins.uninstall`。两个动作、两个入口，不是同一
个的两种写法——对话框里把这句写给了人。
