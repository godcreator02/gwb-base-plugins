**本页回答**：这个仓里放什么、不放什么；插件之间怎么连接、为什么不直接 import 彼此的代码；为什么所有能力都登记成命令；数据与设置为什么按条目而不是按包归属；插件怎么声明自己兼容哪个内核；刻意不做哪些事。每个插件的功能在各自的页，插件之间约定了什么在各接缝页。

## 这个仓只放无界面的基础插件

本仓插件都是 `cordis.yml` 里的普通条目，和别的插件一样装在 home 里、经插件管理升级、可以停用和卸载：

| 插件 | 包名 | 服务 | 做什么 |
| --- | --- | --- | --- |
| [commands](/docs/commands) | `@godcreator/gwb-commands` | `gwbCommands` | 命令总线 |
| [mcp](/docs/mcp) | `@godcreator/gwb-mcp` | 无 | MCP 入口，工具只有 `index`、`search`、`run` |
| [skills](/docs/skills) | `@godcreator/gwb-skills` | `gwbSkills` | 收集插件自带的说明书 |
| [settings](/docs/settings) | `@godcreator/gwb-settings` | `gwbSettings` | 设置 |
| [data](/docs/data) | `@godcreator/gwb-data` | `gwbData` | 插件的数据目录 |
| [node-cli](/docs/node-cli) | `@godcreator/gwb-node-cli` | `gwbNodeCli` | 运行 node 命令行工具 |
| [py-cli](/docs/py-cli) | `@godcreator/gwb-py-cli` | `gwbPyCli` | 运行 python 命令行工具 |
| [workers](/docs/workers) | `@godcreator/gwb-workers` | `gwbWorkers` | 插件的线程池 |

不在这个仓的：

- **内核**在内核仓 gwb-kernel：内核应用和安装包，一个插件也不带
- **插件管理** `@godcreator/gwb-plugin-manager` 在生命周期插件仓 gwb-lifecycle-plugins：装插件、找插件、配包源都是它的命令
- **有界面的插件**（外壳、主题、基础窗格）在界面插件仓 gwb-ui-plugins；查日志的命令 `logger.query` 也由那边的基础界面插件 `@godcreator/gwb-baseui` 登记，本仓没有日志插件（轨迹卡[日志插件并进基础界面](/trajectory/2026-09-28-logger-merged-into-baseui)）

这个仓的插件不依赖任何界面包：peer 里不写界面包，构建产物检查只放行名单里的包名，界面包的 import 进不来。

## 插件的类型只从内核包取

内核包 `@godcreator/gwb-kernel-desktop` 的包根只导出类型，是内核对插件的契约；插件从它 `import type`：`GwbContext`、`GwbKernelApi`；`GwbResult` 从命令插件取。包根的运行时入口一加载就启动 Electron 应用，所以只能 `import type`，构建产物里不出现它。要用内核服务 `gwbKernel` 的插件（数据、设置、MCP 入口）各自在 `src/vocab.ts` 里写一份十几行的 `requireKernel`，不从别的包取运行时代码：

构建产物由 node 直接加载：MCP 插件以外的插件用 `tsc` 直接输出，MCP 插件用 esbuild 把 MCP SDK 与 zod 打包进 `dist/index.js`（类型声明仍由 `tsc` 输出）。所以有两条硬要求，都由各插件的构建产物测试检查：**相对 import 必须带 `.js`**；**构建产物里的包名 import 只能是 node 内置模块与 `cordis`**，只有继承 cordis `Service` 的插件留着 `cordis`。为什么不能用 `nodenext` 让 TypeScript 检查扩展名，见[遇到过的问题](/docs/pitfalls)。

本仓插件的依赖这样写：

- **peer**：内核包 `@godcreator/gwb-kernel-desktop`，每个插件都写（见下面「插件在 peer 里写内核包」）；`cordis`，继承 `Service` 的插件在构建产物里按值 import 它，所以写，运行时必须和内核用同一份；MCP 插件不继承，不写
- **本仓别的插件**：用到的写 peer（`workspace:^`，`devkit.release` 发版时换成 `^<版本号>`），只局部注入、缺了只少一部分功能的在 `peerDependenciesMeta` 标 `optional`；代码只 `import type` 它们
- **生态外的库**：只有 MCP 插件用（MCP SDK、zod），写 dev，由 `build.ts` 打包进构建产物
- **类型引用到、又不是插件的包写 dev**（`@types/node`、MCP 插件打包的库）

## 插件之间只经服务

插件之间不 import 彼此的运行时代码，能力只经 cordis 服务连接：

- **服务**：提供方用 cordis 提供一个服务名，使用方把它写进 `inject`（缺了就不加载），或用 `ctx.inject([...], cb)` 局部注入（缺了只少一部分功能）。服务的类型由提供方的包导出，使用方写 `import type {} from '<提供方包名>'`，让 `ctx` 上有这个服务的类型，构建产物里没有这个包
- **不经命令互调**：命令只给进程外的调用方（页面、agent）。插件同时提供服务和命令时，命令的处理函数校验完参数就调同一个服务方法。规矩正本在生命周期插件仓 gwb-lifecycle-plugins 文档站「写插件的规矩」的服务与插件之间怎么交互两页

哪个依赖是必需的、哪个是可选的、缺了会怎样，以及只靠两边写同一个名字的连接，逐条写在[插件之间怎么连](/docs/wiring)。可选的依赖一律局部注入：说明书对所有插件都是可选的；命令总线对设置插件是可选的（没有命令，别的插件照样读写设置，只是页面与 agent 调不到）。

包之间的依赖只有一个方向：说明书插件依赖命令插件，命令插件不 import 说明书插件的类型，只按形状声明用到的 `register(dir)`。工作区里有依赖环时，pnpm 12 的 `pnpm -r` 直接报错退出（轨迹卡[拆掉 commands ↔ skills 的包依赖环](/trajectory/2026-09-17-break-commands-skills-cycle)）。

两个插件要用同一段小逻辑时各存一份，不为它新建共享包：两个命令行运行插件的 `run.ts`、`invoke.ts`，数据插件的 `entryDirName` 与设置插件的 `entrySection`。这些副本的注释互相提到对方，改一处就要改另一处（见[命令行工具](/docs/seams/cli)、[条目身份](/docs/seams/entry-identity)）。

cordis 不给服务做版本校验，插件之间的版本约束只写在 peer 里：插件管理把 home 里没满足的列在 `plugin-manager.list` 的 `unmetPeers`，只报告、不拦加载，所以服务的接口只增加、不改名、不改形状。细节见[遇到过的问题](/docs/pitfalls)。

## 命令只给页面与 agent

插件的能力要被页面或 agent 调用，就登记成命令总线上的命令，两类调用方用的是同一张表：

- **页面**经 commands 浏览器客户端与 `commands.run` 请求通道，本包的处理器调用 `run` 并固定 `{ via: 'ui' }`，内核只传递通道载荷
- **agent** 经 MCP 入口：`index`、`search` 从命令总线的 `list()` 取清单，`run` 调 `ctx.gwbCommands.run` 并带上 `{ via: 'mcp' }`
- **插件**在进程内也调得到 `ctx.gwbCommands.run`，不带来源时处理函数收到 `{ via: 'plugin' }`；按规矩插件之间不这样调，用对方的服务

由此推出：

- **来源只转交、不限制**：各来源能调的命令一样，命令总线只把 `via` 转交给处理函数；要按来源区分的是处理函数自己（轨迹卡[命令总线把请求来源转交给处理函数](/trajectory/2026-09-24-commands-carry-request-source)）
- **命令行工具也是命令**：两个命令行运行插件把登记的每个工具同时登记成一条命令，不另开入口
- **说明书也经命令读**：`skill.list`、`skill.read` 是普通命令
- **MCP 的工具只有三个，以后也不增加**：MCP 的工具清单是连接时的快照，而插件在运行中装上、升级、停用；命令的变化全在 `run` 的参数里，每次调用现查命令总线（轨迹卡[三个工具](/trajectory/2026-09-14-three-tool-face)）
- **登记的命令跟着登记方注销**：命令总线继承 cordis 的 `Service`，把注销登记在登记方的 `effect` 上，条目停用时命令自动注销，命令表里只有能调通的命令（轨迹卡[命令总线改成继承 cordis Service](/trajectory/2026-09-24-commands-bus-as-service)）
- **每条命令写 `description`（一句话）、`usage`（参数形状，无参数写「无参数」），`plugin`（包名）由命令总线从登记方的条目取**：agent 只看得到这三样，命令与说明书按包名对应；缺一样命令总线就拒收（轨迹卡[命令定义改在登记时检查](/trajectory/2026-09-24-command-def-checked-at-register)）

## 数据与设置按条目归属

cordis 的条目模型里 `id` 是身份，`name` 只说明装的是哪个包；同一个包可以配几条条目，各有各的配置。所以：

- **数据目录与设置分区都按条目 id 的末段分**：`home:hello` 的数据在 `<home>/data/hello/`，普通设置在 `settings.json` 的 `hello` 分区，secret 值在同 home 的 `credentials.json` 对应分区。算法只取末段，不依赖内核的根条目 id，也避开 Windows 上不能进目录名的冒号
- **调用方不自己报身份**：数据、设置、说明书、命令总线、两个命令行运行插件的服务都继承 cordis 的 `Service`，从调用方上下文上的 `fiber.entry` 认出条目 id 与包名。插件报不出别人的名字，也就读写不了别人的数据与设置
- **目录与分区记着归哪个包**：插件管理生成默认 id 时去掉了 scope，不同 scope 的同名包会算出同一个 id，而条目删掉后数据与设置留在磁盘上。数据目录里有 `.owner.json`，`settings.json` 顶层有 `$owners`，包名对不上就拒绝，报错写明磁盘上哪个目录或文件，由人手工改名、删掉或改归属记录里的包名；工作台上没有转移归属的命令（轨迹卡[目录与分区记下归属的包](/trajectory/2026-09-19-owner-stamp)、[归属对不上时由人手工处理](/trajectory/2026-09-25-owner-errors-manual-handling)）
- **每个 home 独立保管配置**：凭据复制用 `credentials.copy` 显式指定来源 home，只写当前 home；复制完成后两边各自独立，不回退读取 default

## 凭据的存储与操作分开

凭据管理集成在 `gwb-settings`：插件声明 `type: 'secret'` 后继续通过服务内部取用，值统一落在本 home 的明文 `credentials.json`，普通设置与声明留在 `settings.json`。命令按对象分开：`settings.*` 只处理普通设置，`credentials.*` 处理凭据；本地输入和查看用 `credentials.set/reveal`，日常 AI 操作只回配置状态。两组命令共用一个插件，不要求插件内部服务调用方拆成两套存储。

AI 导入或复制凭据时只提交来源位置与目标位置，生成随机值时只提交目标，操作不把值交回会话。MCP 客户端接线由 onboard skill 编排，本地进程直接读凭据写配置；MCP 插件仅签发、列出和撤销令牌。`isSet` 只证明本地存有值；第三方认证、签发和撤销仍由业务插件负责。MCP 自己签发的临时凭据由入口逐请求检查有效期，权限与主凭据相同。

这避免常规工作先读出明文再写回，也保留用户要求的明文文件与 home 自治。文件不是加密保险箱，本机插件仍有宿主进程的文件权限。备份或迁移 home 时需一起保存 `settings.json` 与 `credentials.json`；只有旧设置文件的备份不再包含全部凭据。存储选择见[按 home 保管凭据](/trajectory/2026-10-05-home-credentials)，命令边界见[凭据单独编排](/trajectory/2026-10-05-credential-command-boundary)，精确契约见[设置接缝](/docs/seams/settings)。

## 刻意不做的事

- **只有 MCP 插件打包**：其余插件用 `tsc` 直接输出，构建产物由 node 加载；MCP 插件打包只为把生态外的两个库带进构建产物
- **不带界面**：界面在界面插件仓 gwb-ui-plugins
- **不管插件的安装与条目**：在插件管理，生命周期插件仓 gwb-lifecycle-plugins
- **不给命令分权限、不做沙箱**：插件和内核在同一个进程里，装插件就是授权；MCP 入口只绑 127.0.0.1、要 token
- **不为十几行的重复逻辑开共享包**：见上面「插件之间只经服务」
- **旧插件仓不是模板**：旧插件仓 gwb-plugins（已删除）的结构、分层、包划分一概不照搬
