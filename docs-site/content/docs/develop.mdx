## 什么时候进这个仓

改[关键设计](/docs/design)里列的九个插件才进这个仓。插件管理在 devkit 仓 gwb-devkit，界面插件在 gwb-ui-plugins，内核与词汇表包在 gwb-kernel。动手前先读内核仓的 `AGENTS.md`，那是 gwb 各仓共同规矩的正本；写插件的完整流程（新建、修改、验证、取证）在 devkit 的说明书 `gwb-devkit`，经 MCP 入口 `run` 调 `skill.read {"name":"gwb-devkit"}` 读。

## 第一次准备与构建

在仓根：

```powershell
pnpm install
pnpm build
```

`pnpm build` 是 `pnpm -r build`，每个插件用 `tsc -p tsconfig.json` 输出到自己的 `dist/`。pnpm 工作区是 `plugins/*`、`packages/*` 与 `docs-site`；`packages/` 下的 `shared-react`、`tokens` 只剩旧的构建产物、没有 `package.json`，不是在用的包。

## 提交前的检查

```powershell
pnpm check
```

依次是类型检查（仓根 `tsc --noEmit`，再对每个包 `pnpm -r typecheck`）、`oxlint`（带类型信息，警告也算失败）、`vitest`（`plugins/*/tests` 与 `packages/*/tests`）。测试有三类：

- **单元测试**：纯逻辑，比如命令表、路径与名字规则、MCP 的 `index`/`search` 返回、npmrc 的读写
- **构建产物检查**（`tests/artifact.test.ts`）：相对 import 带 `.js`、包名 import 只有名单里的。没构建时整组跳过，所以改了代码要 `pnpm build` 之后再跑一次 `pnpm check`，这组才真的检查了
- **self-report 检查**（`tests/self-report.test.ts`，检查逻辑在 `@godcreator/gwb-repo-kit`）：`package.json` 的 `description` 写齐服务名、说明书份数、命令条数；`gwb.provides` 与源码提供的服务一一对应；源码 `inject` 的每个服务名都出现在这个站的现状区。改了插件的服务、依赖或说明书，同一个提交里改插件页

MCP 插件没有 self-report 检查。

## 在隔离 home 里验证

改动只在隔离 home 里实际运行验证，不碰日常用的 `default`。都是 devkit 的命令，经 MCP 入口的 `run` 调：

1. **建一个隔离 home**：`devkit.home.new {"short":"<这次验什么>"}`，用安装版内核打开，装好一套基础插件，调试端口自动选
2. **改一版看一版**：`devkit.dev {"home":"<home 名>","dir":"<仓根绝对路径>","packages":["plugins/<插件目录>"]}`。它在仓根构建、发一个开发版（标 `dev`，不动 `latest`）、在那个 home 里装上、用 `plugin-manager.remount` 重新加载条目、刷新页面，并确认装上的是这一版、条目是 ACTIVE、日志里没有新的 error
3. **在页面上操作、调命令、截图**：`devkit.cdp {"args":["<home 名>","cmd","<命令名>"]}`
4. **看结果**：那个 home 里的 `gwb.log`；各插件启动与调用都会写日志

只有 node 这部分的插件也可以不启动工作台，直接在 home 里用 node 建一个 cordis 上下文验证，注意事项见[遇到过的问题](/docs/pitfalls)。

实验、测量的材料放仓根 `probes/<时间戳>_<目的>/`：一次实验一个目录、自包含（半年后照 README 第一行运行一次能得到同样结论）、进 git、不进 pnpm 工作区、不进 `pnpm check`。

## 发版

升哪一位版本号、依赖范围怎么写、发破坏性版本要多做什么，正本是 devkit 的说明书 `gwb-release`，**每次升版本号之前都读一遍**。这里只列本仓的要点：

1. **隔离 home 里验证通过**，`pnpm check`、`pnpm doc` 都通过
2. **升版本号并提交**：插件都在 0.x。**改了契约才升 x**：服务名、命令名、说明书名改名或删除，服务方法、命令参数、回执、事件的形状变了，写进磁盘的数据格式（数据文档、设置的键与值、`settings.json`、`runtime.json` 里自己那一项）变了，调用方依赖的语义变了。加功能、加命令、加可选参数、回执加字段、修 bug、改说明书、改内部实现，都升 y
3. **确认 `gwb.testedKernel`**：写的是在哪个内核版本上测过。换了内核之后，在新内核上验证过，再改成新内核的版本号
4. **发到团队包源**：

   ```
   devkit.release {"dir":"<仓根绝对路径>","packages":["plugins/commands","plugins/skills"]}
   ```

   `packages` 相对仓根、被依赖的在前。它先检查 git 工作区干净，在仓根构建，按 `files` 白名单检查产物，检查同号没发过、依赖范围写法对，再检查每个插件的 `gwb.testedKernel`：没写、不是合法版本号、和运行 devkit 的那个 home 的内核不在同一条版本线上，一个包都不发。工作区里的 `workspace:*` 依赖在发出去的包里写成 `^<版本号>`
5. **升级 default**：`plugin-manager.update-all` 一次升级全部插件，不重启；新插件第一次装用 `plugin-manager.install {"pkg":"<包名>"}`。升级到 MCP 插件自己时，这次调用的返回会丢、连接中途断开，重连后用 `plugin-manager.list` 核对

发破坏性版本（升 x）之前，照 `gwb-release` 先用 `devkit.audit-deps` 找出受影响的下游，往各自仓站的 feedback 区投一条。

手工发布是在包目录 `pnpm publish --no-git-checks`，这会先运行 `prepublishOnly`（`pnpm build`）；不写 `--registry`，`@godcreator` 的路由在机器级 `~/.npmrc`。

## 文档

文档站在 `docs-site/`，端口 4315：

```powershell
pnpm --filter gwb-base-plugins-docs-site build
pnpm --filter gwb-base-plugins-docs-site start
```

- **`pnpm doc`**（仓根）：检查文档页引用的代码有没有变、生成物和正本是否一致，不在 `pnpm check` 里；报红时这个提交不许推送
- **`pnpm doc:confirm <页的路径…>`**：引用的代码改了、页上的说法仍然成立时，先提交代码，再只点名自己改过的页确认（路径相对 `docs-site/`）。不带路径会把别人还没复核的页一起确认掉
- **仓根 `AGENTS.md`、`CLAUDE.md`、`README.md` 是生成物**：正本在 `docs-site/content/outputs/`，改完在 `docs-site` 运行 `pnpm exec docfirst render`，生成物和正本放进同一个提交
- **改代码的同一个提交里改文档**：动了服务、命令、依赖或写进磁盘的文件，改对应的插件页与接缝页；做了选型、某条路走不通，写一张轨迹卡
