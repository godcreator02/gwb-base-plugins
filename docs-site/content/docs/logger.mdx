**本页回答**：日志插件有哪些功能；页面、agent 和日志窗格经哪些接口用它，各属于哪条接缝；它依赖什么、缺了会怎样；哪些事常被以为归它、其实归内核或界面插件。包名 `@godcreator/gwb-logger`，源码目录 `plugins/logger/src`，入口文件 `index.ts`。

日志插件没有界面。人在界面上看日志用的日志窗格在界面插件仓 gwb-ui-plugins 的 `@godcreator/gwb-baseui` 里，它从这个插件取数据。

## 功能

- **把三个来源的日志收到一处**：插件与 loader 的日志、内核自己的日志、页面 console（内核把它转成名为 `renderer` 的 cordis 日志），都经 cordis 的日志流来，插件注册一个 exporter 就全部收到
- **给每条日志分来源、定级别**：logger 名是 `renderer` 的算页面，是 `kernel`、`loader` 的算内核，其余算插件；cordis 的 `success` 级别算 `info`
- **保留最近两千条**：插件加载之前已经产生的日志，从 cordis 自带的缓冲里补进来；每条带递增的序号
- **实时推给页面**：每收到一条，经内核的事件通道推给页面
- **两条命令**：`logger.backlog` 取最近两千条，`logger.where` 报 home 目录与日志文件的路径
- **提供一个没有方法的服务 `gwbLogger`**：日志窗格按服务名等它出现，服务上刻意不放任何方法
- **就绪时写一行 info**：写明补进了多少条历史；装了日志窗格的话，这一行会出现在窗格里，可以用来确认整条链路是通的

## 接口

每条接缝上交换什么、各方保证什么，写在接缝页；本节只列日志插件提供了哪些接口、定义在哪里。

| 接口 | 做什么 | 接缝 |
| --- | --- | --- |
| 命令 `logger.backlog` | 无参数，返回最近两千条日志的数组 | [1 命令总线](/docs/seams/bus) |
| 命令 `logger.where` | 无参数，返回 `{ home, logFile }`，`logFile` 是内核写的 `<home>/gwb.log` | [1 命令总线](/docs/seams/bus) |
| 页面事件 `{ t: 'gwb-logger', line }` | 每条新日志经 `gwbKernel.emit` 推给页面，页面用 `window.gwb.on` 收，靠 `t` 认出 | [10 日志](/docs/seams/log) |
| 一条日志 `LogEntry` | `seq`、`ts`、`source`（`plugin` / `kernel` / `renderer`）、`level`（`error` / `warn` / `info` / `debug`）、`name`、`msg`；类型由本包导出 | [10 日志](/docs/seams/log) |
| 服务 `ctx.gwbLogger` | 没有方法；日志窗格写 `inject: ['gwbLogger']` 只为等日志插件加载 | [10 日志](/docs/seams/log) |

两条命令的登记都包在 `ctx.effect` 里，插件卸载时跟着注销。

**日志窗格怎么取**：先用 `window.gwb.on` 订阅实时事件，再调 `logger.backlog` 取历史，两段按 `seq` 接上、去重。反过来先取历史再订阅，中间那一刻产生的日志会漏掉。按 `ts`、`name`、`msg` 拼字符串去重会把同一毫秒里两条一样的日志吃掉一条，所以用 `seq`。

## 依赖

| 依赖 | 用来做什么 | 缺了会怎样 |
| --- | --- | --- |
| 命令插件的服务 `gwbCommands`（写在 `export const inject` 里，[gwb-commands](/docs/commands)） | 登记两条命令 | 插件一直等待、不加载 |
| 内核服务 `gwbKernel` 的 `emit`、`dataDir`（内核仓 gwb-kernel；不写进 `inject`，经 `src/vocab.ts` 里的 `requireKernel` 取） | 推事件给页面；算 `logger.where` 返回的路径 | 加载时抛错「ctx.gwbKernel 不在」 |
| cordis 的日志流：`ctx.logger.exporter`、`ctx.logger.buffer` | 收全部日志；补插件加载之前的历史 | 由内核提供，不会缺；`buffer` 不在时不补历史 |
| cordis 的 `Service`（peer，`^4.0.0-rc.9`） | 提供没有方法的服务 `gwbLogger` | 无法加载；必须和内核用同一份 cordis |
| 词汇表包 `@godcreator/gwb-plugin-api`（peer） | `GwbContext`、`GwbKernelApi` 的类型 | 只在编译时用 |

`@godcreator/gwb-commands` 写在 devDependencies 里：代码只 `import type {}` 它，为的是让 `ctx.gwbCommands` 有类型，构建产物里没有它。

## 不做的事

- **不写日志文件**：`<home>/gwb.log` 与 stderr 由内核写，日志插件不在时人照样看得到日志
- **不画窗格**：日志窗格在界面插件仓 gwb-ui-plugins 的 `@godcreator/gwb-baseui`，筛选、搜索、清屏都是窗格的事
- **不保存缓冲**：两千条只在内存里，重启就清空；更早的日志去 `gwb.log` 找
- **不改日志级别、不决定哪些日志写进文件**：日志插件只收，不管别的插件怎么写日志
- **服务 `gwbLogger` 上不加方法**：取数据走命令，推送走内核事件
