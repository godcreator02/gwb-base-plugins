# gwb-mcp

把 [`ctx.gwbCommands`](/docs/commands) 那份命令注册表开给任意外部 agent。方向**永远**是
agent → 工作台。

包名 `@godcreator02/gwb-mcp`，无界面。`inject: ['gwbCommands', 'gwbSettings']`
——settings 是硬依赖，端口从它来。

> 时间线：2026-09-13 搁置（「HTTP 门接班」），**2026-09-14 复位**——接 command-http 的班
> 成为**唯一的门**，command-http 搁置留作逃生门。判据见轨迹卡「MCP 复位」。

## 怎么连

起来之后日志里有一行：

```
[I] gwb-mcp MCP 门就绪（default home）：http://127.0.0.1:2870/mcp——无鉴权，绑 127.0.0.1 本机自用
```

另一条出口是命令 `mcp.info`——url 加一段可照抄进客户端配置的 `mcpServers` 片段：

{/* ref file="../plugins/mcp/src/index.ts" lines="297-321" */}

无鉴权（0.4 起）：口只绑 127.0.0.1、服务本机，本机进程本就同权——command-http 0.2 摘
token 时验过的判据，复位时原样继承，token 与 401/503 那两段守卫没有回来。

## 工具面封顶两枚

{/* ref file="../plugins/mcp/src/index.ts" lines="75-122" */}

**`surface`**（发现面：命令 + 说明书清单 + 口上的纪律，`plugin` / `prefix` / `q` /
`slim` 四个过滤）与 **`run`**（按名调一切命令）。写死在 `registerTools` 里，没有运行时
名单，登记方也没有申报顶层的字段——top 随 commands 0.3 退役，skills 0.3 摘了两枚 skill
命令的标。其余命令（包括 `skill.list` / `skill.read`）一律经 `run` 按名调。

为什么封顶：MCP 的工具清单是**连接时的快照**，而这台工作台的件以分钟级热重挂为节拍
——任何「件登记、门渲染成顶层工具」的通道都会把快照变成重连债（退位前三次实锤发作
之一）。封顶之后快照里没有会变的东西：命令面的多变全在 `run` 的参数里，每次调用现打
总线，与件的热重挂同一个新鲜度。

加第三枚工具是 **major 级的协议决定**——封顶有守卫：测试经内存信道连一对真的
server/client，按协议往返，`tools/list` 恰好这两枚，多一枚 CI 就红。

参数形状不在 schema 里，在**命令描述**里——所以描述必须写形状，见
[commands](/docs/commands)。

**args 的收口**：`run` 的 `args` schema 是 `z.unknown()`，协议层什么形状都放行——有的客户端
就把对象参数**序列化成 JSON 字符串**才发，到命令端全被 `isRecord` 拒成「参数要是个对象」，
带字符串值的调用全军覆灭而无参命令幸存（实测定位：同一调用 curl 直发对象就成，
换客户端就是字符串）。门在入口收一道：

{/* ref file="../plugins/mcp/src/tools.ts" lines="23-55" */}

业务失败（命令不存在、参数不对）回的是 `isError` 的文本，**不是协议错误**——
agent 读得到原因、连接不断。抛出去只会让对面看见一条 JSON-RPC 错误，
分不清是自己叫错了还是这台工作台坏了。

## surface：现拼的发现面

{/* ref file="../plugins/mcp/src/surface.ts" */}

回执形状与 command-http 时代的 `GET /surface` 一致（复位时抬过来的纯函数，`top` 格随
门面封顶退役）——两代门一个词汇，文档改口只动「怎么调」，不动「回什么」。`home` 自报、
生效的过滤在 `filter` 那格自证；instructions 随每份回执带一遍（客户端不透出 initialize
的 instructions 通道时，第一发 surface 也读得到纪律）。

全量回执实测约八千 token 且随件数线性涨：陌生 home 全量一次就够，此后 `plugin`（按登记
件筛，commands 与 skills 一起筛）、`prefix`（命令名前缀）、`q`（名字与描述找子串，不分
大小写）、`slim`（只回名字+插件的索引行，约五百 token）定向取——反复全量是坏味道。分页
刻意不做——这个量级按组筛比翻页好用。

## 说明书：清单进 surface，正文走 run

清单进 `surface` 的 `skills` 项；正文不另开通道——`run` 调 `skill.list` / `skill.read`
（skills 件登记的命令）。`skill://` resources 不复活（http 时代已退场）。skills 件不在时
门照开，清单那格是空表。门自己也带一份 SKILL.md（连接片段、封顶判据、台没起怎么办），
经 skills 件挂载。

## default 的端口是契约，不是首选

{/* ref file="../plugins/mcp/src/endpoint.ts" lines="54-67" */}

**`default` 这个 home 认死 2870，被占就不开这道门。**（mcp 时代的契约，随复位收回——
command-http 搁置让位。）

「首选 2870、被占退让到系统随机端口」看着体面——多 home 同开是常态——但危险的是这条
时间线：**一台测试 home 先起来占住 2870，随后起的 default 退让到随机端口**。连工作台的
agent 会话手上那份 `.mcp.json` 早就写死了 2870，于是它连上的是**那台测试 home**——命令面、
数据、说明书全是另一套，而两头都不报错。

所以 default 那一支的 `fallback` 是 `false`，接线照着它走：

{/* ref file="../plugins/mcp/src/index.ts" lines="258-267" */}

**不开比开在别处强**——开在别处是静默连错，不开是当场看得见（一行 `log.error`，
外加 `mcp.info` 回 `ok: false`）。本插件其它部分照常挂着，只是这道门这次没开：

{/* ref file="../plugins/mcp/src/index.ts" lines="285-295" */}

其它 home 不吃这条：缺省要系统随机口（没有哪个串是它的契约），显式给了端口才试那个端口、
被占照旧退让并 warn。home 名从 `gwbKernel.dataDir` 的末段认——那个目录就是 home 目录，
插件不必另有一条「你是谁」的入口。

## 端口是一项设置，不是 `cordis.yml` 的 config

**插件的配置一律走 `gwbSettings.define`**，这个插件不收 `apply` 的 `config` 形参：

{/* ref file="../plugins/mcp/src/index.ts" lines="131-145" */}

`port` 的缺省按 home 名给（`defaultPort`），跟 `choosePort` 不给值时的答案一致——界面上
看到的缺省就是真会用的端口，不会出现「显示 0、实际 2870」这种两份真相。设置插件不做运行时
校验，所以 `choosePort` 收的是 `unknown`：不是整数、出了范围一律当没给，数字串也认
（界面上一个文本框写进来的就是串）。改了要重启这个 home 才生效——门是 `apply` 时开的。

## 绑成那一刻补 runtime.json 的 `mcp` 项

{/* ref file="../plugins/mcp/src/runtime.ts" */}

内核开机整份重写 `pid` / `startedAt` / `appDir` / `cdp` 四项，本插件绑成之后**读改写**
补自己那一项。三条边界：**没绑成不写**（那时这个 home 上根本没有这道门，写一项假的比
不写坏得多）、**写失败不影响这道门**（记录是附属品，打一行 warn 继续）、**进程退了不删**
（崩溃与被 kill 是常态，留着的记录还是「上一次它在哪儿」的唯一线索——**验活是读的人的
事**：核 pid 还在、且那个 pid 真持着那个端口）。

## 无状态：每请求一对

{/* ref file="../plugins/mcp/src/index.ts" lines="213-235" */}

`new StreamableHTTPServerTransport({})` 里那个空对象就是无状态：不给
`sessionIdGenerator`，每个请求现造一台 `McpServer` 加一条 transport，随响应关闭。
代价是发不出 list_changed 那类通知——而工具面封顶之后这无所谓：清单里没有会变的
东西，正连着的 agent 没有任何理由等一次清单刷新。

## instructions：固定二十来行，每个 agent 连上来都要读

{/* ref file="../plugins/mcp/instructions.md" */}

包根一份真的 markdown，模块加载时读一次，**不随挂着的 skill 变**。它是每会话的固定成本，
所以按「少一句就漏事、多一句就是废话」裁，测试钉着行数上限。

有两条不写就会出事：**工具面封顶两枚、新装的件不长新工具**——不说明白，agent 装完件就会
在工具清单里干等，而清单永远不会变；**台没起时怎么办**——工具全灰不是协议错误，起台、
重连，MCP 没有「下一发请求自动好」。另一条同性质：**发完新版本调
`plugin-manager.update-all` 一键热升，不重启**；而升到 mcp 自己时这条回执会丢——门随件
重挂，连接断在半路——重连后用 `plugin-manager.list` 核对。热重挂的原理在
[插件管理](/docs/plugin-manager)。

后半段是**这台工作台准许 agent 改自己到哪儿**：修 bug、补 `SKILL.md`、加命令加插件不用
问；改内核、改那几个被别人 `inject` 的插件的契约面或依赖、**破 surface/run 这个封顶**
先问人。判据是**改动的爆炸半径**——前一类错了只波及它自己，后一类错了是整台工作台起不来、
别的插件静默失灵，或者工具面契约被人悄悄改了形状。

## 为什么自己起 `node:http`

三条路都看过：

- **`@cordisjs/plugin-http`** —— 它是 **HTTP 客户端**（`ctx.http`，axios 风格），
  收不了请求
- **`@cordisjs/plugin-server`** —— 能用，但它最后一次发布早于 cordis `4.0.0-rc.9`
  两个半月，属于「semver 说行、作者没验过」
- **拆一个 server 插件出来**—— 一个宿主一个 server、谁要挂路由谁来注册。
  职责分得正，但**这个 server 上只有本件一个客户**

于是自己起，就在 `apply` 里。真出现第二个要开口的件，那时再拆——那一步只动本插件
内部，不动任何跨插件契约。

## 依赖那 4.3MB

官方 SDK 的 `dependencies` 拖着 express@5、hono、cors、jose、ajv、eventsource、
express-rate-limit 一串，解包 4.3MB、693 个文件，跟着这个插件装进装它的 home（default
装回是复位装配的一部分；隔离 home 的底座件集里没有门）。

摆上桌算过：换成自写一份最小 JSON-RPC（只做 initialize / tools/list / tools/call）
是百来行、零依赖，但协议细节（版本协商、Accept 校验、错误码）得自己跟，
而客户端的实际行为是唯一裁判。求的是**能连通**，所以用 SDK。

写成 `dependencies` 而不是 `peer`：这个插件没有导出面（不 provide 服务、没人 import 它的
类型），没有「消费方必须解析得到」这回事。

## 安全边界

**本机的进程就拿到写面**：`run` 能调的是完整的命令注册表，包括往 home 里装插件。
工具面收窄收的是**发现面**，不是权限面。这个系统的信任模型是——**装插件 = 授权**
（插件在宿主进程里有完整 Node 权限，无沙箱），**口不出本机**（绑 127.0.0.1）。
命令级的拒绝名单不做。「用户同意」在这个系统里只能是纪律——agent 有整台机器
——所以它写进 instructions，不做成机制。
