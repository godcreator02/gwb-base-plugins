# gwb-mcp

把 [`ctx.gwbCommands`](/docs/commands) 那份命令注册表开放给任意外部 agent。方向**永远**是
agent → 工作台。

包名 `@godcreator/gwb-mcp`，无界面。`inject: ['gwbCommands', 'gwbSettings']`
——settings 是硬依赖，端口从它来。

> 时间线：2026-09-13 搁置（「HTTP 门接班」），同日恢复为唯一的入口（「MCP 复位」），
> 工具当日从两个重新设计为三个（「三枚面」）。command-http 2026-09-17 退役（「command-http
> 退役」），不再有第二个入口；MCP 入口出问题时怎么办写在随包 SKILL.md 的「门出问题时」一节。

## 怎么连

启动后日志里有一行：

```
[I] gwb-mcp MCP 门就绪（default home）：http://127.0.0.1:2870/mcp——要 Authorization 头，绑 127.0.0.1 本机自用
```

另一个获取方式是命令 `mcp.info`——返回 url 和一段可直接复制进客户端配置的 `mcpServers` 片段
（**片段里只写 token 的获取方式，不写 token 本身**：这段返回会进会话记录），要 token 本身调 `mcp.token`：

## 鉴权：为什么 0.10 又把 token 加回来了

0.4 去掉鉴权的理由是「端口只绑 127.0.0.1、服务本机，本机进程本来就同权」，外加一个实在的代价
「token 跟着内核重启换新，只会让 agent 侧的配置变成一件要反复维护的事」。

前一半是**把「连得上」当成了「有权调」**：回环绑定区分得了本机与外部网络，区分不了本机上的
不同主体——浏览器里的一个页面、另一个 home 的客户端配置、随手写的一个脚本，都能访问
127.0.0.1，而这个入口背后是完整的命令注册表（包括往 home 里装插件）。后一半是可以消除的技术债，
不是鉴权本身的问题：**token 落盘、重启不换**，「反复维护」的代价就没了。

做法（理由都写在 `plugins/mcp/src/auth.ts` 的头部注释里）：

* **token**：每个 home 一份，存在 `<home 数据目录>/mcp/secret.json`（32 字节随机 base64url）。
  文件损坏时先另存为 `.broken-*` 再换，不悄悄覆盖。获取用 `mcp.token`，换新用 `mcp.token {"rotate":true}`
  （换完旧客户端一律 401）
* **Host / Origin 自己检查，不用 SDK 那三个开关**：锁定的那版 SDK（`^1.30.0`）里
  `enableDnsRebindingProtection` / `allowedHosts` / `allowedOrigins` 都标着 `@deprecated`，
  而且 `allowedHosts` 不配置时 Host 检查**整段跳过**——只配 Origin 等于没防住 DNS 重绑定
* **三项检查都在分派任何请求之前**：拒绝 = 401 + 一句可读的原因，`<home>/gwb.log` 里
  `gwb-mcp` 那行 `拒绝了一条请求：…` 说清是哪一项
* **实机验证**：另起一个 http 客户端发了四种请求——无 token / 错 token / 伪造 Host / 跨源 Origin
  全部 401，且被拒时 handler 一次都没被调用；重启后同一 token 仍然有效

## MCP 工具只有三个

{/* ref file="../plugins/mcp/src/index.ts" lines="110-166" */}

**`index`**（全部命令、全部说明书的清单，各带一句话，外加「有哪些插件」一节——包名 + 版本 + 那句话，纯界面插件与库也在表里）、**`search`**（按条件取详情，也可以
搜索，匹配的行带 usage；不带参数就返回全部内容与完整用法）、**`run`**（按名字调用任何命令）。写死在
`registerTools` 里，没有运行时名单，登记命令的一方也没有声明「放到顶层」的字段——top 字段随 commands 0.3
退役。其余命令（包括 `skill.list` / `skill.read`）一律经 `run` 按名字调用。

为什么只有三个：MCP 的工具清单是**连接时的快照**，而这台工作台的插件以分钟为单位热重挂
——任何「插件登记、MCP 入口把它变成顶层工具」的做法，都会让快照过时、客户端只能不断重连。只有三个
工具之后，快照里没有会变的东西：命令的变化全在 `run` 的参数里，每次调用都现查命令总线，与插件的
热重挂一样新。

**变更的级别**：加一个工具是 **major** 级协议变更；给现有工具加可选参数是 **minor**
（老调用方不受影响）；**改返回形状或参数语义是 major**。由测试守着——内存传输连一对
真的 server/client 按协议往返，`tools/list` 必须恰好是这三个，多一个 CI 就失败。

## 逐层查询：先看清单，再按条件取详情，找不到再搜索

{/* ref file="../plugins/mcp/src/inventory.ts" */}

| 要什么 | 调什么 | 成本 |
| --- | --- | --- |
| 清单（每个会话第一次调用） | `index` 不带参数 | 约两千 token |
| 全部内容与完整用法（第一次接触一个 home 时调一次） | `search` 不带参数 | 约八千 token |
| 匹配的部分，带用法（工作中途 / 忘了名字） | `search` 带 `plugin` / `prefix` / `q` | 几百 token |
| 执行 / 读说明书正文 | `run` | 看命令 |

四条规矩写在纯函数里：**两张表同一种形状**（index 的命令行与说明书行都是 名字 + 插件 + 一句话，插件表是另一种形状——包名 + 条目名 + 版本 + 那句话，三张表靠包名对应；
`description` 与 skill 的 description 同义——是导航用的触发条件，不是参数文档）；**匹配的行总是带
usage**（行形状不随条件变——这修掉了旧 surface「一个工具多种模式」的问题）；**不带参数＝不过滤**
（不带条件就是全量，代价提示写死在工具描述里）；**任何查询都不附带整张表**（`prefix` 表示只查
命令，这时说明书表只回名字与插件——一次定向查询曾经附带回 11.6KB 的整张表，这条就是为此加的）。
`q` 对命令**连 usage 一起搜**——概念常常写在用法里（「venv 自愈」在名字里搜不到）。

**不返回 files**：说明书的附件路径由 SKILL.md 正文自己管（正文引用 references/ 是
Agent Skills 的惯例），MCP 入口再列一份就是第二份来源、会不一致。`skill.read {name, file}` 一直
能用，路径从正文里找；写说明书的规矩因此多一条「附件必须在正文里提到」。

参数形状不在 `run` 的 schema 里，在命令的 **usage** 里——`args` 是 `z.unknown()`，协议层
不检查、命令自己校验。有的客户端把嵌套对象序列化成 JSON 字符串才发，MCP 入口在收到时处理一次：

{/* ref file="../plugins/mcp/src/tools.ts" lines="23-55" */}

业务失败（命令不存在、参数不对）返回 `isError` 的文本，**不是协议错误**——agent 读得到
原因、连接不断。

## 说明书：清单在 index 里，正文经 run 读

清单（一句话）放在 `index` 的 `skills` 项里；正文经 `run` 调 `skill.list` / `skill.read`
（skills 插件登记的命令）。skills 插件不在时 MCP 入口照常可用，清单那一项是空表。这个插件自己也带一份
SKILL.md（连接配置片段、为什么只有三个工具与变更级别、工作台没启动怎么办），经 skills 插件加载。

## default 的端口是约定，不是首选

{/* ref file="../plugins/mcp/src/endpoint.ts" lines="54-67" */}

**`default` 这个 home 固定用 2870，被占就不开这个入口。**（mcp 时代的约定，随「MCP 复位」恢复。）

「首选 2870、被占就换」看着合理——多个 home 同时开是常态——但危险的情况是：一台测试
home 先启动占住 2870，随后启动的 default 换到随机端口，而 agent 会话手上那份配置早就
写死了 2870——它连上的是**那台测试 home**，命令、数据、说明书全是另一套，两边都不
报错。所以 default 那一支 `fallback` 是 `false`：

{/* ref file="../plugins/mcp/src/index.ts" lines="375-384" */}

**不开比开在别的端口强**——开在别处是悄悄连错，不开是马上能看出来：

{/* ref file="../plugins/mcp/src/index.ts" lines="403-413" */}

其它 home 不适用这条：缺省用系统随机端口（没有哪个端口号是它的约定），显式给了端口才试那个、
被占照样换端口并 warn。home 名取 `gwbKernel.dataDir` 的最后一段。

## 端口是一项设置，不是 `cordis.yml` 的 config

**插件的配置一律走 `gwbSettings.define`**，这个插件不收 `apply` 的 `config` 形参：

{/* ref file="../plugins/mcp/src/index.ts" lines="175-224" */}

`port` 的缺省按 home 名给，跟 `choosePort` 不给值时的答案一致——界面上看到的缺省就是
真会用的端口。设置插件不做运行时校验，`choosePort` 收 `unknown`：不是整数、超出范围
一律当没给。改了要重启这个 home 才生效——MCP 入口是在 `apply` 时打开的。

## 端口绑定成功时补写 runtime.json 的 `mcp` 项

{/* ref file="../plugins/mcp/src/runtime.ts" */}

内核启动时整份重写 `pid` / `startedAt` / `appDir` / `cdp` 四项，本插件绑定成功之后**读出、修改、写回**
自己那一项。三条边界：**没绑定成功不写**、**写失败不影响 MCP 入口**、**进程退出不删**
——确认它是否还活着是读取方的事（核对 pid 还在，且那个 pid 确实占着那个端口）。

## 无状态：每个请求一对 server 与 transport

{/* ref file="../plugins/mcp/src/index.ts" lines="330-351" */}

`new StreamableHTTPServerTransport({})` 里那个空对象就是无状态：不给
`sessionIdGenerator`，每个请求新建一个 `McpServer` 加一条 transport，随响应关闭。
发不出 list_changed 这类通知——工具只有三个且不会变，所以没关系：清单里没有会变的东西，客户端
等不到通知也不会错过任何事。（SDK 会把 `listChanged` 能力位声明成 `true`；「可能发通知」
在语义上不排斥「永远不发」，不值得为它去改 SDK 的私有字段。）

## instructions：四十行以内，每个 agent 连上来都要读

{/* ref file="../plugins/mcp/instructions.md" */}

包根目录下一份真正的 markdown，模块加载时读一次，**不随加载的 skill 变**。它是每个会话的固定
开销，测试检查长度上限（2000 字符、41 行；Claude Code 超过 2048 字符会静默截断）。initialize 时
附带一份；`index` 的返回再带一份——客户端不把 initialize 的 instructions 转给 agent 时，第一次
调 index 也读得到这些规矩。

有两条不写就会出问题：**MCP 工具只有三个、新装的插件不会多出新工具**（不说清楚，agent 装完插件就会
在工具清单里一直等）；**工作台没启动时怎么办**（工具全灰不是协议错误：启动工作台、重连——MCP 连接
不会在下一次请求时自动恢复）。后半段是**这台工作台允许 agent 改自己到什么程度**，依据是改动的
影响范围；**改变这三个工具要先问人**，与改内核、改被别的插件 inject 的服务并列。

## 为什么自己启动 `node:http`

- **`@cordisjs/plugin-http`** —— HTTP **客户端**（`ctx.http`），收不了请求
- **`@cordisjs/plugin-server`** —— 能用，但最后一次发布早于 cordis `4.0.0-rc.9`
  两个半月，「semver 说行、作者没验证过」
- **拆一个 server 插件**——职责划分对，但这个 server 上只有本插件一个使用方

于是自己启动，就在 `apply` 里。真出现第二个需要开放 HTTP 端口的插件，那时再拆。

## 依赖那 4.3MB

官方 SDK 的 `dependencies` 带着 express@5、hono、cors、jose、ajv 等一串，解包 4.3MB、
693 个文件，跟着这个插件装进它所在的 home（default 重新装回是复位时装配的一部分；隔离 home
预装的基础插件里没有 MCP 插件）。换成自写的最小 JSON-RPC 是一百来行、零依赖，但协议细节（版本协商、
Accept 校验、错误码）得自己跟进，而客户端的实际行为是唯一的判断标准。目标是**能连通**，所以
用 SDK。写成 `dependencies` 而不是 `peer`：这个插件没有导出的接口。

## 安全边界

**本机的进程就拿到写权限**：`run` 能调的是完整的命令注册表，包括往 home 里装插件。
工具只有三个，收窄的是**能发现的范围**，不是权限。信任模型：**装插件 = 授权**（插件在宿主进程里
有完整 Node 权限，没有沙箱），**端口不出本机**（绑 127.0.0.1）。不做命令级的拒绝名单；
「用户同意」只能靠规矩——写进 instructions，不做成机制。
