# gwb-node-cli

包名 `@team/gwb-node-cli`，服务 `ctx.gwbNodeCli`。node-only，没有界面那半。

插件要跑一条命令行时，本来得自己写一遍 spawn、超时、杀进程树、输出截断、编码——这几样
**正是最容易写错的部分**，而且写错了都不当场报错。这个插件把它们收成一处。

## 它不做取址

**CLI 是消费方插件自己 build 出来的产物**，跟插件同一个包发出去。所以路径由插件自己算，
登记时递一个绝对路径进来：

```ts
const CLI_ENTRY = path.join(
  path.resolve(path.dirname(fileURLToPath(import.meta.url)), '..'),
  'dist', 'cli.js',
)
```

这儿**不读 `bin` 字段、不认 `node_modules/.bin` 垫片、不查 PATH、不过 shell**，
`argv[0]` 一律是 `process.execPath`（正在跑本插件的那个 node）。

两个好处：Windows 上的引号地狱与带空格的路径一次根除；pnpm 的隔离结构下「运行器
resolve 不到消费方那一层的包」这个问题根本不会出现——**压根不需要解析**。

将来真要跑第三方 npm 包的 bin 时再加 `pkg + resolveFrom` 那一层，现在不加。

## 怎么用

```ts
export const inject = ['gwbNodeCli']

export function apply(ctx: GwbContext) {
  ctx.gwbNodeCli.register({
    name: 'mine.build',
    description: '跑我的构建 CLI',
    entry: CLI_ENTRY,
    args: ['--json'],
  })
}
```

**不用自己包 `ctx.effect`**——插件卸载时这条命令自动从表上、也从命令总线上摘掉。
要提前摘就收 `register` 回的那个函数。

`cwd` 不给的话落在 `entry` 自己旁边（也就是 `dist/`）。**不继承宿主的 cwd**——那是内核的
目录，跟这条命令毫无关系，而且随内核怎么起而变。要确定的工作目录就自己给。

登记的命令**同时挂进 `gwbCommands` 总线**，所以界面直接调得到：

```js
await window.gwb.command('mine.build', ['--watch'])   // 一串就是追加参数
await window.gwb.command('mine.build', { args: ['--watch'] })  // 这么写也认
await window.gwb.command('mine.build', { args: ['--watch'], cwd: 'D:\\work\\proj' })  // 按次给工作目录
```

总线那头递来的参数怎么认，是一个纯函数：

## 按次给 cwd

`spec.cwd` 是登记时定的缺省，而一条 CLI 常常要**对着某个目录**跑（构建某个工程、扫某个
仓）。所以 `run(name, extraArgs?, opts?: { cwd?: string })` 第三个参数按次给，总线镜像
认 `{ args, cwd }`。优先级：按次给的 > 登记时给的 > `entry` 旁边。

按次的 cwd **必须是存在的目录的绝对路径**，不合规**不抛**、不起进程，回
`{ ok: false, error }`——错误文本就是文档，agent 读一遍就知道该给什么：

不存在或不是目录。`isDirectory` 留了个口子给测试塞假的，真跑时问盘。

于是 `run` 回的是 `CliRunOutcome`——跑过了是进程回执，没跑是那句拒绝。调用方照旧只看 `ok`。

自带一条 `node-cli.list`（此刻登记了哪些）。**没有自检命令**——这个插件只做运行器，
验收归消费方插件；样板是 gwb-hello 仓（`26091217hkq`）的 hello 插件，它自带的
`src/cli.ts` 编译成 `dist/cli.js` 之后登记进来，界面上点一下就跑。

## 超时的天花板是 110 秒，不是随便定的

`timeoutMs` 默认 60 秒，**上限钉死 110 秒，超过当场拒绝注册**。

**一条 CLI 跑过两分钟还不回，人要的是一句 `timedOut` 加一份 `spillPath`，不是一个永远
不回的 promise**——上限就是为这个钉的（插件与桥同进程，这条线上没有比它更长的硬超时兜底）。

## 三条形状上的纪律

都是从 DSH 那套抄来的，各自的现场见[撞过的墙](/docs/walls)：

1. **argv 全程数组，一次都不过 shell** —— 引号、空格、`&`、中文参数原样到达
2. **输出只保尾部 64,000 字节** —— 砍过就把全量落一份临时文件，回执里给 `spillPath`。
   出错原因常常在被砍掉的那头，只留尾巴人就没得查了
3. **超时杀整棵树** —— Windows 上只杀直接子进程的话，孙子进程会变成零 CPU 的僵尸挂着
   占住目录；DSH 实测残留过 20 分钟，而那时父 pid 已经没了、事后再 taskkill 也找不到

## 一条实机才知道的

`process.execPath` 在宿主里是 **electron.exe**（内核用 `ELECTRON_RUN_AS_NODE=1` 把它当
node 使起来的）。所以起 node 子进程时那个变量得跟着传，不然它会去开一扇窗，而不是跑
那个 js。内核起宿主时是同一个绕法。
