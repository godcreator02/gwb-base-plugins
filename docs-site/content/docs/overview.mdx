# gwb-base-plugins

`gwb-kernel`（最小内核，单元 `26090705ymz`）的基础插件仓。

## 插件

| 插件 | 包名 | 服务 | 干什么 |
| --- | --- | --- | --- |
| commands | `@godcreator02/gwb-commands` | `ctx.gwbCommands` | 命令总线 |
| data | `@godcreator02/gwb-data` | `ctx.gwbData` | 插件的数据落盘 |
| logger | `@godcreator02/gwb-logger` | `ctx.gwbLogger` | 日志管道（core） |
| skills | `@godcreator02/gwb-skills` | `ctx.gwbSkills` | 说明书的收集与查询 |
| http | `@godcreator02/gwb-http` | — | 无状态 JSON 入口：GET /surface 现拼清单、POST /run 按名调命令 |
| mcp | `@godcreator02/gwb-mcp` | — | MCP 桥，**搁置中**（入口由 http 接班） |
| node-cli | `@godcreator02/gwb-node-cli` | `ctx.gwbNodeCli` | node 那条命令行 |
| py-cli | `@godcreator02/gwb-py-cli` | `ctx.gwbPyCli` | python 那条命令行 |
| settings | `@godcreator02/gwb-settings` | `ctx.gwbSettings` | 设置 |
| plugin-manager | `@godcreator02/gwb-plugin-manager` | `ctx.gwbPluginManager` | 管包与条目 |

三仓拆分后这个仓只剩**无头**插件：外壳与窗格的界面外观住 UI 平台仓
（`26091217uiz\gwb-ui-plugins`：shell、theme、baseui 与两个共享包），验收插件住验收仓
（`26091217hkq\gwb-hello`），判据见轨迹卡 `2026-09-12-three-repos-split`。
此刻十个插件在册、九个在役：mcp 搁置、http 接班（判据见轨迹卡「HTTP 门接班」）。

**状态与版本号只在[路线](/future/roadmap)一处**——两处各记一份必然漂移，这张表就漂过一轮。

`gwb-commands` 排第一不是随便定的：**内核的 `dispatch` 收到什么就全走 `ctx.gwbCommands`**，
没有它，界面调不到任何 node 侧的能力。

## 两条命名规矩

**包名 `@godcreator02/gwb-<插件名>`。** 加 `gwb-` 前缀跟已废弃的那批错开——
`@godcreator02/cli`、`/shell`、`/logger`、`/settings` 被那批占着。

**服务名一律 `gwb` 开头小驼峰**，默认跟插件名对应（`gwb-commands` → `ctx.gwbCommands`）。
cordis 官方插件的服务照它自己的（`timer`、`loader`），那不是这个生态的东西。

判据与理由在**内核仓的文档站**（`26090705ymz/gwb-kernel/docs-site`）——规则住那边，
这个站只记插件自己的事。

## 内核给的面就这么大

- **`ctx.gwbKernel`**（永不撤销，用 `requireKernel(ctx)` 取，**不写进 `inject`**）：
  `dataDir` / `emit(payload)` / `setShell(url) → 撤销函数`。**就这三样。**
- **`ctx.loader`**：条目树。改条目就是热挂卸——`create` / `remove` / `update` / `store`。
  自己所在的那棵树是 `ctx.fiber.entry?.parent?.tree`
- **一条内核命令都没有**：`gwb:command` 收到什么就原样派给 `ctx.gwbCommands`
- **页面的公共面 `window.gwb`**：`command(name, args)` / `on(cb)` / `onShell(cb)`
- **窗格插件自报浏览器半的地址**：`registerPane({ …, client, style })`，值从自己的
  `import.meta.url` 算成 `file://`；内核不认识任何包名与导出名
- **插件跑在 Electron 主进程里**，`import('electron')` 是插件够得着的

契约包 `@godcreator02/gwb-plugin-api` 0.1 只有这几个名字（`GwbContext` / `GwbKernelApi` /
`GwbResult` / `GwbWindowApi` / `ShellBoot` / `requireKernel` / `isRecord`）。**内核的面本来
就这么小**，别指望有更多。旧内核 `gwb-kernel` 的宿主子进程、fd3、`gwb://`、`kernel.info`
都已退役，正文再提到它们的是留档。

## 一个插件长什么样

```
plugins/<插件名>/
  package.json      name / exports / gwb 段 / peer 与 dev
  tsconfig.json     extends ../../tsconfig.base.json
  src/index.ts      export const name / apply(ctx)
  tests/            纯逻辑的单测 + 产物守卫
```

构建是 `tsc`，不打包——产物给 node 直接加载。所以有两条硬要求，都配了守卫：
**相对 import 必须带 `.js`**、**产物里不许有裸名 import**。为什么，见[撞过的墙](/docs/walls)。

带界面的插件**不在这个仓**：它们的浏览器半（`src/client/` 与样式表）、值与规则怎么共享、
组件怎么复用——原理页在 UI 平台仓（`26091217uiz\gwb-ui-plugins` 的文档站），动手写带界面
的插件之前先读那边。

## 母仓那批是参考，不是模板

废弃的插件仓在 `26090623hyz/gwb-plugins`。去查某个插件当初为什么那么做、踩过什么坑，值得；
**结构、分层、包划分一概不抄**。

它那套有几样这里明确不要：`gwb.minAppVersion` 与精确 peer 号的双份准入、`platform` 分区与
`window.confirm` 拦截、为具体某个插件写的硬编码分支。
