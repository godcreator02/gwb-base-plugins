# gwb-base-plugins

`gwb-kernel`（最小内核）的基础插件仓：没有界面的插件都在这里。

## 插件

| 插件 | 包名 | 服务 | 做什么 |
| --- | --- | --- | --- |
| commands | `@godcreator/gwb-commands` | `ctx.gwbCommands` | 命令总线 |
| data | `@godcreator/gwb-data` | `ctx.gwbData` | 插件的数据写盘 |
| logger | `@godcreator/gwb-logger` | `ctx.gwbLogger` | 日志缓冲与查询（core） |
| skills | `@godcreator/gwb-skills` | `ctx.gwbSkills` | 说明书的收集与查询 |
| command-http | `@godcreator/gwb-command-http` | — | 命令的无状态 JSON 接口，**已退役**（不发版；入口由 mcp 承担） |
| mcp | `@godcreator/gwb-mcp` | — | MCP 入口，**只有这一个**：工具只有 index/search/run 三个，以后也不增加 |
| node-cli | `@godcreator/gwb-node-cli` | `ctx.gwbNodeCli` | 运行 node 写的命令行工具 |
| py-cli | `@godcreator/gwb-py-cli` | `ctx.gwbPyCli` | 运行 python 写的命令行工具 |
| settings | `@godcreator/gwb-settings` | `ctx.gwbSettings` | 设置 |
| plugin-sources | `@godcreator/gwb-plugin-sources` | — | 找插件、配包源 |

外壳与窗格的界面在界面平台仓 gwb-ui-plugins（shell、theme、baseui）。组装后的验收由 devkit
模板当场生成（理由见 devkit 仓轨迹卡「模板即插件」）。管 home 里包与条目的插件管理（plugin-manager）
在 devkit 仓（gwb-devkit）和 devkit 一起开发。
表里十个插件，九个在用：command-http 已退役（理由见轨迹卡「command-http 退役」）。

**状态与版本号只记在[路线](/future/roadmap)一处**——两处各记一份必然不一致。

`gwb-commands` 排第一，因为**内核收到页面发来的命令，全部交给 `ctx.gwbCommands`**，
没有它，页面调不到任何主进程里的能力。

## 一个插件长什么样

```
plugins/<插件名>/
  package.json      name / exports / gwb 字段 / peer 与 dev
  tsconfig.json     extends ../../tsconfig.base.json
  src/index.ts      export const name / apply(ctx)
  tests/            纯逻辑的单元测试 + 构建产物检查
```

`package.json` 的 `gwb` 字段里，`testedKernel` 写这个插件在哪个内核版本上测过（例如 `"0.2.7"`），
插件管理据此报告哪些插件没在当前内核上测过；提供服务的插件还在 `provides` 里写服务的一句话说明与用法。

构建用 `tsc`，不打包——构建产物由 node 直接加载。所以有两条硬要求，都配了检查：
**相对 import 必须带 `.js`**、**构建产物里不许有包名 import**。为什么，见[撞过的墙](/docs/walls)。

带界面的插件**不在这个仓**——页面代码、样式与组件在界面平台仓那边。

## 旧插件仓只作参考，不是模板

废弃的插件仓在 `26090623hyz/gwb-plugins`。去查某个插件当初为什么那么做、踩过什么坑，有用；
**结构、分层、包划分一概不抄**。

它那套里有几样这里明确不要：`gwb.minAppVersion` 与精确 peer 版本号这两处准入检查、`platform` 分区与
`window.confirm` 拦截、为某个具体插件写的硬编码分支。
