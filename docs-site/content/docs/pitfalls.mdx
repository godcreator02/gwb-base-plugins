## 构建与依赖

### 相对 import 必须带 `.js`，少了它不报错

除 MCP 插件外，构建产物由 `tsc` 直接输出、node 直接加载，不经打包器，ESM 不补扩展名。少了 `.js` 时插件加载失败，内核日志里是一行带路径的 `ERR_MODULE_NOT_FOUND`，页面上看不出来。

TypeScript 的 `moduleResolution: nodenext` 能强制相对 import 带扩展名，但 cordis 自己的 `.d.ts` 不兼容它：那边写的是 `export * from './context'`，不带扩展名。用 nodenext 时 `Context` 的类型解析成空，`ctx.logger`、`effect`、`provide` 全报「不存在」。所以只能用 `bundler`：

### 类型从 peer 里的包取，不是插件的类型包写 dev

`gwbCommands.run` 返回的是 `GwbResult`，它出现在命令插件**导出的类型**里，由命令插件自己的 `src/result.ts` 定义。内核包是每个插件的 peer，用到的别的插件也写在 peer，插件仓里 pnpm 把它们装进各插件的 `node_modules`，这些类型总解析得到。类型引用到、又不是插件的包（`@types/node`）写 dev。少列了，`skipLibCheck: true` 下那段类型不报错地变成 any，关掉 `skipLibCheck` 才报「找不到模块」；关掉 `skipLibCheck` 的类型检查既不在 `pnpm check` 里，也不在 `devkit.release` 的发版前检查里。

{/* ref file="../plugins/skills/package.json" lines="27-39" hash="169826d682b3" blob="cc66e816984d" */}

继承 cordis `Service` 的插件在构建产物里按值 import `cordis`，所以 `cordis` 写 peer：必须和内核用同一份 cordis，两份的 `instanceof` 对不上。MCP 插件对 `cordis` 只 import 类型，不写 peer。

### cordis 不给服务做版本校验

cordis 的服务只有一个字符串名字：注册记录里没有版本、没有 schema；`inject` 全是必须满足的依赖，没有可选写法（`'foo?'` 不认，`{ required, optional }` 会被当成两个叫 `required`、`optional` 的服务，一直等待）；依赖不满足时没有日志、没有超时、没有报错。

所以：

- **可选依赖只能用 `ctx.inject([...], cb)` 局部注入**：缺服务时只有这个局部上下文一直等待，插件本身照常加载。本仓插件登记说明书（`gwbSkills`）都这么写
- **插件之间的版本约束只写在 peer 里**：插件管理把 home 里没满足的列在 `plugin-manager.list` 的 `unmetPeers`，只报告、不拦加载。服务的接口改了、home 里装的是旧版时，调用不报错，多出来的参数被旧版忽略

### `await ctx.plugin(...)` 会立即返回，即使插件没有运行

`Fiber.await()` 是 `while (this.inertia) await this.inertia`，依赖没满足时 `inertia` 是 `undefined`，循环一次都不进。写实验脚本时别拿它当「加载完成」：`await ctx.plugin(x)` 之后立刻去调 `x` 提供的服务，服务可能还不存在。

## 服务与调用方身份

### 服务要认出调用方，用 `Service` 基类，不用 `accessor`

数据、设置、说明书、命令总线、两个命令行运行插件给出的东西要自动属于调用它的那条条目：插件不报名字，也就没法用别人的名字。cordis 有两种写法能让服务知道调用方是谁，实测后只有一种可用：

- **`ctx.accessor(name, { get() {…} })`**：`get` 里的 `this` 确实是调用方的上下文，但 `inject` 不认它：插件写 `inject: ['那个名字']` 会一直等待，不执行 `apply`，也不报任何错
- **`Service` 基类**：`inject` 认它，方法里的 `this.ctx` 就是调用方的上下文；两个插件各自取同一个服务，拿到的身份互不相同

{/* ref file="../plugins/data/src/index.ts" lines="46-60" hash="7c365cc01c5b" blob="cc9bc17278e7" */}

身份从 `this.ctx.fiber.entry` 上取：`entry.id` 是条目 id，`entry.options.name` 是包名。`entry` 是 loader 加上的属性，不是 cordis 本身的接口，所以代码按运行时的形状取、不改全局类型声明；根上下文上没有它。插件在 `ctx.inject([...], cb)` 的回调里、或 `ctx.plugin(子插件)` 装的子插件里调服务，`this.ctx.fiber` 是那个子 fiber，上面照样有同一个 `entry`，所以取身份只读 `this.ctx.fiber.entry`，不用沿 `fiber.parent` 往上找；命令总线的测试用真 loader 验证了这一点（见[条目身份](/docs/seams/entry-identity)）。

### 继承 `Service` 的插件，私有字段用 `private`，不用 `#`

cordis 给每个调用方派生一份 `Object.create(this)`，`#` 私有字段的内部槽不在原型链上，在派生对象上一读就抛错。本仓继承 `Service` 的插件，有私有字段的都用 TypeScript 的 `private`：

## 验证

### 只验证 node 这部分的插件不用启动 electron，但 `createRequire` 要先 `realpath`

无界面的插件可以直接在 home 里用 node 建一个真的 cordis 上下文来验证：服务能不能提供、命令能不能登记、子进程能不能启动，都验证得到，比启动 electron 快。要注意两点：

- **`cordis` 不在 home 的 `node_modules` 顶层**：它是插件的 peer，pnpm 把它装在 `.pnpm` 里插件实际所在的那一层，实验脚本直接 `import 'cordis'` 报 `ERR_MODULE_NOT_FOUND`
- **要从插件那一层解析，而且先 `fs.realpathSync`**：`node_modules/@godcreator/x` 是个链接，`createRequire` 从链接路径往上找不到 cordis：

  ```
  Error: Cannot find module 'cordis'
  Require stack:
  - <home>\node_modules\@godcreator\gwb-py-cli\dist\index.js
  ```

  解析链接之后就到了 `.pnpm/<插件>@<hash>/node_modules/` 这一层，cordis 在那里

实验脚本里的 `Context` 也要从插件那一层解析，和插件用同一份 cordis，否则 `Service` 的 `instanceof` 对不上。插件本身按 `<home>/node_modules/...` 的路径 import 即可，node 会解析到 `.pnpm` 里的实际目录，插件算出来的包根就是它实际安装的位置，`gwb-py-cli` 的 venv 也建在那里。

## TypeScript 与 MCP SDK

### 块注释里的 `*/` 会把注释提前结束

在块注释里写 `notifications/*/list_changed` 这样的路径，其中的 `*/` 直接结束了 `/** … */`，后面整段注释变成代码。报错不是「注释没闭合」，而是一整屏

```
error TS1443: Module declaration names may only use ' or " quoted strings.
error TS1127: Invalid character.
```

看着像文件编码坏了。路径样式的 glob 写进块注释之前，先看一眼里面有没有 `*/`。

### 函数声明拿不到外层 `const` 的类型收窄

`const cli = ctx.gwbCommands` 加一句 `if (cli === undefined) return` 之后，箭头函数里的 `cli` 是收窄过的，`function` 声明里不是：函数声明会被提升，TypeScript 认为它可能在那句检查之前就被调用。症状是 `'cli' is possibly 'undefined'`，上面明明刚判断过。写成 `const … = () => {}`，或者把收窄过的值当参数传进一个函数。MCP 插件用后一种：三个工具的处理函数由一个收 `commandBus` 参数的函数生成：

### MCP SDK 的类型声明要 DOM 类型

关掉 `skipLibCheck` 做类型检查时，SDK 的 `shared/transport.d.ts` 用到 `HeadersInit`，插件的 tsconfig 只带 `ES2023` 库，报 `Cannot find name 'HeadersInit'`。现在能通过，是因为内核包的类型声明 `dist/api.d.ts` 第一行写了 `/// <reference lib="dom" preserve="true" />`，MCP 插件 import 了它，DOM 类型就进了同一次检查。内核包去掉这一行，MCP 插件关掉 `skipLibCheck` 的类型检查会先红。
