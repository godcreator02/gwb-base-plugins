**本页回答**：写这个仓的插件时遇到过哪些不报错、难定位的问题；每个问题的症状、原因，现在的代码怎么避开它。规则本身写在各插件页与[关键设计](/docs/design)，这里只写为什么非这样不可。

## 构建与依赖

### 相对 import 必须带 `.js`，少了它不报错

构建产物由 node 直接加载，不经打包器，ESM 不补扩展名。少了 `.js` 时插件加载失败，内核日志里是一行带路径的 `ERR_MODULE_NOT_FOUND`，页面上看不出来。

TypeScript 的 `moduleResolution: nodenext` 能强制相对 import 带扩展名，但 cordis 自己的 `.d.ts` 不兼容它：那边写的是 `export * from './context'`，不带扩展名。用 nodenext 时 `Context` 的类型解析成空，`ctx.logger`、`effect`、`provide` 全报「不存在」。所以只能用 `bundler`：

### 词汇表包写 peer，不写 dev

{/* has file="../plugins/commands/package.json" text="peerDependencies" */}

`gwbCommands.run` 返回的是 `GwbResult`，它出现在命令插件**导出的类型**里，用这个插件的插件装上它之后必须解析得到。写成 devDependency 的话，发布出去的包不带它，用它的插件那边全部解析不到。所以词汇表包在各插件里既写 peer（给使用方）又写 dev（给自己构建）。

cordis 在命令插件里只写 dev：它只出现在 `apply` 的参数类型里，不在导出的类型里。数据、设置、日志这些插件继承 cordis 的 `Service`，运行时真的 import 它，写 peer；必须和内核用同一份 cordis，两份的 `instanceof` 对不上。

### cordis 不给服务做版本校验

cordis 4.0.0-rc.9 的服务只有一个字符串名字：注册记录里没有版本、没有 schema；类型里的 `Plugin.provide` 字段运行时从来不读；`inject` 全是必须满足的依赖，没有可选写法（`'foo?'` 不认，`{ required, optional }` 会被当成两个叫 `required`、`optional` 的服务，一直等待）；依赖不满足时没有日志、没有超时、没有报错。

所以：

- **可选依赖只能用 `ctx.inject([...], cb)` 局部注入**：缺服务时只有这个局部上下文一直等待，插件本身照常加载。本仓插件登记说明书（`gwbSkills`）都这么写
- **插件之间的版本约束只在 pnpm 安装时按 peer 的范围检查一次**：本仓插件对命令插件、设置插件这类服务提供方只写 devDependencies（只 `import type`），装插件时 pnpm 不检查 home 里这些插件的版本。服务的接口改了、home 里装的是旧版时，调用不报错，多出来的参数被旧版忽略

### `await ctx.plugin(...)` 会立即返回，即使插件没有运行

`Fiber.await()` 是 `while (this.inertia) await this.inertia`，依赖没满足时 `inertia` 是 `undefined`，循环一次都不进。写实验脚本时别拿它当「加载完成」：`await ctx.plugin(x)` 之后立刻去调 `x` 提供的服务，服务可能还不存在。

### `pnpm check` 不构建，发版前要构建

`pnpm check` 是类型检查、lint 和测试，不运行 build。手工在包目录 `pnpm publish` 时，要是 `package.json` 里没有 `prepublishOnly`，发出去的就是上一版的 `dist/`：插件照样加载、不报错，只是新写的代码全都不生效。所以每个包都写 `"prepublishOnly": "pnpm build"`；`devkit.release` 自己先在仓根构建一次。

## 命令总线

### 同名命令后登记的生效，但要告警

{/* ref file="../plugins/commands/src/registry.ts" lines="43-55" */}

插件之间平等，换掉一条命令是允许的。但不告警的话，调用方从此调到另一个插件的处理函数上，两边都不报错，所以同名时写一条告警，写明原来是哪个插件、现在是哪个。

### 注销只删自己那条

同一段里的 `if (byName.get(def.name) === record)`：同名命令被替换后，先卸载的插件不能把接手的那条一起删掉。少了这个比较，卸载一个插件会让另一个插件登记的命令跟着消失。两个命令行运行插件、设置插件的声明表用的是同一个写法。

### 处理函数抛错不抛给调用方

{/* ref file="../plugins/commands/src/registry.ts" lines="62-84" */}

调用方可能是页面上的一次点击。处理函数自己返回了带 `ok` 的对象就原样返回，其余一律算成功。

### 服务在 `ctx.effect` 里提供

{/* ref file="../plugins/commands/src/index.ts" lines="30-37" */}

命令插件卸载时服务自动撤销。不包的话，插件卸载了而 `ctx.gwbCommands` 还在，调用方调到一张已经没人维护的命令表上。

### 登记命令不包 `ctx.effect`，条目停用后命令名还在表里

症状：停用一个插件后列命令，它登记的一部分命令还在，调用时报的是 `cannot get required service "gwbData" in inactive context`，和「停用」看不出关系。原因是那几条命令直接调 `register`、没包 `ctx.effect`，返回的注销函数没人调用，条目停用了、上下文销毁了，命令名还留在表上。经命令行运行插件登记的命令不受影响，运行插件替调用方把注销登记在调用方的 `ctx.effect` 上。本仓的写法以日志插件为例：

## 服务与调用方身份

### 服务要认出调用方，用 `Service` 基类，不用 `accessor`

`ctx.gwbData` 给出的目录要自动属于取用它的那条条目：插件不报名字，也就没法用别人的名字读别人的数据。cordis 有两种写法能让服务知道调用方是谁，实测后只有一种可用：

{/* ref file="../plugins/data/src/index.ts" lines="61-78" */}

- **`ctx.accessor(name, { get() {…} })`**：`get` 里的 `this` 确实是调用方的上下文，但 `inject` 不认它：插件写 `inject: ['那个名字']` 会一直等待，不执行 `apply`，也不报任何错
- **`Service` 基类**：`inject` 认它，方法里的 `this.ctx` 就是调用方的上下文；两个插件各自取同一个服务，拿到的身份互不相同

身份从 `this.ctx.fiber.entry` 上取：`entry.id` 决定数据存在哪，`entry.options.name` 是包名。`entry` 是 loader 加上的属性，不是 cordis 本身的接口，所以代码按运行时的形状取、不改全局类型声明；根上下文上没有它。

继承 `Service` 的插件，私有字段用 TypeScript 的 `private`，不用 `#`：cordis 给每个调用方派生一份 `Object.create(this)`，`#` 私有字段的内部槽不在原型链上，在派生对象上一读就抛错。

### 数据与设置按条目归属，不按包

cordis 的条目模型里 `id` 才是身份，`name` 只说明装的是哪个包；同一个包可以在 `cordis.yml` 里配几条条目，各有各的配置（两条 `gwb-py-cli` 分别配不同的解释器）。按包名分的话，这两条共用一个数据目录、互相覆盖。所以[数据插件](/docs/data)的目录与[设置插件](/docs/settings)的分区都按条目 id 分。

### 条目 id 用作目录名：只取末段

条目 id 的样子是 `home:hello`：

- **冒号在 Windows 上是保留字符**：`mkdir home:hello` 不是干净地失败，可能造出一个 NTFS 备用数据流，目录看不见，写进去的内容也找不回来
- **`home` 那段是内核的常量**：承载 `cordis.yml` 的那条 include 条目的 id，`:` 是 cordis 的 `EntryTree.sep`。内核改一次那个常量，所有目录名都会跟着变
- **末段才是人在 `cordis.yml` 里手写的 id**

所以只取末段：没有冒号，也不依赖内核的常量。代价是多段 id 会重名（`home:a:hello` 与 `home:b:hello` 末段一样），所以超过两段直接抛错；真要用嵌套分组时，算法要和这条检查一起重新设计。id 要用作目录名与分区名，每一段都按 kebab-case 校验，字符集里没有点号，`.` 与 `..` 进不来。

{/* ref file="../plugins/data/src/paths.ts" lines="35-64" */}

两个插件的这段算法必须给出同一个答案，而它们是两份副本（数据插件的 `entryDirName`、设置插件的 `entrySection`）。十几行纯逻辑，为它新建一个共享包不值得；两边的注释互相提到对方，改一处就要改另一处。

{/* ref file="../plugins/settings/src/paths.ts" lines="60-92" */}

### 没手写 id 的条目，数据与设置每次启动新建一份

条目没写 `id` 时，loader 生成一个 8 位随机十六进制串，启动时不写回 `cordis.yml`，每次启动换一个，那条条目的数据与设置每次都新建一份。数据插件与设置插件遇到这种条目都写一条 warn：不抛错（这条条目本来能正常运行），也不省略日志（数据对不上是最难查的那种问题）。

`a3f9c210` 是合法的 kebab-case，所以这条检查和上面的字符集校验互不覆盖。手写一个正好 8 位十六进制的 id（`deadbeef`）会多一条 warn，代价只是一行日志。

## 验证

### 只验证 node 这部分的插件不用启动 electron，但 `createRequire` 要先 `realpath`

无界面的插件可以直接在 home 里用 node 建一个真的 cordis 上下文来验证：服务能不能提供、命令能不能登记、子进程能不能启动，都验证得到，比启动 electron 快。要注意两点：

- **`cordis` 不在 home 的 `node_modules` 顶层**：它是插件的 peer，pnpm 把它装在 `.pnpm` 里插件实际所在的那一层，实验脚本直接 `import 'cordis'` 报 `ERR_MODULE_NOT_FOUND`
- **要从插件那一层解析，而且先 `fs.realpathSync`**：`node_modules/@godcreator/x` 是个链接，`createRequire` 从链接路径往上找不到 cordis：

  ```
  Error: Cannot find module 'cordis'
  Require stack:
  - <home>\node_modules\@godcreator\gwb-py-cli\dist\index.js
  ```

  解析链接之后就到了 `.pnpm/<插件>@<hash>/node_modules/` 这一层，cordis 在那里

实验脚本里的 `Context` 也要从插件那一层解析，和插件用同一份 cordis，否则 `Service` 的 `instanceof` 对不上。插件本身按 `<home>/node_modules/...` 的路径 import 即可，node 会解析到 `.pnpm` 里的实际目录，插件算出来的包根就是它实际安装的位置，`gwb-py-cli` 的 venv 也建在那里。

## MCP 入口

### 块注释里的 `*/` 会把注释提前结束

在块注释里写 `notifications/*/list_changed` 这样的路径，其中的 `*/` 直接结束了 `/** … */`，后面整段注释变成代码。报错不是「注释没闭合」，而是一整屏

```
error TS1443: Module declaration names may only use ' or " quoted strings.
error TS1127: Invalid character.
```

看着像文件编码坏了。路径样式的 glob 写进块注释之前，先看一眼里面有没有 `*/`。

### 函数声明拿不到外层 `const` 的类型收窄

`const cli = ctx.gwbCommands` 加一句 `if (cli === undefined) return` 之后，箭头函数里的 `cli` 是收窄过的，`function` 声明里不是：函数声明会被提升，TypeScript 认为它可能在那句检查之前就被调用。症状是 `'cli' is possibly 'undefined'`，上面明明刚判断过。写成 `const … = () => {}`：

### 客户端把 `args` 转成字符串：无参数的命令正常，带参数的全部失败

经 MCP 调命令时，无参数的命令正常，带 `args` 的全部被命令拒绝，报「参数要是一个对象」。用对照实验定位：同一个调用用 curl 直接发对象就成功，说明入口与命令都没问题；`args` 的 schema 是 `z.unknown()`，协议层什么形状都接受，是客户端把嵌套对象序列化成 JSON 字符串再发。

在 MCP 入口修，不指望客户端改：`run` 收到的 `args` 是字符串时先 `JSON.parse`，解析成功就用结果，失败就原样交给命令。JSON 字面量来回转换不丢信息，真要传字符串参数的命令不受影响。

### `Accept` 少一个值就是 406

SDK 的 streamable HTTP 要求 POST 同时接受 `application/json` 与 `text/event-stream`，只写前者拿到的是

```
406 {"error":{"code":-32000,"message":"Not Acceptable: Client must accept both …"}}
```

手工用 curl 或 `Invoke-WebRequest` 试入口时很容易只写 `application/json`，然后把 406 当成鉴权失败或路由没注册。鉴权失败是 401，并带一句原因。
