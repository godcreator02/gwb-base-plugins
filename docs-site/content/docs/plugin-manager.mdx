# gwb-plugin-manager

包名 `@godcreator/gwb-plugin-manager`，服务 `ctx.gwbPluginManager`。它管两样东西，而这两样是两回事：

- **包**——npm 包，pnpm 装进 home 的 `node_modules`。装了包**什么都不会发生**，它只是在磁盘上
- **条目**——`cordis.yml` 里的一行，指向一个包。有了条目，插件的代码才会被加载运行

这个插件的全部工作就是把两层对起来：安装（`install`）、卸载（`uninstall`）、查新版本（`outdated`）、
升级（`update` / `update-all`）、加删条目、启用停用、改显示名。插件管理窗格（已装、可装两栏）的界面
不在这里，在 `@godcreator/gwb-baseui`；查源上有什么可装、配第三方包源在
[gwb-plugin-sources](/docs/plugin-sources)。本插件只有主进程里的服务与命令。

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="29-61" */}

**依赖谁**：`gwbCommands`、`gwbData`、`gwbSettings`、`gwbSkills` 四个都是**局部注入**（`ctx.inject([...])`）——
缺哪个本插件照常加载，只少那一部分功能：命令注册不上、显示名存不下、pnpm 路径只能自动找、说明书不出现。

## 用哪份 pnpm、怎么启动

安装、卸载、查新版本、升级，每一步都是启动一个 pnpm 子进程。**用的是用户电脑上装的 pnpm**，本插件
不带、也不代装。找它有两条路：设置项 `pnpm-path` 优先，填了就不再去找 PATH；没填就按 PATH 顺序找，
和在命令行里敲 `pnpm` 启动的是同一份；都找不到时返回一句点名设置项的错误：

{/* ref file="../plugins/plugin-manager/src/pnpm-path.ts" lines="161-180" */}

**只支持 pnpm 12 起的原生 pnpm**：npm 包的 `bin` 指向 `pnpm.exe`，这个二进制来自可选依赖

说明要装 12 以上，不试着运行。原生二进制的位置照 pnpm 包自带的查找方法，找不到就报「安装它时可选依赖

## 两层怎么对起来

磁盘上那份清单（home 的 `package.json`）与内存里的条目树，由 `reconcile` 对成一张表，**两边都不丢**：

{/* ref file="../plugins/plugin-manager/src/inventory.ts" lines="163-190" */}

清单里有、条目树上没有的包，报成 `entries: []`——它可能是装了还没加条目的插件，也可能是共享包（永远不该有
条目）。这里不下结论，界面用 `plugin-manager.shared` 那张表把共享包分出去。条目树上有、清单里没有的
（手工改过 yml，或者包被 `pnpm remove` 掉了）报成 `installed: false`，界面上是一行找不到包的条目——
**卸载时先删条目、后卸包**就是为了不产生这种情况。

**改条目树只有一条路**：经 loader 那棵树的 `create` / `remove` / `update`，不自己写 yml。loader 把磁盘上的
yml 与内存里加载着的条目绑在一起，绕过它写文件，内存里不知道，下一次写回就用旧的内存状态把磁盘上的覆盖掉：

## 条目 id：连同磁盘上的归属一起定

条目 id 就是身份：`gwb-data` 的数据目录与 `gwb-settings` 的设置分区都按它的最后一段划分，定了就不能改。
默认 id 由包名去掉 scope 和 `gwb-` 前缀得来，所以 `@a/gwb-foo` 与 `@b/foo` 算出同一个 `foo`；而删条目、
卸包都把数据与设置留在磁盘上。只看条目树判断重名的话，空出来的 `foo` 会被下一个同名的包拿走，读到前一个包
的东西。所以定 id 时把数据插件与设置插件记录的归属（两者的 `owners()`）一起看：

{/* ref file="../plugins/plugin-manager/src/ids.ts" lines="108-127" */}

手工给的 id（`add-entry` 的 `id`）属于别的包就直接拒绝。数据插件、设置插件没装时跳过那一边——那时磁盘上
没有可能冲突的东西。同一个插件改了包名、要继续用旧数据与设置，用 `plugin-manager.transfer-owner { id, pkg }`
把两边的归属一起改掉；真正阻止「用了别人的数据」的是那两个插件自己的检查，这里只是定 id 时先避开。

## 装：插件的 peer 也装进 home

`plugin-manager.install` 是三步不是两步：`pnpm add` 进 home → **把该进 home 的 peer 也装成 home 的直接依赖** →
加一条条目。

### 为什么必须装

插件如果依赖一个**会独立升级**的 npm 包，而且只读它的文件、启动它的进程（不 import 它的代码），那个包就该
写成插件的 peer——插件每次现查 `<home>/node_modules/<包名>`：

{/* ref file="../plugins/plugin-manager/src/peers.ts" lines="4-20" */}

**这个路径只有在包写进 home 的 `package.json` 时才存在**，而且它是一个**升级时 pnpm 会改指向的链接**，
永远指向当前版本。反过来，`import.meta.resolve` 拿到的是解析那一刻带版本号的真实路径，之后就不变了——
而 pnpm 不删旧版本目录，于是升级之后读到的仍是旧文件，全程不报错，只能重启。

**pnpm 自动补装的 peer 做不到这一点**（实测记录在内核仓 `probes/2609101500_peer-dep-live-swap`）：自动补装的
只放进 `.pnpm/`、只链接到插件自己能解析到的位置，`<home>/node_modules/<包名>` 根本不存在；于是
`pnpm outdated`（只看 `package.json`）永远看不见它，[一键更新](#一键更新停用再启用)也就永远升不到它。
`auto-install-peers` 这个开关解决不了——默认就是开的，开着也只放进 `.pnpm/`。所以这一步只能由本插件来做。

### 判断：谁装、谁跳过

{/* ref file="../plugins/plugin-manager/src/peers.ts" lines="80-131" */}

按顺序四条。**已经在 home 的 `package.json` 里的一个字不动**——不降级、不改别人定好的版本，那条依赖是谁装的、
为什么是这个版本，这里一概不知道。`cordis` 跳过：插件 `extends Service` 用的那个基类必须是内核那一份，home 里
再装一份就是第二张服务表。`@godcreator/gwb-*` 里还要再分一次——**共享包装、插件跳过**，依据是清单里有没有
`gwb.shared`（内核扫它拼 importmap，`plugin-manager.shared` 读的也是这一批）：

- **共享包本来就该是 home 的直接依赖**——内核只扫 home 的 dependencies 拼 importmap，不在那张清单里就等于没有
- **插件**有自己的安装方式（`plugin-manager.install`，装完还会加一条条目），从 peer 这条路顺带装进来，只会在
  「已装、没有条目」那一栏堆一排没人用的包

判断种类要读那个包自己的清单，而它**不在** `<home>/node_modules/<插件>/node_modules/` 下——pnpm 把 peer 和插件
并排放在 `.pnpm` 那一层，`<home>/node_modules/<插件>` 只是指过去的一个链接。所以先解析链接，按包名有几段就往上
退几层，退到的才是插件能解析到依赖的那个目录：

{/* ref file="../plugins/plugin-manager/src/home.ts" lines="40-69" */}

两处都读不到就**保守地当插件跳过**（常见原因：它是一条可选的 peer，pnpm 不会自动补装）——多装一个包只是
占磁盘，可把一个插件当普通包装进 home，界面上会凭空多出一行「装了没有条目」，人还得回头查它是哪来的。

### 执行：装 latest、一个包一次、永远不让安装失败

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="649-709" */}

**装 latest，不装清单上写的范围**：这一步装的是共享包与生态外的包，latest 通常都满足；按范围装会把 `^1.2.3`
这种范围原样写进 home 的清单。范围原样写进回执；latest 真不满足时照装，那一处出现在回执的 `peerWarnings` 里。
**一个包一次 pnpm，不批量**：一次 `add a b c` 里有一个包源上没有，pnpm 整次失败，好的那几个也装不上，而且
它不说是哪个失败的。**永远不抛错**：插件本身已经装上了，peer 这一步的每一种失败都只是回执里的一行——
这条命令是所有 home 安装插件的必经之路。

peer 排在**加条目之前**：条目一加进去 loader 就会立即加载它，而插件加载后的第一件事很可能就是去查那个路径。

### 回执

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="103-143" */}

`action` 四种：`installed`（这次装成了直接依赖）、`present`（本来就在，版本没动）、`skipped`（不该由这里装，
`note` 里是原因）、`failed`（装不上，`note` 里带 pnpm 输出的最后几行）。有 `failed` 时顶层 `note` 点名，
插件管理窗格把整条提示显示成红色——插件是装上了，可那条依赖运行时会找不到。`peers` 说的是「装了没有」，
版本对不对得上看 `peerWarnings`（见上面「peer 版本对不上」那一节）。

### 卸载不动 peer

`plugin-manager.uninstall` 只删这个包和它的条目，**不去查谁还在用那些 peer，一条都不删。** 这不是漏了：
**代价不对称**——残留一个没人用的包只是占磁盘，误删一个还有插件在用的包会让它运行出错。真要清理，自己在
home 里 `pnpm remove`。

同样，**只有 install 会装 peer**：`update` / `update-all` 不重读 `peerDependencies`（升级会把已经在清单里的那些
一起升到最新，这正是这一步的用意；新版本**新加**的 peer 不会自动装进来）。

## 一键更新：停用再启用

`plugin-manager.update-all`，无参数（或 `{ only?: string[] }` 限定包名）。agent 发完一批新版本、人在工作台点一个
按钮，**全部升级、不重启**。一条命令做完：查清单 → 一次 pnpm → 逐条重新加载 → 整页重新加载界面。

### 为什么「停用再启用」就是重新 import

{/* ref file="../plugins/plugin-manager/src/update-all.ts" lines="5-21" */}

loader 条目树上一条条目的 `update(id, { disabled: true })` 会调用 `fiber.dispose()`；再
`update(id, { disabled: null })`（`null` 表示删掉这个字段）时它发现 fiber 没了，走 `init()`，而 `_init()`
**每次都重新 `tree.import(name)`**。所以不用 remove 再 create——条目在 yml 里的 id 与位置一字不动，数据与设置的
归属（都按 id 划分）也就不动。

这一点成立还要靠内核：主进程没有 `--expose-internals`，插件的包名 import 由内核交给 `loader.internal` 的那个函数
解析，而 Node 的 CJS 解析有**进程级缓存**——装了新版本它还返回旧版本的路径；内核先用 `realpathSync.native` 解出
真实目录再解析（内核仓轨迹卡 `2026-09-09-wall-resolver-cache`），没有那一步，这里重新 import 到的仍是旧文件。
跨仓无法用引用记号固定，所以只能写在这里。

### 计划是纯函数：一次 pnpm、自己最后

{/* ref file="../plugins/plugin-manager/src/update-all.ts" lines="63-96" */}

这段代码定了三件事：

- **pnpm 参数是一次 `add`，每个包写死 outdated 返回的 `latest`**——不是 `@latest` 标签。查到什么装什么，两次
  查询 registry 之间又发了一版，也不会装成回执上没写的那个
- **升了的每个包的每条条目都在清单上**，本来就停用的带 `disabled` 标记（执行时保持停用）。不能指望 cordis
  自动连带：被很多插件 inject 的插件（commands、settings…）重新加载时，cordis 会把依赖它的插件停了再启动，
  可那是重新运行**内存里的旧模块**，磁盘上的新版本它根本没碰
- **自己所在的包排最后，包内自己那条条目也排最后**（`self` 标记）——原因见下面

### 执行：升级与重新加载在同一条命令里，不留空档

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="765-824" */}

pnpm 升级会**删掉旧版本目录**。从 pnpm 退出那一刻起，旧插件如果读磁盘（延迟 import 一个子模块、读自己包里的
模板）就会读空，所以重新加载必须紧跟在同一条命令里——分成两条命令的话，中间空档有多长取决于人什么时候调下一条。

有插件没跟上上游的破坏性版本时照升、不拦：那次 pnpm 之后、重新加载之前查一遍 peer，`peerWarnings` 点名谁要
什么范围（见上面「peer 版本对不上」那一节）——该去追的是那个插件；不想让上游先升就用 `only` 只升别的。

### 自己最后，而且在回执之后

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="826-841" */}

在命令处理函数里停用自己，这条 await 链会随 fiber 一起被卸掉，回执永远到不了调用方——界面上就是「点了没反应」。
所以别人的都做完、回执交出去之后，在下一个宏任务（`setTimeout(…, 0)`）再处理自己：那时命令的应答早已发出。
这段代码**只持有条目树、id、命令总线的引用与那个 logger**——本插件的 fiber 已经卸掉，从 ctx 上取服务会报
「inactive context」；`this` 上别的方法也不调用。

整页重新加载跟着推迟到自己重新加载完之后：回执上 `selfDeferred: true`、`reload: 'deferred'`。自己不在清单里就当场
`shell.reload`（`reload: 'done'`）；命令表里没有它（没装外壳，或外壳版本太旧）就是 `unavailable`，`note` 里写
「界面要手动刷新」——按命令名查找，不 import 外壳的常量，那样会让 shell 成为本插件的运行时依赖。

### 回执

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="169-199" */}

{/* ref file="../plugins/plugin-manager/src/remount.ts" lines="20-31" */}

每条条目的结果有四种：`remounted`（重新 import 了新版本）、`skipped`（本来就停用，保持停用）、`deferred`（本插件
自己那条）、`failed`（修改条目树时抛错，`state` 里是那句错误）。`state` 用 cordis `FiberState` 的原名——
**ACTIVE 才算加载成功**，PENDING 是 inject 的服务还没齐，FAILED 是 `apply` 抛错，原因在日志里。

### 界面：整页重新加载

打开着的窗格用的是旧的页面代码，importmap 只在开机时注入一次；主进程这边换了新版本，页面上那份还是旧的，
而 ESM 没法卸载模块、外壳内部也没法重建。所以最后一步是 `shell.reload`——就是状态栏那个「刷新」按钮的命令版，
由外壳提供。

窗格那边还有两条行为：reload 还在进行时忙碌状态不撤（页面随时会被整页重新加载，撤了只会让人在最后一帧点到
什么；reload 没在进行才照常重新取表、撤掉忙碌状态）；点「全部更新」先在窗格里列出 `from → to` 让人确认（和
卸载的确认框一样，确认后才调命令；有过期包时按钮才亮）。这两条的实现在 `@godcreator/gwb-baseui` 的仓里，
跨仓无法用引用记号固定，这里只说明位置。

## 单条重新加载：remount

`plugin-manager.remount`，参数 `{ entryId }`（完整 entryId 或只写 id）。停用 → 等旧 fiber 卸载完 → 启用 →
等新 fiber 加载完，**在一条命令里做完**，时序与一键更新里每条条目的重新加载相同。本来停用的条目，最后是启用的。

回执形状（成功时在 `data` 里）：

- `{ id, action: 'remounted', state }`：在这条命令里做完了，`state` 是重新加载后的 fiber 状态——**ACTIVE 才算
  加载成功**，PENDING 是 inject 的服务还没齐、FAILED 是 `apply` 抛错（原因在日志里）。目标是命令总线也属于这一种：
  总线的 fiber 被卸掉时，处理函数那条 await 链只持有条目树与 logger，照样走完，回执经调用方手里那份总线引用交回
- `{ id, action: 'deferred', state }`：目标是**本插件自己**。回执先发出，下一个宏任务才重新加载，`state` 是动手前
  的状态。重新加载完没有第二份回执——之后用 `plugin-manager.list` 核对 `active`，或看日志里「本件自己（…）重挂了：…」那一行
- 修改条目树时抛错：`{ ok: false, error: '条目 <id> 重挂没成：…', data: { id, action: 'failed', state: <那句错误> } }`；
  条目不存在：`{ ok: false, error }`，和 `enable` / `disable` 一样

## 卸载：先删条目，后卸包

{/* ref file="../plugins/plugin-manager/src/uninstall.ts" */}

一个包在条目树上的全部条目，逐条 `tree.remove`（写回 yml、当场卸载），再 `pnpm remove`。顺序反过来就会出现上面
说的「找不到包的条目」。**pnpm 失败不回滚**：条目已删是可以接受的结果，包出现在「已装、没有条目」那一栏，
看得见，重试加条目就行。只删一条条目、保留包，用 `remove-entry`——两个动作各管各的，不是同一件事的两种写法。
