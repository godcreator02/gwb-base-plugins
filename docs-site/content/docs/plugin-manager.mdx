# gwb-plugin-manager

包名 `@godcreator/gwb-plugin-manager`，服务 `ctx.gwbPluginManager`。它管两样东西，而这两样是两回事：

- **包**——npm 包，pnpm 装进 home 的 `node_modules`。装了包**什么都不会发生**，它只是躺在盘上
- **条目**——`cordis.yml` 里的一行，指向一个包。挂上条目，插件的代码才真的跑起来

这个插件的全部工作就是把两层对起来：装（`install`）、卸（`uninstall`）、查新版（`outdated`）、
升（`update` / `update-all`）、检索（`search`）、加删条目、启停、改显示名。「插件」窗格
（已装 / 可装两段）的界面不住这儿——浏览器半在 `@godcreator/gwb-baseui`，本插件只剩
node 半的服务与命令。检索与安装同源：`search` 查 npm registry 标准检索协议
（`/-/v1/search`）列 `@godcreator` scope 下 `gwb-` 前缀的全部，基址从 pnpm 配置解析
（`@godcreator:registry` → `registry` → npm 官方），**代码里不出现任何具体源的名字与
地址**——装从哪来、搜就到哪去。

## 用哪份 pnpm、怎么起

装、卸、查、升、检索的每一步都是起一个 pnpm 子进程。**用的是用户电脑上装的 pnpm**，本插件
不带、不代装。找它两路：设置项 `pnpm-path` 优先，填了就不再回退去扫 PATH；没填按 PATH 顺序找，
跟 shell 里敲 `pnpm` 起的是同一份；都不成回一句点名设置项的错：

{/* ref file="../plugins/plugin-manager/src/pnpm-path.ts" lines="161-180" */}

**只支持 pnpm 12 起的原生 pnpm**：npm 包的 `bin` 指 `pnpm.exe`，二进制来自可选依赖
`@pnpm/exe.<平台>-<架构>`，找到的就是这个可执行文件本身。查到的 pnpm 包大版本低于 12 当场报错、
说清要装 12+，不试着跑。原生二进制的查找位置照 pnpm 包自带的解析法，缺了就报「装它时可选依赖或
构建脚本被跳过了」，不拿别的文件凑：

## peer 冲突：严格与否归 home，这儿只报成人话

peer 对不上时 pnpm 报错还是只打 WARN，**由 home 自己的 `pnpm-workspace.yaml` 定**
（`strictPeerDependencies: true`）；本插件调 pnpm 不带任何 peer 相关参数。default home 由内核
`INSTALL.md` 铺这一行，隔离 home 不放——开发版只进隔离 home，上游破坏线的开发版对还没迁的下游永远不满足，

盘上那份清单（home 的 `package.json`）与内存里那棵条目树，`reconcile` 对成一张表，
**两边都不丢**：

## 装：插件的 peer 也进 home

`plugin-manager.install` 是三步不是两步：`pnpm add` 进 home → **把该进 home 的 peer 也装成
home 的直接依赖** → 加一条条目。

### 为什么非装不可

插件如果依赖一个**会独立升级**的 npm 包，而且只是读它的文件、起它的进程（不 import 它的
代码），那个包就该是插件的 peer——插件每次现查 `<home>/node_modules/<包名>`：

{/* ref file="../plugins/plugin-manager/src/peers.ts" lines="4-20" */}

**那条路径只有在包进了 home 的 `package.json` 时才存在**，而且它是一条**会被 pnpm 改指的
junction**，指向永远是当前版本。反过来，`import.meta.resolve` 拿到的是一次性解开的、带
版本号的真实路径，解开那一刻就定死了——而 pnpm 不删旧版本目录，于是升级之后读到的仍是
旧文件，全程零报错、只能重启。

**pnpm 自动补的 peer 顶不上这个用**（读数出自内核仓
`probes/2609101500_peer-dep-live-swap`）：自动补的只塞进 `.pnpm/`、只软链进插件的解析面，
`<home>/node_modules/<包名>` 根本不存在；于是 `pnpm outdated`（只看 `package.json`）
永远看不见它，[一键热升](#一键更新热重挂)也就永远升不到它。`auto-install-peers` 那个开关
解决不了——默认本来就是开的，开着也只塞进 `.pnpm/`。所以这一步只能由这个插件来做。

### 判据：谁装、谁跳过

{/* ref file="../plugins/plugin-manager/src/peers.ts" lines="80-131" */}

按顺序四条。**已经在 home 的 `package.json` 里的一个字不动**——不降级、不改写别人钉好的
版本，那条依赖是谁装的、为什么钉在那儿，这儿一概不知道。`cordis` 跳过：插件
`extends Service` 的那个基类必须是宿主手上那一份，home 里再装一份就是第二张服务注册表。
`@godcreator/gwb-*` 里还要再分一次——**共享包装、插件跳过**，判据是清单里有没有
`gwb.shared`（内核扫它拼 importmap、`plugin-manager.shared` 读同一批，是本生态既有的标记）：

- **共享包**（`gwb-shared-react` / `gwb-tokens`）**本来就该是 home 的直接依赖**——内核只扫
  home 的 dependencies 拼 importmap，它不在那张清单里等于没有。跟这次要装的 peer 同一个形状
- **插件**有自己的进 home 之路（`plugin-manager.install`，装完还落一条条目），从 peer 这条路顺手塞
  进来只会在「已装、没挂条目」区里堆一排没人挂的包

种类要读那个包自己的清单，而它**不在** `<home>/node_modules/<插件>/node_modules/` 下——
pnpm 把 peer 跟插件并排放在虚拟仓那一层，`<home>/node_modules/<插件>` 只是指过去的一条
junction。所以先解软链、按包名有几段往上退几层，退到的才是插件的解析面：

{/* ref file="../plugins/plugin-manager/src/home.ts" lines="40-69" */}

两处都读不到就**保守当插件跳过**（常见原因：它是条 `optional` 的 peer，pnpm 不为这种自动补）
——多装一个包只是占磁盘，可把一个插件当普通包塞进 home 会在界面上凭空多出一行「装了没挂
条目」，人得回头查它是哪来的。

### 执行：装 latest、一条一趟、永不让装机失败

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="593-633" */}

**装 latest 不装清单上那条 range**：这一步装的是共享包与生态外的包，latest 通常都满足；按 range
装会把 `^1.2.3` 这种范围原样写进 home 的清单。range 原样带进回执；latest 真不满足而 home 开着严格
检查时，这一条就是 `failed`。**一条一趟 pnpm，不批量**：一趟 `add a b c` 里有一个包源上没有，
pnpm 整趟失败、好的那几个一个都装不上，而且它不告诉你是哪个挂的。**永不抛**：插件本身已经
装上了，peer 这一步的每一种没成都只是回执里的一行——这条命令是所有 home 装插件的必经之路。

peer 排在**建条目之前**：条目一落 loader 就当场挂它，而插件挂起来第一件事很可能就是现查
那条路径。

### 回执

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="93-125" */}

`action` 四种：`installed`（这次装成了直接依赖）、`present`（本来就在，版本没动）、
`skipped`（不该由这条路装，`note` 里是理由）、`failed`（装不上，`note` 里带 pnpm 尾巴）。
有 `failed` 时顶层 `note` 点名，窗格那侧（住 gwb-baseui 的那个窗格）把整条提示压成红的——
插件是装上了，可那条依赖跑起来会扑空。

### 卸载不动 peer

`plugin-manager.uninstall` 只拿走这个包与它的条目，**不去追谁还在用那些 peer、一条都不删。**
这不是漏了，是判过的：**代价不对称**——残留一个没人用的包只是占磁盘，误删一个还有插件在用的
包是运行时故障。真要清，人自己在 home 里 `pnpm remove`。

同理，**只有 install 这一条路会种 peer**：`update` / `update-all` 不重读 `peerDependencies`
（升级把已经在清单里的那些一起升到最新，那正是这一步的用意；新版本**新加**的 peer 不会
自动进来）。

## 一键更新：热重挂

`plugin-manager.update-all`，无参数（或 `{ only?: string[] }` 限定包名）。agent 发完一批新版本、
人在工作台点一颗键，**全升、不重启**。它一条命令做完三件事：查清单 → 一趟 pnpm →
逐条重挂 → 整页重载。

### 为什么「停用再启用」就是重 import

{/* ref file="../plugins/plugin-manager/src/update-all.ts" lines="5-21" */}

loader 那棵树上一条条目的 `update(id, { disabled: true })` 会 `fiber.dispose()`；再
`update(id, { disabled: null })`（`null` 是「删掉这个字段」）时它看到 fiber 没了走 `init()`，
而 `_init()` **每次重新 `tree.import(name)`**。所以不用 remove / create——条目在 yml 里的
id 与位置一字不动，设置与数据的归属（都按 id 分区）也就不动。

这条成立还差一半在内核：主进程没有 `--expose-internals`，插件的裸名由内核塞给
`loader.internal` 的那几行解析，而 Node 的 CJS 解析有**进程级缓存**——装了新版本它还回
旧版本的路径；内核先 `realpathSync.native` 解出真实目录再解析（内核仓轨迹卡
`2026-09-09-wall-resolver-cache`），没有那一步这儿重 import 到的仍是旧文件。跨仓钉不了，
所以这句只能写在这儿。

### 计划是纯函数：一趟 pnpm、自己最后

{/* ref file="../plugins/plugin-manager/src/update-all.ts" lines="63-96" */}

三件事在这段里定死：

- **pnpm 参数是一趟 `add`，每个包钉 outdated 回的 `latest`**——不是 `@latest` 标签。查到
  什么装什么，两次问 registry 之间又发了一版也不会装成回执上没写的那个
- **升了的每个包的每条条目都在清单上**，本来就停用的带 `disabled` 标（执行时保持停用）。
  不能指望级联：被大家 inject 的插件（commands / settings…）重挂时 cordis 会把依赖它的插件
  停了再起，可那是重跑**内存里的旧模块**，盘上的新版本它碰都没碰
- **自己所在的包排最后，包内自己那条条目也排最后**（`self` 标）——理由在下面

### 执行：升级与重挂同一条命令，不留窗口

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="718-741" */}

pnpm 升级会**删掉旧版本目录**。从 pnpm 退出那一刻起，旧插件若读盘（惰性 import 一个子模块、
读自己包里的模板）就读空，所以重挂必须紧跟在同一条命令里——分成两条命令，中间那段有多长
取决于人什么时候调下一条。

那一趟 pnpm 也先预检（见上面「peer 冲突」那一节）。home 开着严格检查（default 开着）而有插件没跟上上游的
破坏版，就整趟拒——一个包没升、一条条目没动、home 原样，`peerConflict` 点名谁要什么范围；先把那个下游
升上来，或 `only` 只升别的。

一条条目的重挂是四步，不是两步：

**等旧的拆完再启用**这一步不能省：loader 的 `update({ disabled: true })` 调 `fiber.dispose()`
**不等它**，而 Service 插件的 `provide` 是在卸载那趟里撤的。不等就启用，新 fiber 起来时旧服务
可能还没撤，cordis 报「service has been registered」。等的方式是 cordis 自己的
`Fiber.await()`（`while (inertia) await inertia`），它不会因为「依赖永远不满足」而挂死
（PENDING 时 inertia 是空的）；会挂死的只有某个插件的 `apply` 自己不回来，那种情况到点就走，

### 自己最后，而且在回执之后

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="743-759" */}

处理器里停用自己，这条 await 链随 fiber 一起拆掉，回执永远到不了调用方——界面上就是
「点了没反应」。所以别人的都做完、回执交出去，`setTimeout(…, 0)` 的下一个宏任务再动自己：
那时命令的应答早已发出。闭包**只持 tree、id、总线的引用与那只 logger**——本插件的 fiber
已经拆了，ctx 上取服务会「inactive context」；`this` 上别的方法也不进来。

整页重载跟着推迟到自己重挂完之后：回执上 `selfDeferred: true`、`reload: 'deferred'`。
自己不在清单里就当场 `shell.reload`（`reload: 'done'`）；命令表里没有它（外壳没装、或
版本太旧）就 `unavailable`，`note` 里写「界面要手动刷新」——按名探，不 import 外壳的常量，
那会把 shell 变成本插件的运行时依赖。

### 回执

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="147-175" */}

{/* ref file="../plugins/plugin-manager/src/remount.ts" lines="20-31" */}

每条条目的去向有四种：`remounted`（重 import 了新版本）、`skipped`（本来就停用，保持停用）、
`deferred`（本插件自己那条）、`failed`（动树时抛了，`state` 里是那句错）。`state` 照 cordis
`FiberState` 的原名报——**ACTIVE 才算真起来了**，PENDING 是 inject 没满足，FAILED 是
`apply` 抛了，原因在日志里。

### 渲染层：整页重载

开着的窗格持的是旧的 client 束，importmap 只在开机注一次；node 半换了新版本，页面上那份
还是旧的，而 ESM 没有卸载、外壳内部重建做不到。所以收尾是 `shell.reload`——就是状态栏
那颗「刷新」的命令版，归外壳。

窗格那侧的两条行为语义——reload 在路上时 busy 不撤（页面随时会被整页重载，自己也升了
的话先是这一个窗格关掉再开，撤了只会让人在最后一帧点到什么；没在路上才照常重取表、撤
busy），与点「全部更新」先在窗格内列 `from → to` 让人看一眼（照卸载确认框的做法，确认才
调命令；有过期包才亮，没查过与查了全新都是灰的）——正本在 `@godcreator/gwb-baseui`
那边（`plugin-manager` 那个窗格）的仓里，跨仓钉不住，这儿只留这两句指路。

`plugin-manager.remount`，参数 `{ entryId }`（完整 entryId 或裸 id）。停用 → 等旧 fiber 拆完 →
启用 → 等新 fiber 起完，**在一条命令里做完**，时序与一键热升重挂每条条目的是同一份。本来停用的
条目，终态是启用。给 `devkit.dev` 这类「装了新号、要这条条目重 import」的调用方用。

回执形状（成功时在 `data` 里）：

- `{ id, action: 'remounted', state }`：这条命令里做完了，`state` 是重挂后的 fiber 状态——
  **ACTIVE 才算挂上**，PENDING 是 inject 没满足、FAILED 是 `apply` 抛了（原因在日志里）。
  目标是命令总线也走这一支：总线的 fiber 被拆时处理器那条 await 链只持条目树与 logger，
  照样走完，回执经调用方手上那份总线引用交回
- `{ id, action: 'deferred', state }`：目标是**本插件自己**。回执先发出，下一个宏任务才重挂，
  `state` 是动手前的状态。重挂完没有第二份回执——之后用 `plugin-manager.list` 核对 `active`，
  或看日志里「本件自己（…）重挂了：…」那一行
- 动条目树时抛了：`{ ok: false, error: '条目 <id> 重挂没成：…', data: { id, action: 'failed', state: <那句错> } }`；
  条目不在：`{ ok: false, error }`，跟 `enable` / `disable` 同一个长相

## 卸载：先摘条目后卸包

{/* ref file="../plugins/plugin-manager/src/uninstall.ts" */}

一个包在树上的全部条目，逐条 `tree.remove`（写回 yml、当场卸 fiber），再 `pnpm remove`。
顺序反过来就是上面说的 ghost。**pnpm 失败不回滚**：条目已摘是正当落点，包落进「已装、
没挂条目」区看得见、重试加条目就行。只摘一条条目、包留着，走 `remove-entry`——两个动作
分工，不是同一个的两种写法。
