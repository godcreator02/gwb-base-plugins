# gwb-plugin-sources

包名 `@godcreator/gwb-plugin-sources`，不提供服务，只有四条命令：`plugin-sources.search`、`add`、`list`、
`remove`。它回答两件事：配好的源上**有哪些插件可装**，**从哪些源装**。安装、卸载、升级与条目管理在
插件管理 gwb-plugin-manager（在 devkit 仓 gwb-devkit 和 devkit 一起开发），两个插件之间没有代码依赖：
这里查到包名，交给 `plugin-manager.install` 去装。

**依赖谁**：`gwbCommands` 是硬依赖（写在 `inject` 里），没有它四条命令都登记不了；`gwbSkills` 是局部注入，
没装说明书插件时照常工作，只是说明书 `gwb-plugin-sources` 不出现。

## 从哪装就在哪搜：registry 地址怎么找

检索和安装必须查同一个源，否则「可装」列表里的包会装不上，或者源上有的包列不出来。pnpm 安装时按
scope 读两份 npmrc（机器级 `~/.npmrc` 与 home 级 `<home>/.npmrc`），这里照同样的优先级找地址：
先找 `@scope:registry=`，再找 `registry=`，每一种都是 home 级优先于机器级，都没写就是 npm 官方源。

{/* ref file="../plugins/plugin-sources/src/sources.ts" lines="125-137" */}

这里不调用 pnpm。代价是：用环境变量或 pnpm 全局配置指定的源，这里看不到，检索可能和安装查的不是同一个源。
本机的配置都写在 `~/.npmrc` 里，目前不会遇到。**代码里不出现任何具体源的名字与地址**——换一台机器、
换一个源，只改 npmrc。

## 检索：npm 标准协议，一条源失败不影响别的

每条源走 npm registry 的标准检索接口 `/-/v1/search`，Verdaccio、npmjs、gitea 都实现了它。响应里的
包名有两种形状（npmjs、verdaccio 把 scope 写在 name 里，gitea 分开放），解析时拼回全名。
**「是不是插件」只看包自己在清单 `keywords` 里写没写 `gwb-plugin`**，名字前缀不参与判断：

{/* ref file="../plugins/plugin-sources/src/search.ts" lines="1-24" */}

不带参数的 `search` 查全部配好的源：两层 npmrc 里出现过的每个 scope，`@godcreator` 永远第一、
其余按名字排。各条源并发查询，查询成功的合并进 `packages`，失败的在 `note` 里写明是哪条源；全部失败才 `ok: false`。

## 包源写在机器级 ~/.npmrc

装第三方 scope 的插件（`@j/gwb-…` 这种个人源）之前，要先让 pnpm 知道这个 scope 从哪装——
**scope 路由与凭据写进机器级 `~/.npmrc`**。为什么是机器级：`@godcreator` 的路由本来就写在那里，
本机每个 home 的安装、每个源码仓的安装与发版都读它，包源是整台机器共用的配置。home 级 `.npmrc`
pnpm 也读、同名行还优先，但那里只放手工加的行：`list` 两层合起来显示、逐条标出处，`add` 与 `remove`
不写它。

解析、增改、删除都是纯函数。token 行按**源地址**配对，不按 scope：同一个 token 可以配几条源，
各是各的一行；换源、删源时，旧源的 token 行只有在没有别的 scope 再指向同一个地址时才一起删：

## 怎么单独测

`search.ts` 与 `sources.ts` 都是纯函数：检索响应的两种包名形状、keywords 判断、多源合并、npmrc 的解析与增删、
token 行的配对与保留、registry 地址的优先级，全部用字符串做输入测（`tests/search.test.ts`、
`tests/sources.test.ts`）。真的连源检索、真的改 `~/.npmrc`，只在隔离 home 里实机验证。
