**本页回答**：python 命令行运行插件有哪些功能；插件、页面和 agent 经哪些接口用它，各属于哪条接缝；登记方的 python 项目要满足什么；它依赖什么、缺了会怎样；哪些事常被以为归它、其实不归它。包名 `@godcreator/gwb-py-cli`，源码目录 `plugins/py-cli/src`，入口文件 `index.ts`。

它和 [gwb-node-cli](/docs/node-cli) 是同一套运行办法（登记时校验、同名登记成总线命令、参数、工作目录校验、时限、输出截断、回执形状都一样），多出来的是 venv：检查 venv 在不在、对不对，不对就用 uv 重建。它自己不带 python 项目，python 项目在登记它的插件的包根下。

## 功能

- **登记 python 命令行工具**：插件给名字、自己的包根、python 项目的名字与版本，以及要运行的入口点（`command`）或模块（`module`），二选一；插件卸载时自动注销
- **venv 建在登记方的包根下**：`<包根>/py/.venv`；插件装在 `node_modules` 里，venv 也就在 `node_modules` 里
- **每次运行前检查 venv**：三样都对就跳过——venv 目录在；venv 里的包根记号 `.gwb-built-for` 写的是这个包根；`Lib/site-packages` 下有 `<distName>-<version>.dist-info`（项目名按 PyPA 的规则归一化后比较）。只看目录名、不启动 python：每次运行前都要检查，承担不起启动解释器的开销。pnpm 重新安装时整个包目录被替换、venv 随之消失，下一次运行自己重建
- **包根记号认出包目录被移动过**：venv 里的可编辑安装记着建它那次的包根，整个包目录被搬走（home 被复制或改名）后照样能启动、却指向原来的目录。记号放在 venv 里面，跟 venv 一起创建、一起删除；放在外面的话 venv 被删了记号还在
- **不对就用 uv 重建**：运行 `uv sync --frozen --no-dev --inexact`，`--inexact` 是因为开发时 `py/.venv` 也是项目自己的开发环境，不删里面多装的包；时限 300 秒，第一次可能要下载 python 解释器。记号最后写，写完再检查一遍，版本仍不对就算失败
- **检查失败不抛错**：uv 不在 PATH、`uv sync` 失败或超时，都收成 `{ ready: false, reason }`，原因写成人读得懂的一句；插件本身照常加载，只是这些工具运行不了
- **登记时顺带检查一次**：不等它完成，不阻塞登记方的 `apply`
- **同一个包根同时只建一次**：并发的运行共用同一次检查
- **venv 没就绪时运行抛错**：写一条 warn 再抛，经命令总线调用时变成失败回执；按次给的工作目录不合规时连 venv 都不检查
- **登记的工具同时是命令总线上的命令**：命令名就是登记的名字，`plugin` 固定是登记方的包名，`effect` 照登记时给的写
- **中文输出不乱码**：给 python 子进程加 `PYTHONUTF8=1` 与 `PYTHONIOENCODING=utf-8`
- **时限、输出截断、同名处理、日志**：和 node 命令行运行插件一样；工作目录缺省是 `<包根>/py`
- **带一份说明书 `gwb-py-cli`**：给 agent 讲第一次运行为什么慢、venv 怎么重建、回执与 node 的异同

## 接口

每条接缝上交换什么、各方保证什么，写在接缝页；本节只列 python 命令行运行插件提供了哪些接口。

<Diagram name="py-cli-run" title="python 命令行工具的 venv 检查、重建与运行（分步）">
- 登记方插件调 `ctx.gwbPyCli.register({ name, packageRoot, distName, version, command 或 module })`，同名登记成总线命令，顺带发起一次 venv 检查、不等它完成
- 每次运行前检查三样：`<包根>/py/.venv` 在；`.gwb-built-for` 写的是这个包根；`Lib/site-packages` 下有 `<distName>-<version>.dist-info`。都对就跳过
- 不对就运行 `uv sync --frozen --no-dev --inexact --project <包根>/py` 重建；uv 不在 PATH、失败或超过 300 秒时 venv 没就绪，运行抛错，经命令总线调用时变成失败回执
- 就绪后运行 `Scripts/<command>.exe` 或 `Scripts/python.exe -m <module>`，加 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`，回执形状和 node 命令行工具一样
</Diagram>

`command: 'x'` 运行 `<venv>/Scripts/x.exe`（`[project.scripts]` 生成的入口程序），`module: 'x.cli'` 运行 `<venv>/Scripts/python.exe -m x.cli`。

**登记方的 python 项目要满足什么**：

- 在包根的 `py/` 下，有 `pyproject.toml`；它的项目名与版本就是登记时给的 `distName`、`version`
- **`uv.lock` 必须在**：重建用的是 `uv sync --frozen`，没有锁文件当场失败
- 用 `command` 时，`[project.scripts]` 里要有这个入口点
- 包清单的 `files` 要带上 `py`

## 依赖

注入了哪些服务、peer 怎么写、缺了会怎样，以及用了哪些约定通道（登记方包目录下的 `py/.venv`、PATH 上的 `uv`、venv 里的程序与两个编码环境变量、从 gwb-node-cli 复制来的 `run.ts` 与 `invoke.ts`），见[插件之间怎么连](/docs/wiring#godcreatorgwb-py-cli)。uv 不在 PATH 时 venv 建不成，报错原因是「启动不了 uv（PATH 上没有？）」，装上 uv 后再调用一次就行，不用重新加载插件。

## 不做的事

- **不带 python 项目**：`py/` 与 venv 都在登记方的包根下
- **不装 uv**：npm 上没有 astral 官方发布的 uv 包，uv 由机器自己装、从 PATH 找
- **不在安装时建 venv**：home 不放行依赖的 `postinstall`，pnpm 默认跳过它；venv 在登记与运行时建
- **不启动 python 查版本**：只看 `dist-info` 目录名
- **不让登记方另写 `plugin`**：总线命令的 `plugin` 固定是调用方的包名
- **不支持 Windows 以外的系统**
- **没有自检命令**：工具对不对由登记它的插件验收
