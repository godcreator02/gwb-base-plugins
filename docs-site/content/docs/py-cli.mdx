**本页回答**：python 命令行运行插件有哪些功能；插件、页面和 agent 经哪些接口用它，各属于哪条接缝；登记方的 python 项目要满足什么；它依赖什么、缺了会怎样；哪些事常被以为归它、其实不归它。包名 `@godcreator/gwb-py-cli`，源码目录 `plugins/py-cli/src`，入口文件 `index.ts`。

它和 [gwb-node-cli](/docs/node-cli) 是同一套运行办法（参数、工作目录、时限、输出截断、回执形状都一样），多出来的是 venv：检查 venv 在不在、对不对，不对就用 uv 重建。它自己不带 python 项目，python 项目在登记它的插件的包根下。

<Diagram name="py-cli-run" title="python 命令行工具的 venv 检查、重建与运行（分步）">
- 登记方插件调 `ctx.gwbPyCli.register({ name, packageRoot, distName, version, command 或 module })`，同名登记成总线命令，顺带发起一次 venv 检查、不等它完成
- 每次运行前检查三样：`<包根>/py/.venv` 在；`.gwb-built-for` 写的是这个包根；`Lib/site-packages` 下有 `<distName>-<version>.dist-info`。都对就跳过
- 不对就运行 `uv sync --frozen --no-dev --inexact --project <包根>/py` 重建；uv 不在 PATH、失败或超过 300 秒时 venv 没就绪，运行抛错，经命令总线调用时变成失败回执
- 就绪后运行 `Scripts/<command>.exe` 或 `Scripts/python.exe -m <module>`，加 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`，回执形状和 node 命令行工具一样
</Diagram>

## 功能

- **登记 python 命令行工具**：插件给名字、自己的包根、python 项目的名字与版本，以及要运行的入口点（`command`）或模块（`module`），二选一；插件卸载时自动注销
- **venv 建在登记方的包根下**：`<包根>/py/.venv`；插件装在 `node_modules` 里，venv 也就在 `node_modules` 里
- **每次运行前检查 venv**：已经就绪时只做三次文件检查、不启动任何进程；venv 不在、不是在这个包根上建的、装的版本不对，就运行一次 `uv sync` 重建。pnpm 重新安装时整个包目录会被替换、venv 随之消失，下一次运行自己重建
- **登记时顺带检查一次**：不阻塞登记方的 `apply`；第一次可能要下载 python 解释器，所以慢
- **同一个包根同时只建一次**：并发的运行共用同一次 `uv sync`
- **登记的工具同时是命令总线上的命令**：命令名就是登记的名字，所属插件是登记方的包名
- **中文输出不乱码**：给 python 子进程加 `PYTHONUTF8=1` 与 `PYTHONIOENCODING=utf-8`
- **时限、输出截断、工作目录、同名处理、日志**：和 node 命令行运行插件一样；工作目录缺省是 `<包根>/py`
- **带一份说明书 `gwb-py-cli`**：给 agent 讲第一次运行为什么慢、venv 怎么重建、回执与 node 的异同

## 接口

每条接缝上交换什么、各方保证什么，写在接缝页；本节只列 python 命令行运行插件提供了哪些接口、定义在哪里。

| 接口 | 做什么 | 接缝 |
| --- | --- | --- |
| 服务 `ctx.gwbPyCli` 的 `register(spec)` | `spec`：`name`、`packageRoot`（包根的绝对路径）、`distName`、`version`、`command` 或 `module`、`description?`（命令总线要求非空，不给登记会被拒）、`usage?`、`args?`、`cwd?`、`env?`、`timeoutMs?`；类型 `PyCliSpec` 由本包导出 | [9 命令行工具](/docs/seams/cli) |
| 服务 `ctx.gwbPyCli` 的 `ensureReady({ packageRoot, distName, version })` | 检查并在需要时重建 venv，不抛错，返回 `{ ready, reason?, action }`，`action` 是 `skipped`、`synced` 或 `failed` | [9 命令行工具](/docs/seams/cli) |
| 服务 `ctx.gwbPyCli` 的 `list()`、`run(name, extraArgs?, { cwd? })` | 列出已登记的工具；运行一条，回执形状同 node 命令行运行插件的 `CliRunResult`；venv 没就绪时抛错，经命令总线调用时成为失败回执 | [9 命令行工具](/docs/seams/cli) |
| 登记出来的命令、命令 `py-cli.list` | 参数形状同 node 命令行运行插件 | [1 命令总线](/docs/seams/bus) |
| venv 目录 `<包根>/py/.venv` 与其中的 `.gwb-built-for` | venv 建成后把包根写进 `.gwb-built-for`；记号缺失或指着别的包根，就当 venv 不是这里的、重建 | [9 命令行工具](/docs/seams/cli) |

`command` 与 `module` 只能给一个：`command: 'x'` 运行 `<venv>/Scripts/x.exe`（`[project.scripts]` 生成的入口程序），`module: 'x.cli'` 运行 `<venv>/Scripts/python.exe -m x.cli`。

### 登记方的 python 项目要满足什么

- 在包根的 `py/` 下，有 `pyproject.toml`；它的项目名与版本就是登记时给的 `distName`、`version`。检查 venv 时读 `Lib/site-packages` 下 `dist-info` 目录的名字比对，不启动 python；项目名按 PyPA 的规则归一化（`-`、`_`、`.` 折成 `_` 再小写）后比较
- **`uv.lock` 必须在**：重建用的是 `uv sync --frozen`，没有锁文件当场失败
- 用 `command` 时，`[project.scripts]` 里要有这个入口点
- 包清单的 `files` 要带上 `py`

### 检查 venv 的规则

{/* ref file="../plugins/py-cli/src/bootstrap.ts" lines="61-72" */}

- **只看目录名、不启动 python**：每次运行前都要检查，承担不起启动解释器的开销
- **包根记号 `.gwb-built-for` 放在 venv 里面**：跟 venv 一起创建、一起删除；放在外面的话，venv 被删了记号还在，就会出现「记号说建好了、其实没有」的状态。记号防的是 venv 跟着包目录被整个搬走：venv 里的可编辑安装记着建它那次的包根，搬到别处照样能启动、却指向原来的目录，home 被整体复制或改名时就会这样
- **失败不抛错**：uv 不在 PATH、`uv sync` 退出码不是 0 或超过 300 秒，都收成 `{ ready: false, reason }`，原因写成人读得懂的一句；插件本身照常加载，只是这些工具运行不了
- **`uv sync` 带 `--inexact`**：开发时 `py/.venv` 也是项目自己的开发环境，不删里面多装的包
- **记号最后写**：`uv sync` 成功后才写 `.gwb-built-for`，写完再检查一遍，版本仍不对就算失败

## 依赖

| 依赖 | 用来做什么 | 缺了会怎样 |
| --- | --- | --- |
| 命令插件的服务 `gwbCommands`（服务类上的 `static inject`，[gwb-commands](/docs/commands)） | 把登记的工具登记成命令；登记 `py-cli.list` | 服务 `gwbPyCli` 不提供，插件一直等待 |
| 说明书插件的服务 `gwbSkills`（局部注入，[gwb-skills](/docs/skills)） | 登记自带的说明书 | 不登记说明书，运行插件照常加载 |
| PATH 上的 `uv` | 建 venv、装依赖，第一次还会下载 python 解释器 | venv 建不成，回执原因是「启动不了 uv（PATH 上没有？）」；装上 uv 后再调用一次就行，每次运行前都会重新检查 venv，不用重新加载插件 |
| Windows 的 venv 布局（`Scripts/*.exe`、`Lib/site-packages`） | 找要运行的程序、读装了哪个版本 | 别的系统上找不到程序；工作台只支持 Windows |
| cordis 的 `Service`（peer，`^4.0.0-rc.10`） | 提供服务；方法里的 `this.ctx` 是调用方的上下文 | 无法加载；必须和内核用同一份 cordis |
| loader 在调用方上下文上加的 `fiber.entry.options.name` | 认出登记方的包名 | 不是经 `cordis.yml` 加载的插件调用 `register` 时抛错「取不到调用方的身份」 |
| 词汇表包 `@godcreator/gwb-plugin-api`（dev，`^0.4.1`） | `GwbContext` 的类型 | 只在编译时用 |
| 内核包 `@godcreator/gwb-kernel-desktop`（peer，`^0.4.1`） | — | — |

`@godcreator/gwb-commands`、`@godcreator/gwb-skills` 写在 devDependencies 里：代码只 `import type {}` 它们。`src/run.ts` 与 `src/invoke.ts` 和 [gwb-node-cli](/docs/node-cli) 里的同名文件内容一样，改一处就要改另一处。

## 不做的事

- **不带 python 项目**：`py/` 与 venv 都在登记方的包根下
- **不装 uv**：npm 上没有 astral 官方发布的 uv 包，uv 由机器自己装、从 PATH 找
- **不在安装时建 venv**：home 不放行依赖的 `postinstall`，pnpm 默认跳过它；venv 在加载与运行时建
- **不启动 python 查版本**：只看 `dist-info` 目录名
- **不支持 Windows 以外的系统**
- **没有自检命令**：工具对不对由登记它的插件验收
