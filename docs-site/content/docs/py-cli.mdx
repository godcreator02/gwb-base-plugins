**本页回答**：python 命令行运行插件 `@godcreator/gwb-py-cli` 管什么、刻意不知道什么；登记表与 venv 的形状；它提供哪些接口、依赖哪些接口；不启动工作台、不装 uv 怎么测它；代码从哪读起。登记方的 python 项目要满足什么写在接缝页[命令行工具](/docs/seams/cli)。

## 管什么

它和 [gwb-node-cli](/docs/node-cli) 是同一套运行办法：登记时校验、同名登记成总线命令、经调用方的上下文取命令总线、按次给的工作目录先校验、时限与输出截断、回执形状都一样，`src/run.ts` 与 `src/invoke.ts` 是那边的逐字副本。多出来的只有 **venv**：检查它在不在、对不对，不对就用 uv 重建。

**登记方给包根、项目名与版本、入口。** 与 node 那边不同的几项：`packageRoot`（登记方包根的绝对路径）、`distName` 与 `version`（`pyproject.toml` 里的项目名与版本）、`command` 或 `module` 二选一。`command: 'x'` 运行 `<venv>/Scripts/x.exe`（`[project.scripts]` 生成的入口程序），`module: 'x.cli'` 运行 `<venv>/Scripts/python.exe -m x.cli`：

**venv 建在登记方的包根下**：`<包根>/py/.venv`。插件装在 `node_modules` 里，venv 也就在 `node_modules` 里；pnpm 重新安装时整个包目录被替换、venv 随之消失，下一次运行自己重建：

{/* ref file="../plugins/py-cli/src/bootstrap.ts" lines="23-33" */}

**检查只看目录名、不启动 python。** 每次运行前都要检查，承担不起启动解释器的开销。三样都对就跳过：venv 目录在；venv 里的包根记号 `.gwb-built-for` 写的是这个包根；`Lib/site-packages` 下有 `<distName>-<version>.dist-info`（项目名按 PyPA 的规则归一化后比较）：

{/* ref file="../plugins/py-cli/src/bootstrap.ts" lines="61-72" */}

包根记号防的是 venv 跟着包目录被整个搬走：venv 里的可编辑安装记着建它那次的包根，搬到别处照样能启动、却指向原来的目录，home 被整体复制或改名时就会这样。记号放在 venv 里面，跟 venv 一起创建、一起删除；放在外面的话 venv 被删了记号还在。

**不对就运行 `uv sync` 重建**，记号最后写，写完再检查一遍；失败不抛错，收成 `{ ready: false, reason }`，原因写成人读得懂的一句：

{/* ref file="../plugins/py-cli/src/bootstrap.ts" lines="138-167" */}

`uv sync` 带 `--frozen`（照 `uv.lock` 装）、`--no-dev`、`--inexact`（开发时 `py/.venv` 也是项目自己的开发环境，不删里面多装的包），时限 300 秒——第一次可能要下载 python 解释器：

{/* ref file="../plugins/py-cli/src/bootstrap.ts" lines="107-125" */}

**同一个包根同时只建一次**：正在进行的检查按包根记在内存里，并发的运行共用同一次：

{/* ref file="../plugins/py-cli/src/index.ts" lines="137-152" */}

**登记时顺带检查一次、不等它完成**，不阻塞登记方的 `apply`；**每次运行前再检查一次**，没就绪就写 warn 并抛错，经命令总线调用时变成失败回执。按次给的工作目录不合规时连 venv 都不检查：

{/* ref file="../plugins/py-cli/src/index.ts" lines="224-249" */}

**中文输出不乱码**：给 python 子进程加 `PYTHONUTF8=1` 与 `PYTHONIOENCODING=utf-8`；工作目录缺省是 `<包根>/py`。

**一条自己的命令 `py-cli.list`**。**带一份说明书 `gwb-py-cli`**，讲第一次运行为什么慢、venv 怎么重建、回执与 node 的异同。

## 不知道什么

**不带 python 项目。** `py/` 与 venv 都在登记方的包根下；本包只有 `dist`、`skills`、`src`，测试检查包根没有 `py/`：

{/* ref file="../plugins/py-cli/tests/artifact.test.ts" lines="57-65" */}

**不装 uv、不装 python。** npm 上没有 astral 官方发布的 uv 包，uv 由机器自己装、从 PATH 找；python 解释器由 uv 下载。

**不在安装时建 venv。** home 不放行依赖的 `postinstall`，pnpm 默认跳过它；venv 在登记与运行时建。

**只认 Windows 的 venv 布局**（`Scripts/*.exe`、`Lib/site-packages`），工作台只在 Windows 上分发。

**登记方写不了别的 `plugin`。** 与 node 那边不同，`PyCliSpec` 没有 `plugin` 字段，总线命令的 `plugin` 固定是调用方的包名：

{/* ref file="../plugins/py-cli/src/index.ts" lines="164-174" */}

**找程序、shell、输出解释、权限、运行记录、调用方的超时**：和 node 命令行运行插件一样都不管，见 [gwb-node-cli](/docs/node-cli)。

## 提供的接口

| 接口 | 做什么 | 契约在 |
| --- | --- | --- |
| 服务 `ctx.gwbPyCli` 的 `register(spec)` | 登记一个工具，同时登记成总线命令，顺带发起一次 venv 检查；返回注销函数，调用方卸载时自动注销 | [9 命令行工具](/docs/seams/cli) |
| 服务 `ctx.gwbPyCli` 的 `ensureReady({ packageRoot, distName, version })` | 检查并在需要时重建 venv，不抛错，返回 `{ ready, reason?, action }` | [9 命令行工具](/docs/seams/cli) |
| 服务 `ctx.gwbPyCli` 的 `list()`、`run(name, extraArgs?, { cwd? })` | 列出已登记的工具；运行一条，venv 没就绪时抛错 | [9 命令行工具](/docs/seams/cli) |
| 登记出来的总线命令、命令 `py-cli.list` | 参数形状同 node 命令行运行插件 | [1 命令总线](/docs/seams/bus) |
| venv `<包根>/py/.venv` 与其中的 `.gwb-built-for` | 记号缺失或指着别的包根，就当 venv 不是这里的、重建 | [9 命令行工具](/docs/seams/cli) |
| 导出的类型 `PyCliSpec`、`RegisteredPyCli`、`BootstrapResult`、`VenvPaths`、`CliRunResult`、`CliStream`、`CwdCheck`、`Invocation`，函数 `venvPaths`、`checkCwd`、`parseInvocation`，常量 `STAMP_NAME`、`DEFAULT_TIMEOUT_MS`、`MAX_TIMEOUT_MS`、`LIST_COMMAND` | `import type {} from '@godcreator/gwb-py-cli'` 让 `ctx.gwbPyCli` 有类型 | [9 命令行工具](/docs/seams/cli) |
| 说明书 `gwb-py-cli` | 包根 `skills/gwb-py-cli/` | [4 说明书](/docs/seams/skills) |

## 依赖的接口

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| 命令总线服务 `gwbCommands` 的 `register`（服务类上的 `static inject`） | 把登记的工具登记成命令；登记 `py-cli.list`；缺了服务 `gwbPyCli` 不提供 | [gwb-commands](/docs/commands) | 只记登记的替身；另有按 `Service` 写、记下登记方的替身与拒收的替身 |
| 说明书服务 `gwbSkills` 的 `register`（局部注入） | 登记自带的说明书；缺了不登记 | [gwb-skills](/docs/skills) | 不提供 |
| cordis 的 `Service`、`effect`、`get`、`logger` | 提供服务；方法里的 `this.ctx` 是调用方的上下文 | 内核带的 cordis（peer `^4.0.0-rc.10`） | dev 里的 `cordis` 4.0.0-rc.10 |
| loader 放在调用方 fiber 上的 `entry.options.name`（[8 条目身份](/docs/seams/entry-identity)） | 认出登记方的包名；取不到时 `register` 抛错 | 内核带的 cordis loader | 调用方插件在 `apply` 里自己往 fiber 上放一个 `entry` |
| PATH 上的 `uv` | 建 venv、装依赖，第一次还会下载 python 解释器；启动不了时回执原因是「启动不了 uv（PATH 上没有？）」，装上后再调用一次就行 | 机器上装的 uv | 服务测试把 venv 摆成已就绪的样子，不启动 uv；`ensureVenv` 可以传入替身 `sync` |

| Windows 的 `taskkill` | 超时时结束整个进程树 | 系统自带 | 真的 `taskkill` |
| 词汇表包的 `GwbContext` | 类型 | `@godcreator/gwb-plugin-api`（dev，`^0.4.1`） | 同一份 |
| 内核包 `@godcreator/gwb-kernel-desktop` | peer 范围 `^0.4.1` 声明兼容哪些内核 | home 根上装的内核包 | 不装 |

## 怎么单独测

七个测试文件，都在 `plugins/py-cli/tests/`：

- `bootstrap.test.ts`：项目名归一化、`dist-info` 的比对、venv 是否过期的四种原因与判断顺序、venv 各位置
- `registry.test.ts`：包根要绝对路径、缺项目名或版本不收、`command` 与 `module` 恰好一个、时限范围、同名后登记的生效、注销只删自己那条
- `invoke.test.ts`、`run.test.ts`：副本各有一份测试，内容与 node 那边相同
- `service.test.ts`：见下
- `artifact.test.ts`：构建产物规则；包里只有 `dist`、`skills`、`src`，没有 `py/`；仓根 `.gitignore` 忽略 `.venv/`

**`service.test.ts` 测服务这一层**，不装 uv：venv 按已就绪的样子摆好（目录、包根记号、`dist-info`），检查因此直接跳过；入口程序 `Scripts/tool.exe` 是当前 node 的一份拷贝，靠固定参数 `-e <脚本>` 把它看到的 argv、工作目录与两条 UTF-8 环境变量写到 stdout：

{/* ref file="../plugins/py-cli/tests/service.test.ts" lines="9-42" */}

证明的是：`py-cli.list` 登记与注销；登记成总线命令、登记时的那次检查写 info；`ensureReady` 在已就绪时跳过；argv 顺序、UTF-8 环境变量、`cwd` 的优先级（这两条只在 Windows 上跑）；`module` 形态缺 `python.exe` 时回启动失败的回执；不合规的 `cwd` 不启动进程；venv 建不起来时 `run` 抛错并写 warn；注销同时撤掉两处；取不到身份时抛错；总线看到的登记方是调用方、总线拒收时撤掉表里那条。

`uv sync` 真的建出 venv，只能在隔离 home 里验证。
