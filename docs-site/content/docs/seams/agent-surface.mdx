**本页回答**：`index`、`search`、`run` 三个工具的内容从哪来；命令回执怎么变成 MCP 工具结果；MCP 插件对命令插件、说明书插件依赖了哪几样；哪些地方只靠约定、写在哪两处。HTTP 与鉴权见 [MCP 协议](/docs/seams/mcp-protocol)。

## 连接的模块

- [MCP 插件](/docs/mcp) `@godcreator/gwb-mcp`：`index` / `search` 的返回由 `src/inventory.ts` 生成，`run` 的结果由 `src/tools.ts` 翻译
- [命令插件](/docs/commands)：`gwbCommands.list()` 提供命令清单，`gwbCommands.run()` 执行命令；写在 MCP 插件的 `export const inject` 里，缺了 MCP 插件不加载
- [说明书插件](/docs/skills)：`gwbSkills.list()` 提供说明书清单；MCP 插件局部注入，缺了照常工作、说明书清单是空表
- 命令行运行插件（[gwb-node-cli](/docs/node-cli)、[gwb-py-cli](/docs/py-cli)）：它们的回执形状由 MCP 插件单独认出

## 接口

<Diagram name="mcp-tools" title="三个工具的内容从哪来、run 的回执怎么翻译（分步）">
- `index`（无参数）：每次重新读取 `gwbCommands.list()`、`gwbSkills.list()` 与 `instructions.md`，返回说明书清单和按包名分组的命令名
- `search`（`plugin?`、`prefix?`、`q?`）：每次重新读取同一份清单再筛选，命中的命令带 `usage`
- `run`（`command`、`args?`）：参数是字符串时先试着按 JSON 解析，再交给 `gwbCommands.run`，带上 `{ via: 'mcp' }`
- `run` 的回执分三种形状：同时有 `stdout` 与 `exitCode` 的命令行工具回执只留六项；有 `ok`、`data`、`error` 以外的键的原样转成文本；标准回执失败时回「执行失败：…」并带 `isError`
</Diagram>

**`index` 与 `search` 每次调用都重新读取**命令表与说明书清单，运行中新登记的命令下一次调用就在：

{/* ref file="../plugins/mcp/src/index.ts" lines="205-221" */}

- `index`：home 名、MCP 插件版本、`instructions.md` 全文、说明书清单（名字、包名、完整 description，超过 200 字才截）、命令按包名分组只列名字（顺序是命令表里首次出现的顺序）、末尾一句提示。description 不取「第一句」：那会把触发条件截掉一部分；截断只防写得过长的描述把清单撑大
- `search`：`plugin` 精确匹配包名，命令与说明书一起筛；`prefix` 只筛命令名，只给它时说明书只回名字与包名；`q` 在命令的名字、description、usage 里找子串，在说明书的名字、description 里找；多个条件同时满足；命中的命令总带 `usage`；不带参数返回全部，带了条件时返回里多一个 `filter` 写明这次按什么筛的
- 说明书的 `files` 不进任何一个工具的返回：附件路径由 SKILL.md 正文自己提到，读附件用 `skill.read {name, file}`

{/* ref file="../plugins/mcp/src/inventory.ts" lines="135-155" */}

**回执的三种形状**靠键名区分：

{/* ref file="../plugins/mcp/src/tools.ts" lines="26-36" */}

{/* ref file="../plugins/mcp/src/tools.ts" lines="50-65" */}

| 形状 | 怎么认出来 | 翻译成 |
| --- | --- | --- |
| 命令行工具回执 | 同时有 `stdout` 与 `exitCode` 两个键 | `{ ok, exitCode, timedOut, durationMs, stdout, stderr }` 的文本；失败也不带 `isError` |
| 处理函数原样返回的对象 | 有 `ok`、`data`、`error` 以外的键 | 整个对象原样转成文本，不带 `isError` |
| 标准回执 | 只有 `ok` / `data` / `error` | 成功是 `{ ok: true, data }` 的文本（没有 `data` 给 `null`）；失败是 `执行失败：<error>` 并带 `isError` |

这张表**靠约定**：命令行工具回执的形状定义在 node-cli、py-cli 两份相同的 `run.ts` 里（`CliRunResult`），MCP 插件在 `tools.ts` 里另写一份只含用得到字段的 `CliRunResultView`，不依赖这两个包；命令插件「带 `ok` 就原样返回」的规则（见[命令总线](/docs/seams/bus)）决定了这两种对象会绕过标准回执到达这里。`run.ts` 改了键名，MCP 插件的类型检查发现不了。

**命令表和说明书表靠 `plugin` 对上**：两边的 `plugin` 都是服务从登记方条目取的包名（见[条目身份](/docs/seams/entry-identity)）；`search {plugin}` 同时筛两张表。

**按名字提到的别的插件的命令**：`instructions.md` 在 initialize 时发给客户端，`index` 的返回再带一份——有的客户端不把 initialize 里的 instructions 交给模型，`index` 里这一份是它们唯一拿到的地方。它、`index` 末尾的提示、`index` 工具的描述、`mcp.client` 的用法与 `bin/client.mjs` 的帮助按名字提到别的插件的命令：

这几个名字**靠约定**：`skill.read` 由说明书插件登记；`plugin-manager.list`、`plugin-manager.update` 由 devkit 仓的插件管理登记；`shell.reload` 由界面插件仓（gwb-ui-plugins）的外壳登记；`unit-folder.list` 由单元目录插件仓（gwb-unit-folder）的插件登记；`devkit.home.list` 由 devkit 登记。名字写在登记处与本插件两处，改了命令名这里不会报错，agent 照着调会收到「没有这条命令」。

## 约定

**MCP 插件**保证：

- `index`、`search` 每次调用都重新读取命令表与说明书清单，不缓存；同样的输入生成的 `index` 逐字节一致
- 说明书插件不在时照常工作，说明书清单是空表；说明书插件卸载时清单跟着清空
- 命令执行失败翻译成带 `isError` 的文本结果，不抛成 JSON-RPC 错误
- 命令行工具回执与处理函数原样返回的对象不按标准回执拆，字段一个不丢
- agent 每次调 `run` 都写一条日志：成功写 info，失败写 warn 并带原因

**命令插件**保证：

- `list()` 的每条都带 `name`、`plugin`、`description`、`usage`，四项都是非空字符串，`plugin` 是命令总线从登记方条目取的完整包名
- `run()` 不抛错，回执形状见[命令总线](/docs/seams/bus)

**说明书插件**保证：

- `list()` 的每条带 `name`、`description`、`plugin`，`plugin` 是登记方的包名

**登记命令、说明书的插件**保证：

- 命令的 `description` 与说明书的 description 都写成一句话（触发条件），参数形状写进 `usage`
- 处理函数自己返回带 `ok` 的对象时，不和标准回执的三个键混用

## 不负责的事

- MCP 插件不校验参数、不给命令分权限：`args` 原样交给 `gwbCommands.run`；带上的来源 `mcp` 只是告诉处理函数，不限制能调哪条命令
- MCP 插件不把命令登记成单独的工具，也不列出装了哪些插件（那是插件管理的 `plugin-manager.list`）
- 命令插件、说明书插件不知道 MCP 插件的存在，不为它调整任何格式
