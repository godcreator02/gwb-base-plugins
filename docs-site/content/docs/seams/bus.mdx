**本页回答**：插件怎么把能力登记成命令、调用方怎么按名字执行；这条接缝上交换什么；命令插件、登记命令的插件、调用命令的一方各保证什么；由哪些测试保护。命令插件的功能见 [gwb-commands](/docs/commands)。

## 连接的模块

- [命令插件](/docs/commands) `@godcreator/gwb-commands`：提供服务 `ctx.gwbCommands`，一张只在内存里的「命令名 → 处理函数」表
- 登记命令的插件：本仓的设置、说明书、MCP 入口、日志、两个命令行运行插件，以及别的仓里的插件
- 调用命令的一方：别的插件直接调 `run`；[MCP 入口](/docs/mcp)把 agent 的 `run` 交给它（见[命令表开给 agent](/docs/seams/agent-surface)）；本包页面请求处理器把客户端发来的命令名与参数交给 `run`
- [gwb-node-cli](/docs/node-cli) 与 [gwb-py-cli](/docs/py-cli)：替登记给它们的命令行工具在总线上登记同名命令（见[命令行工具](/docs/seams/cli)）

## 接口

**服务的类型**由命令插件导出（`import type { GwbCommands } from '@godcreator/gwb-commands'`），不在内核包里；回执类型 `GwbResult`（`{ ok: boolean, data?, error?: string }`）也由本包导出，正本是 `plugins/commands/src/result.ts`：

- 三类调用方：页面调本包的 `./client`，本包请求处理器交给 `run` 并带上 `{ via: 'ui' }`；agent 调 MCP 入口的 `run` 工具，MCP 入口交给 `run` 并带上 `{ via: 'mcp' }`；别的插件直接调 `ctx.gwbCommands.run`，不带来源
- 命令总线按命令名查内存里的命令表，找不到回 `{ ok: false, error: '没有这条命令：<命令名>' }`
- 找到就把参数和来源交给登记方的处理函数（没带来源就是 `{ via: 'plugin' }`）：返回带 `ok` 的对象原样返回，返回别的值包成 `{ ok: true, data }`，抛错收成 `{ ok: false, error }`
- 回执沿原路回到调用方；成功写 info（只读命令写 debug），失败写 warn
</Diagram>

**执行**：`run(name, args?, context?)` 返回 `Promise<GwbResult>`。处理函数返回带 `ok` 键的对象就原样返回，这个对象里 `ok` 以外的字段（比如命令行运行插件回执里的 `stdout`、`exitCode`）和 `ok` 在同一层；返回别的值包成 `{ ok: true, data: 值 }`；处理函数抛错、命令不存在都回 `{ ok: false, error }`：

**请求来源**：`run` 的第三个参数 `{ via }` 原样成为处理函数的第二个参数。`via` 只有三个值：`ui` 由本包页面请求处理器带上，`mcp` 由 MCP 入口带上，别的插件直接调时不带，处理函数收到 `plugin`。

**列出**：`list()` 返回全部命令的 `{ name, description, usage, plugin }`，四项都是非空字符串，`plugin` 是登记方的完整包名；登记时写了 `effect`、`hiddenFromAgents` 的再带这两项。这两项是给 MCP 入口读的（见[命令表开给 agent](/docs/seams/agent-surface)），命令总线的 `run` 不看它们。

**命令行运行插件的登记**：两个运行插件经调用方的上下文取总线（`this.ctx.get('gwbCommands')`），所以总线认出的登记方是调用方而不是运行插件；登记方在 spec 里写的 `effect` 原样带进总线命令的定义；总线拒收时运行插件撤掉自己表里那条，把错抛给调用方：

## 约定

**命令插件**保证：

- `run` 从不抛错：命令不存在回 `{ ok: false, error: '没有这条命令：<命令名>' }`，处理函数抛错回 `{ ok: false, error: '<异常文本>' }`
- 处理函数返回带 `ok` 键的对象时原样返回，一个字段都不改；其余返回值包进 `data`
- 同名命令后登记的生效，同时写一条 warn，写明原来是哪个包、现在是哪个包
- 注销函数只删自己登记的那条；重复调用无副作用
- 登记方卸载时，它登记的命令自动注销，登记方不用包 `ctx.effect`；包了也不出错，卸载时只注销一次
- `name`、`description`、`usage` 缺一项或为空串就抛错，不进表；`effect`、`hiddenFromAgents` 写了不认识的值也抛错
- `plugin` 由命令总线从调用方 fiber 上的条目取；登记方写了不同的包名就抛错，取不到条目也抛错
- 处理函数的第二个参数总是 `{ via }`：调用方带了来源就原样交给它，没带就是 `plugin`
- 每次登记、执行都写日志：成功写 info，`effect` 是 `read` 的命令执行成功写 debug，失败与找不到命令写 warn

**登记命令的插件**保证：

- `description` 写一句话，`usage` 写参数形状与注意事项，无参数的写「无参数」
- `effect` 按调用的实际后果标；只给页面调用的命令写 `hiddenFromAgents: true`
- 在经 `cordis.yml` 加载的插件里登记（含它 `ctx.inject`、`ctx.plugin` 出来的子上下文）；`def.plugin` 不写，要写就写自己的包名
- 处理函数自己校验参数，校验不过就抛错或返回 `{ ok: false, error }`
- 处理函数自己返回带 `ok` 的对象时，要么只用 `ok` / `data` / `error` 三个键，要么放心加别的键——加了别的键的对象会原样到达调用方，MCP 入口也不按标准回执拆它
- 需要总线才能工作的插件把 `gwbCommands` 写进 `export const inject`；命令对它可有可无时用 `ctx.inject(['gwbCommands'], …)` 局部注入（设置插件就是这样）

**调用命令的插件、MCP 插件与内核**保证：

- 只看回执的 `ok` 判断成败，失败原因读 `error`
- 处理函数自己返回的带 `ok` 的对象，按那条命令的 `usage` 读它的字段
- 带的 `via` 如实写来源：内核只给页面发来的命令写 `ui`，MCP 入口只给 agent 的调用写 `mcp`

## 不负责的事

- 命令插件不登记任何业务命令，不校验参数，不给命令分权限，也不按来源限制调用：`run` 对页面、agent、插件一视同仁，也不看 `effect`、`hiddenFromAgents`；要按来源区分行为的是处理函数自己，不让 agent 调到 `hiddenFromAgents` 命令的是 MCP 入口
- 命令插件不核实 `via`：它是调用方自己写的
- 命令插件不保存命令表，不给命令设时限
- 命令插件不接收页面的 IPC 消息；内核不认识任何命令名
- 命令插件不决定命令怎么展示给 agent：`index` / `search` 的格式由 MCP 入口决定
