**本页回答**：插件怎么把自己带的 node 或 python 命令行工具交给运行插件；运行插件怎么启动子进程、回执长什么样；子进程拿到什么；python 的 venv 由谁建、建在哪；运行插件、登记工具的插件、子进程各保证什么。两个运行插件的功能见 [gwb-node-cli](/docs/node-cli)、[gwb-py-cli](/docs/py-cli)。

## 连接的模块

- [gwb-node-cli](/docs/node-cli) `@godcreator/gwb-node-cli`：服务 `ctx.gwbNodeCli`，运行 node 写的命令行工具
- [gwb-py-cli](/docs/py-cli) `@godcreator/gwb-py-cli`：服务 `ctx.gwbPyCli`，运行 python 写的命令行工具，在登记方包根下用 uv 建 venv
- 登记命令行工具的插件：本仓的 MCP 插件把 `bin/client.mjs` 登记成 `mcp.client`；别的仓里的插件登记自己编译出来的工具
- 被启动的子进程：登记方包里的 js 文件，或 venv 里的程序
- 命令插件：两个运行插件都 `inject` 了 `gwbCommands`，登记的每个工具同时登记成总线命令（见[命令总线](/docs/seams/bus)）

## 接口

<Diagram name="cli-run" title="node 命令行工具的登记、调用与回执（分步）">
- 登记方插件调 `ctx.gwbNodeCli.register({ name, entry, … })`，`entry` 是它随包发布的 js 的绝对路径；gwbNodeCli 同时用同一个名字调 `gwbCommands.register`，登记成总线命令
- 页面、agent、别的插件经 `gwbCommands.run(name, args)` 调它；按次给的 `cwd` 不合规就不启动进程
- gwbNodeCli 用 `process.execPath` 加 `ELECTRON_RUN_AS_NODE=1` 启动子进程，argv 是 `[entry, ...固定参数, ...追加参数]`，不经 shell
- 缺省 60 秒时限，到时限用 `taskkill /T /F` 结束整个进程树；输出只留尾部 64,000 字节，超出时全量写进系统临时目录
- 回执 `CliRunResult` 带 `ok`，命令总线原样返回给调用方
</Diagram>

<Diagram name="py-cli-run" title="python 命令行工具多出来的 venv 检查（分步）">
- 登记方插件调 `ctx.gwbPyCli.register({ name, packageRoot, distName, version, command 或 module })`，同名登记成总线命令，顺带发起一次 venv 检查、不等它完成
- 每次运行前检查三样：`<包根>/py/.venv` 在；`.gwb-built-for` 写的是这个包根；`Lib/site-packages` 下有 `<distName>-<version>.dist-info`。都对就跳过
- 不对就运行 `uv sync --frozen --no-dev --inexact --project <包根>/py` 重建；uv 不在 PATH、失败或超过 300 秒时 venv 没就绪，运行抛错，经命令总线调用时变成失败回执
- 就绪后运行 `Scripts/<command>.exe` 或 `Scripts/python.exe -m <module>`，加 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`，回执形状和 node 命令行工具一样
</Diagram>

## 约定

**两个运行插件**保证：

- 身份取自调用方条目的包名，登记方不用报名字（见[条目身份](/docs/seams/entry-identity)）
- 登记时就校验：名字为空或带空白、node 的 `entry` 不是绝对路径、python 的 `packageRoot` 不是绝对路径或缺 `distName` / `version`、`command` 与 `module` 都给或都不给、时限不在范围内，当场抛错
- 同名后登记的生效并写 warn；注销只删自己那条；注销函数登记到调用方的 `effect` 上，调用方卸载时工具从运行插件的表上和总线上一起注销
- 总线上那条命令的 `usage` 缺省是运行插件写的参数说明；总线拒收（没写 `description`、`plugin` 不是调用方的包名）时撤掉运行插件表里那条，把错抛给调用方
- argv 全程是数组，不经过 shell：引号、空格、中文参数原样到达子进程
- 不继承内核进程的工作目录；子进程的 stdin 是空的；环境变量是内核进程的环境加上运行插件与登记时给的几条
- 启动失败（可执行文件不在）收成 `exitCode: null` 的回执、原因写进 `stderr`，不抛错；按次给的 `cwd` 不合规回 `{ ok: false, error }`；运行一个不存在的工具抛错
- 每次运行的开始与结束都写日志

**gwb-py-cli** 另外保证：

- 登记时发起一次 venv 检查、不等它完成；每次运行前再检查一次，venv 被删了当场重建
- 同一个包根同时只运行一次 `uv sync`
- venv 检查只读目录名，不启动 python
- venv 没就绪时运行抛错，经总线调用时变成 `{ ok: false, error }`

**登记命令行工具的插件**保证：

- node：`entry` 是自己包里编译好的 js 的绝对路径，从 `import.meta.url` 算出来
- python：包根下有 `py/` 目录，里面是带 `pyproject.toml` 与 `uv.lock` 的 python 项目（重建用 `--frozen`，没有锁文件当场失败）；`distName`、`version` 与 `pyproject.toml` 一致；用 `command` 时 `[project.scripts]` 里有这个入口点；包的 `files` 带上 `py`
- 写 `description`：命令总线要求非空，不写登记会被拒
- 命令名不和别的命令重名；需要的环境变量写在 `env` 里

**子进程**保证：

- 成功时退出码 0，失败时非 0，原因写 stderr
- 在时限之前结束；要更长时间就在登记时给 `timeoutMs`
- 输出用 UTF-8

## 不负责的事

- 运行插件不查 PATH 找可执行文件（uv 除外）、不读包的 `bin` 字段、不认 `.bin` 里的包装脚本
- 运行插件不解释子进程的输出：`stdout` 原样放进回执，结构化内容由调用方自己解析
- 运行插件不做交互：没有 stdin，不支持需要输入的工具
- gwb-py-cli 自己不带 python 项目，也不装 uv 与 python 解释器
- 子进程不知道自己是被总线、MCP 入口还是别的插件调用的
