**本页回答**：日志插件从哪读日志、一行日志的形状；日志窗格与 agent 怎么取最近的日志、怎么只取新写的；轮转之后怎么接上；日志插件、内核、日志窗格、写日志的插件各保证什么；哪些地方靠约定。日志怎么写进 `gwb.log` 由内核负责，见内核仓文档站的「日志」接缝。

## 连接的模块

- [日志插件](/docs/logger) `@godcreator/gwb-logger`：`inject` 里有 `gwbCommands`；登记命令 `logger.query`，读 `<home>/gwb.log` 与 `gwb.log.1`
- 内核写的日志文件：内核、插件、页面 console 三个来源的日志都由内核写进 `<home>/gwb.log`，一行一个 JSON；满 128 MB 改名成 `gwb.log.1`，只留这一份旧的；stderr 另写一份文本，给终端看
- 日志窗格：界面插件仓里的一个窗格，经命令总线调 `logger.query`
- agent：经 MCP 入口调 `logger.query`

## 约定

**日志插件**保证：

- 只读 `gwb.log` 与 `gwb.log.1`，不写、不改名、不删
- `entries` 从旧到新，是文件里原样的对象
- `cursor` 是读完时 `gwb.log` 里最后一个完整行末尾的字节位置；下一次带着它调，不漏也不重复
- `gwb.log` 末尾没以换行结尾的那一段当作内核还没写完的行，不返回、不报错；`gwb.log.1` 不再有人写，它的末行没以换行结尾就报错
- 坏行、坏参数直接报错，不跳过、不猜调用方的意思
- 命令在插件卸载时注销

**内核**保证（内核仓的约定）：

- `gwb.log` 是 UTF-8，一行一个 JSON，以 `\n` 结尾，五个键固定、顺序固定
- 一行只用一次 `writeSync` 写完：读的时候碰上的半行，下一次读时就完整了
- 满 128 MB 改名成 `gwb.log.1`，只留一份旧的；改名之后新写的落进新的 `gwb.log`
- 三个来源都写进这一份文件，`source` 由内核按 logger 名分

**日志窗格**保证：

- 先不带 `after` 取一次，之后带上一次回执里的 `cursor` 取新写的
- 可见时每秒调一次，不可见不调
- 在收日志的路径上不写 `console`：页面 console 会被内核写回日志文件，再被窗格读到，形成循环

**写日志的插件**保证：

- 用 `ctx.logger('<自己的名字>')`，名字不用 `kernel`、`loader`、`include`、`renderer`，否则会被内核算成内核或页面

## 不负责的事

- 日志插件不写日志文件、不写 stderr、不在 cordis 的日志流上注册任何东西：那是内核的事
- 日志插件不在内存里留日志、不推给页面：每次调用都现读文件
- 日志插件不分来源：`source` 由内核写进每一行
- 日志插件不画窗格：窗格在界面插件仓，窗格里的显示与筛选由窗格自己做
