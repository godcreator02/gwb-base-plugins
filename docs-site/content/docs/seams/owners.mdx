**本页回答**：数据目录与设置分区怎么记住自己属于哪个包；包名对不上时发生什么、人怎么手工处理；两个服务上的 `owners()` / `transferOwner()` 此刻是什么状态；各方保证什么。

## 连接的模块

- [数据插件](/docs/data)：每个数据目录里一个 `.owner.json`
- [设置插件](/docs/settings)：`settings.json` 顶层一张 `$owners`
- 照报错手工处理归属的人：改名或删掉旧的数据目录与设置分区，或改归属记录里的包名
- 两个服务上的 `owners()`、`transferOwner()` 此刻没有调用方：插件管理 `@godcreator/gwb-plugin-manager`（生命周期插件仓 `gwb-lifecycle-plugins`）0.14 起选条目 id 时不读归属，也没有转移归属的命令

为什么要记归属：数据目录名与设置分区名都是条目 id 的末段（见[条目身份](/docs/seams/entry-identity)），而不同 scope 的同名包会算出同一个条目 id（`@a/gwb-foo` 与 `@b/foo` 都叫 `foo`）；条目删了数据与设置留在磁盘上，下一个拿到这个 id 的包就会读到前一个包的东西（轨迹卡[目录与分区记下归属的包](/trajectory/2026-09-19-owner-stamp)）。

## 接口

<Diagram name="owner-transfer" title="包名对不上时，归属怎么拒绝、人怎么手工处理（分步）">
- 两处归属记录：数据目录里的 `.owner.json`（`{ "pkg": "<包名>" }`）、`settings.json` 顶层 `$owners` 里的一项，键都是条目 id 的末段
- 第 1 步：`@old/gwb-foo` 的条目 `home:foo` 第一次取数据目录、第一次 `define` 时，两处都记成 `@old/gwb-foo`
- 第 2 步：同一个插件改名成 `@new/gwb-foo`，条目 id 还是 `foo`；数据插件与设置插件都抛错、不动数据，报错写明归属于谁、磁盘上哪个目录或文件要手工处理
- 第 3 步：人确认是同一个插件后手工改归属记录：`<home>/data/foo/.owner.json` 的 `pkg` 改成 `@new/gwb-foo`；关掉工作台，把 `settings.json` 里 `$owners` 的 `foo` 改成 `@new/gwb-foo`。不是同一个插件时改名或删掉旧的目录与分区
- 第 4 步：之后新包名放行、旧包名被拒
</Diagram>

- `owners()`：目录名或分区名（条目 id 末段）→ 包名。数据插件的是异步的，设置插件的是同步的；还没记过归属的不列

## 约定

**数据插件与设置插件**保证：

- 目录或分区第一次被访问（数据）或 `define`（设置）时，没有归属就记成调用方的包名
- 调用方的包名和记下的不同就抛错、不动任何数据，报错写明归属于谁、由人在磁盘上哪个目录或文件处理
- 数据插件的归属文件坏了当场抛错，不当成没有归属（当成没有等于谁都能认领）；设置插件的 `$owners` 里坏掉的那一项丢掉并写 warn，那个分区回到「谁先声明归谁」
- `transferOwner` 立刻写入磁盘，之后新包名放行、旧包名被拒
- `owners()` 只列出有归属记录的目录或分区；数据插件列的时候遇到坏的归属文件写 warn、不列它

**手工处理归属的人**保证：

- 只在确认是同一个插件改了包名时才把归属记录里的包名改成新包名；不是同一个插件时改名或删掉旧的目录与分区，否则新包会读到别的包留下的数据
- 改 `settings.json` 之前关掉工作台
- 设置分区改名或删掉时，同时删掉 `$owners` 里那一项，不然新包 `define` 时还按旧记录拒绝

## 不负责的事

- 数据插件与设置插件不判断「是不是同一个插件改了名」：包名对不上一律拒绝，由人决定怎么处理
- 数据插件与设置插件不删除旧包留下的数据与设置
- 工作台上没有转移归属的命令，本仓的两个插件也不登记这样的命令
- 这套归属不是安全边界：插件在同一个进程里，能直接改这两个文件；它防的是同名 id 误读别人的数据
