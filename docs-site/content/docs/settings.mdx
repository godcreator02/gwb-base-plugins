**本页回答**：设置插件 `@godcreator/gwb-settings` 管什么、刻意不知道什么；内存与 `settings.json` 里是什么形状；它提供哪些接口、依赖哪些接口；不启动工作台怎么测它；代码从哪读起。声明方、按位置读写的一方各保证什么写在接缝页[设置](/docs/seams/settings)，分区归属写在[数据归属](/docs/seams/owners)。

## 管什么

插件声明「我有一项叫 `level` 的设置，标题是这个、类型是那个」，值存到哪由设置插件决定。它管三样：**一张声明表**（此刻哪些插件声明了哪些项）、**一份值表**（从 `settings.json` 读进来的整份内容）、**把值表写回文件**。

**分为三层。** `registry.ts` 是内存里的两张表与全部读写规则，不碰上下文、不碰文件；`store.ts` 读写 `settings.json`；`index.ts` 是继承 cordis `Service` 的服务，负责认出调用方、登记命令、安排写文件：

{/* ref file="../plugins/settings/src/registry.ts" lines="4-4" */}

**服务按调用方条目定分区。** `define`、`get`、`set`、`delete` 只收短的 `key`；服务从调用方 fiber 上 loader 放的条目取条目 id 与包名，分区名是条目 id 的末段（`home:logger` 的分区是 `logger`），插件报不出别人的身份：

{/* ref file="../plugins/settings/src/index.ts" lines="143-153" */}

**`get` 的查找顺序**：调用方声明过这一项，回存下的值，没有值回 `default`；没声明过，去公共区 `*` 找；都没有回 `undefined` 并写 warn。`set`、`delete` 只能动调用方自己声明过的项，没声明就抛错——写一项谁也不认识的设置进文件，出了问题没人查得到：

{/* ref file="../plugins/settings/src/registry.ts" lines="245-260" */}

**声明写进文件，插件加载着时以代码为准。** `define` 把 `title`、`type`、`description` 写进值表（值不动），插件停用后界面上仍看得到这一项；同一个条目重复声明同一个键，后声明的生效并写 warn；注销函数只删自己那份：

{/* ref file="../plugins/settings/src/registry.ts" lines="229-243" */}

**分区记着归哪个包。** 第一次 `define` 时分区没有归属就记成调用方的包名，归别的包就抛错，报错写明两种处理办法（给条目换 id，或确认是同一个插件改了包名、调 `plugin-manager.transfer-owner`）：

{/* ref file="../plugins/settings/src/registry.ts" lines="188-197" */}

**`settings.all` 不回 secret 项的值**：secret 行摘掉 `value` 与 `default`，补上 `secret: true`、`isSet`，设过值时再带定长掩码 `••••`；`settings.get` 与服务的 `get` 照旧回明文（轨迹卡[凭据掩码](/trajectory/2026-09-20-secret-mask)）：

{/* ref file="../plugins/settings/src/registry.ts" lines="115-121" */}

**读文件在构造函数里同步做完。** `Service` 构造一返回就提供了服务，别的插件随即可能加载并调同步的 `get`；异步读的话那一刻表还是空的：

{/* ref file="../plugins/settings/src/index.ts" lines="81-91" */}

**写文件**：整份替换，先写同目录的临时文件（名字带随机后缀）再改名；同一个文件的写入按发起顺序排队，内容在发起时就序列化好（轨迹卡[写入排队](/trajectory/2026-09-24-serialize-file-writes)）。同一轮里的多次 `define` 合并成一次写文件，否则每个插件加载时各写一次；合并写入还没开始时有别的写入，那次合并写入取消，因为每次写的都是整张表。写失败先写 warn 再把异常抛给调用方，日志里只写「哪一项已写、已删」，不写值：

{/* ref file="../plugins/settings/src/index.ts" lines="217-243" */}

**四条命令**：`settings.all`、`settings.get`、`settings.set`、`settings.delete`，按 `{ section, key }` 定位，不认调用方身份——页面不是插件，没有身份可取。命令总线是可选的，局部注入，没有它服务照样完整：

{/* ref file="../plugins/settings/src/index.ts" lines="101-135" */}

**条目没写 id 时提醒**：`define` 时发现条目 id 是 loader 生成的 8 位十六进制随机串，写一条 warn——这种 id 每次启动都变，设置重启后就对不上了。

**带一份说明书 `gwb-settings`**，放在包根 `skills/gwb-settings/`，讲四条命令的参数、分区是什么、secret 项怎么取值。

## 不知道什么

**不校验值的类型。** `type` 只用来给界面挑控件，读的一方自己判断值对不对；`settings.set` 写的位置有没有插件声明过也不查。

**不加密、不是安全边界。** 文件里 secret 项也是明文；名字校验只防误写（名字里带斜杠、条目占用公共区），插件本来就能直接改这个文件。

**不知道界面长什么样。** 编辑设置的界面在别的仓，经四条命令读写。

**不收 `cordis.yml` 里条目的 `config`。** 插件的配置一律经 `define` 声明。

**没有跨 home 的设置。** 一个 home 一份 `settings.json`，要共享就复制文件。

**不删分区。** 条目删掉后它的设置留在文件里，由调 `settings.delete` 的一方清理。

**算分区名的那段逻辑与数据插件各有一份**（`entrySection` 与 `entryDirName`），两份靠约定保持一致，见[条目身份](/docs/seams/entry-identity)。

## 提供的接口

| 接口 | 做什么 | 契约在 |
| --- | --- | --- |
| 服务 `ctx.gwbSettings` 的 `define(def)`、`get(key)`、`set(key, value)`、`delete(key)` | 声明一项；同步读；写并写入文件；抹掉值（声明还在，`get` 回到 `default`） | [5 设置](/docs/seams/settings) |
| 服务 `ctx.gwbSettings` 的 `owners()`、`transferOwner(id, pkg)` | 各分区归哪个包；把一个分区改归另一个包 | [7 数据归属](/docs/seams/owners) |

| 说明书 `gwb-settings` | 包根 `skills/gwb-settings/` | [4 说明书](/docs/seams/skills) |

| 接口 | 用来做什么 | 生产实现 | 测试实现 |

## 怎么单独测

五个测试文件，都在 `plugins/settings/tests/`：

**`registry.test.ts` 测内存里的全部规则**：直接调 `createRegistry`，warn 传 `vi.fn()`，几个调用方身份是写死的对象，不碰文件：

{/* ref file="../plugins/settings/tests/registry.test.ts" lines="4-14" */}

证明的是：`get` 的查找顺序与公共区；同一个包的两条条目各存各的；重复声明后声明的生效并告警、注销只删自己那份；名字与条目 id 不合规在动表之前抛错；代码里的声明覆盖文件里的元信息、插件停了标成不 `live`；文件内容坏了只丢那一项；归属的记录、拒绝与转移，公共区不能转移；secret 行的掩码与明文读法。

**`paths.test.ts`** 测设置名、分区名、条目 id 转分区名、随机 id 的判断；**`store.test.ts`** 在临时目录里测文件的两半（`$owners` 与各分区）读写，以及同一个文件同时写好几次时最后发起的那次留在文件里。

**`service.test.ts` 测服务这一层**：真 cordis 上下文，内核、命令总线、说明书用替身，调用方插件在 `apply` 里往自己的 fiber 上放一个 `entry`：

{/* ref file="../plugins/settings/tests/service.test.ts" lines="54-67" */}

证明的是：构造时同步读完文件，调用方 `apply` 里第一次 `get` 就读得到；`define` 之后合并写一次文件；`define` 之后马上 `set` 不报错；写删没声明过的项抛错；随机 id 写 warn；调用方卸载后它的项不再 `live`；取不到身份时抛错；写失败先 warn 再抛；四条命令的登记、回执与参数报错。

**`artifact.test.ts`** 查构建产物：相对 import 带 `.js`，包名 import 只有 node 内置模块与 `cordis`。

loader 真的把调用方自己那条条目放在 fiber 上，只能在隔离 home 里验证。
