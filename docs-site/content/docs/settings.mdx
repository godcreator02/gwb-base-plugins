**本页回答**：设置插件有哪些功能；插件、页面和 agent 经哪些接口用它，各属于哪条接缝；值写在哪、怎么分区、读的时候按什么顺序找；它依赖什么、缺了会怎样；哪些事常被以为归它、其实不归它。包名 `@godcreator/gwb-settings`，源码目录 `plugins/settings/src`，入口文件 `index.ts`。

插件声明「我有一项叫 `level` 的设置，标题是这个、类型是那个」，值写到哪由设置插件决定。一个 home 的全部设置在 `<home>/settings.json` 一份文件里，和 `cordis.yml` 在同一个目录。

## 功能

- **插件声明设置项**：给 `key`（kebab-case）、`title`、`type`，可选 `shared`、`description`、`default`；插件卸载时声明自动撤销
- **按条目分区**：值写在调用方条目 id 的末段那个分区里，同一个包的两条条目各存各的；`shared: true` 的项写进公共区 `*`
- **认得出调用方**：服务从调用方的上下文里认出条目，插件只能读写自己声明的项，报不出别人的身份
- **读的顺序**：调用方声明过这一项，回它的值，没有值回 `default`；没声明过，去公共区 `*` 找——一个插件把 token 声明进公共区，别的插件不用声明就读得到；都没有回 `undefined` 并写一条 warn
- **只写自己声明过的项**：`set`、`delete` 没声明就抛错——写一项谁也不认识的设置进文件，出了问题没人查得到
- **页面与 agent 用命令读写**：四条命令按「分区 + 键」定位，不认调用方身份
- **列出全部设置时不给 secret 项的值**：`settings.all` 里 secret 项只说设没设过，带定长掩码；要值按位置用 `settings.get` 取，回明文（轨迹卡[凭据掩码](/trajectory/2026-09-20-secret-mask)）
- **分区记着归哪个包**：文件顶层的 `$owners` 记每个分区归哪个包，包名对不上的声明直接抛错；插件管理经 `owners`、`transferOwner` 列出和改写归属
- **声明写进文件，加载着时以代码为准**：`title`、`type`、`description` 写进 `settings.json`，插件停用后界面上仍看得到这一项；插件加载着时以代码里的声明为准，值不动。同一个条目重复声明同一个键，后声明的生效并写 warn
- **读文件在构造函数里同步做完**：`Service` 在构造时就提供了服务，构造一返回，别的插件就可能加载并调用同步的 `get`；异步读的话那一刻表还是空的
- **写入是原子的**：先写同目录的临时文件再改名，临时文件名带随机后缀；同一个文件的多次写入按发起顺序一次一个，后发起的那次最后写进文件（轨迹卡[写入排队](/trajectory/2026-09-24-serialize-file-writes)）；写失败写一条 warn、异常照样抛给调用方。同一轮里的多次 `define` 合并成一次写文件，否则每个插件加载时各写一次；合并写入还没开始时有别的写入，那次合并写入取消，因为每次写的都是整张表
- **值不写进日志**：日志里只有「哪一项已写、已删」
- **条目没写 id 时提醒**：声明时发现条目 id 是 loader 生成的随机串，写一条 warn
- **带一份说明书 `gwb-settings`**：给 agent 讲四条命令的参数、分区是什么、secret 项怎么取值

## 接口

每条接缝上交换什么、各方保证什么，写在接缝页；本节只列设置插件提供了哪些接口。

<Diagram name="settings-layout" title="settings.json 按条目分区，服务与命令各读写哪一块">
- 右边是 `<home>/settings.json` 的顶层：`$owners`（分区名 → 包名）、每条条目一个分区（条目 `home:mcp` 的分区叫 `mcp`）、公共区 `*`
- 插件经服务 `ctx.gwbSettings` 的 `define` / `get` / `set` / `delete` 只给 `key`，分区由设置插件从调用方条目算出
- 别的插件 `get` 一项自己没声明的设置时读公共区，`shared: true` 的项在那里
- 页面与 agent 经 `settings.all` / `get` / `set` / `delete` 四条命令按 `{ section, key }` 读写任意分区；`settings.all` 里 secret 项只给 `isSet` 与掩码，`settings.get` 回明文
</Diagram>

| 接口 | 做什么 | 接缝 |
| --- | --- | --- |
| 服务 `ctx.gwbSettings` 的 `define(def)`、`get(key)`、`set(key, value)`、`delete(key)` | 声明一项；同步读；写并写入文件；抹掉值（声明还在，`get` 回到 `default`） | [5 设置](/docs/seams/settings) |
| 服务 `ctx.gwbSettings` 的 `owners()`、`transferOwner(id, pkg)` | 各分区归哪个包；把一个分区改归另一个包 | [7 数据归属](/docs/seams/owners) |
| 命令 `settings.all` | 无参数，返回全部设置项，每行带 `section`、`key`、`title`、`type`、`description`、`value`、`live`（此刻还有插件声明它吗）、`default`（只有 `live` 的项带）；secret 项不带 `value` 与 `default`，改带 `secret: true`、`isSet`，设过值时再带定长掩码 `mask: '••••'` | [5 设置](/docs/seams/settings) |
| 命令 `settings.get`、`settings.set`、`settings.delete` | 参数 `{ section, key }`，`set` 另加 `value`；`get` 对 secret 项也回明文，没设过回 `undefined`，不回落到 `default` | [5 设置](/docs/seams/settings) |
| 文件 `<home>/settings.json` | 顶层 `$owners`（分区名 → 包名），其余每个键是一个分区：条目 id 的末段，或公共区 `*`；分区下是设置名 → `{ title, type, description, value }` | [5 设置](/docs/seams/settings) |
| 分区名 | 调用方条目 id 的末段，`home:logger` 得 `logger`；超过两段、有段不是 kebab-case 就抛错；条目不能叫 `*` | [8 条目身份](/docs/seams/entry-identity) |
| 说明书 `gwb-settings` | 包根 `skills/gwb-settings/`，交给说明书插件登记 | [4 说明书](/docs/seams/skills) |

声明一项：

```ts
export const inject = ['gwbSettings']

export function apply(ctx: GwbContext) {
  ctx.gwbSettings.define({ key: 'level', title: '日志级别', type: 'string', default: 'info' })
  const level = ctx.gwbSettings.get('level')
}
```

插件的配置一律用 `define` 声明，不收 `cordis.yml` 里条目的 `config`。

## 依赖

| 依赖 | 用来做什么 | 缺了会怎样 |
| --- | --- | --- |
| 内核服务 `gwbKernel` 的 `dataDir`（内核仓 gwb-kernel；不写进 `inject`，经 `src/vocab.ts` 里的 `requireKernel` 取） | 算出 `<home>/settings.json` | 构造时抛错「ctx.gwbKernel 不在」，插件加载失败 |
| 命令插件服务 `gwbCommands`（局部注入，[gwb-commands](/docs/commands)） | 登记四条命令 | 服务照常提供，别的插件照样读写；页面与 agent 调不到设置 |
| 说明书插件服务 `gwbSkills`（局部注入，[gwb-skills](/docs/skills)） | 登记自带的说明书 | 不登记说明书，设置插件照常加载 |
| cordis 的 `Service`（peer，`^4.0.0-rc.10`） | 提供服务；方法里的 `this.ctx` 是调用方的上下文 | 无法加载；必须和内核用同一份 cordis |
| loader 放在调用方 fiber 上的 `entry`（`id`、`options.name`，[8 条目身份](/docs/seams/entry-identity)） | 认出调用方的条目 id 与包名 | 不是经 `cordis.yml` 加载的插件调用时抛错「取不到调用方的身份」 |
| 词汇表包 `@godcreator/gwb-plugin-api`（dev，`^0.4.1`） | `GwbContext`、`GwbKernelApi` 的类型 | 只在编译时用 |
| 内核包 `@godcreator/gwb-kernel-desktop`（peer，`^0.4.1`） | 声明兼容哪些内核 | — |

`@godcreator/gwb-commands`、`@godcreator/gwb-skills` 写在 dev 里（`workspace:*`）：代码只 `import type {}` 它们，构建产物里没有它们；这两个插件对设置插件都是可有可无的，只局部注入。

设置插件和[数据插件](/docs/data)用同一个办法从条目 id 算名字：两边各有一份十几行的算法（`entrySection` 与 `entryDirName`），必须给出同一个答案，改一处就要改另一处（见[条目身份](/docs/seams/entry-identity)）。

## 不做的事

- **没有跨 home 的设置**：一个 home 一份 `settings.json`，要在几个 home 之间共享就复制文件
- **不做运行时类型校验**：`type` 只给界面挑控件，读的一方自己判断值对不对（[gwb-mcp](/docs/mcp) 的端口设置就是这样）
- **不加密**：文件里是明文；`settings.all` 不回 secret 项的值，`settings.get` 与服务的 `get` 照旧回明文
- **命令不认身份**：四条命令按分区与键定位，能读写任何分区；服务按调用方身份分区
- **不是安全边界**：名字校验只防误写，插件本来就能直接改这个文件
- **不画设置界面**：界面由别的插件用这四条命令做
- **不写数据文件**：插件的其他数据在 [gwb-data](/docs/data)
- **不删分区**：条目删掉后它的设置留在文件里，由调用 `settings.delete` 的一方清理
