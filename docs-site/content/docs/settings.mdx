**本页回答**：设置插件有哪些功能；插件、页面和 agent 经哪些接口用它，各属于哪条接缝；值写在哪、怎么分区、读的时候按什么顺序找；它依赖什么、缺了会怎样；哪些事常被以为归它、其实不归它。包名 `@godcreator/gwb-settings`，源码目录 `plugins/settings/src`，入口文件 `index.ts`。

插件声明「我有一项叫 `level` 的设置，标题是这个、类型是那个」，值写到哪由设置插件决定。一个 home 的全部设置在 `<home>/settings.json` 一份文件里，和 `cordis.yml` 在同一个目录；没有跨 home 的设置，要共享就复制文件。

## 功能

- **插件声明设置项**：给 `key`（kebab-case）、`title`、`type`，可选 `shared`、`description`、`default`；插件卸载时声明自动撤销
- **按条目分区**：值写在调用方条目 id 的末段那个分区里，同一个包的两条条目各存各的；`shared: true` 的项写进公共区 `*`
- **认得出调用方**：服务从调用方的上下文里认出条目，插件只能读写自己声明的项
- **凭据跨插件共享**：插件读一项自己没声明的设置时，去公共区找；一个插件把 token 声明进公共区，别的插件不用声明就读得到
- **页面与 agent 用命令读写**：四条命令按「分区 + 键」定位，不认调用方身份
- **列出全部设置时不给 secret 项的值**：`settings.all` 里 secret 项只说设没设过；要值按位置用 `settings.get` 取，回明文
- **分区记着归哪个包**：文件顶层的 `$owners` 记每个分区归哪个包，包名对不上的声明直接抛错；插件管理经 `owners`、`transferOwner` 列出和改写归属
- **写入是原子的**：先写同目录的临时文件再改名；写失败写一条 warn、异常照抛
- **声明写进文件**：`title`、`type`、`description` 写进 `settings.json`，插件停用后界面上仍看得到这一项；插件加载着时以代码里的声明为准
- **条目没写 id 时提醒**：声明时发现条目 id 是 loader 生成的随机串，写一条 warn
- **带一份说明书 `gwb-settings`**：给 agent 讲四条命令的参数、分区是什么、secret 项怎么取值

## 接口

每条接缝上交换什么、各方保证什么，写在接缝页；本节只列设置插件提供了哪些接口、定义在哪里。

| 接口 | 做什么 | 接缝 |
| --- | --- | --- |
| 服务 `ctx.gwbSettings` 的 `define(def)`、`get(key)`、`set(key, value)`、`delete(key)` | 声明一项；同步读；写并写入文件；抹掉值（声明还在，`get` 回到 `default`）；类型 `GwbSettingsApi`、`SettingDef` 由本包导出 | [5 设置](/docs/seams/settings) |
| 服务 `ctx.gwbSettings` 的 `owners()`、`transferOwner(id, pkg)` | 各分区归哪个包；把一个分区改归另一个包 | [7 数据归属](/docs/seams/owners) |
| 命令 `settings.all` | 无参数，返回全部设置项，每行带 `section`、`key`、`title`、`type`、`description`、`value`、`live`（此刻还有插件声明它吗）、`default`（只有 `live` 的项带）；secret 项不带 `value` 与 `default`，改带 `secret: true`、`isSet`，设过值时再带定长掩码 `mask: '••••'` | [1 命令总线](/docs/seams/bus) |
| 命令 `settings.get`、`settings.set`、`settings.delete` | 参数 `{ section, key }`，`set` 另加 `value`；`get` 对 secret 项也回明文 | [1 命令总线](/docs/seams/bus) |
| 文件 `<home>/settings.json` | 顶层 `$owners`（分区名 → 包名），其余每个键是一个分区：条目 id 的末段，或公共区 `*`；分区下是设置名 → `{ title, type, description, value }` | [5 设置](/docs/seams/settings) |
| 分区名 | 调用方条目 id 的末段，`home:logger` 得 `logger`；超过两段、有段不是 kebab-case 就抛错；条目不能叫 `*` | [8 条目身份](/docs/seams/entry-identity) |
| 说明书 `gwb-settings` | 包根 `skills/gwb-settings/`，交给说明书插件登记 | [4 说明书](/docs/seams/skills) |

声明一项：

```ts
export const inject = ['gwbSettings']

export function apply(ctx: GwbContext) {
  ctx.gwbSettings.define({ key: 'level', title: '日志级别', type: 'string', default: 'info' })
  const level = ctx.gwbSettings.get('level')
}
```

插件的配置一律用 `define` 声明，不收 `cordis.yml` 里条目的 `config`。

### 读与写的规则

- **`get(key)`**：调用方声明过这一项，回它的值，没有值回 `default`；没声明过，去公共区 `*` 找；都没有回 `undefined` 并写一条 warn
- **`set`、`delete`**：只能动调用方自己声明过的项，没声明就抛错；写一项谁也不认识的设置进文件，出了问题没人查得到
- **同一个条目重复声明同一个键**：后声明的生效，写一条告警
- **`type` 只给界面选控件**：`string`、`number`、`boolean`、`secret`、`string-list`；设置插件不做运行时校验，读的一方自己判断值对不对（[gwb-mcp](/docs/mcp) 的端口设置就是这样）
- **值不写进日志**：日志里只有「哪一项已写、已删」

**同一个条目 id、不同的包**：分区名只取条目 id 的末段，而插件管理生成默认 id 时去掉了 scope，`@a/gwb-foo` 与 `@b/foo` 都叫 `foo`；条目删掉后设置留在文件里。所以 `define` 时核对 `$owners`：分区没有归属就归调用方，归别的包就抛错，错误里写明两种处理办法：给条目换个 id，或确认是同一个插件改了包名、走 `plugin-manager.transfer-owner`。

**`settings.all` 与 `settings.get` 为什么不一样**：`settings.all` 一次把整个 home 的设置交给调用方（界面、经 MCP 入口调命令的 agent），它要知道的只是「这一项配没配」，所以 secret 项不回值；`settings.get` 是调用方已经知道要哪一项，照旧回明文。别的插件读另一个插件分区里的凭据就走这条：[gwb-plugin-sources](/docs/plugin-sources) 经 `settings.get` 读 `gitea` 分区的 `base-url` 与 `token`。文件里的值是明文。

**读文件在构造函数里同步做完**：`Service` 在构造时就提供了服务，构造一返回，别的插件就可能加载并调用同步的 `get`；异步读的话那一刻表还是空的。

## 依赖

| 依赖 | 用来做什么 | 缺了会怎样 |
| --- | --- | --- |
| 内核服务 `gwbKernel` 的 `dataDir`（内核仓 gwb-kernel；不写进 `inject`，经 `src/vocab.ts` 里的 `requireKernel` 取） | 算出 `<home>/settings.json` | 构造时抛错「ctx.gwbKernel 不在」，插件加载失败 |
| 命令插件的服务 `gwbCommands`（局部注入，[gwb-commands](/docs/commands)） | 登记四条命令 | 服务照常提供，别的插件照样读写；页面与 agent 调不到设置 |
| 说明书插件的服务 `gwbSkills`（局部注入，[gwb-skills](/docs/skills)） | 登记自带的说明书 | 不登记说明书，设置插件照常加载 |
| cordis 的 `Service`（peer，`^4.0.0-rc.9`） | 提供服务；方法里的 `this.ctx` 是调用方的上下文 | 无法加载；必须和内核用同一份 cordis |
| loader 在调用方上下文上加的 `fiber.entry`（`id`、`options.name`） | 认出调用方的条目 id 与包名 | 不是经 `cordis.yml` 加载的插件调用时抛错「取不到调用方的身份」 |
| 词汇表包 `@godcreator/gwb-plugin-api`（peer） | `GwbContext` 的类型 | 只在编译时用 |

`@godcreator/gwb-commands`、`@godcreator/gwb-skills` 写在 devDependencies 里：代码只 `import type {}` 它们；命令对设置插件是可有可无的，写成 peer 会强制把命令插件装进 home。

设置插件和[数据插件](/docs/data)用同一个办法从条目 id 算名字：两边各有一份十几行的算法（`entrySection` 与 `entryDirName`），必须给出同一个答案，改一处就要改另一处。

## 不做的事

- **没有跨 home 的设置**：一个 home 一份 `settings.json`，要在几个 home 之间共享就复制文件
- **不做运行时类型校验**：`type` 只给界面选控件
- **不加密**：文件里是明文；`settings.all` 不回 secret 项的值，`settings.get` 与服务的 `get` 照旧回明文
- **命令不认身份**：四条命令按分区与键定位，能读写任何分区；服务按调用方身份分区
- **不画设置界面**：界面由界面插件用这四条命令做
- **不写数据文件**：插件的其他数据在 [gwb-data](/docs/data)
- **不删分区**：条目删掉后它的设置留在文件里，由调用 `settings.delete` 的一方清理
