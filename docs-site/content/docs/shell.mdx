# gwb-shell

包名 `@godcreator02/gwb-shell`，服务 `ctx.gwbShell`。它有两半：

- **node 半**——窗格注册服务，件在自己的 `apply` 里说「我有一格窗格」
- **浏览器半**——一口 dockview 窗格井，把注册表里的每一格开出来

分四刀做，**眼下到第三刀半**：井开得出格了、一个件能有好几格、同一格能开好几份；
导航、状态栏、布局落盘还没有。四刀各是什么、到哪了，见[路线](/docs/roadmap)。

## 怎么用

**注册窗格、报自己的名字**（在你的件里）：

```ts
export const inject = ['gwbShell']

export function apply(ctx: GwbContext) {
  ctx.gwbShell.registerPane({ id: 'main', title: '我这一格', icon: 'flask-conical' })
  // 声明了 duplicable 的格才开得出第二份
  ctx.gwbShell.registerPane({ id: 'doc', title: '文档', duplicable: true })
  ctx.gwbShell.describeSelf({ title: '我这个件', icon: 'box' })
}
```

一个件想有几格就注册几格。`icon` 是 [lucide](https://lucide.dev) 的图标名，kebab-case，
可以不给——画它是第四刀导航的事，这一刀只原样收下。

**`duplicable` 不写就是「我只能有一份」**。默认单份是因为代价不对称：一个没想过多实例
的件被开两份可能状态打架（它可能用了模块级单例），而默认单份的代价只是想多份的件多写
一个字段。第四刀的导航也要靠它决定「点一下是聚焦还是新开」。

**给人看的名字归运行时**（`describeSelf`），不进包清单。包清单里那种没人读的字段死掉时
没有任何机制会发现——`gwb.title` 就这么放了一阵，四个包声明着、零处读、两仓文档站一句
没提。如今包清单里只剩 `gwb.shell` 与 `gwb.shared` 两个字段有人读。

**跟 `gwb-cli` 的 `register` 不一样，这两个都不用自己包 `ctx.effect`**：件卸载时表上
那几条自动摘掉。它们仍然回注销函数，那是给要提前摘的场景。

**从界面取表**（在你的 client 束里），两张各取各的：

```js
await args.host.call('shell.panes')
// { ok: true, data: [{ id, title, icon?, duplicable?, entryId, pkg }, …] }
await args.host.call('shell.plugins')
// { ok: true, data: [{ title, icon?, entryId, pkg }, …] }
```

**两张表不合并**：那张的键是 `(entryId, 窗格 id)`、一条条目可以有好几条；这张的键就是
`entryId`、一条条目至多一条。消费方也不同（井里开格吃前者，导航列件名吃后者）。

## 身份不由件自己报

`registerPane` 只收 `{ id, title, icon?, duplicable? }`，`describeSelf` 只收
`{ title, icon? }`。`pkg` 与 `entryId` 由服务从**调用方的 fiber** 上取：

{/* ref file="../plugins/shell/src/index.ts" lines="91-106" */}

靠的是 cordis `Service` 的机制——方法里的 `this.ctx` 是消费者的 ctx，不是提供方的
（`gwb-data` 的 `owner()` 是同一个套路）。件报不出名字，也就没法冒充别人的窗格。

这一点实机验时有过直接证据：`shell.panes` 的回执里 `entryId` 是 hello 的
（`home:hello`）而不是 shell 自己的。`registerPane` 挂在 `this.ctx.effect` 上的自动
收尾，靠的正是这同一点。

**两样都要，不是只要包名**：同一个包挂两条条目是两份独立配置的实例，只有 `entryId`
分得开它们。

## 定义与实例是两回事

|  | 是什么 | 谁产出 |
| --- | --- | --- |
| 窗格**定义** | 注册表里一条，件说「我有这么一格」 | `pane-registry` |
| 窗格**实例** | 井里一个 panel，声明了 `duplicable` 就能有好几份 | `uniquePanelId` |

这两个概念一开始是同一个东西——`panelIdOf(entryId, paneId)` 是纯函数，同一格必然拼出
同一个 id。而 dockview 的 `addPanel` 撞 id 是**同步抛 Error**，所以「开第二份」这件事
在拼 id 这一层就被堵死了。

分家之后 `panelIdOf` 的身份是**基名**，实例 id 由 `uniquePanelId` 算：

- 第一份的 id **就是基名**，跟只能开一份的那些格长得一模一样——落盘的东西因此不受影响
- 第二份起追 `:2` / `:3`。分隔用 `:` 不用 `#`（`#` 在 CSS 里是 id 选择器）
- 查的是**当下井里真有哪些**，不是任何一个计数器。所以第四刀恢复落盘布局之后再开新格
  也不会撞
- 序号跟 id 一起回，**不让调用方从 id 里拆**——标题要追的「(2)」得有个正当来源，而反解
  id 正是这一族函数反复禁的事

## 窗格 id 是个不透明的键

`plugin:<entryId>:<窗格 id>`。实机长这样：**`plugin:home:hello:main`**——四段，
因为 loader 把件的条目挂在 include 那条下面，`entryId` 自带 `home:` 前缀。

那个前缀不能去掉，理由见[撞过的墙](/docs/walls)。要 `entryId` 或 `paneId` 就从面板的
`params` 里取,那儿本来就分开存着,从来不必反解。

**窗格 id 里不许有 `:`**——注册那一步就拒了。`entryId` 自己带冒号，窗格 id 里再有一个的
话，两组不同的「条目 × 窗格」能拼出同一个基名，而查重会把它当成「已经开着」静默追个
`:2` 上去。人看到的是自己的窗格标题莫名多了个「(2)」，源头却在另一个件的注册参数里。

## 为什么硬 inject 命令总线

注册发生在 node 半，而排窗格的是浏览器半——表得过桥。而内核的 `dispatch` 除
`kernel.info` 与 `kernel.install` 两条自省命令外**全部走 `ctx.gwbCli`**，内核本体
不认识任何件的命令名。

所以只有一条路：shell 自己注册一条 `shell.panes`。没有命令总线，注册表出不了这个
进程，外壳就是个开不出任何东西的空井——那种时候不如不挂，cordis 会在日志里明说
它在等谁。

「内核的 `kernel.info` 顺手把窗格表带上」过不了准入判据第一关（内核零 UI 知识）。

## 运行时注册让 openable 瘦了一圈

母仓那份 `openable` 吃的是「条目表 × **包声明的** `gwb.panes`」，这份吃的是注册表
快照。三样东西一起消失了：

- **没有 join**——`pkg` 与 `entryId` 注册时就填好了
- **没有过滤**——禁用的件根本没跑 `apply`、注册不进来；卸掉的件 effect 收尾时自己摘。
  「在表里」就等于「该开得出来」，`!disabled && !shell` 那两条判断连同它们会出的错
  一起没了
- **没有 `canonicalPanelId`**——母仓那个函数整个是老布局兼容（盘上的格 id 少一段），
  这条线没有那份历史

## 浏览器半：井与一格

`bootShell` 拿到内核给的 `{ host, home, entries }`，占住整页那个根：注三张表 → 取一次
注册表 → 渲染 dockview → 把每一格开出来。**眼下没有导航、没有状态栏、布局不落盘**，
所以默认布局就是「表里有几格开几格」，全落在一个 group 里当兄弟 tab，没有「上次摆成
什么样」要恢复。

一格窗格由 `PluginPane` 承载，它是 `mountPane` 契约的外壳这一侧：

```
注件的样式表 → 等它真到位 → 动态 import client 束
→ mountPane({ host, shell, pane }, 容器) → 收下 dispose
```

**样式与模块在同一个 effect 里**：件的表要先注、而且要等它真到位再 import，这两件事是
一条时序上的承诺；拆成两个 effect 就只剩「谁先跑」这种靠排列顺序的默契。格间总线的句柄
也在这条 effect 里取、清理时松手。**拿不到 `dispose` 就报契约不符**，不装作成功——那条
路上关格时清不掉，让写件的人当场看见。

## 窗格件拿到的 args

这是**窗格件契约的正本**（内核只定 `bootShell`，`mountPane` 的 args 由外壳定）：

```ts
mountPane({ host, shell, pane }, container) => { dispose() }
```

| | 是什么 |
| --- | --- |
| `host.call(command, args?)` | 命令通道，走到宿主分发再原路回 |
| `shell.openPane(paneId, { duplicate? })` | 打开**本件**的另一格 |
| `shell.bus` | 格间小总线，`emit(type, detail?)` 与 `on(type, fn)` 回注销函数 |
| `pane.id` | 这一格是本件的哪一格（注册时给的那个 id） |
| `pane.instance` | 这**一份**的唯一键。开两份时两份的这个值不一样 |

**只开得了自己那几格**：`entryId` 由 `PluginPane` 造这个对象时闭包绑定，件报不出别人的
条目——跟 `registerPane` 不收身份是同一条理由。

`openPane` 的行为：已经开着就聚焦；`duplicate: true` **而且**那格声明过 `duplicable`
才再开一份；要多份但没声明就退回聚焦、外加一条 console 警告（不静默也不抛）；认不出
`paneId` 什么都不做，但话里带得出是谁要开什么。

判断全在 `planOpen` 那个纯函数里，接线那侧只剩「按 kind 分派」——那四条分支**有两条
实机点不出来**（要多份而没声明那条，得专门写一个错的件才走得到）。

**表现取不用快照**：件是热挂载的，后挂上的件在快照里没有自己。取表是一次本地 IPC，
而调用方全是 click 回调、没人等返回值。

**总线的桶按条目分**，所以同一条条目的几格——含同一格的两份——在同一个桶里。一格松手时
自己挂的听众要摘干净，理由见[撞过的墙](/docs/walls)。

**重复那份开在右边一个新 group**：不给 `position` 的话它落进当前 group 当兄弟 tab，
一开就把第一份盖住，而「两份同屏」正是多实例唯一能眼见为实的地方。

**样式表注过就不摘**：同一个件开几格没必要注几条，而摘它需要引用计数，计数错了的症状是
「关掉一格，另一格的样式跟着没了」——静默，且要两格同开才复现。留着的代价只是内存里
一份 CSSOM。

## 状态栏

井底下那条，**它是唯一不进窗格系统的东西**——也正因如此它兜得住「窗格全关光了怎么办」。
布局是两行：井 `flex-1 min-h-0`，状态栏 `flex-none`。

**`min-h-0` 少不了**：flex 子项默认 `min-height: auto`，井里内容一高就把状态栏挤出屏幕。

三格：

| 项 | 干什么 |
| --- | --- |
| **＋ 可开窗格** | 点开列出注册表里所有格，选一个就开 |
| **home** | 一眼看出自己在哪个 home 里，开测试 home 时不用翻日志 |
| **亮暗** | 切 `html.dark`，令牌整套跟着换 |

**＋列表走跟件调 `openPane` 同一个 `planOpen`**，所以行为一致：已经开着的点了是聚焦，
声明了 `duplicable` 的行尾多一个「＋一份」。**已开的那条不 disable**——点它是聚焦，
那是个有用的动作，标一下就够。

判断与副作用继续分开：`planOpen` 出判断，`applyPlan` 落成动作，两个入口（件调的
`openOwnPane`、状态栏调的 `openSpec`）共用后者。

### 菜单的 portal 必须挂回外壳的根

件的样式表整张 scope 在 `[data-gwb-plugin="…"]` 之下，而 radix 的 Portal 默认挂 `body`
——挂出去之后菜单一个类名都不生效。所以 `shadcn add` 拉下来的 `dropdown-menu.tsx`
**本仓改过一处**：给 `DropdownMenuContent` 加了 `container`，透给 Portal。

（这跟 dockview 那张表不 scope 是同一个根因的两面：`.dv-*` 我们管不着，所以整张不 scope；
而我们自己的菜单归我们管，得让它待在 scope 里面。）

**重新 `shadcn add dropdown-menu` 会覆盖那个文件**，那时要把这段补回来——组件源码里也写着
这句。

## 两张样式表，规矩不同

| 产物 | scope | 装什么 |
| --- | --- | --- |
| `./style.css` | `:where([data-gwb-plugin="@godcreator02/gwb-shell"])` | 外壳自己 JSX 的 Tailwind 类 |
| `./dockview.css` | **一处都没有** | **裁过的** dockview 基础规则 + 我们自己那套 theme |

后者不能 scope，两个理由：它管的 `.dv-*` 类名不经我们的手，而且门户元素可能挂在
`body` 下——包进 `:where(…)` 就一条都匹配不上。产物守卫钉着这条。

### 它的 18 套主题一套都不挂

`.dockview-theme-gwb` 是**唯一真源**，不是在谁的基底上打的补丁。要它的布局与拖放，
不要它的审美——「看着不像 shadcn」的来源全在主题里，而主题跟引擎是分得开的：形状与配色
全走 CSS 变量（`.dv-tab` 自己只有一句 `flex-shrink: 0`）。

一度反对过这条，理由是「不挂基底就有 682 处 `var()` 读空」。**那个理由不成立**：读空的
前提是我们没定义，而这条路要做的正是全定义。量下来裁剩的基础规则引用 **54 个**不同变量，
`dockview-theme.css` 定义了 71 个（多出来的是企业模块那批，全定义好过维护例外清单）。

### 因此原表能裁掉三分之二

`build.ts` 用 postcss 解析原表，**凡是选择器带 `.dockview-` 的规则整条剔掉**；一条规则挂
几个选择器时只摘属于他们的那几个。实测原表 154,125 字节裁到 50,686，**省 103,439**；
拼上我们那套 theme 之后产物是 59,422。

被裁的不只是 18 套配色，还有 `.dockview-spaced` 这个 modifier——圆角与间距的落地规则原本
住在那儿，所以我们那张 theme 表把用得上的**复刻了一份**（眼下圆角全 0，那几条空转着，
但「圆角怎么落地」这件事的实现在，将来想加只要改一个变量）。

**这跟第三刀写的「原表整张带上一行不裁」是同一条判据的两个结果，不是翻案**。那条的理由
是「基础规则与主题规则交错着，裁错一条的症状是某个交互没样式」——**当时成立**：那时挂着
它的 `dockview-theme-light`，没有可靠的切分依据。现在一个内置主题都不用了，整类可以按
选择器整体剔除，风险从「猜」变成了「解析」。

裁表是**每次构建都在跑的代码**，写坏了两头都不报错（裁多了某处没样式，裁少了他们的主题
偷偷把我们的值盖掉），所以产物守卫钉了两条：一条 `.dockview-` 都不许剩、基础规则的字节
数得落在 50–70KB 这一档。

### 亮暗不靠换类

`--dv-*` 全接令牌，令牌跟着 `html.dark` 变，井、标签条、件里的按钮一起变，**一行都不用
重新构建**。实机逐处量过。

**一个例外：`--dv-floating-box-shadow`**。dockview 给的默认值在暗底上量出来是
`rgba(0,0,0,0.12)`，浮动组整个失去立体感。这个变量的语义**本来就跟明暗有关**（阴影就是
影子），所以表里给暗色单独一档 `.dark .dockview-theme-gwb`。

这不违反上面那条：**换的不是主题类，是我们自己这张表按 `.dark` 给不同的值**——跟令牌表
本身 `:root` / `.dark` 两套值是同一个做法。往后再发现哪个变量在暗色下不对，照这条补。

### 升级 dockview 之后要核对一次变量全集

62 个全由我们给，它新增一个我们就漏一个，而漏了是**读空、不报错**。核对方法与「为什么
不做成构建期守卫」见[撞过的墙](/docs/walls)，主题怎么交给它（挂在 `<html>` 上是没用的）
也在那儿。

## 为什么不用 dockview 自己的注册

**下一个人一定会问**：dockview 有 `components` 表，为什么还要 `pane-registry`？

因为那两样管的不是一回事。dockview 的 `components` 是「component 名 → React 组件」——
我们全部窗格都映到**同一个** `plugin` 名上；而 `pane-registry` 是「有哪几格值得存在」。

它替代不了，差的三样是根本性的：

- **跨进程**——dockview 的注册面全是同一个 JS 堆里的对象引用，没有任何可序列化的形态；
  我们的注册方在 node 进程、消费方在浏览器
- **未开也在表里**——dockview 所有枚举口（`api.panels` / `groups` / `toJSON`）**只回
  已实例化的**。`DockviewOptions` 六十多个字段里没有 `catalog` / `availablePanels` 这类
  东西
- **身份与元数据**——`title` 在它那儿是 `addPanel` 的入参、不是可查询的目录项；
  `icon` / `duplicable` / `entryId` / `pkg` 它完全没有

一句话：**dockview 管「已经决定要有这一格之后它长什么样」，`pane-registry` 管「有哪几格
值得存在」**——后者 dockview 从设计上就留给宿主。

## 撞名与说不清自己是谁

注册表本体的三条判据，都写进了测试：

1. **一条条目一个命名空间**——键是 `entryId` + 窗格 id。同一个包的两条条目各注册一格
   同名的，两条都在，这不叫撞名
2. **撞名后来者赢，但要告警**——跟命令总线一个规矩，一个仓里两套撞名规则是无谓的
   记忆负担
3. **空 id / 空 title 抛错**，不是静默忽略——撞名是「两条都说得清，该听谁」，而空 id
   是「这一格根本没说自己是谁」。让它进表只会在井里多出一格点不开的空白，而且回头
   查不到源头。注册参数是件自己写死的常量，抛在它自己的 `apply` 里、日志指名道姓，
   好查得多
