# gwb-shell

包名 `@godcreator02/gwb-shell`，服务 `ctx.gwbShell`。它有两半：

- **node 半**——窗格注册服务，件在自己的 `apply` 里说「我有一格窗格」
- **浏览器半**——多口 dockview 窗格井（**一口桌面一口、井常驻保活**），把注册表里的
  每一格开出来

分四刀做：一二三刀与状态栏都完成了；第四刀的**布局落盘**也落地——每口井自动存档、可起名
存布局、点开哪套铺哪套；**多桌面第二波（0.3.0，保活）落地**，见下文专节；只剩导航。四刀
各是什么、到哪了，见[路线](/future/roadmap)。

## 怎么用

**注册窗格、报自己的名字**（在你的件里）：

```ts
export const inject = ['gwbShell']

export function apply(ctx: GwbContext) {
  ctx.gwbShell.registerPane({ id: 'main', title: '我这一格', icon: 'flask-conical' })
  ctx.gwbShell.registerPane({ id: 'doc', title: '文档' })
  ctx.gwbShell.describeSelf({ title: '我这个件', icon: 'box' })
}
```

一个件想有几格就注册几格。`icon` 是 [lucide](https://lucide.dev) 的图标名，kebab-case，
可以不给——画它是第四刀导航的事，这一刀只原样收下。

**注册说不出「我能开几份」**（2026-09-11 起，那个 `duplicable` 布尔删掉了）：一格开几份
取决于它**装着几份不同的内容**，见[一格的身份是它装的内容](#一格的身份是它装的内容)。

**给人看的名字归运行时**（`describeSelf`），不进包清单。包清单里那种没人读的字段死掉时
没有任何机制会发现——`gwb.title` 就这么放了一阵，四个包声明着、零处读、两仓文档站一句
没提。如今包清单里只剩 `gwb.shell` 与 `gwb.shared` 两个字段有人读。

**跟 `gwb-commands` 的 `register` 不一样，这两个都不用自己包 `ctx.effect`**：件卸载时表上
那几条自动摘掉。它们仍然回注销函数，那是给要提前摘的场景。

**从界面取表**（在你的 client 束里），两张各取各的：

```js
await args.host.call('shell.panes')
// { ok: true, data: [{ id, title, icon?, client?, style?, entryId, pkg }, …] }
await args.host.call('shell.plugins')
// { ok: true, data: [{ title, icon?, entryId, pkg }, …] }
```

**两张表不合并**：那张的键是 `(entryId, 窗格 id)`、一条条目可以有好几条；这张的键就是
`entryId`、一条条目至多一条。消费方也不同（井里开格吃前者，导航列件名吃后者）。

## 身份不由件自己报

`registerPane` 只收 `{ id, title, icon?, client?, style? }`，`describeSelf` 只收
`{ title, icon? }`。`pkg` 与 `entryId` 由服务从**调用方的 fiber** 上取：

{/* ref file="../plugins/shell/src/index.ts" lines="190-205" */}

靠的是 cordis `Service` 的机制——方法里的 `this.ctx` 是消费者的 ctx，不是提供方的
（`gwb-data` 的 `owner()` 是同一个套路）。件报不出名字，也就没法冒充别人的窗格。

这一点实机验时有过直接证据：`shell.panes` 的回执里 `entryId` 是 hello 的
（`home:hello`）而不是 shell 自己的。`registerPane` 挂在 `this.ctx.effect` 上的自动
收尾，靠的正是这同一点。

**两样都要，不是只要包名**：同一个包挂两条条目是两份独立配置的实例，只有 `entryId`
分得开它们。

## 定义与实例是两回事

|  | 是什么 | 谁产出 |
| --- | --- | --- |
| 窗格**定义** | 注册表里一条，件说「我有这么一格」 | `pane-registry` |
| 窗格**实例** | 井里一个 panel，装着不同内容的可以有好几份 | `uniquePanelId` |

这两个概念一开始是同一个东西——`panelIdOf(entryId, paneId)` 是纯函数，同一格必然拼出
同一个 id。而 dockview 的 `addPanel` 撞 id 是**同步抛 Error**，所以「开第二份」这件事
在拼 id 这一层就被堵死了。

分家之后 `panelIdOf` 的身份是**基名**，实例 id 由 `uniquePanelId` 算：

- 第一份的 id **就是基名**，跟只能开一份的那些格长得一模一样——落盘的东西因此不受影响
- 第二份起追 `:2` / `:3`。分隔用 `:` 不用 `#`（`#` 在 CSS 里是 id 选择器）
- 查的是**当下井里真有哪些**，不是任何一个计数器。所以第四刀恢复落盘布局之后再开新格
  也不会撞
- 序号跟 id 一起回，**不让调用方从 id 里拆**——标题要追的「(2)」得有个正当来源，而反解
  id 正是这一族函数反复禁的事

## 窗格 id 是个不透明的键

`plugin:<entryId>:<窗格 id>`。实机长这样：**`plugin:home:hello:main`**——四段，
因为 loader 把件的条目挂在 include 那条下面，`entryId` 自带 `home:` 前缀。

那个前缀不能去掉，理由见[撞过的墙](/docs/walls)。要 `entryId` 或 `paneId` 就从面板的
`params` 里取,那儿本来就分开存着,从来不必反解。

**窗格 id 里不许有 `:`**——注册那一步就拒了。`entryId` 自己带冒号，窗格 id 里再有一个的
话，两组不同的「条目 × 窗格」能拼出同一个基名，而查重会把它当成「已经开着」静默追个
`:2` 上去。人看到的是自己的窗格标题莫名多了个「(2)」，源头却在另一个件的注册参数里。

## 为什么硬 inject 命令总线

注册发生在 node 半，而排窗格的是浏览器半——表得过桥。而内核的 `dispatch` 除
`kernel.info` 与 `kernel.install` 两条自省命令外**全部走 `ctx.gwbCommands`**，内核本体
不认识任何件的命令名。

所以只有一条路：shell 自己注册一条 `shell.panes`。没有命令总线，注册表出不了这个
进程，外壳就是个开不出任何东西的空井——那种时候不如不挂，cordis 会在日志里明说
它在等谁。

「内核的 `kernel.info` 顺手把窗格表带上」过不了准入判据第一关（内核零 UI 知识）。

## 运行时注册让 openable 瘦了一圈

母仓那份 `openable` 吃的是「条目表 × **包声明的** `gwb.panes`」，这份吃的是注册表
快照。三样东西一起消失了：

- **没有 join**——`pkg` 与 `entryId` 注册时就填好了
- **没有过滤**——禁用的件根本没跑 `apply`、注册不进来；卸掉的件 effect 收尾时自己摘。
  「在表里」就等于「该开得出来」，`!disabled && !shell` 那两条判断连同它们会出的错
  一起没了
- **没有 `canonicalPanelId`**——母仓那个函数整个是老布局兼容（盘上的格 id 少一段），
  这条线没有那份历史

## 浏览器半：井与一格

`bootShell` 拿到内核给的 `{ host, home, entries }`，占住整页那个根：注三张表 → 取一次
注册表 → **取一次布局档** → 渲染。档没有（第一次开机 / 认不出）就从默认布局起——默认
布局就是「表里有几格开几格」，全落在一个 group 里当兄弟 tab。

一格窗格由 `PluginPane` 承载，它是 `mountPane` 契约的外壳这一侧：

```
注件的样式表 → 等它真到位 → 动态 import client 束
→ mountPane({ host, shell, pane }, 容器) → 收下 dispose
```

**样式与模块在同一个 effect 里**：件的表要先注、而且要等它真到位再 import，这两件事是
一条时序上的承诺；拆成两个 effect 就只剩「谁先跑谁后跑」这种靠排列顺序的默契。格间总线的句柄
也在这条 effect 里取、清理时松手。**拿不到 `dispose` 就报契约不符**，不装作成功——那条
路上关格时清不掉，让写件的人当场看见。

## 布局落盘：自动存 + 起名存，回得去

第四刀欠的那半在这份里落地。档是 gwbData 里的一份文档 `layout`——**单文档装三样**：
「每口桌面各自的井」（自动防抖保存，每井一份）、「active」（重启回到哪口）与「存下来的
清单」（人手起名），形状住 `src/layout.ts`（`LayoutDoc` / `DesktopRow` / `SavedLayout`，
纯模块、有单测）。node 半两条命令过桥：

| 命令 | 干什么 |
| --- | --- |
| `shell.layout.get` | 读档，没存过回 null（`readDoc` 对没有的文档回 undefined，**这不是错、不出声**） |
| `shell.layout.save` | **整份替换**。存这头过一遍形状——浏览器半自己的 bug 拼出的坏档，没资格盖掉盘上好的那份 |

几样东西几个节律：

- **desktops（自动）**：每口井一变 → `onDidLayoutChange` → 400ms 防抖 → **按当下重拼
  整档** 再写（回调读的全是 ref，迟到的旧定时器写不坏账）；还没挂井的桌面用它那条
  存着的。重启按 active 回到那口井。落盘失败状态栏亮「布局没存上」（点一下重试）；
  外壳被拆之前抢着 flush 一次，赶不上也就丢最后 400ms 的挪动
- **切换同步 flush**：切桌面先记账（active 跟着走）再整档写一次，然后才动显隐——
  `shell.desktop.list` 读的是盘上的档，写在前头它才不至于答上一轮的旧账
- **saved（人手）**：状态栏「布局」菜单里「存当前为布局…」把**活动那口井**起名存进
  清单，**同名覆盖**（名字就是钥匙，重存就是更新）；点清单里哪条就把哪条 `fromJSON`
  铺回**活动那口井**上；行尾 ✕ 删那条。应用某套之后照常走自动落盘，不用另存。**照片
  与活房间是两回事**：桌面各自自动存（活房间），saved 是模板（照片、铺开即弃）——
  判据见[定过的事](/docs/decisions)
- **档版本**：v3 是现行。v2（单井时代）**解析时当场迁**——current 变第一口「主桌面」、
  saved 原样带走，下一次自动保存写的就已是 v3；v1（0.0.14 多桌面那版）照旧认不出整档
  当没有

两条失败路径分开走：**开机恢复不了**（存档坏 / dockview 升了版本）回默认并 warn，
不拦外壳起；**点开某套铺不回去只报不回默认**——人点名要的是这一套，悄悄换回默认
布局装没事比失败更糟。「重置布局」也在那菜单里：清掉**活动那口井**照「表里有几格开几格」
重铺——逐格关，不走 `api.clear()`（它内部账对不上时会抛，母仓撞过）。

## 多桌面（0.3.0 第二波）：井常驻保活，浮层户口在本桌

第一波（0.0.14）保活撤回过一次，现场与门槛见[定过的事](/docs/decisions)。第二波重做，
**语义还是保活**——一口桌面一口井，井常驻：非活动那口 `visibility:hidden` +
`pointer-events:none` + `inert`，只是不显示、不可交互，DOM、定时器、订阅全活着；
开机只挂活动井，其余第一次切到才挂（冷挂）、挂上常驻。重做的依据（社区证据钉住 0.0.14
那晚的两个向量、为什么这么藏、为什么动契约）整段在 decisions 那页，这儿只记形状。

**切桌面发生什么**，顺序是机制的一部分：

1. 记账（active 换人）→ 整档 flush 一次（两口井此刻都活着，`toJSON` 抓到的都是各自
   当下）
2. 显隐交给 React：旧那口藏起来、新那口显示；没挂的井这轮冷挂
3. 可见性通知（`shell.onVisibility` 的听众们）→ 焦点接管（给新那口 section 焦点，
   键盘不用先点一下）→ body 探雷（扫 body 直接子节点里非 #root 的陌生节点，**点名
   不删**——件的浮层该挂 `args.shell.portal`，挂 body 的藏不掉，探出来就是漏接线）

**桌面是分组不是宇宙**（0.4.0 起，判据见[定过的事](/docs/decisions)）：窗格宇宙**全局
一份**——实例 id 全页唯一（`pane.instance` 可当全局键用）；`openPane` 的 key 全局找份，
命中的份在别的桌面就**切过去聚焦**（任务栏语义），同一格两桌并存不经 openPane 发生；
状态栏「已开」看全局表。两个保留口径：**预览格每井一份**（全案唯一的桌面特例——预览
是本桌的快速翻看）；**新份落位在活动井算**（position 参照不能跨井）。布局动作（新桌
默认、照片、重置）仍可造出多份，各拿全局唯一 id。格间总线按条目分桶——两口桌面上同一
条条目的格在同一个桶里，跨桌面听得见（这是现状，不是缺陷）。

**命令面**（node 半转发的三条）：`shell.desktop.list`（无参数，回
`{ desktops: [{id,name}], active }`，读盘上的档）、`shell.desktop.switch`（`{ id?, name? }`，
id 优先）、`shell.desktop.new`（`{ name? }`）。井在页面那半，switch 与 new 经内核事件口
转发给页面执行，**回执 ok 只代表转发了**——要确认结果稍等一下再 list。

**模态从此只盖本桌主区**：状态栏 z 更高、永远可点（可以从模态里切桌面逃出）。这是有意
的行为变化，判据见 decisions。

## 窗格件拿到的 args

这是**窗格件契约的正本**（内核只定 `bootShell`，`mountPane` 的 args 由外壳定）：

```ts
mountPane({ host, shell, pane }, container) => { dispose(); retarget?(params) }
```

| | 是什么 |
| --- | --- |
| `host.call(command, args?)` | 命令通道，走到宿主分发再原路回 |
| `shell.openPane(paneId, { key?, params?, preview? })` | 打开**本件**的另一格 |
| `shell.setPaneTitle(title)` | 改这一格标签上的标题 |
| `shell.keepPane()` | 把这一格留住：它不再是预览格 |
| `shell.bus` | 格间小总线，`emit(type, detail?)` 与 `on(type, fn)` 回注销函数 |
| `shell.portal` | 本格所在桌面的**浮层户口**（0.3.0 起）：件里 radix Portal 的挂载点指它，桌面切走浮层跟着一起藏。不在桌面体系里时是 `document.body`（radix 缺省），件不必判空 |
| `shell.onVisibility(cb)` | 本格所在桌面的可见性（0.3.0 起）：切走收 `false`、切回收 `true`，**注册即回一次当下值**，回注销函数。协作式降级——件拿它停订阅 / 停渲染 / 停媒体，外壳只通知不强制 |
| `pane.id` | 这一格是本件的哪一格（注册时给的那个 id） |
| `pane.instance` | 这**一份**的唯一键。开两份时两份的这个值不一样；**全页唯一**（0.4.0 起，可当全局键用；0.3.x 曾按井算、跨井会撞名） |
| `pane.params` | 挂上这一刻这一份装的那份参数。没传就没有这一项 |

**只开得了自己那几格**：`entryId` 由 `PluginPane` 造这个对象时闭包绑定，件报不出别人的
条目——跟 `registerPane` 不收身份是同一条理由。

## 一格的身份是它装的内容

**2026-09-11 换的模型**，判据与推翻的那条见[定过的事](/docs/decisions)。一句话：

> 一格开几份，**是因为它们装着不同的东西**，不是因为谁给过它开第二份的权限。

件开格时给一个不透明字符串 `key`（不给等于空串，所以「没给 key」不是特例），外壳只拿它
去这一格已开的几份里找，一个字都不解释。`planOpen` 那个纯函数的全部规则：

```
want = options.key ?? ''

1. 有一份 p.key === want            → 聚焦那一份（预览格正式格都算）
2. 没有，且没要 preview             → 开一份新的（params 带 key，不带 preview）
3. 没有，且要了 preview
   3a. 有一份是预览格               → **软换**它：params 整份换成新内容
   3b. 没有                        → 开一份新的并标成预览格
4. 认不出那一格                     → 什么都不做，但话里带得出是谁要开什么
```

判断全在 `planOpen` 里，接线那侧只剩「按 kind 分派」——**有一条分支实机点不出来**
（传的参数踩了保留键，得专门写一个乱传的件才走得到），这也正是它必须是纯函数的理由。

`planOpen` 吃的**不是**「这个 id 占着没有」，而是**这一格此刻开着的几份**——0.4.0 起
这张表是**全井聚合**的（`{ id, key, preview, here? }[]`，由接线侧从各口井现摘，开在
别的桌面的份带 `here: false`）：聚焦与查重看全表（key 命中别桌的份也走聚焦，接线侧切
过去激活），预览槽与落位只看本井。查重（`uniquePanelId`）也从这张表里推，所以实例 id 的
算法一点没变——第一份仍然就是基名，第二份起追 `:2`，而**占号看全页**：别桌占着的序号
不能用。

### 预览格：至多一份，可被顶掉，开始用就转正

照 VS Code 那套语义，**实现是我们自己的**：dockview 的 PinnedTabs 是付费模块，而且它的
pin 管的是排序与溢出，跟「别换我的内容」不是一件事。

| | |
| --- | --- |
| 怎么进 | 件开格时 `preview: true`。同一格的预览格**至多一份** |
| 被顶掉 | 下一次 `preview: true` 打开且内容不同 → **原地换内容**（`retarget`），格数不变 |
| 怎么转正 | 件调 `shell.keepPane()`，或人**双击标签**。两条落到同一个动作：把 `preview` 从这一份的 params 上删掉 |
| 标成什么样 | 标题前面**一枚小空心圆点**（边框走 currentColor，带 `aria-label`）。**不用斜体**——中文没有真斜体，浏览器画的伪斜体很难看 |
| 没有的动作 | **正式格变不回预览格**。VS Code 也没有 |

**标例外不标常态**：预览格至多一份，正式格可以很多，所以记号打在预览格身上、正式格一个
像素都不变。

**记号是形状不是深浅。** 第一版是「标题淡一档」，当天就换掉了：**未激活的标签本来整体
就是 muted 前景色**，在那半边「再淡一档」等于没标，而预览格多数时候恰恰不是激活的那一枚。
圆点靠的是有没有这个东西，激活未激活都认得出；颜色交给 currentColor，跟着标签四态走，
不用自己配一套。

件该在「人真的开始用这一格」那一刻调 `keepPane()`（开始编辑、改了什么），**不是挂上就调**
——挂上就调等于这个件没有预览格。它是幂等的：已经是正式格时那一下什么都不做（连一次
params 变更都不发，不然每次击键都要带起一轮重渲染与一次布局落盘）。

### 换内容：软换与硬换

外壳换掉这一格的 params 之后，**件给了 `retarget` 就调它（软换），没给就拆了重挂（硬换）**。
判的是句柄上有没有那支函数，不是件说了什么：

```ts
mountPane(args, container) {
  const view = mount(args.pane.params)
  return {
    dispose: () => view.destroy(),
    // 有它就是软换：这棵树、这份滚动位置、人正打到一半的字全留着
    retarget: (params) => view.go(params.root),
  }
}
```

硬换是**正常路径**，不是契约不符：简单的件不必为此写一行代码，代价是那一格的内部状态跟着
重来一遍（`hello` 的 `counter` 故意不给 `retarget`，验的就是这条）。

接住这条的是 `PluginPane` 的第二条 effect。两处讲究，都是实机会静默出错的地方：

- **比的是 params 的稳定序列化，不是对象引用**（`paramsKeyOf`：键先排序再 `JSON.stringify`）。
  面板 params 每轮渲染都摘出一个新对象，按引用比等于每轮都算「换了」；而 params 本来就要求
  可 JSON 序列化。挂载那条 effect 的依赖数组里**故意没有 `paneParams`**，理由同上
- **件还没挂上时什么都不做**：挂载那条链读的是 ref、读到的一定是最新那份。这时候扳重挂
  只会把正在挂的那一次白白掐掉

### 开出来的几份靠 `params` 彼此不同

`key` 解决「这是不是同一格」，`params` 解决「这一份里装的东西长什么样」：

```js
args.shell.openPane('doc', { key: 'a.md', params: { file: 'a.md' } })
// → 那一份的 mountPane 拿到 pane.params === { file: 'a.md' }
// 再点一次同一个 key：聚焦那一格，不新开也不换内容
```

**它跟着布局落盘**：这份参数并进面板 `params`，`api.toJSON()` 原样带上、整档写进
gwbData 的 `layout`，`fromJSON` 再原样喂回来——重启之后那一份拿到的还是当初那一份，
件不用自己存一遍。

代价就写在这条好处背面：**必须可 JSON 序列化**。函数、DOM 节点、类实例塞进去，症状是
重启之后才现形的「参数变形了」。

**保留键 `pluginKey` / `entryId` / `paneId` / `icon` / `key` / `preview` 归外壳**：件传了会被
**摘掉**并出一条 console 警告——不是盖掉，也不是静默丢。摘掉而不是让外壳的值压上去，是因为
「悄悄用了另一个值」这种现象从件那头查不回来；出声之后件当场看得见自己传错了。反方向同理：
件拿到的 `pane.params` 也不含这几个键，件不该认识外壳内部的身份字段。

后两个（`key` / `preview`）进这张名单是有代价的：**件从此不能拿这两个名字当自己的参数名**。
换来的是身份跟着面板 params 一起落盘——整页重载之后外壳照旧认得出哪一格装着什么、哪一格是
预览格，不用另存一份账。

**不作用于聚焦**：走到聚焦时那一格装的本来就是这份内容（key 对上了），它早挂好、
`mountPane` 已经拿过一次参数。这时改面板 `params` 只会让盘上的档跟界面上活着的那份对不上
——要换内容走的是 `preview` 那条（软换），那条会连着通知件。

**表现取不用快照**：件是热挂载的，后挂上的件在快照里没有自己。取表是一次本地 IPC，
而调用方全是 click 回调、没人等返回值。

**总线的桶按条目分**，所以同一条条目的几格——含同一格的两份——在同一个桶里。一格松手时
自己挂的听众要摘干净，理由见[撞过的墙](/docs/walls)。

**多出来那份摆哪儿，按这一格此刻开着几份分三档**（`placeNext`，判断跟别的一样住
`planOpen`，`applyPlan` 只把它换成 dockview 的 `position`）：

| 已经开着 | 新那份开在哪 |
| --- | --- |
| 0 份 | 不给 `position`——落当前 group 当兄弟 tab |
| 1 份 | `right`，不给参照（相对当前活动的那一格） |
| 2 份及以上 | `below`，**参照已开的某一份非基名实例** |

第一档不能用在第二份上：不给 `position` 它就当兄弟 tab，一开就把第一份盖住，而「两份同屏」
正是多实例唯一能眼见为实的地方。第三份起也不能再用第二档：件开第二份、第三份多半是从**基名
那一份**点出来的（正文格里点两下评论），活动的一直是它，于是每一份都开在它右边，一格一列。

**第三档的参照必须显式给。** dockview 那头只有 `direction` 的 `position` 是
`AbsolutePosition`（`_doAddPanel` 里 orthogonalize 那一支），落的是整口井的边——只说
`below` 的话新那份横在正文格底下，不是叠在上一份下面。

**参照挑的是「不是基名那一份」，不是「最后开的那一份」**：基名那一份装的是件先开出来的内容，
参照它就又挂回它底下。挑哪一份非基名的只决定新格落在那一列的哪个位置，所以取表里最后一份就够
——那张表的顺序是 dockview 的布局序（`api.panels` = 组按建组先后 flatMap 组内标签先后），
同一刻读两次一样，但人拖过标签之后就不再等于开格先后，判断不吊在那上面。

**软换是 `api.updateParameters`，而它是并不是换**：dockview 那头做的是 `{ …旧, …新 }`，
只有值写成 `undefined` 的键才删（8.2.0 的 `DockviewPanel.update`）。所以换内容前要拿
`replaceParams` 把旧那份里多出来的键显式写成 `undefined`——不补这一道，上一份内容的参数
会赖在这一格里跟着落盘，而现象只是「件收到了一个它这一轮没传过的参数」。转正正好是这条
机制的另一面：**删掉 `preview` 就是给它写一个 `undefined`**。

**样式表注过就不摘**：同一个件开几格没必要注几条，而摘它需要引用计数，计数错了的症状是
「关掉一格，另一格的样式跟着没了」——静默，且要两格同开才复现。留着的代价只是内存里
一份 CSSOM。

## 状态栏

井底下那条，**它是唯一不进窗格系统的东西**——也正因如此它兜得住「窗格全关光了怎么办」，
也正因如此它是桌面切换器唯一合理的落点：它不属于任何一口桌面，站在所有井外面
（z 也更高，模态遮罩盖不住它）。布局是两行：桌面区 `flex-1 min-h-0`，状态栏 `flex-none`。

**`min-h-0` 少不了**：flex 子项默认 `min-height: auto`，井里内容一高就把状态栏挤出屏幕。

左起五段，外加一枚告警：

| 项 | 干什么 |
| --- | --- |
| **桌面** | 列出桌面、点谁切谁（当前那口标「当前」）；「新建桌面…」（格子变内联输入框，空名由外壳拿「桌面 N」顶上）。井常驻保活，切走的那口原样活着 |
| **布局** | 已存布局清单：点谁把谁铺回**活动那口井**上、行尾 ✕ 删谁；「存当前为布局…」（格子变内联输入框，Enter 存、Esc 弃、**同名覆盖**）；「重置布局（铺回全部格）」 |
| **＋ 可开窗格** | 点开列出注册表里所有格，选一个就开；点下去会走成聚焦的那几条标一下「已开」 |
| **home** | 一眼看出自己在哪个 home 里，开测试 home 时不用翻日志 |
| **刷新** | `location.reload()` 整页重跑——重取注册表、按档恢复布局，宿主进程不动。渲染层「boot 之后注册表就旧了」的手动答卷 |
| **亮暗** | 切 `html.dark`，令牌整套跟着换 |
| （告警）**布局没存上** | 只在落盘失败时出现，点一下立刻重试 |

**刷新是整页 reload，不是外壳内部重建**：渲染层那条 boot 链（kernel.info → importmap →
bootShell → 取注册表 → 取布局档 → 恢复）原样重跑一遍；内核那半与页面加载无关（IPC
句柄在主进程启动时注册，宿主进程也活在那边），reload 对它只是一次重新连线。装了新件、
启停了件之后点它，比重启整个应用轻一档。

### `shell.reload`：同一件事的命令版

0.2.2 起那颗「刷新」有了命令面的版本——`shell.reload`，无参数，给
[`plugins.update-all`](/docs/plugins) 一键热升收尾用：node 半换成新版本之后，开着的格持的
仍是旧的 client 束、importmap 只在开机注一次，只有整页重载能让页面重新 import 到新东西。

{/* ref file="../plugins/shell/src/reload.ts" */}

件跑在 Electron **主进程**里，`import('electron')` 拿得到 `BrowserWindow`——开窗、重载全归件，
内核一条都不代办。三处讲究：

- **取窗口列表抽成可注入的 deps**。测试里没有 electron，纯逻辑那半（没窗口怎么答、有几扇就
  reload 几扇）喂一份假的就能测；真机那份 `electronWindows()` 不在 Electron 里就 reject
- **`BrowserWindow` 是一个类，`typeof` 是 `'function'`**（`windowsOf`）。0.2.2 / 0.2.3 两版
  按「是对象」判它再取 `getAllWindows`，实机回的都是「不在 Electron 主进程里」——而探针证明
  命名空间与 `default` 上都有它。0.2.3 以为根因是 ESM 的 `default`，改错了地方；0.2.4 才修对：
  对象或函数都往下取。「先看 `default`」那步留着（两处都挂，不吃亏），但它不是根因。
  记在[撞过的墙](/docs/walls)
- **说明符走变量**，不让 tsc 去解析 `electron` 这个模块——本包不依赖它的类型（那要把整个
  electron 装进件的 devDependencies，只为一个方法名），运行时它就在主进程里

**没有窗口回 `ok: false`**，不静默回成功——回成功的话调用方以为界面刷了，其实什么都没发生。
登记那头把「拿不到 electron」也收成回执：

{/* ref file="../plugins/shell/src/index.ts" lines="162-181" */}

**＋列表走跟件调 `openPane` 同一个 `planOpen`**，所以行为一致。**已开的那条不 disable**
——点它是聚焦，那是个有用的动作，标一下就够。

**那枚「＋一份」删掉了**（2026-09-11，随 `duplicable` 一起）：这张表回到它本来的职责
——打开这一格，已经开着就聚焦。「再来一份」是件说了算的事，它要几份取决于装的是什么
内容，不是状态栏点得出来的。状态栏这条入口不给 `key`（等于空串），所以它开/聚焦的是
**那份没有身份的**。

**「已开」那个记号问的是 `planOpen` 自己**（`willFocus`：点下去会不会走成聚焦），
不是「这一格有没有开着」。两者会岔开——件拿几个 `key` 开了几份、而空身份那一份没开着，
那时后者说「已开」，点下去却多一格空白的。**记号与效果必须同一个判据**，在接线侧另写
一条就是第二份真相，而漂了没有任何现象：只是那个记号开始说谎。记号跟着
`onDidLayoutChange` 重算，**换 params 也在这条事件上**（dockview 8.2.0 把每一组的
`onDidPanelParametersChange` 接进了它），所以一格被软换或转正之后记号不会停在上一轮。

判断与副作用继续分开：`planOpen` 出判断，`applyPlan` 落成动作，两个入口（件调的
`openOwnPane`、状态栏调的 `openSpec`）共用后者。

### 菜单的 portal 曾经必须挂回外壳的根，0.2 起不必

**0.1 时是这样的**：外壳那张表整张 scope 在 `[data-gwb-plugin="…"]` 之下，而 radix 的
Portal 默认挂 `body`——挂出去之后菜单一个类名都不生效。所以 `shadcn add` 拉下来的
`dropdown-menu.tsx` 本仓改过一处：给 `DropdownMenuContent` 加了 `container`，透给 Portal；
为了把外壳的根送到那儿，`App` 与 `StatusBar` 之间还拖着一条 `scopeRef` / `root` 的 prop 链。

（这跟 dockview 那张表不 scope 是同一个根因的两面：`.dv-*` 我们管不着，所以整张不 scope；
而我们自己的菜单归我们管，得让它待在 scope 里面。）

**0.2.0 换成 Tailwind 前缀围栏之后，这一条整个消失了。** 类名自带 `shell:` 前缀、规则全页
有效，弹层 portal 到哪都有样式：`dropdown-menu.tsx` **重拉成了官方原样**，那处 `container`
补丁与那条 prop 链一起连根删掉。实机量过——状态栏的「布局」与「＋可开窗格」两个菜单都挂在
`body` 下，底色等于 `--popover`。

**这条留在这儿是为了防它回来**：以后再看到「菜单得知道自己该挂哪个容器」这种要求，先确认
是不是有人把围栏又改回了 scope。判据见[定过的事](/docs/decisions)。

## 两张样式表，规矩不同

**围栏是怎么回事、值与规则为什么一个共享一个隔离、组件为什么各拉各的——原理全在
[样式与组件](/docs/styles)那一页**，这儿只记外壳自己那两张表的规矩。

| 产物 | 围栏 | 装什么 |
| --- | --- | --- |
| `./style.css` | **类名前缀**——类选择器一律 `.shell\:` 开头 | 外壳自己 JSX 的 Tailwind 类 |
| `./dockview.css` | **没有，也不需要** | **裁过的** dockview 基础规则 + 我们自己那套 theme |

后者套不了任何围栏，两个理由：它管的 `.dv-*` 类名不经我们的手（改不了名，也就加不上
前缀），而且门户元素可能挂在 `body` 下——包进 `:where(…)` 一条都匹配不上。前者的围栏则
**跟 DOM 位置无关**，所以状态栏那两个 portal 到 `body` 的菜单照样有样式。

产物守卫把两张表的两套规矩分开钉着：

### 外壳跟件如今同一套围栏

**2026-09-09 全仓一套。** 外壳 0.2.0 与四个带界面的件同日迁完 Tailwind 前缀围栏
（类名从源头是 `shell:flex` / `hello:flex` 这种），`tools/build-styles.ts` 那条选择器 scope
的构建线随之删除——**一度存在的「两代件并存」结束了**，外壳不用再同时伺候两套。判据、
产物大小与实机读数见[定过的事](/docs/decisions)。

件那一格的容器上因此只剩两样东西，一样在围栏之外，一样是围栏换代后的遗留：

{/* ref file="../plugins/shell/src/client/PluginPane.tsx" lines="189-200" */}

- **`@container` 让这一格成为容器查询的根。** **窗格不是视口**——件里写的 `@sm:` / `@md:`
  这类变体按**这一格现在有多宽**判，跟整窗大小无关。同一个件在窄格里竖排、在宽格里横排，
  拖动分隔条当场变。实机量过：hello 那格 1069px 时变体按钮排 `row`，压到 300px 变 `column`。
  **容器查询跟围栏本来就是两回事**，换围栏一点没碰它。类名带 `shell:` 是因为这条规则出自
  外壳自己那张表（容器是外壳画的），件那边写的 `@md:` 用的是件自己的前缀
- **`data-gwb-plugin` 如今只是身份标记。** scope 时代它**是围栏本身**——表整张包在
  `:where([data-gwb-plugin="…"])` 之下，容器上不挂它，那个件的类名一个都不生效；换成前缀
  之后件的类名全页有效，挂不挂它一模一样。留着是为了让人在 devtools 里一眼看出这一格是谁的，
  外加给探针和样式调试一个认件的把手。**正因为它现在少挂一个也不会有任何现象**，别再把它
  当成「样式生效的前提」去写代码

### 它的 18 套主题一套都不挂

`.dockview-theme-gwb` 是**唯一真源**，不是在谁的基底上打的补丁。要它的布局与拖放，
不要它的审美——「看着不像 shadcn」的来源全在主题里，而主题跟引擎是分得开的：形状与配色
全走 CSS 变量（`.dv-tab` 自己只有一句 `flex-shrink: 0`）。

一度反对过这条，理由是「不挂基底就有 682 处 `var()` 读空」。**那个理由不成立**：读空的
前提是我们没定义，而这条路要做的正是全定义。量下来裁剩的基础规则引用 **54 个**不同变量，
`dockview-theme.css` 定义了 71 个（多出来的是企业模块那批，全定义好过维护例外清单）。

### 因此原表能裁掉三分之二

`build.ts` 用 postcss 解析原表，**凡是选择器带 `.dockview-` 的规则整条剔掉**；一条规则挂
几个选择器时只摘属于他们的那几个。实测原表 154,125 字节裁到 50,686，**省 103,439**；
拼上我们那套 theme 之后产物是 59,422。

被裁的不只是 18 套配色，还有 `.dockview-spaced` 这个 modifier——圆角与间距的落地规则原本
住在那儿，所以我们那张 theme 表把用得上的**复刻了一份**（眼下圆角全 0，那几条空转着，
但「圆角怎么落地」这件事的实现在，将来想加只要改一个变量）。

**这跟第三刀写的「原表整张带上一行不裁」是同一条判据的两个结果，不是翻案**。那条的理由
是「基础规则与主题规则交错着，裁错一条的症状是某个交互没样式」——**当时成立**：那时挂着
它的 `dockview-theme-light`，没有可靠的切分依据。现在一个内置主题都不用了，整类可以按
选择器整体剔除，风险从「猜」变成了「解析」。

裁表是**每次构建都在跑的代码**，写坏了两头都不报错（裁多了某处没样式，裁少了他们的主题
偷偷把我们的值盖掉），所以产物守卫钉了两条：一条 `.dockview-` 都不许剩、基础规则的字节
数得落在 50–70KB 这一档。

### 亮暗不靠换类

`--dv-*` 全接令牌，令牌跟着 `html.dark` 变，井、标签条、件里的按钮一起变，**一行都不用
重新构建**。实机逐处量过。

**一个例外：`--dv-floating-box-shadow`**。dockview 给的默认值在暗底上量出来是
`rgba(0,0,0,0.12)`，浮动组整个失去立体感。这个变量的语义**本来就跟明暗有关**（阴影就是
影子），所以表里给暗色单独一档 `.dark .dockview-theme-gwb`。

这不违反上面那条：**换的不是主题类，是我们自己这张表按 `.dark` 给不同的值**——跟令牌表
本身 `:root` / `.dark` 两套值是同一个做法。往后再发现哪个变量在暗色下不对，照这条补。

### 升级 dockview 之后要核对一次变量全集

62 个全由我们给，它新增一个我们就漏一个，而漏了是**读空、不报错**。核对方法与「为什么
不做成构建期守卫」见[撞过的墙](/docs/walls)，主题怎么交给它（挂在 `<html>` 上是没用的）
也在那儿。

## 为什么不用 dockview 自己的注册

**下一个人一定会问**：dockview 有 `components` 表，为什么还要 `pane-registry`？

因为那两样管的不是一回事。dockview 的 `components` 是「component 名 → React 组件」——
我们全部窗格都映到**同一个** `plugin` 名上；而 `pane-registry` 是「有哪几格值得存在」。

它替代不了，差的三样是根本性的：

- **跨进程**——dockview 的注册面全是同一个 JS 堆里的对象引用，没有任何可序列化的形态；
  我们的注册方在 node 进程、消费方在浏览器
- **未开也在表里**——dockview 所有枚举口（`api.panels` / `groups` / `toJSON`）**只回
  已实例化的**。`DockviewOptions` 六十多个字段里没有 `catalog` / `availablePanels` 这类
  东西
- **身份与元数据**——`title` 在它那儿是 `addPanel` 的入参、不是可查询的目录项；
  `icon` / `client` / `entryId` / `pkg` 它完全没有

一句话：**dockview 管「已经决定要有这一格之后它长什么样」，`pane-registry` 管「有哪几格
值得存在」**——后者 dockview 从设计上就留给宿主。

## 撞名与说不清自己是谁

注册表本体的三条判据，都写进了测试：

1. **一条条目一个命名空间**——键是 `entryId` + 窗格 id。同一个包的两条条目各注册一格
   同名的，两条都在，这不叫撞名
2. **撞名后来者赢，但要告警**——跟命令总线一个规矩，一个仓里两套撞名规则是无谓的
   记忆负担
3. **空 id / 空 title 抛错**，不是静默忽略——撞名是「两条都说得清，该听谁」，而空 id
   是「这一格根本没说自己是谁」。让它进表只会在井里多出一格点不开的空白，而且回头
   查不到源头。注册参数是件自己写死的常量，抛在它自己的 `apply` 里、日志指名道姓，
   好查得多
