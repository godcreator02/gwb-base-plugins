**本页回答**：说明书插件 `@godcreator/gwb-skills` 管什么、刻意不知道什么；一份说明书在它的表里是什么形状；它提供哪些接口、依赖哪些接口；不启动工作台怎么测它；代码从哪读起。带说明书的插件要遵守什么写在接缝页[说明书](/docs/seams/skills)。

## 管什么

说明书是给 agent 读的文档：一个目录，里面必有 `SKILL.md`，可以带附件。agent 经 MCP 入口只拿得到命令名与用法，多步流程、调用顺序、遇到过的问题写在说明书里。说明书插件管的是**一张按说明书名索引的登记表**，外加读正文的那条路。

**插件自己把目录交进来。** 带说明书的插件在 `apply` 里调 `ctx.gwbSkills.register(dir)`，`dir` 下每个有 `SKILL.md` 的子目录是一份。服务从调用方条目认出包名，扫目录，把扫到的逐份放进表；注销登记在调用方的 `effect` 上，调用方卸载时它的说明书跟着撤掉：

{/* ref file="../plugins/skills/src/index.ts" lines="116-132" */}

**名字全局唯一，先登记的保留。** 同名的第二份不登记，写一条 warn 说明名字被哪个包占着；撤的时候只删表里仍是自己那条记录的，别的插件后来登记的同名说明书不受影响：

{/* ref file="../plugins/skills/src/index.ts" lines="94-114" */}

这一点和命令总线的「后登记的生效」相反：说明书被静默换掉的话，agent 照着另一个插件的说明书做，症状只是做错了，查不到原因。

**扫描有上限、超出就报。** 只收 `.md`、`.txt`、`.json`、`.yml`、`.yaml`，单个文件 512KB，往下三层，一份最多 64 个文件；超限的、读不了的、缺 `SKILL.md` 的都记成问题，由服务按调用方包名逐条写 warn，不悄悄丢掉：

{/* ref file="../plugins/skills/src/collect.ts" lines="6-13" */}

**frontmatter 手写逐行解析。** 只认单行 `key: value`，在第一个冒号处切开；折叠块（`>-`、`|`）取不到值。`name` 缺了用目录名，`description` 缺了照样收、同时报一条问题——没有描述的说明书 agent 不会去读，比整份不收好查：

{/* ref file="../plugins/skills/src/collect.ts" lines="53-75" */}

**正文每次从磁盘读，只读登记过的文件。** `read(name, file)` 先按名字查表，再看文件名在不在登记时扫出的清单里，不做路径拼接，所以参数里带 `../` 读不到目录以外的东西。改了 `SKILL.md` 正文立刻生效；增删文件、改 frontmatter 要重新加载那个插件，文件清单在登记那一刻就定了：

{/* ref file="../plugins/skills/src/index.ts" lines="138-149" */}

**两条命令**：`skill.list`、`skill.read`，在 `Service.init` 里登记到命令总线；`skill.read` 读不到时不区分「没这份说明书」与「没这个文件」，分开报等于告诉外面哪些名字存在：

{/* ref file="../plugins/skills/src/index.ts" lines="56-82" */}

## 不知道什么

**不认识 MCP。** 说明书清单怎么进 MCP 入口 `index` 的返回、附件清单给不给 agent，都是 [MCP 入口](/docs/mcp)决定的；它局部注入 `gwbSkills`、只调 `list()`。

**不扫 `node_modules`、不看条目树。** 表里只有插件主动交来的目录，所以只有正在运行的插件的说明书，不会出现「说明书在、它讲的命令不在」。

**不检查正文。** 正文写什么、提到的命令存不存在、附件在正文里提没提到，由写说明书的插件负责。

**扫描那一层不知道 cordis。** `collect.ts` 不碰上下文、不写日志，扫到的问题放进返回值交给服务写：

## 提供的接口

| 接口 | 做什么 | 契约在 |
| --- | --- | --- |
| 服务 `ctx.gwbSkills` 的 `register(dir)` | 登记一个装说明书的目录（字符串路径或 `URL`），返回注销函数；调用方卸载时自动注销 | [4 说明书](/docs/seams/skills) |
| 服务 `ctx.gwbSkills` 的 `list()`、`read(name, file?)` | 列出全部说明书；读某份里的一个文件，缺省 `SKILL.md`，读不到回 `undefined` | [4 说明书](/docs/seams/skills) |
| 命令 `skill.list` | 无参数，返回 `{ count, skills }` | [4 说明书](/docs/seams/skills) |
| 命令 `skill.read` | `{ name, file? }`，返回 `{ name, file, text }`；agent 经 MCP 入口的 `run` 调它读正文 | [3 命令表开给 agent](/docs/seams/agent-surface) |
| 导出的类型 `GwbSkillsApi`、`GwbSkill`，常量 `SKILL_ENTRY`、`SKILL_LIST_COMMAND`、`SKILL_READ_COMMAND` | `import type {} from '@godcreator/gwb-skills'` 让 `ctx.gwbSkills` 有类型 | [4 说明书](/docs/seams/skills) |

## 依赖的接口

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| 命令总线服务 `gwbCommands` 的 `register`（服务类上的 `static inject`） | 登记 `skill.list`、`skill.read`；缺了服务 `gwbSkills` 不提供，插件一直等待 | [gwb-commands](/docs/commands) | 只记登记与注销的替身，按名字取出处理函数直接调 |
| cordis 的 `Service`、`effect`、`logger` | 提供服务；方法里的 `this.ctx` 是调用方的上下文；注销登记在调用方的 `effect` 上 | 内核带的 cordis（peer `^4.0.0-rc.10`） | dev 里的 `cordis` 4.0.0-rc.10 |
| loader 放在调用方 fiber 上的 `entry.options.name`（[8 条目身份](/docs/seams/entry-identity)） | 认出登记方的包名，写进每份说明书的 `plugin`；取不到时 `register` 抛错 | 内核带的 cordis loader | 调用方插件在 `apply` 里自己往 fiber 上放一个 `entry` |
| 文件系统 | 登记时同步扫目录，读正文时异步读文件 | `node:fs` | 临时目录里的真文件 |
| 词汇表包的 `GwbContext`、`GwbResult` | 类型 | `@godcreator/gwb-plugin-api`（dev，`^0.4.1`） | 同一份 |
| 内核包 `@godcreator/gwb-kernel-desktop` | peer 范围 `^0.4.1` 声明兼容哪些内核 | home 根上装的内核包 | 不装 |

{/* ref file="../plugins/skills/src/index.ts" lines="36-44" */}

`@godcreator/gwb-commands` 写在 dev 里（`workspace:*`），代码只 `import type` 它，为的是让 `ctx.gwbCommands` 有类型，构建产物里没有它。

## 怎么单独测

三个测试文件，都在 `plugins/skills/tests/`：

**`collect.test.ts` 测扫描与 frontmatter**：在系统临时目录里造一棵真的目录树再扫，扫描本身就是这个文件的全部工作，拿替身测等于没测。证明的是：frontmatter 只在第一个冒号切开、成对引号剥掉、折叠块取不到值；`SKILL.md` 恒在第一位；非文本不收；缺 `SKILL.md` 的目录不算一份并报一句；缺 `description` 照收并报一句；只看一层子目录。

{/* ref file="../plugins/skills/tests/collect.test.ts" lines="7-11" */}

**`service.test.ts` 测服务这一层**：真 cordis 上下文，命令总线用只记登记的替身；调用方插件在 `apply` 里往自己的 fiber 上放一个 `entry`，模拟 loader：

{/* ref file="../plugins/skills/tests/service.test.ts" lines="62-75" */}

证明的是：两条命令登记在本包包名下、说明书插件卸载时注销；`plugin` 取自调用方条目，字符串路径与 `file:` URL 都认；正文每次现读；清单外的文件与带 `..` 的路径读不到；同名先到先得并写 warn；注销函数不删别人后来登记的同名说明书；取不到调用方身份时 `register` 抛错；两条命令的回执形状。

**`artifact.test.ts` 查构建产物**，相对 import 带 `.js`、包名 import 只有 node 内置模块与 `cordis`，没构建时整组跳过。

loader 真的把调用方的包名放在 fiber 上，只能在隔离 home 里验证。
