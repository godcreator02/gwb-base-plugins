# 样式与组件

这条线上带界面的件有好几个：外壳自己占整页，其余的各画各的一格窗格。它们的界面**全落在同一张
页面上**，而且是**分别构建、分别发版、装机时才第一次见面**的。

这一页讲的就是这件事怎么成立：什么东西全页共享一份、什么东西必须各一份且互相隔离、
共享的到底是源码还是运行时的对象。**方向了断本身不在这儿**——「围栏为什么从选择器 scope 换成
Tailwind 前缀」记在[定过的事](/docs/decisions)的 2026-09-09 那条，撞出来的坑记在
[撞过的墙](/docs/walls)。这一页管的是原理：为什么非得这么分，以及一次开机从注第一张表到
件在容器里画出第一个像素，中间每一步为什么排在那个位置。

---

## 一、一张页面，三种共享

### 先摆物理事实

不管这套东西设计成什么样，浏览器给的条件是死的，一共三条：

- **只有一个 DOM。** 每个件画出来的元素，跟别人的元素是同一棵树上的兄弟或后代
- **只有一套级联。** 页面上所有 CSS 规则最终排进同一个优先级体系里比大小，不存在
  「这条规则只在这一块里参与比较」这种东西（除非上 Shadow DOM——那条路否掉的理由在第五节）
- **只有一个 JS realm。** 一个全局对象、一份模块缓存、一份 importmap

「多个件共享一套外观」这句话听着是一件事，落到这三条物理事实上其实是**三个不同的问题**，
答案也各不相同：

| 问的是什么 | 答案 | 凭什么 |
| --- | --- | --- |
| 颜色、圆角、字体这些**值** | **全页共享一份** | CSS 自定义属性沿 DOM 继承，`:root` 上写一次全树读得到 |
| 工具类这些**规则** | **各一份，而且必须互相隔离** | 每个件按需编译，各是各的子集，叠在一起会互相污染 |
| 按钮、菜单这些**组件** | **共享的是源码的出处，不是运行时的对象** | 每个件各拉各的、各打各的束 |

下面三节各讲一个。

### 第一问：值——全页共享一份

这一问是浏览器白送的。CSS 自定义属性（`--background` 这种）**沿 DOM 继承**：在 `:root`
上写一次，整棵树上任何一个元素读 `var(--background)` 都读得到，不管这个元素是谁画的、
什么时候插进来的。

所以令牌包只做一件事：把语义变量的值在页面上写一份。亮色写在 `:root`、暗色写在 `.dark`
（挂在 `<html>` 上）：

{/* ref file="../packages/tokens/src/tokens.css" lines="1-9" */}

**换主题＝换这一份值。** 件那边的规则里写的是 `var(--primary)` 而不是某个具体颜色，所以
页面上这份值一变，所有件当场跟着变，**一个都不用重新构建**。状态栏那颗亮暗开关做的事就是
给 `<html>` 加一个类名而已。

同一份表还负责两件全页只该有一份的事——给所有元素一个默认边框色、给 `body` 定底色与字体：

{/* ref file="../packages/tokens/src/tokens.css" lines="99-112" */}

字体那一行尤其要紧：**不经 Tailwind 工具类的那些 DOM**（dockview 画的标签条、件里的裸
HTML）全靠从 `body` 继承。

### 第二问：规则——各一份，而且必须互相隔离

这一问才是这整页的核心，而且它的必要性**不是显然的**——很容易觉得「大家用的都是同一套
Tailwind，表合成一张不就完了」。不能。得一步一步看清楚为什么。

**第一步：Tailwind 是按需编译的。** 它扫源码，你用到哪个类就编哪条规则，编不出来的一个
字节都不出。所以每个件那张表都是**全集的一个子集，而且各是各的子集**——甲件用到的那些，
乙件多半没用到；乙件用到的那些，甲件也未必有。

**第二步：子集本身没问题，问题出在几张子集表叠进同一层。** Tailwind 的工具类全在
`@layer utilities` 里，件的表只写这一层、不声明层与层的顺序：

{/* ref file="../plugins/hello/src/client/styles.css" lines="34-38" */}

顺序由**先加载的那张令牌表**声明，而这张表还得把 preflight 包进 `base` 层——CSS 里
**未分层的规则优先级高于所有分层规则**，preflight 原样拼进去就是一份裸规则，会压过每一个
件的工具类：

{/* ref file="../packages/tokens/build.ts" lines="16-32" */}

**第三步：同层、同权重，胜负只看文档序。** 于是会疼的那一下是这样发生的——甲件的元素上
挂着两个类，一条管四边、一条只改左右；乙件只用到了前者，所以**乙的表里没有后者**；而乙的表
**后加载**。层里的顺序就成了「甲的①、甲的②、乙的①」，乙那条①排在甲的②后面，**把甲的元素
整个重置回①的样子**。

**而且没有任何一处报错**：两张表都编得对、都加载成功了，只是撞在了一起。构建是绿的，控制台
是干净的，页面上只有「这块怎么跟我写的不一样」。

这一下发生在时间上，写成文字必然是一串「先……然后……于是……」，所以画了一遍：

**所以隔离是必需的，不是洁癖。** 这条判据从头到尾没被推翻过，换过的只是**隔离的手段**。

### 隔离靠名字，不靠位置

隔离两张表，直觉上的办法是**按位置**：把甲件那张表里的每条选择器都改写成「只有待在甲件那个
容器底下的元素才算」。这条路走过，也被换掉了。换掉的理由不是它不管用，是它的**失效点在
运行时**：

- 弹层的浮层默认 portal 到 `<body>` 上，一挂出去就不在那个容器底下了，整层菜单一个类名都不生效
- 外壳的根是每一格窗格的祖先，所以外壳那张表的规则对所有窗格里同名的元素照样成立
- 哪张表先注进页面决定谁盖谁，而那个顺序是运行时才定的

三种都不报错。**DOM 的位置是运行时才确定的**，所以按位置隔离，等于把围栏建在一堆隐含前提上，
前提破了没有任何人会告诉你。

现在这条路是**按名字**：让类名从源头就唯一（每个件一个短前缀，类名长成 `hello:flex` /
`shell:flex` 这种）。规则仍然全页有效、跟 DOM 祖先关系无关，但**它只可能匹配到本件画出来的
元素**——因为别的件根本不会写出这个名字。

这一换，失效点从运行时挪到了写代码那一刻：

| | 按位置隔离 | 按名字隔离 |
| --- | --- | --- |
| 围栏是什么 | DOM 祖先关系 | 类名的唯一性 |
| 弹层 portal 出去 | 整层裸奔 | 无关，照样有样式 |
| 加载顺序 | 是隐含前提 | 不参与 |
| 会怎么坏 | 三种，全部静默 | 只剩一种：忘写前缀 |
| 什么时候看得见 | 某个弹层被打开、某两个件同时装上的那天 | **当场**——那个类不生效，写的人打开页面就看见 |

「忘写前缀」还能用一条守卫堵死（第四节），而上面那三种一条都堵不住。

**工具链原生支持这条路**，不用自己写手术：Tailwind 4 的 `prefix()` 写在拆开的主题导入上、
shadcn 的 `components.json` 里有 `tailwind.prefix`、`cn` 那个包（tailwind-merge）对带前缀的
类名本来就合并得对。按位置那条路则是我们自己写的 postcss 改写，外加给每个带浮层的组件打补丁
——两笔自维护的成本，换来的围栏还更弱。逐条读数与拍板经过在[定过的事](/docs/decisions)。

### 第三问：组件——共享的是源头，不是运行时

按钮、下拉菜单这些东西，两个件长得一模一样，靠的**不是**它们跑同一段代码。

每个件自己有一份 `components.json`，要什么组件就从 shadcn 官方拉什么，**拉下来就是这个件
自己目录里的一个 tsx 文件**，跟着这个件一起被 esbuild 打进它自己的束：

{/* ref file="../plugins/hello/components.json" lines="6-12" */}

那两个件的按钮长得一样，是因为**源码来自同一处**（同一个 registry、同一个 `style` 与
`baseColor`），而颜色**读的是同一份令牌**。运行时它们是两段互不相识的代码。

这么做的代价是每个件的束里各有一份按钮的字节。买到的是：一个件想改自己那颗按钮，
改自己目录里那个文件就行，**不用发一个共享包、不用等别人升级、也不可能改坏别人的**。
「共享一个组件库」这条候选否掉的实测理由在第五节。

`prefix` 那一行让 CLI 直接写出带前缀的类名，所以拉下来的组件不用手改。这也是围栏换成前缀之后
白得的一条：以前为了把浮层拽回容器里，拉下来的组件得逐个打补丁，现在**重拉成官方原样**。

外置的判据很硬：**在 importmap 里的才许外置**。不在里头的（组件用的那些库）外置成裸名，

### 一条从头到尾的链

把上面几件事按时间摆一遍，就是外壳开机做的事。每一步都有它必须在那个位置的理由：

**第一步：内核注 importmap，然后才 import 外壳的浏览器半。** 顺序反了，外壳顶层那句
`import { … } from 'react'` 就解析不到。

{/* ref file="../plugins/shell/src/client/index.tsx" lines="825-830" */}

**第二步：外壳问一次 `shell.env`**，拿到 home 和三张样式表的地址。地址由 node 半算（本包的从
`import.meta.url` 算，令牌表按包解析），**顺序是写死的**：令牌、dockview、外壳自己那张。

{/* ref file="../plugins/shell/src/index.ts" lines="39-64" */}

**第三步：三张表全注上、并且全等到位，才往下走。** 令牌那张必须最先——层顺序是它声明的；
dockview 那张管的类名不经我们的手（改不了名，也就加不上前缀），所以它整张不套围栏；
外壳自己那张类名一律带自己的前缀。

**第四步：取主题件的启动样式，注在这三张之后。** 用户自己写的那段 CSS 要压得过令牌的默认值，
同权重下靠文档序取胜，所以它得是 head 里靠后的那张；而「重启后开机即生效」要求它赶在
第一帧之前落位。

{/* ref file="../plugins/shell/src/client/index.tsx" lines="79-100" */}

**第五步：挂 `.dark`、挂身份标记，然后 `createRoot`。** 深色是默认态，令牌的暗色那半在这儿
生效。身份标记只是个把手，不参与任何选择器（下面还会再说一遍，因为它以前不是）。

{/* ref file="../plugins/shell/src/client/index.tsx" lines="751-767" */}

**第六步：开一格窗格时**——从注册表里取这个件自报的两个地址 → **先注它的样式表、等它真到位**
→ 再动态 import 它的束 → 调它的挂载函数、把容器交出去 → 收下清理句柄。

{/* ref file="../plugins/shell/src/client/PluginPane.tsx" lines="113-132" */}

最后一步里「等它到位再 import」不是讲究，是必需的：`<link>` 是异步取的，件的第一帧完全可能
落在表到位之前，那一瞬间是一堆没有样式的裸元素。这两件事因此绑在同一个清理单元里——拆成两处
就只剩「谁先跑」这种靠排列顺序的默契。

## 二、模块划分与依赖方向

五块东西，箭头**全是单向的**：

| 模块 | 管什么 | 它**不知道**什么 |
| --- | --- | --- |
| 令牌包 | 值：语义变量的两套值、preflight、层顺序声明 | 不知道有哪些件，不知道 Tailwind 前缀这回事，**连 node 半都没有**（产物是两份 css） |
| 每个件自己的表 | 规则：本件用到的那些工具类，类名带本件的前缀 | 不知道别的件存在，不知道值最终是多少（它只写 `var(…)`） |
| 外壳 | 搬运与容器：注三张表、给每一格一个容器、把这一格变成容器查询的根 | **不知道任何件的类名**，也不知道件的表里有什么 |
| 主题件 | 用户覆盖：字体两项 + 一整段自定义 CSS，交给外壳在最后注 | 不知道任何件存在，也不知道外壳把它注在第几位（它只交出一段字符串） |
| 内核 | 只搬运共享声明，拼 importmap | 不认识 `react`，不认识任何类名，不认识任何包名 |

依赖方向是：**件 → 令牌**（构建期引映射面、运行期读页面上那份值），**件 → 外壳**
（注册窗格时报自己那两个地址），**外壳 → 主题件**（一条软契约命令），**内核 → 谁都不依赖**
（它只读清单字段）。反向的箭头一条都没有：

- 令牌包不知道有哪些件，所以加一个件、删一个件，它一个字都不用改
- 外壳不知道件的类名，所以件改自己的样式，外壳不用重新构建
- 主题件不知道谁在用它的启动样式，外壳没装它就没有这一步，它自己照常活着

**换掉实现要不要改调用方**，逐个问一遍都过得去：令牌把 zinc 换成别的底色，件一行不改；
一个件把自己的表从头重写，外壳一行不改；主题件被另一个件顶替掉（只要还应那条命令名），
外壳一行不改。

## 三、接口划分

这一层是**契约**：变了就得所有人跟着变，所以要一条条钉住。

### 令牌的契约有两个面，缺一不可

下面这几段是「看了就懂这个机制为什么长这样」的那种，每段配一句它说明了什么。

### 层顺序与 preflight，为什么由令牌表来管

{/* ref file="../packages/tokens/build.ts" lines="16-32" */}

**这段说明什么**：件的表只写工具类那一层、不声明层与层的先后，所以顺序只能由**先加载的那张**
来声明。而 preflight 是一份裸规则，**未分层的规则优先级高于所有分层规则**——不把它包进
`base` 层，它会盖掉每一个件的工具类。**「未分层的规则赢过所有分层规则」这一条语法事实，
在这一页解释了两件事**：preflight 为什么必须包起来，以及（下面会讲到）用户自己那段
自定义 CSS 为什么能压过一切。

### 映射面为什么单独一个文件

## 五、取舍与了断

拍板经过、验的读数、迁移的那几笔提交，全在[定过的事](/docs/decisions)的 2026-09-09 那条，
这儿不重抄。这一节补两样那条没展开的：**否掉的候选**与**残余的耦合**。

### 否掉的三个候选

**Shadow DOM。** 最彻底的隔离，每个件一个 shadow root，样式天然出不去也进不来。否掉有两条：
一是 `@property` 声明在 shadow root 里被忽略，而 Tailwind 4 的内部机制大量用它；二是弹层
组件的「点外面关掉」那类判断在 shadow 边界上有一堆历史问题。**为了一层隔离，把组件生态的
可用性押上去，不划算**——何况值本来就该穿透，shadow 恰恰把值也挡在外面。

**共享一个组件库。** 所有件从一个包里 import 按钮。母仓实测过：**CSS 一分没省**——因为每个件
仍然要为自己用到的类编一张表，共享的只是 JS 那点字节；换来的是一条硬依赖，那个包升一次版
所有件都得跟。

**每个件全自带。** 连令牌也各带各的。那样**主题的一致性无从保证**：几个件几份颜色值，
换主题要所有件一起重新构建、一起发版。这条恰恰是「值必须全页共享一份」那一问的反证。

### 残余的耦合，两条

**一、Tailwind 内部那批 `@property` 不随前缀走。** 每张表各注册一遍同名的那批，同名后注册的
赢。所以**全生态仍然得同一个 Tailwind 大版本**——这条不是前缀方案引入的，但前缀方案也没消掉
它。

**二、前缀会把内置主题变量名也改掉**，所以令牌只能经映射面送值（第四节钉过那条包清单注释）。
这意味着「在页面上全局声明一份 Tailwind 默认主题去统一所有件」这条路是走不通的，
**语义令牌是唯一的送值通道**。

还有一条明面上的税：**源码里每个类多一个前缀**，一直要交。

## 六、写一个带界面的件

原理讲完了，做法就很短。

**一、`components.json` 填两处**：`tailwind.css` 指一个真实存在的样式入口路径（这个字段是
必填的，省了报一句没有细节的错），`tailwind.prefix` 填本件的短名——CLI 拉下来的组件因此自带
前缀，一处都不用手改。形状照第一节钉的那份抄。

**二、写那五行样式入口。** 照第四节钉的那五行原样抄，只把前缀换成本件的短名。四条 import
一条都不能省。

### 会静默出事的那几件事

这一族有个共同的性质：**「编不出规则」在编译器眼里跟「这不是个类名」是同一回事**，
所以它们全都不报错。

| 干了什么 | 现象 | 怎么防 |
| --- | --- | --- |
| 入口里没引令牌的映射面 | 颜色类**整个是空的**——语义色编不出对应的变量引用 | 五行入口一行不省 |
| 入口里没引动画那个包 | 动画那一族类名一个字节都不出，菜单永远硬切 | 同上 |
| 类名忘了带前缀 | 那个类不生效，页面上就是那一处没样式 | 前缀守卫 |
| 标记类（当锚的那种）没带前缀 | 变体的选择器**永远不命中**，类名和规则都在，只是对不上 | **守卫抓不住**，只能靠知道这条 |
| 在件的表里写 `:root { --primary: … }` | 要么盖了全页，要么跟别处不一致 | 令牌是页面共享的那一份，件的表里不碰它 |
| 想按窗格宽度换布局，却写成了视口断点 | 按整窗大小判，拖窄这一格毫无反应 | 用容器查询变体（带 `@` 的那种），根是外壳给的容器 |

最后一条值得多说一句：**窗格不是视口**。这条线上一个件可能被拖成 300px 宽的一条，也可能占
满 1000 多像素，而整窗大小自始至终没变过。件里的响应式判据要问的是「我这一格现在有多宽」，
不是「这个窗口有多大」。
