## 相对 import 必须带 `.js`，少了它不报错

构建产物由 node 直接加载（loader 不打包），ESM 不补扩展名。少了 `.js` 的症状是
**插件加载不了，日志里一个字都没有**——写第一个插件时就遇到了，查了几分钟才定位。

（现在内核会把这类加载错误写进日志：同样的错是一行带路径的 `ERR_MODULE_NOT_FOUND`。）

本想让 TypeScript 替我们强制这一条，**结果不行**：

{/* ref file="../tsconfig.base.json" lines="4-6" */}

`moduleResolution: nodenext` 会强制相对 import 带扩展名，但 **cordis 自己的 `.d.ts` 不兼容
它**——那边写的是 `export * from './context'`，相对 import 不带扩展名。nodenext 解析不了，
整个 `Context` 类型退化成空，症状是 `ctx.logger` / `effect` / `provide` 全报「不存在」。

所以只能用 `bundler`，这一条改由构建产物检查负责：

{/* ref file="../plugins/commands/tests/artifact.test.ts" lines="21-43" */}

同一组测试还检查第二条：**构建产物里不许有包名 import**（node 内置模块除外）。插件要自包含——
词汇表包与 cordis 都只 `import type`，编译时擦除，`gwb-commands` 的构建产物里只有一条 `./registry.js`。

没构建时整组跳过，`pnpm check` 不依赖构建。

## 词汇表包写 peer，不写 dev

判据「运行时真 import 了才写 peer，只 `import type` 写 dev」**漏了中间一种情况**：

{/* has file="../plugins/commands/package.json" text="peerDependencies" */}

`gwbCommands.run` 返回的是 `GwbResult`——它出现在**导出的类型**里，用这个插件的插件装上它之后必须
解析得到。写成 `devDependency` 的症状是用它的插件那边全解析不到，因为**发布出去的包不带
devDependencies**。

内核仓也遇到过同一个问题（词汇表包的 `GwbContext extends Context` 把 cordis 写成 dev）。
三档判据的正本在内核仓的 `CLAUDE.md`。

**附带的好处**：声明成 peer 之后，pnpm 把词汇表包自动装进 home，用它的插件不用手动装。

`cordis` 仍然是 dev——它只在 `apply` 的参数类型里用，不出现在导出的类型里。

## 同名命令后登记的生效，但要告警

{/* ref file="../plugins/commands/src/registry.ts" lines="43-55" */}

插件之间平等，换掉一条命令是允许的。但不告警的话，调用方从此调到另一个插件的处理函数上，
**两边都不报错**——所以同名时要写一条告警，写明原来是哪个插件、现在是哪个。


## 注销只删自己那条

同一段里那个 `if (byName.get(def.name) === record)`：同名命令被替换后，**先卸载的那个插件不能把接手
的那条一起删掉**。少了这个比较，卸载一个插件会让另一个插件登记的命令跟着消失。


## 处理函数抛错不抛给调用方

{/* ref file="../plugins/commands/src/registry.ts" lines="62-84" */}

调用方可能是页面上的一次点击。处理函数自己返回了带 `ok` 的对象就原样返回，其余一律算成功。

## 服务
### 服务要知道调用方是哪个插件，用 `Service` 基类，别用 `accessor`

`ctx.gwbData` 返回的目录要**自动绑定到取用它的那个插件**——插件不自报名字，也就没法冒用别人的
名字读别人的数据。cordis 有两种写法能让服务知道调用方是谁，实测后只有一种可用：

{/* ref file="../plugins/data/src/index.ts" lines="61-78" */}

- **`ctx.accessor(name, { get() {…} })`**：`get` 里的 `this` **确实**是调用方的 ctx（实测
  `child.probe === child`）。但**`inject` 不认它**——插件写 `inject: ['那个名字']` 会一直等待，
  fiber 建出来了、`apply` 不执行，**而且不报任何错**。只能从「插件加载了但什么都没发生」这个现象去查
- **`Service` 基类**：`inject` 认它，而且方法里的 `this.ctx` 就是**调用方**的 ctx。实测两个插件
  各自取同一个服务，拿到的身份互不相同

身份从 `this.ctx.fiber.entry` 上取两样：**`entry.id` 是身份**（数据存在哪按它算），
`entry.options.name` 只说明装的是哪个包，用在提示文字里。**`entry` 是 loader 加上去的属性，
不是 cordis 本身的接口**，所以代码里按运行时的形状取、不改全局类型声明——普通的 `Context` 上没有它
（根上下文取到的 `hasEntry` 是 false）。

另外：`extends Service` 意味着 **cordis 是运行时依赖，要写 peer**（两份 cordis 的
`instanceof` 对不上）。对比 `gwb-commands`：它只在 `apply` 的参数类型里用 cordis，写 dev。
同一个包在两个插件里写法不同，所以依赖写法的三档判据要逐个插件判断。

### 数据归**条目**所有，不归包

`gwb-data` 不按包名分目录（`<home>/data/@godcreator/gwb-x/`）：cordis 的条目模型里
**`id` 才是身份**，`name` 只说明装的是哪个包——同一个包可以在 `cordis.yml` 里配好几条条目，
各有各的 config（两条 `gwb-py-cli` 分别配 3.11 与 3.12 的解释器）。按包名分的话这两条
**共用一个数据目录、互相覆盖**。

**这条不是出了问题才发现的，是统一归属时看出来的**：`gwb-settings` 一开始就按条目 id 分区，
两个插件对「一份数据归谁」给出了两个答案。不一致本身就是问题——将来清理「没有所属条目的
数据 / 设置」的插件得同时懂两套规则。

两边现在是同一个答案：`gwb-data` 存在 `<home>/data/<末段>/`，`gwb-settings` 的 home 级分区也用
那个末段（机器级那一层仍按包名，那是有意的，理由在[设置](/docs/settings)那页）。

### 条目 id 用作目录名：不能含冒号，所以只取末段

`entryId` 的样子是 **`home:hello`**。有三点：

- **冒号在 Windows 上是保留字符**（盘符分隔）。`mkdir home:hello` 不是干净地失败，
  而是可能造出一个 NTFS 备用数据流——目录看不见，写进去的字节也找不回来
- **`home` 那段不归插件管**：它是**内核**的 `ENTRY_ROOT` 常量（`cordis:include`
  那条条目的 id），`:` 是 cordis 的 `EntryTree.sep`，`Entry.id` 的 getter 用它把父条目 id
  和自己的 id 拼起来。内核改一次那个常量，所有目录名都会跟着变
- **末段才是人在 `cordis.yml` 里手写的那个 id**

所以取末段：既没有冒号，又**不依赖内核那个常量**。比「把冒号换成短横线」好在第二点。

代价是**多段 id 会重名**——group 嵌套出来的 `home:a:hello` 与 `home:b:hello` 末段一样。
所以加了一条检查：**超过两段直接抛错**，不让它们悄悄共用目录。真用上 group 时，目录算法要和
这条检查一起重新设计。

id 要用作目录名与分区名，比包名危险，于是和文档名、设置名用同一套 kebab-case 规则，
**对分段后的每一段**校验（字符集里没有点号，`.` 与 `..` 这两个路径穿越段也就进不来）。

{/* ref file="../plugins/data/src/paths.ts" lines="35-64" */}

**两个插件的这段算法必须给出同一个答案**，而它们是两份副本（`gwb-data` 的 `entryDirName`、
`gwb-settings` 的 `entrySection`）。十几行纯逻辑，为它新建一个共享包通不过准入判据的第二条；
两边注释里互相提到对方，改一处就要改另一处。**再有第三个插件要用它时，重新判断要不要抽成共享包。**

{/* ref file="../plugins/settings/src/paths.ts" lines="60-92" */}

### 没手写 id 的条目，数据每次启动新建一份

条目没写 `id` 时，loader 的 `ensureId` 生成一个 8 位随机十六进制串，**而且启动时不写回
文件**——每次启动换一个，那条条目的数据与设置每次都新建一份。

`gwb-settings` 和 `gwb-data` 遇到这种条目都写一条 warn。**不抛错**（这个条目本来能正常运行），
**也不省略日志**（数据对不上是最难查的那种问题）。

`a3f9c210` 是**合法的 kebab-case**，所以这条检查和上面的字符集校验互不覆盖，两条都要。
误报可以接受：手写一个正好 8 位十六进制字符的 id（`deadbeef`）会多一条 warn，代价只是
一行日志。

### cordis 对服务不做任何版本校验，所以 peer 的 range 是唯一的校验点

读 cordis 4.0.0-rc.9 的构建产物确认的，四条都是「没有」：

- **服务的契约只有一个字符串名字**。注册记录只有 `{name, value, fiber, check}` 四个
  字段，没有版本、没有 schema、没有描述
- 类型里那个 `Plugin.provide` 字段**运行时从来不读**，只在类型里存在（全文搜过，只有类型声明
  处出现，没有任何读取点）
- **`inject` 全是硬依赖，没有可选形式**——没有 `'foo?'` 后缀，也没有 `{required, optional}`
  分组（那是 cordis 3.x 的老写法，rc.9 会把它当成两个**叫 `required` 和 `optional` 的服务名**，
  于是一直 PENDING）
- **依赖不满足时什么都不提示**：无日志、无超时、无报错

所以可选依赖只能用 `ctx.inject([...], cb)` 建一个子 fiber——子 fiber 缺服务就一直
PENDING，父插件照常加载。本仓的插件登记说明书（`gwbSkills`）用的都是这种写法。

**插件之间的版本约束因此只有 `peer` 的 range 一处起作用**，在 pnpm 安装的时候。插件用了
新版才有的字段、而 home 里装的是旧版时，旧版的 `normalize` 直接忽略那个字段——整个调用过程没有任何提示。
两种错的代价不对称：不必要地写了，只是多一条声明；该写没写，就是不报错地失效。所以**服务依赖也写 peer**，
哪怕构建产物里一处都不 import 它。

### `await ctx.plugin(...)` 会立即 resolve，即便插件根本没运行

`Fiber.await()` 是 `while (this.inertia) await this.inertia`——依赖没满足时 `inertia` 是
`undefined`，那个 while 一次都不进。**别拿它当「加载完成」的信号**：写实验脚本时 `await
ctx.plugin(x)` 之后立刻去调 `x` 提供的服务，服务可能还不存在。


## 发版
### `pnpm check` 不构建——不加 `prepublishOnly` 就会把旧的构建产物发出去，而且不报错

`pnpm check` 是 typecheck + lint + test，**它不运行 build**。而插件的 `package.json` 里如果没有
`prepublishOnly`，`pnpm publish` 就把上一版的 `dist/` 原样发出去了。

**hello 0.0.4 就遇到过**：加了 store 的实验代码，发布、装进 home，日志里写着已加载
`home:hello`，可是实验代码的输出一行都没有，磁盘上也没出现文件。查了一圈代码才想到——**发布的是
0.0.3 的构建产物**（那时 `apply` 还是空的）。

症状很难认出来：插件加载了、不报错，只是新写的代码全没生效。

所有包都补上 `"prepublishOnly": "pnpm build"`。


## 验收方法
### 装插件时**共享包要显式列出**——pnpm 自动装的 peer 不算

验收用的新 home 里装了 `cli` / `shell` / `logger` / `hello` 四个插件，启动之后**页面一片空白**。

**症状**：日志里一条加载错误都没有，四个插件都报告已加载，外壳也识别出来了；错误在渲染进程日志的最后一行：

```
19:02:46.548 I renderer SHARED （空）
19:02:46.581 E renderer 起不来:TypeError: Failed to resolve module specifier "react".
```

**为什么**：插件的 `peerDependencies` 里写着两个共享包，而 pnpm 的 `auto-install-peers` 确实
把它们装进了 `node_modules`——**但没写进 home 的 `dependencies`**。而内核收集 `gwb.shared`
声明时**只看 `dependencies`**（共享包不是插件、不在条目树上，dependencies 是唯一能看到它们的地方）。
于是 importmap 是空的，任何带界面的插件都解析不到 `react`。

**解决办法**：`kernel.install` 的 specs 里把 `@godcreator/gwb-shared-react` 与
`@godcreator/gwb-tokens` 一起写上。**验收清单里只要有带界面的插件，这两个就要一起装。**

容易被「peer 会被 pnpm 自动装进 home」这句话误导——**这句话没错，但装进 `node_modules` 不等于
写进了 dependencies**。

### 验证只有 node 侧的插件不必启动 electron，但 `createRequire` 要先 `realpath`

无界面的插件可以直接在 home 里用 node 建一个真的 cordis 上下文来验证——服务能不能提供、命令能不能
登记到命令总线、能不能启动子进程，都验证得到，比启动 electron 快得多。要注意两点：

- **`cordis` 不在 home 顶层**。它是插件的 peer，pnpm 把它装在 `.pnpm` 里插件实际所在的那一层。
  实验脚本 `import 'cordis'` 直接报 `ERR_MODULE_NOT_FOUND`
- **要从插件那一层解析，而且要先 `fs.realpathSync`**。`node_modules/@godcreator/x` 是个
  软链接，`createRequire` 从软链接路径往上找 node_modules 是找不到 cordis 的：

  ```
  Error: Cannot find module 'cordis'
  Require stack:
  - <home>\node_modules\@godcreator\gwb-py-cli\dist\index.js
  ```

  解析软链接之后就到了 `.pnpm/<插件>@<hash>/node_modules/` 这一层，cordis 在那里

**还必须是同一份 cordis**——两份的 `Service` instanceof 对不上，插件加载后会出各种难以解释的错。
所以实验脚本里的 `Context` 也从插件那一层解析，不从脚本自己的位置解析。

另外：插件按 `<home>/node_modules/...` 的路径 import 即可，node 会自己解析到 `.pnpm`
里的实际目录——插件算出来的包根就是它实际安装的位置，`gwb-py-cli` 的 venv 也建在那里，
这正是要验证的。

## MCP 与说明书
### 块注释里出现 `*/` 会把注释提前结束

写 MCP 插件的文件头注释时提到了 `notifications/*/list_changed`——**其中的 `*/` 直接结束了
`/** … */`**，后面整段注释变成了代码。

症状最难认：报的不是「注释没闭合」，而是一整屏

```
error TS1443: Module declaration names may only use ' or " quoted strings.
error TS1127: Invalid character.
```

**看着完全像文件编码坏了**——第一反应是去查 UTF-8 与 BOM，读了文件开头的字节才排除。
路径样式的 glob 写进块注释之前先看一眼里面有没有 `*/`。

### 函数声明拿不到外层 `const` 的类型收窄

`const cli = ctx.gwbCommands` 加一句 `if (cli === undefined) return` 之后，箭头函数里 `cli`
是收窄过的，**`function` 声明里不是**——它会被提升，TS 认为它可能在那句检查之前就被调用。

{/* ref file="../plugins/mcp/src/index.ts" lines="237-249" */}

症状是 `'cli' is possibly 'undefined'`，而上面明明刚判断过。改成 `const … = () => {}` 即可。

### args 被客户端转成字符串——无参数的命令正常，带参数的全部失败

2026-09-12 起多次遇到：经 MCP 调用命令（当时的工具名是 `gwb_command_run`），无参数的命令一切正常，
**带 args 的调用全部被命令拒绝，报「参数要是个对象」**，两天里提了两条反馈才定位。用对照实验判断是
哪一层的问题：同一调用用 curl 直接发对象就成功——MCP 入口与命令本身都没问题，`args` 的 schema 是
`z.unknown()`，协议层什么形状都接受，**是客户端把嵌套对象序列化成 JSON 字符串再发**；
`isRecord(字符串)` 为假，命令拒收。

在 MCP 入口这边修，不指望客户端改：`runCommand` 入口先过一道 `coerceArgs`，字符串先
`JSON.parse`，解析成功就用结果，解析失败就原样传入——JSON 字面量来回转换不丢信息，真要传字符串参数的
命令不受影响。

{/* ref file="../plugins/mcp/src/tools.ts" lines="23-55" */}

### `Accept` 少一个值就是 406

SDK 的 streamable HTTP 要求 POST 同时带 `application/json` **与** `text/event-stream`。
只写前者拿到的是

```
406 {"error":{"code":-32000,"message":"Not Acceptable: Client must accept both …"}}
```

手工用 curl / `Invoke-WebRequest` 试这个入口时很容易只写 `application/json`，然后把 406
误判成鉴权失败或者路由没注册。这条只在实机上试得出来，代码里看不见。

### 共享包被当作 peer 自动装，就不在 home 顶层，importmap 是空的

新建一个 home、`pnpm add` 几个插件之后启动，渲染进程报

```
[renderer] SHARED （空）
[renderer] 起不来:TypeError: Failed to resolve module specifier "react"
```

原因是内核的 `collectShared` 读的是 **`<home>/package.json` 的 `dependencies`**，
而 `gwb-shared-react` / `gwb-tokens` 是作为别的包的 peer 被 pnpm 顺带装进 `node_modules` 的
——文件在那里、import 得到，但**不在顶层 dependencies 里**，所以 importmap 一条声明都收集不到。

`pnpm add` 显式装一次这两个包就好。**只有 node 侧的插件完全不受影响**，所以验证无界面的插件时
这条报错可以先不管——但别把它当成自己刚写的那个插件的问题。

hello，再用 `gwb_command_list` 列命令。命令表从 52 条变成 50 条——**只少了 `hello.node` 与
`hello.python`**，`hello.probe` / `hello.bump` 还在，直接调用返回的是
`Error: cannot get required service "gwbData" in inactive context`。

后一对是 hello 自己直接 `cli.register`，**没包 `ctx.effect`**——`register` 返回的注销函数
