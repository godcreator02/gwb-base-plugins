## 相对 import 必须带 `.js`，而它是个静默失败

产物给 node 直接加载（loader 不打包），ESM 不做扩展名补全。少了 `.js` 的症状是
**插件挂不上，而日志一个字都没有**——第一个插件就是这么撞的，查了几分钟才定位。

（内核后来补了保底 error 出口，同样的错现在当场是一行 `ERR_MODULE_NOT_FOUND` 带路径。）

本想让 TypeScript 替我们强制这一条，**结果不行**：

{/* ref file="../tsconfig.base.json" lines="4-6" */}

`moduleResolution: nodenext` 会强制相对 import 带扩展名，但 **cordis 自己的 `.d.ts` 不兼容
它**——那边写的是 `export * from './context'`，相对 import 不带扩展名。nodenext 解析不了，
整个 `Context` 类型退化成空，症状是 `ctx.logger` / `effect` / `provide` 全报「不存在」。

所以只能回 `bundler`，那一条改由产物守卫拦：

{/* ref file="../plugins/commands/tests/artifact.test.ts" lines="21-43" */}

顺带钉住第二条：**产物里不许有裸名 import**。插件该是自包含的——契约包与 cordis 都只
`import type`、编译期擦除，`gwb-commands` 的产物里除了一条 `./registry.js` 什么都没有。

缺产物时整组跳过，门禁不依赖 `build`。

## 契约包走 peer，不是 dev

判据「运行时真 import 了才写 peer，只 `import type` 写 dev」**漏了中间一档**：

{/* has file="../plugins/commands/package.json" text="peerDependencies" */}

`gwbCommands.run` 回的是 `GwbResult`——它出现在**导出的类型**里，消费方装了这个插件之后必须
解析得到。写成 `devDependency` 的症状是消费方那边全解析不到，因为**发布出去的包不带
devDependencies**。

同一个坑在内核仓也撞了一次（词汇表包的 `GwbContext extends Context` 把 cordis 写成 dev）。
三档判据的正本在内核仓的 `CLAUDE.md`。

**白得的一条**：peer 声明之后，pnpm 把契约包自动装进了 home，消费方不用手动装。

`cordis` 仍然是 dev——它只在 `apply` 的参数类型里用，不出现在导出面。

## 撞名是后来者赢，但不许静默地赢

{/* ref file="../plugins/commands/src/registry.ts" lines="26-44" */}

插件一律平等，换掉一条命令是应有之义。但静默改派的话，调用方从此打到另一个插件的处理器上，
**两边谁都不会报错**——所以撞名要出一条告警，说清谁换了谁。


## 注销只收自己那份

同一段里那个 `if (byName.get(def.name) === record)`：撞名之后**先卸载的那个插件，不该把接手
的那份一起带走**。少了这个判等，卸一个插件会让另一个插件注册的命令跟着消失。

## 服务
### 要认出「是谁在取我」，用 `Service` 基类，别用 `accessor`

`ctx.gwbData` 交出来的那个目录得**自动绑定到取它的那个插件**——插件不报名字，也就没法报别人的
名字去读别人的数据。cordis 有两条路能做到「服务感知调用方」，实测过才知道只有一条能走：

{/* ref file="../plugins/data/src/index.ts" lines="52-71" */}

- **`ctx.accessor(name, { get() {…} })`**：`get` 里的 `this` **确实**是访问者的 ctx（实测
  `child.probe === child`）。但**`inject` 不认它**——插件写 `inject: ['那个名字']` 会永远等下去，
  fiber 建出来了、`apply` 不跑，**而且一声不吭**。查这个现象只能靠「插件挂上了但什么都没发生」
- **`Service` 基类**：`inject` 认它，而且方法里的 `this.ctx` 就是**消费者**的 ctx。实测两个插件
  各自取同一个服务，拿到的身份互不相同

身份从 `this.ctx.fiber.entry` 上取两样：**`entry.id` 是身份**（数据落哪按它算），
`entry.options.name` 只是「装的哪个包」，用来把话说清楚。**`entry` 是 loader 挂上去的、
不是 cordis 本体的面**，所以代码里按运行时形状取、不动全局类型声明——裸 `Context` 上没有它
（根上下文取到的 `hasEntry` 就是 false）。

顺带一条：`extends Service` 意味着 **cordis 是运行时依赖，得写 peer**（两份 cordis 的
`instanceof` 对不上）。对照 `gwb-commands`——它只在 `apply` 的参数类型里用 cordis，那边是 dev。
同一个包在两个插件里档位不同，这正是三档判据要一条条判的原因。

### 一份数据的主人是**条目**，不是包

`gwb-data` 原来按包名切目录（`<home>/data/@godcreator/gwb-x/`）。但 cordis 的条目模型里
**`id` 才是身份**，`name` 只说「装哪个包」——同一个包可以在 `cordis.yml` 里挂好几条条目，
各有各的 config（两条 `gwb-py-cli` 分别配 3.11 与 3.12 的解释器）。按包名切的话这两条
**共用一个数据目录、互相覆盖**。

**这条不是撞出来的，是改归属时认出来的**：`gwb-settings` 一开始就按条目 id 分区，两个
姊妹插件对「谁是一份数据的主人」给出了两个答案。不一致本身就是坑——将来扫「无主的数据 /
无主的设置」的那个插件得同时懂两套规则。

现在两边同一个答案：`gwb-data` 落 `<home>/data/<末段>/`，`gwb-settings` 的 home 级分区也是
那个末段（机器级那档仍是包名，那是有意的，理由在[设置](/docs/settings)那页）。

### 条目 id 当目录名：冒号进不去，所以只取末段

`entryId` 长这样：**`home:hello`**。三件事叠在一起：

- **冒号在 Windows 上是保留字符**（盘符分隔）。`mkdir home:hello` 不是干净地失败，
  而是可能造出一个 NTFS 备用数据流——目录看不见，写进去的字节也找不回来
- **`home` 那段不是插件的东西**：它是**内核**的 `ENTRY_ROOT` 常量（承载 `cordis:include`
  那条条目的 id），`:` 是 cordis 的 `EntryTree.sep`，`Entry.id` 的 getter 拿它把父条目 id
  跟自己的拼起来。内核改一次那个常量，所有目录名跟着变
- **末段才是人在 `cordis.yml` 里手写的那个 id**

所以取末段：既没有冒号，又**跟内核那个常量脱钩**。比「把冒号换成短横线」好在第二条。

代价是**多段 id 会撞**——group 嵌套出来的 `home:a:hello` 与 `home:b:hello` 末段一样。
配一条守卫顶着：**超过两段当场抛**，别静默撞。真出现 group 的那天，目录算法要连着这条
守卫一起重新定。

id 现在要当目录名与分区名用，比包名危险，于是跟文档名、设置名同一套 kebab-case，
**对分段后的每一段**校验（点号不在字符集里，`.` 与 `..` 这两个穿越段因此也进不来）。

{/* ref file="../plugins/data/src/paths.ts" lines="35-64" */}

**两个插件的这段算法必须给同一个答案**，而它们是两份拷贝（`gwb-data` 的 `entryDirName`、
`gwb-settings` 的 `entrySection`）。十几行纯逻辑，为它新建一个共享包过不了准入判据第二关；
两边注释里互相点名，改一处就得改另一处。**下一处要用到它的插件出现时，这个判断要重看。**

{/* ref file="../plugins/settings/src/paths.ts" lines="52-84" */}

### 没手写 id 的条目，数据每次启动新建一份

条目没写 `id` 时 loader 的 `ensureId` 发一个 8 位随机十六进制串，**而且启动这条路上不写回
文件**——每次启动换一个，那条条目的数据与设置每次都新建一份。

`gwb-settings` 先有的这条 warn，`gwb-data` 这次跟上。**不抛错**（那条件本来能跑），
**也不静默**（对不上是最难查的那种）。

`a3f9c210` 是**合法的 kebab-case**，所以这个守卫跟上面那条字符集校验完全不重叠，两条都要。
误报也认了：手写一个正好 8 位十六进制字母的 id（`deadbeef`）会白挨一句 warn，代价只是
一行日志。

### cordis 对服务不做任何版本校验，所以 peer 的 range 是唯一的校验点

读 cordis 4.0.0-rc.9 的产物查实的，四条都是「没有」：

- **服务的契约面就是一个裸字符串名字**。注册记录只有 `{name, value, fiber, check}` 四个
  字段，没有版本、没有 schema、没有描述
- 类型里那个 `Plugin.provide` 字段**运行时从来不读**，是个死类型（全文搜过，只有类型声明
  处出现，没有任何读取点）
- **`inject` 全是硬依赖，没有可选形式**——没有 `'foo?'` 后缀，也没有 `{required, optional}`
  分组（那是 cordis 3.x 的老写法，rc.9 会把它当成两个**叫 `required` 和 `optional` 的服务名**，
  于是永远 PENDING）
- **依赖不满足是完全静默的**：无日志、无超时、无报错

所以「可选依赖」只能靠 `ctx.inject([...], cb)` 开一个子 fiber——子 fiber 缺服务就永远
PENDING，父插件照常挂上。hello 给 `gwbSkills` 与两条 CLI 用的都是这一招。

**跨插件的版本约束因此只剩 `peer` 的 range 一个执行点**，就在 pnpm 装包那一刻。插件调一个
新版才有的字段、而 home 里装着老版时，老版的 `normalize` 直接忽略那个字段——全链路零提示。
代价不对称：写了而不必要，只是多一条声明；该写而没写，是静默失效。所以**服务依赖也写 peer**，
哪怕产物里对它零 import。

### `await ctx.plugin(...)` 会立即 resolve，即便插件根本没跑

`Fiber.await()` 是 `while (this.inertia) await this.inertia`——依赖没满足时 `inertia` 是
`undefined`，那个 while 一次都不进。**别拿它当「加载完成」信号**：写探针时 `await
ctx.plugin(x)` 之后立刻去调 `x` 提供的服务，服务可能压根还不在。


## 发版
### `pnpm check` 不构建——不加 `prepublishOnly` 就会静默发出旧产物

`pnpm check` 是 typecheck + lint + test，**它不跑 build**。而插件的 `package.json` 里如果没有
`prepublishOnly`，`pnpm publish` 就把上一版的 `dist/` 原样发出去了。

**这次就中招了**：hello 0.0.4 加了 store 探针，发出去、装进 home、日志里明明写着「挂上
home:hello」，可是探针的输出一行都没有，盘上也没出现文件。查了一圈代码才想起来——**发的是
0.0.3 那版的产物**（那时 `apply` 还是空的）。

症状极难认：插件挂上了、不报错、只是新写的东西全没生效。

所有包都补上 `"prepublishOnly": "pnpm build"`。

## 验收方法
### 装插件时**共享包要显式带上**——pnpm 自动装的 peer 不算数

验收开的干净 home 里装了 `cli` / `shell` / `logger` / `hello` 四个插件，起来之后**页面一片空白**。

**症状**：日志里一句挂载错误都没有，四个插件全报「挂上」，外壳也认出来了；错在渲染层的最后一行：

```
19:02:46.548 I renderer SHARED （空）
19:02:46.581 E renderer 起不来:TypeError: Failed to resolve module specifier "react".
```

**为什么**：插件的 `peerDependencies` 里写着两个共享包，而 pnpm 的 `auto-install-peers` 确实
把它们装进了 `node_modules`——**但没写进 home 的 `dependencies`**。而内核收 `gwb.shared`
声明时**只扫 `dependencies`**（共享包不是插件、不在条目树上，那是唯一看得见它们的地方）。
于是 importmap 是空的，任何带界面的插件都解析不到 `react`。

**修**：`kernel.install` 的 specs 里把 `@godcreator/gwb-shared-react` 与
`@godcreator/gwb-tokens` 一起写上。**验收清单里但凡有带界面的插件，这两个就得跟着装。**

这条容易被「peer 会被 pnpm 自动装进 home」那句话骗过去——**那句话没错，错在「装进来」不等于
「进了 dependencies」**。

### 验 node-only 的插件不必起 electron，但 `createRequire` 得先 `realpath`

无界面的插件可以直接在 home 里拿 node 挂一个真的 cordis 上下文验——服务挂得上、命令进得了
总线、执行核起得来进程，全都验得到，比起 electron 快得多。两处讲究：

- **`cordis` 不在 home 顶层**。它是插件的 peer，pnpm 把它装在 `.pnpm` 里插件的真身那一层。
  探针 `import 'cordis'` 直接报 `ERR_MODULE_NOT_FOUND`
- **要从插件那一层解析，而且得先 `fs.realpathSync`**。`node_modules/@godcreator/x` 是条
  软链，`createRequire` 拿软链路径往上找 node_modules 是找不到 cordis 的：

  ```
  Error: Cannot find module 'cordis'
  Require stack:
  - <home>\node_modules\@godcreator\gwb-py-cli\dist\index.js
  ```

  解开软链之后就落在 `.pnpm/<插件>@<hash>/node_modules/` 那一层，cordis 在那儿

**还必须是同一份 cordis**——两份的 `Service` instanceof 对不上，插件挂上去会以莫名其妙的方式坏掉。所以探针里的
`Context` 也从插件那一层解析，不从探针自己的位置。

顺带：插件走 `<home>/node_modules/...` 的路径 import 就好，node 会自己 realpath 到 `.pnpm`
里的真身——插件算出来的包根正是它实际装着的位置，`gwb-py-cli` 的 venv 也就建在那儿，
而那正是要验的东西。


## gwb:// 取货
### 子路径是 `exports` 表里的键，不是文件名

约定是 `gwb://asset/plugins/<包名>/<exports 子路径>`，而**子路径就是 `exports` 键去掉
开头那两个字符**：`"./client": "./dist/client.js"` 这条，地址里写的是 `client`，
不是 `client.js`，也不是 `dist/client.js`。

第三阶段写 `PluginPane` 时想当然写成了 `client.js`，症状是

```
TypeError: Failed to fetch dynamically imported module: gwb://asset/plugins/@godcreator/gwb-hello/client.js
```

——**读着像网络错或者文件不在**，实际是内核拿 `./client.js` 去 `exports` 表里查、查不到。
同一个 URL 里紧挨着的 `style.css` 反而是对的（那条 exports 键就叫 `./style.css`），
两条并排更容易看漏。

（那段代码已随 `gwb://` 协议与外壳迁走——本页留档，钉码随之退场。）

## MCP 与 skill
### 块注释里出现 `*/` 会把注释提前关掉

写 MCP 那段头注释时提了一句「发不出 `notifications/*/list_changed`」——**那个 `/*/`
里的 `*/` 当场关掉了 `/** … */`**，后面整段注释变成代码。

症状最坑：报的不是「注释没闭合」，而是一屏

```
error TS1443: Module declaration names may only use ' or " quoted strings.
error TS1127: Invalid character.
```

**看着完全像文件编码坏了**——第一反应是去查 UTF-8 与 BOM，读了字节头才排除。
路径样式的 glob 写进块注释之前先看一眼里头有没有 `*/`。

### 函数声明拿不到外层 `const` 的窄化

`const cli = ctx.gwbCommands` 加一句 `if (cli === undefined) return` 之后，箭头函数里 `cli`
是收窄过的，**`function` 声明里不是**——它会 hoist，TS 认为它可能在那句检查之前就被调用。

{/* ref file="../plugins/mcp/src/index.ts" lines="189-201" */}

症状是 `'cli' is possibly 'undefined'`，而上面明明刚判过。改成 `const … = () => {}` 即可。

### args 被客户端串化——无参命令幸存，带参全灭

2026-09-12 起多轮撞到：经 MCP 调 `gwb_command_run`，无参命令一切正常，**带 args 的调用
一律被命令端拒成「参数要是个对象」**，两天里投了两条 feedback 才定位。对照实验判的层：
同一调用 curl 直发对象就成——桥与命令面都没病，`args` 的 schema 是 `z.unknown()`，
协议层什么形状都放行，**是客户端把嵌套对象序列化成 JSON 字符串才发**；`isRecord(字符串)`
为假，命令端拒收。

修在桥上不赌客户端：`runCommand` 入口一道 `coerceArgs`，字符串先 `JSON.parse`，解析成
就用，解析不了原样送——JSON 字面量是无损 round-trip，真要传字符串参数的命令不受伤。

{/* ref file="../plugins/mcp/src/tools.ts" lines="23-55" */}

### `Accept` 少一个值就是 406

SDK 的 streamable HTTP 要求 POST 同时带 `application/json` **与** `text/event-stream`。
只写前者拿到的是

```
406 {"error":{"code":-32000,"message":"Not Acceptable: Client must accept both …"}}
```

手工 curl / `Invoke-WebRequest` 试这个入口时极容易只写 `application/json`，然后把 406
误判成鉴权挂了或者路由没挂上。这条只在实机试得出来，代码里看不见。

### 共享包被当 peer 自动装，就不在 home 顶层，importmap 是空的

新开一个 home、`pnpm add` 几个插件之后起来，渲染层报

```
[renderer] SHARED （空）
[renderer] 起不来:TypeError: Failed to resolve module specifier "react"
```

原因是内核的 `collectShared` 扫的是 **`<home>/package.json` 的 `dependencies`**，
而 `gwb-shared-react` / `gwb-tokens` 是作为别人的 peer 被 pnpm 顺手装进 `node_modules` 的
——躺在那儿够得着，但**不在顶层 dependencies 里**，所以一条 importmap 声明都收不到。

`pnpm add` 显式装一次这两个包就好。**node 半的插件完全不受影响**，所以验无界面的插件时
这条红字可以先放着——但别把它当成自己刚写的那个插件的问题。

### 停用条目不等于命令注销：登记命令不包 `effect`，名字就留在表里

hello，再 `gwb_command_list`。命令表从 52 条变 50 条——**只掉了 `hello.node` 与
`hello.python`**，`hello.probe` / `hello.bump` 还在，直接调回的是
`Error: cannot get required service "gwbData" in inactive context`。

两对命令的差别只在登记的写法。前一对经运行器登记，运行器内部替调用方挂在它的 effect 上；
后一对是 hello 自己直接 `cli.register`，**没包 `ctx.effect`**——`register` 回的注销函数
没人调，条目停了、fiber 灭了、表上的名字还在。hello 已迁验收仓（钉码跟过去钉得住），
