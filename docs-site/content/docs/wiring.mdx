**本页回答**：本仓插件提供哪些服务、命令与事件；注入了哪些服务、是必需还是局部注入、peer 怎么写；按名字调用了别家哪些命令、用了哪些约定通道。

每个插件一节，三张表：**提供**（别人能用它什么）、**注入**（它用 cordis 注入了谁的服务）、**按名字调用与约定通道**（没有类型检查连起来、只靠两边写同一个名字或同一个形状的连接）。第三张表里的连接没有类型检查，一边改了名字或形状，另一边多半要到运行时才出错，改之前先查这里。

几件八个插件共同的事，不在各节重复：

- **peer 里都写内核包** `@godcreator/gwb-kernel-desktop`（日志插件 `^0.10.0`，其余 `^0.9.0`），只 `import type` 它的 `GwbContext`、`GwbKernelApi`；命令回执 `GwbResult` 从 commands 取；继承 cordis `Service` 的插件另写 peer `cordis`（`^4.0.0-rc.10`），MCP 插件与日志插件不写。为什么这样写见[关键设计](/docs/design)
- **内核服务 `gwbKernel`** 由内核在根上下文上提供，不写进 `inject`。数据、设置、日志、MCP 四个插件用它，各自在 `src/vocab.ts` 里写一份 `requireKernel` 取它，取不到就抛错「ctx.gwbKernel 不在」；commands 另用它登记页面请求处理器，其余三个插件不用它
- **本仓别的插件写 peer** `workspace:^`（`devkit.release` 发版时换成 `^<版本号>`），只局部注入的在 `peerDependenciesMeta` 标 `optional`；代码只 `import type` 它们，构建产物里没有它们
- **loader 放在 fiber 上的条目** `fiber.entry`（`id`、`options.name`）不在 cordis 的类型里，提供服务的插件按运行时形状取，用它认出调用方是哪条条目、哪个包。细节见[条目身份](/docs/seams/entry-identity)

| 通道 | 对方 | 名字 | 用来做什么 |
| --- | --- | --- | --- |
| loader 的 `fiber.entry` | cordis loader | `entry.id`、`entry.options.name` | 条目 id 的末段定分区，包名记归属；服务按它分区，插件只能读写自己声明的项 |
| 磁盘文件（各插件共用一份） | 声明过设置的每个插件、设置界面、手工处理归属的人 | `<home>/settings.json`：每条条目一个分区（条目 id 末段）、`shared` 项进公共区 `*`、顶层 `$owners` 记分区归哪个包 | 所有插件的设置写在同一个文件里，按分区隔开 |
| 命令总线（被调） | 页面、agent、任何插件 | `settings.get`、`settings.set`、`settings.delete` 的 `{ section, key }` | 按位置读写**任意分区**，不看调用方身份 |
| 同一套算法的另一份 | gwb-data 的 `entryDirName` | `entrySection` | 条目 id 转分区名；两份必须给出同一个答案 |
