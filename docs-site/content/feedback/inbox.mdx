# 投来的反馈

**这一页收别的仓在用这些插件的过程中投来的意见。** 一条一节，新的在下。

处理一条的做法：改代码或改文档，定下来的设计写进[关键设计](/docs/design)，然后把这一条

## 2026-09-11 `plugins.install` 对已经装过的包也新建一条条目

来源：总控台（单元 `26090520ntn/console`，做块笔记那轮界面扩展点时遇到的）

`plugins.install { pkg, spec }` 眼下不看这个包在 home 里有没有条目，装完包就加一条。实际运行时
拿它装一个插件的开发版，结果 home 里出现了 `home:bn-comment` 与 `home:bn-comment-2` 两条，
同一个插件加载了两遍，同名命令登记了两次。只能再调 `plugins.remove-entry` 清理。

**好的那一面**：`spec` 给了准确版本时它装对了，装进来的就是那个版本。

**投来的建议**（最终怎么改是这个仓的事）：`install` 检查一下「这个包已经有条目了」。有条目
就只升版本、不再建条目；或者不替调用方决定，回一句让调用方选。

**为什么现在提**：devkit 正在做一条「改一版看一版」的循环命令，步骤是发开发版、装进隔离
home、停用再启用重新加载、收集结果。那条命令**有意绕开了 `plugins.install`**，用的是 `pnpm add` 加一条
已有条目，绕开的正是这个重复建条目的行为。也就是说这个行为已经在实际使用中逼出了一条绕开的路：装插件
本来只该有一条路，现在开发循环那边得自己再走一条。

原始记录原在总控台的暂存区（2026-09-12 停用那个收件箱时一并清掉）
原本投给 devkit，这里是同一条的副本。

## 2026-09-14 带路径的 JSON 经 curl 必定出错；稳妥的做法（body 写成文件）没写进 command-http 说明书

来源：总控台（第三轮新会话自举验收，功能题 gwb-timer）。

经入口 `POST /run` 传含 Windows 路径的 JSON，bash 里 curl 的引号与反斜杠转义怎么写都不对：
双反斜杠被去掉一层、`printf` 写文件也去掉一层，回执只回 `bad json`，不指出根因（正斜杠的绕法
09-12 在 devkit 那边提过，本轮复验还是会出错，而且对 devkit 的 scaffold 行不通——那条投给了
devkit）。本轮 agent 最后确定的稳妥做法：**用写文件工具把 body 写成 JSON 文件（转义交给它），
再 `curl --data-binary @file`**，此后全程没再出错。

**投来的建议**：command-http 说明书补一段「带路径或复杂参数的调用用 body 文件」，把这个
做法写成推荐写法；`bad json` 的回执顺带点一句根因（反斜杠进 JSON 的错误转义），省得下一个
agent 再猜。

## 2026-09-24 要适配内核 0.5：词汇表包并进内核包

来源：gwb-kernel（内核仓），2026-09-24。

内核 0.5.0 起词汇表包 `@godcreator/gwb-plugin-api` 不再发布，它的类型（`GwbContext`、`GwbKernelApi`、`GwbResult`、`GwbWindowApi`、`ShellBoot`、`window.gwb` 的全局声明）
改由内核包 `@godcreator/gwb-kernel-desktop` 的包根导出。本仓八个插件都要改：

- `import type { … } from '@godcreator/gwb-plugin-api'` 改成 `from '@godcreator/gwb-kernel-desktop'`（`import type {} from '@godcreator/gwb-plugin-api'` 也一样改），本仓有 17 个文件
- devDependencies 删掉词汇表包：内核包已经写在 peer 里，pnpm 会把它装进包的 node_modules，类型检查从那里取
- peer 里内核包的范围从 `^0.4.1` 改成 `^0.5.0`，在运行内核 0.5.0 的隔离 home 里验过再发布；devkit 的发版检查要求这个范围包含正在运行的内核

内核 0.5.0 发布之后再改；改的时候照说明书 `gwb-release` 升各插件自己的版本号。

## 2026-09-25 gwb.provides 不用写了：logger 等清单字段与文档段落可以删

来源：总控台会话（devkit 仓删掉过度设计的机制，devkit 0.19.0、插件管理 0.10.0 同一批发布）。

devkit 0.19.0 删了 `devkit.capabilities`、`devkit.audit-structure`、`devkit.audit-deps`，以及 `package.json` 里 `gwb.provides` 这一整套（发版不再核对它，也没有命令再读它）。`devkit.services` 改成每次调用时从 home 里各包的 `.d.ts` 读取：给 cordis `Context` 补了服务、类型定义在自己声明里的包就是提供方，回执带类型定义原文。插件作者不用再写 `gwb.provides`；想让别人看懂服务，就在类型上写文档注释。发版检查还改了一条：node 侧产物的包名 import 只放行 node 内置模块、electron 与本包 peer 里写了的包。
`plugins/logger/package.json`（以及别的插件如果有）的 `gwb.provides`，AGENTS 正本、develop 页、design 页里讲 `gwb.provides` 与 `devkit.services` 旧用法的段落，下次改到时删掉或改成现状。

## 2026-09-25 内核直接跟 0.6：跳过 0.5，外置名单写死 react 的四个名字

来源：gwb-kernel（内核仓），2026-09-25，9061518。

上一条「要适配内核 0.5」照做，但版本改成跟 0.6：内核 0.6.0 把页面的 importmap 写死在页面入口里，只有 `react`、`react/jsx-runtime`、
`react-dom`、`react-dom/client` 四个包名；内核包清单的 `gwb.shared` 字段和 `./react*` 出口都删了。所以：

- peer 里的内核包写 `^0.6.0`（不是 `^0.5.0`），在运行内核 0.6.0 的隔离 home 里验过再发
- 浏览器端构建（`build.ts` 或 `tools/build-plugin.ts`）里从内核包清单读 `gwb.shared` 的那段删掉，`external` 直接写上面四个名字；
  产物测试里读 `gwb.shared` 的名单一样写死。没有浏览器端产物的包只改 peer
- 等 devkit 发了认 0.6 的新版再发：devkit 现在的发版检查还读内核包的 `gwb.shared`，装上 0.6 会被拒（已投 devkit 收件页）

## 2026-09-25 用到的插件写 peer：从 dev 挪到 peer，gwb.requires 已删

来源：gwb-lifecycle-plugins（devkit 所在仓的交接页「插件之间的运行时要求写 peer」，总控台会话），2026-09-25。插件管理 0.9.0、devkit 0.18.15 起生效，源上现在是插件管理 0.11.0、devkit 0.19.1。

插件运行时用到的别的插件，从 devDependencies 挪到 peerDependencies，范围写 `^x.y.z`，下限写开发、验证时用的那一版；同一个仓里的插件写 `workspace:^`，发版时换成 `^<版本号>`。「用到」指：经 `ctx.inject` 用它的服务、经命令总线 `@godcreator/gwb-commands` 登记命令、用外壳 `@godcreator/gwb-shell` 注册窗格或样式令牌、import 它的类型。只用 `ctx.inject([...], fn)` 局部注入、缺了只少一部分功能的，在 `peerDependenciesMeta` 里标 `optional: true`；只按命令名调它的命令的不用写。写进 peer 的插件不再另写 dev：插件仓里 pnpm 会把 peer 装进 `node_modules`，类型从那里取。

- peer 里只许三类：按值 import 的 `cordis`、内核包 `@godcreator/gwb-kernel-desktop`、别的插件（清单 `keywords` 含 `gwb-plugin`）。库、接口定义包、构建工具照旧写 dev 或 `dependencies`
- 清单字段 `gwb.requires` 已删：插件管理不再报它，发版检查也不再查
- 发版检查（devkit 0.18.15 起）：peer 里每个 `@godcreator` 插件的范围要是 `^x.y.z`，并且和源上 `latest` 在同一条线（0.x 比次版本号，≥1 比主版本号），不在同一条线就拒；peer 里有这三类以外的包也拒
- home 里关掉了 pnpm 自动补装 peer：插件管理、`devkit.home.new`、`devkit.dev` 在 home 里运行 pnpm 时都带环境变量 `pnpm_config_auto_install_peers=false`。peer 里的插件 home 里没装，不会被顺带装上，由 `plugin-manager.list` 每个包的 `unmetPeers`（`{ pkg, range, installed? }`）报出来，只报告、不拦加载；在隔离 home 里验证时，peer 里的插件要自己装上
- 升级一个插件时，peer 写了它的插件会被 pnpm 装进新目录，插件管理在同一次升级里把它们一起重新加载（回执里的 `dependents`）

本仓要改的：

- 同仓插件之间 dev 写的 `workspace:*` 改成 peer 写 `workspace:^`：
  - `gwb-logger`、`gwb-skills`：命令总线
  - `gwb-settings`、`gwb-node-cli`、`gwb-py-cli`：命令总线、说明书
  - `gwb-mcp`：命令总线、node 命令行、设置、说明书
- `gwb-commands`、`gwb-data` 没有用到别的插件，不用改
- 几乎每个插件都会在 peer 里写命令总线，所以命令总线热升级时 home 里大部分插件会被一起重新加载，这是交接页定下的代价

随适配内核 0.6 那一轮一起改、一起发，版本号照说明书 `gwb-release` 升。规矩正本是 devkit 文档站的规则页「用到的插件写 peer」与说明书 `gwb-release`（`run skill.read {"name":"gwb-release"}`）。

## 2026-09-25 要跟内核 0.7：八个插件 peer 里内核包改成 ^0.7.0

来源：gwb-kernel（内核仓 `D:\unitfolders\igldu-gwbkernel\gwb-kernel`），提交 `6ab4ed8`，2026-09-25；总控台会话代为投递。

内核包 `@godcreator/gwb-kernel-desktop` 马上从 0.6.2 发 0.7.0，这是破坏性版本：内核服务删掉了 `gwbKernel.launcherVersion`，home 里的 `runtime.json` 删掉了 `appDir`（内核仓轨迹卡 `2026-09-25-drop-launcher-version`）。此前 0.6.1、0.6.2 还给页面加了导航锁（内核仓 `docs-site/content/docs/seams/ipc.mdx` 的「页面保证」）：

- 页面的主框架只能是内核的 `index.html`：不带 `target` 的链接点击、拖进窗口的链接一律拒绝，页面上没有任何反应
- `window.open(url)` 与 `target="_blank"` 的链接不再开新窗口：`http:`、`https:` 地址交给系统默认浏览器打开，别的协议（`file:`、`javascript:`、`data:`、自定义协议）拒绝
- 页面经 `window.gwb.command` 调命令，只接收顶层框架发来的；iframe 里调用拿到的是 `ok: false` 的回执

本仓八个插件 peer 里内核包写的都是 `^0.4.1`，不包含 0.7.0（也不包含现在的 0.6）：

- `@godcreator/gwb-commands`（`plugins/commands/package.json` 第 54 行）
- `@godcreator/gwb-mcp`（`plugins/mcp/package.json` 第 33 行）
- `@godcreator/gwb-skills`（`plugins/skills/package.json` 第 29 行）
- `@godcreator/gwb-settings`（`plugins/settings/package.json` 第 31 行）
- `@godcreator/gwb-data`（`plugins/data/package.json` 第 30 行）
- `@godcreator/gwb-logger`（`plugins/logger/package.json` 第 39 行）
- `@godcreator/gwb-node-cli`（`plugins/node-cli/package.json` 第 31 行）
- `@godcreator/gwb-py-cli`（`plugins/py-cli/package.json` 第 31 行）

用到删掉字段的地方只有一处测试数据：`plugins/mcp/tests/runtime.test.ts` 第 13 行的假 `runtime.json` 里有 `appDir`。mcp 插件写 `runtime.json` 时保留别的字段、不读 `appDir`，运行时不受影响；想让假数据跟上现状，可以改成 0.7.0 实际写的 `pid`、`startedAt`、`version`、`cdp`。`launcherVersion`、`window.open`、`target="_blank"`：没有用到；本仓插件没有页面，导航锁对它们没有影响。

要做的：

1. 内核 0.7.0 发布后，在装了 0.7.0 的隔离 home 里把八个插件验一遍，再把 peer 里内核包的范围改成 `^0.7.0`，版本号照说明书 `gwb-release` 升，然后发版。上面「内核直接跟 0.6」那条还没做的，peer 直接写 `^0.7.0`，不用先改到 0.6；那条里别的改动照做
2. 不改的后果：`plugin-manager.list` 会把这些插件标成 `kernelUntested`；`devkit.release` 发版前检查要求 peer 里内核包的范围包含运行中的内核，不改就拒绝发布。运行时照常

## 2026-09-25 要跟 devkit 0.21：packages 必给，要发的包写 publishConfig.registry

来源：gwb-lifecycle-plugins（devkit 所在的仓 `D:\unitfolders\igldu-gwbkernel\gwb-lifecycle-plugins`），提交 `9caafe0`，2026-09-25；总控台会话代为投递。

`@godcreator/gwb-devkit` 0.21.0 已发到团队源。这是破坏性版本，删掉了两个只为旧仓留着的缺省值（devkit 仓轨迹卡 `2026-09-25-drop-legacy-defaults`）：

1. **`devkit.dev` 与 `devkit.release` 的 `packages` 必给**：非空数组，每一项是相对仓根的包目录，如 `["plugins/<短名>"]`；`devkit.release` 的按依赖顺序排，被依赖的排前面。不给或写错直接拒。这两条命令不再把仓根当成插件包：仓根本身就是插件包的仓（仓根 `package.json` 就是插件，`pnpm-workspace.yaml` 里没有 `plugins/*`）要先改成 workspace 布局才能用——插件放在 `plugins/<短名>/`，仓根是 `"private": true` 的 `package.json`，照 devkit 仓或 `devkit.scaffold` 新建的仓的样子。devkit 不替仓改布局
2. **每个要发的包在自己的 `package.json` 里写 `publishConfig.registry`**：发到团队源写 `"publishConfig": { "registry": "https://git.tianshen02.online:28377/api/packages/godcreator/npm/" }`，发到别的源就写那个源的地址。没写的包 `devkit.release` 拒绝发布。发到哪只看这个字段：`devkit.release` 不再在命令行带 `--registry`，这个字段的优先级也高于用户级 `~/.npmrc` 里的范围行（devkit 仓轨迹卡 `2026-09-25-scope-and-publish-target`）

同一天还发了插件管理 0.12.1，修了发出去的包里带着过时文件的问题，用它的插件不用改。另外有一项早就可以做的清理：命令总线 `@godcreator/gwb-commands` 0.4.6 起（源上现在是 0.5.0），`gwbCommands.register` 自己把注销登记在调用方的上下文上，调用方卸载时命令自动注销，登记命令不用再在外面包一层 `ctx.effect(() => ….register(…))`。包着也只注销一次、照样能用，删不删随意；登记说明书的 `gwbSkills.register` 不是命令总线的方法，外面那层 `effect` 要留着。

本仓的情况：

- 布局：workspace 仓（`pnpm-workspace.yaml` 里有 `plugins/*`），不用改。`README.md` 第 33 行、`docs-site/content/docs/develop.mdx` 第 43、62 行的调用写法已经带了 `packages`
- 没写 `publishConfig.registry` 的包：八个都没写——`plugins/commands`、`plugins/data`、`plugins/logger`、`plugins/mcp`、`plugins/node-cli`、`plugins/py-cli`、`plugins/settings`、`plugins/skills` 各自的 `package.json`（`@godcreator/gwb-commands`、`gwb-data`、`gwb-logger`、`gwb-mcp`、`gwb-node-cli`、`gwb-py-cli`、`gwb-settings`、`gwb-skills`）
- 外面包着 `effect` 的命令登记（可选清理）：`plugins/logger/src/index.ts` 第 128、131 行；`plugins/mcp/src/index.ts` 第 349、369 行；`plugins/settings/src/index.ts` 第 111、117、122、129 行；`plugins/skills/src/index.ts` 第 57、63 行。另外两处形式一样但先看清再删：`plugins/node-cli/src/index.ts` 第 87 行、`plugins/py-cli/src/index.ts` 第 113 行是替别的插件转登记命令，外层 `effect` 登记在提供方的上下文上，和总线拒收时撤掉表里那条的逻辑连着。`plugins/commands/src/index.ts` 第 73 行是命令总线自己的实现，不算。各插件登记说明书的 `gwbSkills.register` 留着
