# 投来的反馈

**这一页收别的仓在用这些插件的过程中投来的意见。** 一条一节，新的在下。

处理一条的做法：改代码或改文档，定下来的设计写进[关键设计](/docs/design)，然后把这一条
删掉。本仓自己遇到的问题不在这里，去[遇到过的问题](/docs/pitfalls)。

条目的格式照生态里别的文档站的反馈区：标题写「日期 + 一句话」，正文第一行写来源。

## 2026-09-11 `plugins.install` 对已经装过的包也新建一条条目

来源：总控台（单元 `26090520ntn/console`，做块笔记那轮界面扩展点时遇到的）

`plugins.install { pkg, spec }` 眼下不看这个包在 home 里有没有条目，装完包就加一条。实际运行时
拿它装一个插件的开发版，结果 home 里出现了 `home:bn-comment` 与 `home:bn-comment-2` 两条，
同一个插件加载了两遍，同名命令登记了两次。只能再调 `plugins.remove-entry` 清理。

**好的那一面**：`spec` 给了准确版本时它装对了，装进来的就是那个版本。

**投来的建议**（最终怎么改是这个仓的事）：`install` 检查一下「这个包已经有条目了」。有条目
就只升版本、不再建条目；或者不替调用方决定，回一句让调用方选。

**为什么现在提**：devkit 正在做一条「改一版看一版」的循环命令，步骤是发开发版、装进隔离
home、停用再启用重新加载、收集结果。那条命令**有意绕开了 `plugins.install`**，用的是 `pnpm add` 加一条
已有条目，绕开的正是这个重复建条目的行为。也就是说这个行为已经在实际使用中逼出了一条绕开的路：装插件
本来只该有一条路，现在开发循环那边得自己再走一条。

原始记录原在总控台的暂存区（2026-09-12 收件箱退役时随处理清掉）
主送 devkit，这一条是抄送。

## 2026-09-14 带路径的 JSON 经 curl 必定出错；稳妥的做法（body 写成文件）没写进 command-http 说明书

来源：总控台（第三轮新会话自举验收，功能题 gwb-timer）。

经入口 `POST /run` 传含 Windows 路径的 JSON，bash 里 curl 的引号与反斜杠转义怎么写都不对：
双反斜杠被去掉一层、`printf` 写文件也去掉一层，回执只回 `bad json`，不指出根因（正斜杠的绕法
09-12 在 devkit 那边提过，本轮复验还是会出错，而且对 devkit 的 scaffold 行不通——那条投给了
devkit）。本轮 agent 最后确定的稳妥做法：**用写文件工具把 body 写成 JSON 文件（转义交给它），
再 `curl --data-binary @file`**，此后全程没再出错。

**投来的建议**：command-http 说明书补一段「带路径或复杂参数的调用用 body 文件」，把这个
做法写成推荐写法；`bad json` 的回执顺带点一句根因（反斜杠进 JSON 的错误转义），省得下一个
agent 再猜。

## 2026-09-24 要适配内核 0.5：词汇表包并进内核包

来源：gwb-kernel（内核仓），2026-09-24。

内核 0.5.0 起词汇表包 `@godcreator/gwb-plugin-api` 不再发布，它的类型（`GwbContext`、`GwbKernelApi`、`GwbResult`、`GwbWindowApi`、`ShellBoot`、`window.gwb` 的全局声明）
改由内核包 `@godcreator/gwb-kernel-desktop` 的包根导出。本仓八个插件都要改：

- `import type { … } from '@godcreator/gwb-plugin-api'` 改成 `from '@godcreator/gwb-kernel-desktop'`（`import type {} from '@godcreator/gwb-plugin-api'` 也一样改），本仓有 17 个文件
- devDependencies 删掉词汇表包：内核包已经写在 peer 里，pnpm 会把它装进包的 node_modules，类型检查从那里取
- peer 里内核包的范围从 `^0.4.1` 改成 `^0.5.0`，在跑内核 0.5.0 的隔离 home 里验过再发布；devkit 的发版检查要求这个范围包含正在运行的内核

内核 0.5.0 发布之后再改；改的时候照说明书 `gwb-release` 升各插件自己的版本号。
