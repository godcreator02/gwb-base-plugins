## 共享包（`packages/`，不是插件）

它们不在 cordis 上加载，是**插件的依赖**，跟插件平级装进 home。插件写 `peerDependencies` 依赖它们。

| 包 | 内容 | 状态 |
| --- | --- | --- |
| **shared-react** | `@godcreator/gwb-shared-react`：react 系的 CJS→ESM 打包，内核读它的 `gwb.shared` 声明拼 importmap | **已发 0.0.2** |
| **tokens** | `@godcreator/gwb-tokens`：设计令牌的声明（页面加载）+ 映射（插件构建时引用），亮暗两套值 | **已发 0.0.5** |

**构建脚本不再是仓里共用的一份。** 选择器 scope 方案的那部分 `tools/build-styles.ts`
（在内存里拼输入、再用 postcss 把每条选择器改写成 `:where([data-gwb-plugin="…"]) …`）
2026-09-09 **随最后一批插件迁完一起删掉**；`@tailwindcss/postcss` / `postcss` / `tailwindcss` /
`gwb-tokens` / `esbuild` 也从仓根删掉，仓根 devDependencies 只剩检查要用的四个。
**插件自己装 `esbuild` 与 `@tailwindcss/cli`**，`build` 脚本直接调这两个命令——插件本来就该是
能单独拿出去建仓的东西，构建脚本放在插件里才符合这个形状。理由见[关键设计](/docs/design)。

那套构建脚本**始终没做成包**，现在连做的必要都没了：当初的理由是「使用方只有仓内的插件，
抽一个共享构建包过不了准入标准的第二条」，而插件各装各的之后连要抽的东西都不剩了。

## 组件：各自从 shadcn 拉取

**这个仓里没有组件库，也没有 registry。** 每个插件自己放一份 `components.json`，要什么组件就
`pnpm dlx shadcn@latest add <名>` 从 shadcn 官方拉取。插件之间的组件不需要一致——统一风格由设计令牌
保证，不靠组件源码一致。

`plugins/hello` 是样板，**新插件照它 0.2 那版复制**：`components.json`（`tailwind.css` 指向自己那份
样式入口、`tailwind.prefix` 填插件的**短名**）+ 两份 tsconfig 的 `paths` + `build.ts` 的 esbuild
`alias`，三处的 `@/` 都指向 `src/client`；插件自己的 devDependencies 里带上 `esbuild` 与
`@tailwindcss/cli`。**别去看 0.1 那版**——那版没有样式入口、没有 `prefix`，构建用的是
2026-09-09 已经删掉的 `tools/build-styles.ts`，照着复制一行都运行不了。

**`prefix` 那一项是新插件最省事的一处**：填了它，CLI 拉下来的组件类名**自带前缀**，不用回头
逐个手改；`cn`（tailwind-merge）合并带前缀的类本来就对，不用为它配任何东西。拉下来的
组件也**一个补丁都不用打**——前缀方案不依赖 DOM 位置，portal 到 `body` 的弹层照样有样式。

**标记类也要带前缀。** `group` / `peer` 这一类是「一个类当锚、另一个类的变体去找它」，
而 `logger:group-hover:*` 编译出来的选择器认的是**带前缀的** `.logger\:group`——锚那头写成
不带前缀的 `group`，规则永远不命中，还不报错。手写这类搭配时两头一起带前缀，细节见
[遇到过的问题](/docs/pitfalls)。

分量最大的一个。旧插件仓里那个插件 1351 行，分四个阶段做：

| **二** | `ctx.gwbShell` 窗格注册服务；`openable` 这时才搬 | **完成**，实际运行验证通过 |
| **三** | dockview 骨架 + 打开一个插件窗格 | **完成**，实际运行验证通过 |
| **三点五** | 一个插件多个窗格、同一个窗格开多份、`args.shell` 实现 | **完成**，实际运行验证通过 |
| **四·状态栏** | ＋列表 / home / 亮暗，外加外壳身份改成运行时注册 | **完成**，实际运行验证通过 |
| **四·布局保存** | 工作区自动保存＋起名保存布局、选一套打开，存在 `ctx.gwbData` | **完成**，实际运行验证通过 |
| **四·导航** | 常驻侧边栏 | 待做（＋列表已经覆盖了主要用途，真需要再做） |

**外壳插件现在在界面插件仓 gwb-ui-plugins，各阶段交出的接口与理由见那边文档站的 shell 页。**

- **一**：搬进来的四个模块全是纯逻辑，`openable` 特意推迟到第二阶段
- **二**：`openable` 是**重写不是搬**——旧插件仓那份用的是「条目表 × 包声明的 `gwb.panes`」，
  改成运行时注册之后，join、过滤、兼容旧窗格三样一起去掉了。`mount-handle` 也跟着接口改名
- **三**：`hello` 从这个阶段起降为**窗格插件**（导出 `mountPane`、去掉 `gwb.shell`），
  外壳的位置归 shell。两个 `shell: true` 会让页面无法选择，所以这两处必须在同一次改动里换过来
- **三点五**（不在原来的四个阶段里）：窗格的**定义**与**实例**分开。它插在三与四之间，因为
  **第四阶段的导航要靠这一步定下来的形状**——点一下是聚焦还是新开、右键给不给「新开一份」、
  导航列出的插件名从哪来。顺带清掉两处：`gwb.title` 这个没用的字段（四个包声明、没有地方读、
  两个仓的文档站一句没提），以及 `bus.ts` 那个「搬进来三个阶段、有测试、没有使用方」的模块
- **四·状态栏**：工作区外面那一条。**＋列表覆盖了导航的主要用途**（旧插件仓的导航主要就做这件事），
  所以导航从「第四阶段的一部分」降为「真需要常驻侧边栏时再说」。顺带把外壳身份也改成
  运行时注册了——包清单里现在只剩 `gwb.shared`，而那个是**必须的**（共享包不是插件、没有运行时）
- **四·布局保存**：一个工作区，自动保存（400ms 防抖，每次整份重写）＋起名保存布局、打开哪套就铺哪套
  （同名覆盖）。存的是 gwbData 的 `layout` 这一份文档。「重置布局」与「布局没存上」告警两个
  状态栏项一并补上。**多桌面试到 0.0.14 撤回**——经过与理由见[关键设计](/docs/design)

## 剩下那部分要用的东西

**旧插件仓那几条 dockview 工程细节，用了三条，剩两条**：

| 细节 | 状态 | 为什么 |
| --- | --- | --- |
| 面板组件表必须是**模块级常量** | **已用** | 换引用会让 dockview 重建全部窗格 |
| 订阅 `onDidLayoutChange` | **已用**（「已开」与布局保存都靠它） | 保存布局订阅的就是这个事件 |
| 布局保存 400ms 防抖 | **已用** | 一阵拖拽合并成一次写；每次整份重写，迟到的定时器写不坏数据 |
| 首帧等待 | **不需要** | 数据在 `createRoot` 之前就取齐了（布局也是），根本没有「还没拿到」的那一帧 |
| 导航定宽 `constraints` **必须去重** | 待用 | 不去重的话 `setConstraints` 自己触发 `onDidLayoutChange` 无限递归、卡死主线程 |
| 默认布局里 `setSize` 等第二个窗格就位 | 待用 | 目前不摆多列 |

状态栏缺的那两项（「重置布局」「布局没存上」）随布局保存一起补上了——前者进了桌面
标签的右键菜单（按桌面算），后者只在保存失败时显示。

**`liveness` 的输入将来要换**。它现在按「条目表」判断一个窗格背后的插件是 live / idle / gone，
而第三阶段根本没用它——运行时注册已经说明了「插件在运行」，注册表里没有的窗格本来就打不开。
但**在运行中卸载一个插件**时：插件卸载 → effect 清理 → 注册表删掉那个窗格 → **dockview 里那个窗格还开着**。
那时要关掉它，判断的依据是**注册表变了**而不是条目表变了。第四阶段真用它时按这个形状改。

**页面感知变化的现状**：启动时取一次注册表就完了，插件后来加载、卸载，界面不知道——
**手动的办法已经有了**：状态栏「刷新」整页重新运行，重新取注册表。事件推送（插件一变界面自己跟着变）
仍是将来的事，真需要再说。

**明确不照搬**：旧布局兼容（约 60 行 + 5 个双分支）、旧插件仓里写死的插件名（`console` 特判、
六个图标名的列表）、CDP 探针驱动的接口、状态栏里旧插件仓的品牌、`void host` 那个不完整的约定
（参数里给了 host bridge 却改用 `window.gwb`）。

**保存那条已经解决了**：`gwb-data` 插件先做出来了，shell 写 `inject: ['gwbData']` 就能
`ctx.gwbData.writeDoc('layout', …)`，不用自己拼路径、也不用碰 `fs`。原子写入由那边保证——
布局写到一半崩了不会毁掉上一份。

## 已接：mcp × skills 的接口

以前记的是「等真有 agent 连上来、发现只有命令名清单不够用再做」——**用户点名「把 skill
功能用起来」就是那个真实需求**，提前做的理由记在这里。做法照当初提议的形状：

- `instructions` 列出此刻登记的说明书（**唯一的发现途径**——客户端不会自己去
  `resources/list`），每份一行名字 + 描述 + URI，正文一个字不放
- 正文登记成 `skill://gwb/<名>/<文件>` resources，读取回调用 `ctx.gwbSkills.read`，
  读不到就 throw（回 JSON-RPC 错误好过骗对方「说明书是空的」）
- mcp 那边**局部注入** `gwbSkills`：没装 skills 插件的 home 里入口照开，只是没有说明书
- 转换逻辑抽在 `plugins/mcp/src/skills.ts`（纯函数、有单元测试）；**没有加说明书专用工具**——
  元工具还是 `gwb_cli_list` / `gwb_cli_run` 两个

照 hello 样板登记说明书的一批：`commands` / `settings` / `plugins` / `node-cli` /
`py-cli` 各一份，讲的全是 agent 经命令总线真用得上的东西（回执格式、参数形状、两层结构、
回执字段）。

## 之后

**`gwb-settings` 的第二版**：node 这部分的设置读写[已经做完了](/docs/settings)，还缺两块。

**界面那部分**——设置面板。`settings.all` 已经按界面要的形状给出了（每行带
`scope`/`section`/`key` 与 title/type，外加一个 `live` 标明「此刻还有插件声明它吗」），
窗格插件照着排就行。

**插件启停/卸载**。旧插件仓那 981 行里这部分建立在 config 插件的 `host.config.*` 之上，而**新内核
有 loader**，直接用 `ctx.loader` 的 `create`/`remove`/`update`，**运行中加载卸载是自带的、不用重启**。
已经决定不用官方的 `plugin-loader-webui`（它硬性 peer 依赖 webui，而 webui 要 server），理由见
内核仓 decisions。

**动手前先看内核仓 walls 里那几条**：`update` 改 config 是**整个重新加载**、而且 `inject` 它的
插件跟着重新加载；写回 yml 会把用户手写的注释与空行全丢掉；没有文件监听；`remove` 可能只认短 id；
`create` 不传 `parent` 写不进文件。**后三条是读源码得出的、没实际遇到过**，真用之前各验证一次。

**明确不照搬**：`platform` 分区 + `window.confirm` 拦截（那个布尔值不带任何特权，弹窗文案里的
「兜底页」是旧插件仓的概念）、`settings.data.list` 那个目录统计器（跟「设置」没有必然关系）。

**要修的名不副实**：旧插件仓那个「卸载」按钮只删 yml 条目、不碰 `node_modules`。要么接上真的
卸包，要么改叫「移出插件树」。
