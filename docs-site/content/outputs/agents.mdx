# gwb-base-plugins

**gwb 的无界面基础插件仓**：九个插件 commands、mcp、skills、settings、data、logger、node-cli、py-cli、plugin-sources，
全部只依赖词汇表包（`@godcreator/gwb-plugin-api`）的类型。插件管理（plugin-manager）在 devkit 仓 gwb-devkit，
界面插件（shell、theme、baseui）在 gwb-ui-plugins，内核与词汇表包在 gwb-kernel，改它们去那些仓。
**这个仓的插件不依赖任何界面包**：peer 里不写，构建产物检查只放行名单里的包名。
仓根 `packages/shared-react`、`packages/tokens` 如果还在，是旧构建留下的未跟踪文件（没有 `package.json`），不是在用的包。

每个插件在 `package.json` 的 `gwb.testedKernel` 里写明在哪个内核版本上测过：插件管理据此报告哪些插件没在
当前内核上测过，`devkit.release` 发版前检查它。在新的内核版本上测过之后更新这个字段。

## 动手之前

- 先读内核仓的 `AGENTS.md`，那是 gwb 各仓共同规矩的正本
- 写插件的完整流程（新建、修改、隔离 home 里验证、发版）读 devkit 的说明书 `gwb-devkit`（`skill.read {"name":"gwb-devkit"}`）
- 升版本号、改依赖版本号之前读 `gwb-release`；写文档、改代码引用读 `docfirst-docs`

## 构建产物的规矩

- 相对 import 必须带 `.js`；构建产物里的包名 import 只能是各插件测试名单里的——两条都有测试检查
- 命名（包名前缀、服务名以 `gwb` 开头）与依赖写法的正本在 devkit 的说明书 `gwb-devkit`、`gwb-release`

## 检查

提交前 `pnpm check`（类型检查 + oxlint + vitest，含构建产物检查与 self-report 检查）。self-report 检查要求
源码 `inject` 的每个服务名都出现在文档站现状区，改了依赖就同一个提交改插件页。文档检查单独运行 `pnpm doc`，
报红时这个提交不许推送；改了被文档引用的源码，先 commit，再 `pnpm doc:confirm <自己改的页…>`。

## 旧插件仓只作参考，不是模板

废弃插件仓 `26090623hyz/gwb-plugins`：查它遇到过的问题有用，结构、分层、包划分一概不照搬。有一个仍然存在的
问题要避开：接口包声明成 `peerDependencies` 时 tsdown 会把它外置成包名 import——接口包要么声明进
importmap、要么强制打包进来，并配上构建产物检查。

## 实验材料放 `probes/`

实验、测量的全部材料放在仓根 `probes/<时间戳>_<目的>/`：一次实验一个目录、**自包含**（半年后照
README 第一行运行一次能得到同样结论）、**进 git**、**不进 pnpm 工作区**、不进 `pnpm check`。
依据类轨迹卡在依据段写相对仓根的路径指向它。

## 文档地图

文档站在 `docs-site/`，端口 4315（`pnpm --filter gwb-base-plugins-docs-site dev`）。现状区：

- **入口页** `/docs`：接缝图，插件之间的十一条接缝各有一页（`/docs/seams/…`）
- **九个插件页**：每页写功能、接口（各属于哪条接缝）、依赖、不做的事
- **关键设计** `/docs/design`、**开发** `/docs/develop`、**遇到过的问题** `/docs/pitfalls`

其余五个区：轨迹（`trajectory/`）、交接（`spec/`）、未来（`future/`）、生成文件正本（`outputs/`）、反馈（`feedback/`）。

## 生成文件

仓根 `README.md`、`AGENTS.md`、`CLAUDE.md` 都是生成文件，别手改——正本在 `docs-site/content/outputs/`
（`readme.mdx` / `agents.mdx` / `claude.mdx`），改完在 `docs-site` 运行 `pnpm exec docfirst render`
重新生成，一起提交。
