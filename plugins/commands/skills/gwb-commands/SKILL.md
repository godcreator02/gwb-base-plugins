# 命令总线怎么用

这台工作台的能力面是一条**命令总线**：每个插件把自己的能力登记成一条命令，谁来调都走这一份
注册表。够到它的口有两类：

- **agent 经 MCP 门**：`index` 拿地图（全部命令各带一句话）、`search` 查用法（命中行带
  usage，参数形状就在那儿）、`run` 按名调（`{"command": 名字, "args": {...}}`）
- **界面经 `window.gwb.command(名字, 参数)`**：页面上的插件直接调，拿到的就是总线回执本身

命令本身没有协议——handler 就是普通函数，参数和返回值由各命令自己定。

## 回执信封

总线回执统一是这两种形状之一：

- 成了：`{ "ok": true, "data": … }`
- 没成：`{ "ok": false, "error": "原因" }`

**取值往 `data` 里再走一层。** 直接读顶层字段拿到的永远是 undefined。

例外只有一种：handler **自己回了带 `ok` 的对象**，总线原样透传、不再包 `data`——那时字段就在
顶层。CLI 运行器（gwb-node-cli / gwb-py-cli）登记的命令都是这样，`stdout` / `exitCode` 与
`ok` 平级。

经 MCP 门 `run` 调时，这份回执再翻成一段文本：

- 成了：正文是 `{ "ok": true, "data": … }` 的 JSON
- 没成：`isError` 的文本 `执行失败：原因`
- 原样透传的那种（`ok` 之外还带自己的字段）：正文就是它本身的 JSON；CLI 进程回执摊平成
  `ok` / `exitCode` / `timedOut` / `durationMs` / `stdout` / `stderr` 六样

## 失败的三种长相

1. **没有这条命令**——原因是「没有这条命令：xxx」。多半是名字拼错了，或者那个插件根本
   没装/没启用。回到 `index` 对一遍
2. **参数不对**——命令自己校验参数，抛出来也被收成失败回执，原因里写着它要什么形状；形状
   本身在 `search` 里那条命令的 usage 上
3. **业务上没成**——handler 干了活但结果失败（比如要装的包名不合规），一样是失败回执。
   这不是坏事：它把原因说清楚了，照着改参数重试就是

三种**都不是协议错误**：总线上是 `ok: false`，MCP 门上是 `isError` 的文本，连接不断，把原因
读出来接着往下走。

## 查账看哪几条

- `index` / `search` 回的每条命令带 `plugin` 字段——登记这条命令的插件的包名
  （`@godcreator/gwb-xxx`）。「这条命令是干嘛的」看 description（`search` 再带 usage），
  「这条命令归谁管」看 plugin；`search {"plugin": 包名}` 按它精确筛
- **内核没有自省口**：想知道此刻有哪些插件、挂上没有，问 `plugin-manager.list`——它每条条目
  带 `active`（fiber 真 ACTIVE 才算）。装了外壳的 home 里，谁报过名字、注册了哪些窗格问
  `shell.plugins` 与 `shell.panes`。**插件挂没挂上看这些，别猜**

## 装了新插件之后

命令注册表随装了哪些插件而变：装一个新插件、启用一条停用的条目，都可能多出一批命令。
**动过 `plugin-manager.*` 之后重新调一次 `index`**（它每次现拼），别凭上一次的清单干活。
MCP 工具面不会因此长出新工具——新命令一律经 `run` 够到。
