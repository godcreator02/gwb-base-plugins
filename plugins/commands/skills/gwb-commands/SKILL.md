# 命令总线怎么用

这台工作台对外提供能力的方式是**命令总线**：每个插件把自己的能力登记成一条命令，谁来调都经这一张
命令表。调用它的入口有两类：

- **agent 经 MCP 入口**：`index` 拿到全部命令的清单（每条带一句话介绍）、`search` 查用法（命中的
  那条带 usage，参数形状就写在里面）、`run` 按名字调用（`{"command": 名字, "args": {...}}`）
- **页面经 `window.gwb.command(名字, 参数)`**：页面上的插件直接调用，拿到的就是总线回执本身

命令本身没有协议——处理函数就是普通函数，参数和返回值由各命令自己定。

## 回执形状

总线回执统一是这两种形状之一：

- 成功：`{ "ok": true, "data": … }`
- 失败：`{ "ok": false, "error": "原因" }`

**取值要往 `data` 里再走一层。** 直接读顶层字段拿到的永远是 undefined。

例外只有一种：处理函数**自己返回了带 `ok` 的对象**，总线原样返回、不再包 `data`——这时字段就在
顶层。命令行运行插件（gwb-node-cli / gwb-py-cli）登记的命令都是这样，`stdout` / `exitCode` 与
`ok` 在同一层。

经 MCP 入口 `run` 调用时，这份回执再转成一段文本：

- 成功：正文是 `{ "ok": true, "data": … }` 的 JSON
- 失败：`isError` 的文本 `执行失败：原因`
- 原样返回的那种（`ok` 之外还带自己的字段）：正文就是它本身的 JSON；命令行进程的回执展开成
  `ok` / `exitCode` / `timedOut` / `durationMs` / `stdout` / `stderr` 六个字段

## 失败的三种形式

1. **没有这条命令**——原因是「没有这条命令：xxx」。多半是名字拼错了，或者那个插件没装、没启用。
   回到 `index` 对一遍
2. **参数不对**——命令自己校验参数，抛出的错误也被转成失败回执，原因里写着它要什么形状；形状
   本身写在 `search` 里那条命令的 usage 上
3. **业务上没成功**——处理函数执行了，但结果是失败（比如要装的包名不合规），同样是失败回执。
   它把原因说清楚了，照着改参数重试就是

三种**都不是协议错误**：总线上是 `ok: false`，MCP 入口上是 `isError` 的文本，连接不断，把原因
读出来接着往下做。

## 命令归谁、插件加载了没有，看哪几处

- `index` / `search` 返回的每条命令带 `plugin` 字段——登记这条命令的插件的包名
  （`@godcreator/gwb-xxx`）。「这条命令做什么」看 description（`search` 还带 usage），
  「这条命令归哪个插件」看 plugin；`search {"plugin": 包名}` 按它精确筛选
- **内核没有查询自身状态的命令**：想知道此刻有哪些插件、加载了没有，调 `plugin-manager.list`——
  它的每条条目带 `active`（fiber 确实处于 ACTIVE 才算）。装了外壳的 home 里，哪些插件登记过名字、
  注册了哪些窗格，调 `shell.plugins` 与 `shell.panes`。**插件加载了没有看这些，别猜**

## 装了新插件之后

命令表随装了哪些插件而变：装一个新插件、启用一条停用的条目，都可能多出一批命令。
**调过 `plugin-manager.*` 之后重新调一次 `index`**（它每次调用都重新生成清单），别凭上一次的清单
继续做。MCP 入口的工具不会因此增加——新命令一律经 `run` 调用。
