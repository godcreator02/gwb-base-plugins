# 线程池

工作台的主线程上跑着界面、MCP 入口和所有插件。插件在命令处理函数或服务方法里同步算上几百毫秒，这段时间里界面不响应、别的命令全部排队；几个 agent 同时调这类命令，主线程就一直是满的，工作台看起来卡死。

线程池服务 `ctx.gwbWorkers`（包 `@godcreator/gwb-workers`）让插件把这类计算放进自己的线程池：主线程只转交参数、等结果。

## 什么要放进线程池

- 同步的数据库调用（`node:sqlite` 的 `DatabaseSync`、better-sqlite3），哪怕单次只要几十毫秒：调用一多就排满主线程
- 全表扫描、大 JSON 解析、大文件逐行处理这类同步算几十毫秒以上的事
- 不用放：联网、读写文件、起子进程这类异步调用，它们等待时不占主线程

## 用法

1. 把要放进线程的计算写成一个独立的模块（构建时单独出一个文件，比如 `dist/worker.js`），导出普通函数。这个模块在线程里加载，拿不到主线程里的对象与服务：用到的东西从参数传入，或在模块里自己打开（数据库连接可以留在模块级变量里常驻）
2. 插件 inject `gwbWorkers`（peer 里写 `@godcreator/gwb-workers`），在 apply 里开池：

   ```ts
   const pool = ctx.gwbWorkers.pool({ name: 'library', module: new URL('./worker.js', import.meta.url), threads: 4, taskTimeoutMs: 600_000 })
   ```

   - `threads`：最多开几个线程（1–16），有任务排队才开，开了就常驻，模块在每个线程里只加载一次
   - `taskTimeoutMs`：一个任务最多跑多久，超了终止它所在的线程、任务报错；不给就不限
   - 线程池随插件卸载关闭；同一个插件里池名不能重
3. 调用：`await pool.run('<导出函数名>', [参数…])`。线程都忙时先来先跑
   - 参数与返回值要能被结构化克隆：不能有函数，类的实例按普通对象过去
   - 函数抛错时，主线程拿到同 name、同 message 的 Error，自定义错误类的身份过不来；调用方要分辨的拒绝（参数不对、找不到），在线程里换成返回值交回
   - 写操作要不要排队由资源自己管：SQLite 开 WAL 后多个线程可以同时读、写入由它的锁排队；资源自己管不了并发的，`threads` 给 1

## 查现状

`workers.stats`（无参数）回每个线程池开了几个线程、忙几个、排队几个、成功失败各多少，以及最近 20 个任务各等了多久（`waitMs`）、跑了多久（`runMs`）。`waitMs` 一直很大说明线程不够或任务太慢。

完成的判据：插件的重计算命令经线程池跑；几个 agent 同时调它时，工作台界面照常响应，`workers.stats` 里看得到这个池的任务。
